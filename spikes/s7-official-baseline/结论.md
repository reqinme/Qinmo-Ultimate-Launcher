## 1. 一个必须先纠正的**错误诊断**（它让 S7 空等了十三轮）

任务书与多轮汇报里都写着：

> S7 的前置：**等官方启动器把 `libraries` 下完**（74 文件 / 83.7 MB，多轮未变）。

**这个前置是错的。`libraries` 一直是完整的。**

| 项 | 数 | 怎么得到 |
|---|---|---|
| `26.3.json` 声明的库 | **114** | 读 JSON |
| 按 `rules` 过滤后 **Windows 需要**的 | **74** | 逐条求值 `rules`（`allow/disallow` + `os.name`） |
| **磁盘上实际存在**的 | **74** | 数 `libraries/` 下的文件 |
| 缺的 40 条 | — | **全部是 `natives-linux` / `natives-macos` / `os: osx` 被规则排除的** |

**74 = 74，一条不缺。** 那 40 条**本来就不该被下载到这台机器上**。

> **教训（本项目反复记录过的那一条，我这次又犯了）**：
> **"数字不再变化"不等于"还没下完"** —— 它完全可能等于"已经下完了"。
> 我把"74 文件看起来很少"当成了"没下完"的证据，而没有去**读权威数据**
> （版本 JSON 的 `rules`）。**一个未经核对的诊断，会让整条关键路径空等。**

`libraries` 的文件数从来没有变过，因为**它从一开始就是终态**。

## 2. 成功启动的**独立证据**

`.minecraft/logs/latest.log` 是**游戏自己写的**（不是启动器的日志），
头尾都指向"进了游戏"：

```
[00:27:57] [Datafixer Bootstrap #0/INFO]: 307 Datafixer optimizations took 195 milliseconds
[00:28:01] [Render thread/INFO]: Environment: Environment[discoveryUrl=https://discovery.minecraftservices.com/minecraft/client, name=PROD]
[00:28:01] [Render thread/INFO]: Setting user: qinme
[00:28:01] [Render thread/INFO]: Backend library: LWJGL version 3.4.3+4
[00:28:05] [Render thread/INFO]: Created: 1024x1024x0 minecraft:textures/atlas/gui.png-atlas
[00:28:52] [Render thread/INFO]: Stopping!
```

**为什么这份日志比启动器日志有力**：
`Datafixer Bootstrap` / `Render thread` / `Setting user` 都是**游戏进程内部**的输出 ——
启动器无法伪造它们。而 `Stopping!` 说明它是**正常退出**，不是崩溃。

## 3. 🔴 真实命令行基准（**S7 第 5 步的输入**）

### 任务书建议的取法在这台机器上不可用

S7 第 5 步建议：

```powershell
(Get-CimInstance Win32_Process -Filter "caption='javaw.exe'" | Select-Object -First 1).CommandLine
```

**我试了：没有 java 进程在跑**（游戏是前台应用，用户玩完就关）。
这不是偶然 —— 它意味着那个取法**要求你去抢一个很窄的时间窗口**。

### 更好的来源存在：**官方启动器自己把每条参数写进日志**

```
JavaLaunchConfiguration.cpp(281)] Java argument:<一条参数>
```

于是**读历史**取代了**抢进程**：可复现、可复核、还能对比多次启动。

**取证脚本**：`spikes/s7-official-baseline/capture.ps1`
**产物**：`baseline-args.txt`（20 行，**未排序** —— `-cp` 的顺序有意义）
`baseline-summary.json`

### 抓到的 20 条（会话 `2026-10-01 16:27:55`，即本地 00:27:55，与 `latest.log` 吻合）

| # | 参数 | 备注 |
|---|---|---|
| 1 | `-XX:HeapDumpPath=MojangTricksIntelDriversForPerformance_javaw.exe_minecraft.exe.heapdump` | windows 专属 |
| 2 | `-Xss1M` | |
| 3 | `-XX:StackShadowPages=32` | |
| 4 | `--enable-native-access=ALL-UNNAMED` | |
| 5–6 | `--add-exports` `java.base/jdk.internal.misc=ALL-UNNAMED` | **两条一组** |
| 7 | `-Djava.library.path=<WORKDIR>\.minecraft\bin\…/java` | **natives 的位置** |
| 8 | `-Djna.tmpdir=<WORKDIR>\.minecraft\bin\…/jna` | |
| 9 | `-Dorg.lwjgl.system.SharedLibraryExtractPath=<WORKDIR>\.minecraft\bin\…/lwjgl` | |
| 10 | `-Dio.netty.native.workdir=<WORKDIR>\.minecraft\bin\…/netty` | |
| 11 | `-Dminecraft.launcher.brand=minecraft-launcher` | 我们该换自己的品牌名 |
| 12 | `-Dminecraft.launcher.version=3.41.18` | |
| 13 | `-cp` | |
| 14 | `<WORKDIR>\.minecraft\libraries\…;…;…\versions\26.3\26.3.jar` | **6829 字符，74 条库 + 客户端 jar** |
| 15 | `-Xms2G` | 官方默认 |
| 16 | `-Xmx4G` | 官方默认 |
| 17 | `-XX:+UseCompactObjectHeaders` | **Java 25 才有** |
| 18 | `-XX:+AlwaysPreTouch` | |
| 19 | `-XX:+UseStringDeduplication` | |
| 20 | `-XX:+UseZGC` | **只有 ZGC，没有 G1** |

**`<WORKDIR>` 是官方启动器自己写的占位符**（代替真实用户路径）——
**这对我们是幸运的**：基准里没有绝对用户路径，**可以直接提交，不需要脱敏**。

### ⚠️ 这 20 条**只含 JVM 参数，不含游戏参数**

证据（日志时间戳顺序）：

```
L3226  Java argument:-XX:+UseZGC          <- 第 20 条，最后一条
L3229  Starting game in folder %USERPROFILE%\AppData\Roaming\.minecraft
L3231  Starting game with token 3
L3237  [00:27:57] Datafixer ...           <- 游戏已经在跑
```

**中间没有任何 `--username` / `--accessToken` / `--uuid` 行。**

**这不是漏抓，而是正确的安全做法**：账号令牌**不该进日志**。
官方启动器把游戏参数作为**参数数组**传给进程，只记了 JVM 那一部分。

> **对我们 S7 第 5 步的影响（必须写清）**：
> **JVM 参数可以逐条与官方比对**（20 条，已取得）。
> **游戏参数无法这样比对** —— 只能拿**版本 JSON 的 `arguments.game` 模板 + 已知变量值**
> 自己算出来，再与"官方会怎么填"推理核对。
> **这是"能比多少比多少"，不是"全部比完了"** —— 不许把它说成后者。

## 4. natives 的真实去处（**与方案 §8 第 6 项有关的高价值发现**）

### 它不叫 `natives/`

官方启动器把 natives 解到：

```
%APPDATA%\.minecraft\bin\44685878b69bb36a6fb05390c06c8b0243d34f57\
                        e65e1985fa45697085ef29d8d1f93b77d6cdc778\
                        ├── java\          <- -Djava.library.path 指这里
                        ├── jna\           jna13116920357846596608.dll (+ .x 标记)
                        ├── lwjgl\3.4.3+4\x64\   freetype/jemalloc/lwjgl/OpenAL/SDL3/shaderc/spirv-cross 等 9 个 dll
                        └── netty\         <- -Dio.netty.native.workdir 指这里
```

### 其中一个哈希**已经确定**

```
e65e1985fa45697085ef29d8d1f93b77d6cdc778  == SHA1("26.3")   ← 无盐，就是版本 id
```

**实测确认**（我对 `"26.3"` 求 SHA-1 得到同一个值）。

**外层 `44685878…` 我没有确定它的算法。** 试过的候选（版本 JSON 原文、
客户端 sha1、assetIndex sha1、jre manifest sha1、javaVersion 块、库名拼接……）
**都不匹配**。

> **而我决定停止穷举，并写清理由**：
> **那是官方启动器的内部命名方案，不是任何契约的一部分。**
> S7 要回答的是"natives 能不能落在**我们控制的**位置、且游戏能起来" ——
> 那个问题的答案**不依赖复现它的目录名**。
> 继续猜下去是在解决一个**我们不需要解决的问题**。

### 它对我们的意义（**这正是方案 §8 第 6 项要防的**）

| | 官方启动器 | 我们 |
|---|---|---|
| natives 去哪 | `.minecraft\bin\<hash>\<hash>\` | **实例内** `<实例>\natives\<版本>-<平台>\` |
| 会被清理软件删吗 | **可能** —— 它在一个看起来像缓存的 `bin\` 下 | **不会** —— 它在实例内，语义明确 |
| 换版本时 | 新哈希目录，旧的留着 | 按版本号命名，可枚举、可清理 |

方案 §8 第 6 项的原话：

> natives | 按平台解压到**实例内** natives 目录（不落系统 `%temp%`）

**这次实测把它从"一条规定"变成了"一个已证实的对照"**：
官方把它放在一个内容寻址的缓存位置，而**我们不放那里是有具体理由的**。

## 5. 🔴 阻断点：**游戏参数需要账号令牌**

### 事实

- `arguments.game` 里的变量（`${auth_player_name}` / `${auth_uuid}` / `${auth_accessToken}` …）
  **必须有值**，否则游戏起不来（或起来后是未授权状态）。
- 官方启动器用**微软账号**提供这些值。
- 本项目的**微软登录在 M5**（且审批仍在等待中 —— 见 `docs/流程A-执行记录.md`）。
- 本项目**离线身份在 M2/M3**（`qul-core/src/identity.rs` 已有模型，但还没有"产出可用的
  `--accessToken`"这条实现）。

### 这意味着什么

**S7 第 6 步（用离线身份拉起游戏）需要 M2/M3 的一个组件，而那个组件按方案在 M1 之后。**

任务书说 S7 是 M0 的尖刺、**不许降级**。而现在的实际情况是：

> **S7 的"能取到基准、能算参数、能定 natives 去处"这几步已做完；
> 而"真的拉起游戏"这一步卡在"离线身份还没实现"上 ——
> 而那个实现属于 M2/M3。**

**这不矛盾，而是顺序问题**：M0 的 S7 本意是"证明这条路走得通"，
而它需要的最后一块（离线身份）**在关键路径上排在后面**。

### 所以有三种走法，需要你定

| 方案 | 做什么 | 代价 |
|---|---|---|
| **A（推荐）** | **S7 就地挂起，先推进 M2/M3**；等 M2/M3 有了离线身份，**回头把 S7 第 5–8 步一次做完** | S7 暂时是"部分完成"，M0 的出口条件 #1 里 S7 记"待 M3 回填" |
| **B** | **现在就把最小离线身份补上**（只做"产出一个能被游戏接受的 `--accessToken`"），专门为 S7 服务 | 会把 M3 的一部分提前，且那时它没有 M2 的元数据支撑 |
| **C** | 用**官方启动器的账号**做一次参数比对（读它的 `launcher_accounts_*.json` 拿令牌） | ⚠️ **我不建议**：那是在借用户的真实账号令牌做实验，且与"不伪官方会话"的红线精神相冲突 |
