# M2 前置取证：跨年代结构差异**到底有几个**

> **这一轮的产出**：把 M2 最不确定的那一项（"跨年代结构差异"）
> 从**一句任务书描述**变成**两个已精确测量的断代点 + 可复现的取证脚本**。
>
> **它可自证，因此不需要等 M0/S7 的走法定下来。**

---

## 1. 做法：采样 + 连续差分，而不是"抓一批文件"

| 步骤 | 脚本 | 说明 |
|---|---|---|
| ① 采样 17 个版本 | `sample.ps1` | **每个版本记明"为什么挑它"**（见 `sample-index.json`） |
| ② 比较 JSON 形态 | `analyse.ps1` | 按**时间序**连续差分，**只打印差异** |

**为什么是采样而不是全部 917 个**：要回答的问题是"结构在哪里变"，
而结构**在少数几个边界上变**，不是每个版本都变。
全下（约 40 MB）不会让答案更清楚，只会让证据更难读。

**为什么必须按时间序连续差分**：列 17 份独立的字段清单会把"比较"这件事
留给读者在脑子里做 —— 而那正是任务书禁止的"看起来差不多"。

**为什么每个样本要写"为什么挑它"**：一份没写下挑法的样本只是一堆文件。
将来报告说"结构在 X 与 Y 之间变了"，读者需要知道那两个版本是**被挑来夹住
一个可疑边界**的，而不是随手拿的。

> 采样索引里的 `type` 字段第一版写成了恒真判断
> （`Where-Object { $_.id -eq $_.id }`），会让每一行都报第一个条目的类型。
> 已改成从已查到的清单条目取。**一个恒真的过滤条件就是"不存在的检查"。**

> ### ⚠️ 而我挑样本时写下的一条理由**是错的**，实测纠正了它
>
> `sample-index.json` 里我原本给 `1.19.3` 写的理由是
> 「**the release that ADDED `arguments.jvm/game`**」。
>
> **实测：`arguments` 是在 1.13.2 加进来的**（见 §2），
> 而 `1.19.3` 的真正意义是**另一个断代**（natives 表达变化）。
>
> **这不是"写得不精确"，而是我把一个预期当成了事实写进证据文件。**
> 若不做这次逐条核对，那个错的理由会留在 `sample-index.json` 里，
> 而下一个读它的人会据此认为"arguments 是 1.19.3 才有的"。
>
> **已实测纠正 8 条**（其中 4 条是同一类错误：把断代归错了位置），
> 现在每条理由都对应 §2 里实测到的那个变化。
>
> **教训与上一轮那条同源**：*预期不是证据*。而这一次的代价更小 ——
> 因为核对发生在提交之前，而且核对的方式是**跑一遍分析看实际输出**。

## 2. 🔴 结论：**17 年只有两个真正的断代点**

| # | 断代 | 变化 | 影响 |
|---|---|---|---|
| **①** | **1.12.2 → 1.13.2** | `minecraftArguments`（**一个字符串**）→ `arguments.jvm` + `arguments.game`（**两个数组**） | **参数组装必须支持两种形态** |
| **②** | **1.18.2 → 1.19.3** | natives 从 **`downloads.classifiers` + `natives` 字段** → **独立库条目**（名字带 `:natives-windows`） | **natives 收集必须支持两种形态** |

### 而"跨年代"这件事**远没有任务书听起来那么可怕**

其余 13 个被检出的"边界"**全是内容变化，不是结构变化**：
`lib_count` 增长、`assetIndex` 换名字、`javaVersion` 从 8→16→17→21→25。
**它们不需要任何新代码分支** —— 解析器把它们当数据读就行。

**换句话说：M2 的解析器只需要两套形态判定，而不是"每几年一套"。**

## 4. 三个**必须处理但不能想当然**的细节

### ① `javaVersion` 会**缺失**

**1.6.4 是全表唯一没有 `javaVersion` 的样本。**
一个"读到就用"的实现在这里会拿到 `null`，然后要么崩、要么猜一个版本。

> **正确行为**：缺失时**回退到那条长期的默认**，并**把这个决定记进日志** ——
> 因为"我们替你假设了 Java 8"是用户该知道的事。

### ② `logging` 在 1.7.10 之前**不存在**

`1.12.2` 及更早没有 `logging` 字段。而 log4j 配置是**要下载并当参数传的**。
一个假定 `logging.client.file` 一定存在的实现会在老版本上崩。

### ③ `extract`（排除 `META-INF/`）**在 1.19.3 起完全消失**

| 版本 | 带 `extract` 的条目 |
|---|---|
| 1.16.5 | **2 条**（`com.mojang:text2speech` · `ca.weblite:java-objc-bridge`） |
| 1.18.2 | 有（含在旧式 natives 里） |
| **1.19.3 / 1.21.4 / 26.3** | **0 条** —— 连独立 natives 条目也**没有** `extract` |

> **它为什么重要**：`extract.exclude` 是"**解压时不要解这些路径**"的唯一来源。
> 一个忽略它的实现会把 `META-INF/` 一起解出来 —— 而那正是
> **签名相关文件**所在的位置。**这不是卫生问题，是安全问题。**

**所以"新式 natives 没有 extract"这个事实要如何处理，是一个 M2/M3 的决策点**，
不是可以默默忽略的差异。它要么说明"新式 natives 不需要排除"，
要么说明**我们要自己补一条默认排除**。**本轮不猜** —— 记下来，在 M3 组参数时实测。

## 5. 一个**必须记下**的方法论限制

**本采样不是全量。** 一个**在这里没被报出的边界，仍可能存在于两个样本之间。**

我在挑样本时特意夹住了**已知可疑的边界**（`1.12.2`╱`1.13.2`、
`1.18.2`╱`1.19.3`、`1.6.4`╱`1.7.10`、`1.16.5`╱`1.17.1`╱`1.18.2`），
所以**报出的两个断代是可靠的**；而**"只有两个"这个结论的强度受采样限制**。

**若 M2 实现时发现某个版本解析失败，第一件事是补采样** ——
`sample.ps1` 里加一个 id 再跑一次，就是全部代价。

## 6. 给 M2 的直接结论（可直接当实现清单）

| # | 结论 |
|---|---|
| 1 | 参数组装**两套形态**：`minecraftArguments`（字符串，按空白切分）与 `arguments.jvm`/`arguments.game`（数组，元素可以是字符串或**带 `rules` 的对象**） |
| 2 | natives **两套形态**：`downloads.classifiers` + `natives` 字段（旧） vs 独立库条目（新）。**收集逻辑要能同时吃下** |
| 3 | **`rules` 求值只有一套**：`os.name` / `os.version`（正则）/ `os.arch` / `features`。它是唯一贯穿 17 年都在的机制 |
| 4 | `javaVersion` / `logging` / `extract` / `complianceLevel` **都可能缺失**，缺失时的回退必须**显式且记日志** |
| 5 | `assetIndex.id` 是**数据**不是常量（`pre-1.6` / `legacy` / `1.12` / `2` / `19` / `34`）—— 它**不是**版本号 |
| 6 | `mainClass` 变了三次（`RubyDung` → `launchwrapper.Launch` → `client.main.Main`），**永远从 JSON 读，不许硬编码** |
