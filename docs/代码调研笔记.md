### 1.2 下载引擎（`internal/downloader/downloader.go`，641 行）——**可直接照抄的形态**

**它是"临时文件 + 校验 + 原子重命名"的教科书实现**：

| 机制 | 证据（行号） | 说明 |
|---|---|---|
| **临时文件后缀** | `:234` `downloadDest := local.dest + ".download"` | 未校验完成的文件**永远不带正式文件名** |
| **原子提交** | `:480` `os.Rename(downloadDest, local.dest)` | 校验通过才重命名 |
| **提交与取消串行化** | `:472-484` | 注释原文：*"Serialize the commit with Pause/Cancel. Once the rename wins, detach the task before emitting completion so a late cancellation cannot contradict it."* ——**先锁住、重命名赢了就先把任务从表里摘掉、再发完成事件**，避免"已取消"与"已完成"两条事件互相矛盾 |
| **校验后才发布** | `:87` `StartVerified(ctx, src, dest, verify func(string) error)` | 注释：*"publishes the final file only after a package-specific integrity check"*——**校验函数按包类型注入**（.mcpack 与普通文件校验方式不同） |
| **MD5 失败重试 3 次** | `:442-457` | 不匹配 → 删临时文件 → 重试计数 +1 → **`time.Sleep(1s)` 退避** → 重传；第 3 次失败才发 `ERR_MD5_MISMATCH` |
| **续传判定** | `:249-253, 278-280` | 用 **`.download` 文件的实际大小**当已下载量；带 `Range: bytes=<cur>-` |
| **服务端不支持 Range 的处理** | `:303-309` | 若返回 `200` 而非 `206` → **删掉临时文件、`cur=0` 重头下**（不产生拼接损坏） |
| **总长从 Content-Range 取** | `:312-324` | 优先解析 `Content-Range` 的 `/total`；没有则 `total = cur + ContentLength` |
| **进度节流** | `:68-70, 376-379` | 默认 **250 ms** 节流；128 KB 读取缓冲 |
| **暂停 ≠ 取消** | `:120-133, 173-194` | 暂停：置 `paused` + cancel context，**保留 `.download`**；取消：置 `cancelled`，可选删临时文件 |
| **同目标去重** | `:100-104` | 同一 `dest` 已有运行中的任务 → **直接复用**，不重复下载 |
| **暂停在"校验阶段"的处理** | `:424-426` 注释 | *"A pause during verification retains the complete transfer. Resuming runs all integrity checks again without an invalid HTTP Range request beyond EOF."* ——**校验期间暂停不丢数据，恢复时重跑校验，且不会发出越过 EOF 的 Range 请求**（这是个很细的坑） |

**值得直接采纳的四条**：
1. **`.download` 临时文件 + 校验后 `Rename`**（我们的方案里也写了原子写，这里有了完整参考实现）。
2. **"重命名赢了就摘任务、再发事件"** 的竞态处理——这是"取消/完成事件互相矛盾"这一整类 bug 的根治方式。
3. **校验函数按包类型注入**（`StartVerified`），而不是在下载器里 `switch` 文件类型。
4. **服务端忽略 Range 时删临时文件重头下**，而不是接着写（否则文件必然损坏）。

### 1.3 一处需要留意的实现细节

`:481-483`：提交成功后 `progress` 用的是 `local.downloaded`，但**在续传场景下 `downloaded` 可能小于文件总长**
（因为 `downloaded` 是从 0 累加的本次会话字节数，而 `cur` 是历史大小）。见 `:255` `local.downloaded = cur`——
它在每次开新一轮前把 `downloaded` 设为 `cur`，所以是自洽的，但这个"会话内增量"与"文件总进度"混用的写法
容易在改造时引入 bug。**我们实现时应把"文件已下载字节"与"本次会话新增字节"分开表达。**

### 2.2 核心抽象：**组件栈（Component Stack）**

> **这是本轮读到的最有价值的架构思想**，比"版本 + 加载器"两层的写法高一档。

`PackProfile.h:59` —— `PackProfile` **同时是一个 `QAbstractListModel`**（组件列表即 UI 模型）：

| 能力 | 证据 | 说明 |
|---|---|---|
| 有序组件列表 | `PackProfile.h:91-93` `move(index, MoveUp/MoveDown)` | 组件**顺序有意义**（覆盖关系），可上下移动 |
| 增删 | `:95-99` `remove(index)` / `remove(id)`、`:80-89` 安装 jar mod / 自定义主 jar / MMC 组件 / Java agent | 内容种类多但**统一为"组件"** |
| 启用/禁用 | `Component.h:66-68` `isEnabled() / setEnabled() / canBeDisabled()` | 禁用是**一等状态**，不是删除 |
| 可变更性查询 | `Component.h:70-77` `isMoveable / isCustomizable / isRevertible / isRemovable / isCustom / isVersionChangeable / isKnownModloader` | **能力由组件自己回答**，UI 据此决定按钮是否可用——与我们 §3.3 的"能力描述符 + reason"是同一思路 |
| 覆盖到启动 | `Component.h:64` `applyTo(LaunchProfile* profile)` | **组件按顺序把配置叠加到一份 `LaunchProfile` 上**——这就是"声明式启动计划"的实现 |
| 版本切换动作 | `Component.h:41-45` `UpdateAction = variant<None, ChangeVersion, LatestRecommendedCompatible, Remove, ImportantChanged>` | **更新是"动作"而非"直接改值"**：先算动作、用户确认、再应用 |
| **冲突内建在组件里** | `Component.h:47-50` `ModloaderMapEntry { type, knownConflictingComponents }`、`:62` `KNOWN_MODLOADERS`、`:77` `knownConflictingComponents()` | **"哪些加载器互相冲突"是组件模型的一等数据**，不是散落的 if |
| 问题上报 | `Component.h:96-99` `getProblems()` / `addComponentProblem(severity, description)`；继承 `ProblemProvider` | 组件能**自带问题与严重级别** |
| 从零构建 | `PackProfile.h:77` `buildingFromScratch()` | 明确区分"加载已有"与"从零新建" |
| 更新任务分离 | `minecraft/update/` 下 `LibrariesTask` / `AssetUpdateTask` / `FoldersTask` / `LegacyFMLLibrariesTask`，共同基类 `ComponentUpdateTask` | **每类更新是一个 Task**，不是一个巨型 install 函数 |
| 旧格式迁移 | `Component.h:79-81` 注释：*"DEPRECATED: explicit numeric order values, used for loading old non-component config. TODO: refactor and move to migration code"* | **它自己也有"旧配置格式迁移"的债**——印证我们 §4.7 的迁移链不是过度设计 |

### 2.3 对我们最有价值的四条

1. **组件栈取代"版本 + 加载器"两层**：加载器、jar mod、Java agent、自定义主 jar、资源覆盖**都是组件**，
   统一 `move / enable / disable / remove / applyTo`。**这比我们方案里的 `inheritsFrom` 链式合并更通用**，
   且天然支持"禁用某个组件而不删除"。
2. **`applyTo(LaunchProfile)`**：组件按序叠加成一份启动清单——**与我们"先算完整启动计划再执行"完全一致**，
   但它的组织方式（每个组件负责自己的叠加）比集中式组装更好扩展。
3. **组件自带问题与冲突数据**：`getProblems()` + `knownConflictingComponents`——
   **把"校验"从安装流程里拿出来，变成模型自带的能力**。这比"安装后报错"体验好得多。
4. **更新是 `UpdateAction`，先算再应用**：`LatestRecommendedCompatible` 这种语义化的动作，
   让"要不要升级加载器"变成用户可确认的决策，而不是静默改值。

### 2.4 不适合我们的

- **Qt 的 `QAbstractListModel` 双重身份**（模型即 UI 模型）：在 React 侧应由前端从数据派生，内核不该依赖 UI 框架的模型接口。
- **`ui/` 占一半代码**：C++/Qt 的界面成本远高于 Web，这部分对我们没有参考价值。
- 代码总量 7.5 MB，**只读核心抽象即可，不值得逐文件读**。

### 3.2 下载引擎的核心设计（`nx-dl-engine`，规模很大）

文件量级：`segment_coordinator.rs` **6488 行**、`proxy_config.rs` 2018、`downloader.rs` 1980、`db.rs` 479、`speed_limiter.rs` 383。

| 机制 | 证据 | 我们的判断 |
|---|---|---|
| **独立 workspace crate**，与主工程依赖隔离 | `src-tauri/Cargo.toml:11` | ✅ 抄（与我们 §3.5 的分层一致） |
| **引擎重导出自己的 reqwest**，强制宿主用同版本 | `nx-dl-engine/src/lib.rs:24-26`（主工程 reqwest 0.11 / 引擎 0.12） | ✅ 抄——**这是"依赖版本不一致导致类型无法互通"的根治手法** |
| **`trait EventSink`，明确"同步 fire-and-forget，不得阻塞"** | `events.rs:36-42` | ✅ 抄——引擎可脱离框架单测 |
| **自适应爬坡代替固定并发**：初 4 worker、每 2s 评估、改善 ×1.25、劣化 ×0.65、连续 2 次劣化即收缩 | `segment_coordinator.rs:456-535` | ✅ **尤其适合我们 0.28 MB/s 的跨境链路** |
| **域名连接上限记忆 24h**（`domain_conn_caps`，格式版本 v3） | `:92-95, 262, 328, 396` | ✅ 抄——避免对同一站点反复试探最优并发 |
| 分片参数 | `MAX_SEGMENTS=64`(:441)、`MIN_SPLIT_BYTES=2MB`(:416)、`TAIL_MIN_SPLIT_BYTES=64KB`(:777) | 参考 |
| 带宽分档 | `BW_LOW=512KB/s` / `BW_MED=5MB/s` / `BW_HIGH=50MB/s`、`SINGLE_SEGMENT_THRESHOLD=2MB`（`segment_advisor.rs:45-52`） | 参考 |
| 重试与超时 | `MAX_RETRIES=5` + `RETRY_BASE_DELAY=2s`(:822-823)；`CHUNK_STALL_TIMEOUT=5s` / **`..._HOSTILE=60s`**(:838/:845) | ✅ **"对敌意服务器单独给宽容超时"值得抄** |
| **Windows 预分配**用 `SetFileInformationByHandle(FileAllocationInfo)` 而非 `set_len` | `:1640, 2143`，理由见 `:3243` 注释：**避免稀疏文件导致碎片与延迟 ENOSPC** | ✅ 抄理由 |
| 临时文件 `.fdownloading` + 分片持久化 | `downloader.rs:2099` | ✅ 但**我实测发现它的下载文件本体没有 tmp→final 原子 rename**（只有 DB 层有 `db.rs:5`）→ **我们要补上这一半**（LeviLauncher 有，见 §1.2） |
| 进度双层节流：引擎 200ms + 宿主 200ms | `segment_coordinator.rs:814`、`download_accelerator.rs:709/734` | ✅ 与我们灵动岛"≤10 次/s"对齐 |

### 3.4 值得抄的启动顺序（四步，前两步很关键）

`src-tauri/src/main.rs`：

1. **`init_early_logging()` 在所有 Tauri 代码之前**（`main.rs:36`）——保证 `.build()` 崩溃也有日志（注释 `:28-34`）。
2. **强制切换工作目录到 exe 所在目录**（`main.rs:46-52`）——**开机自启经注册表/计划任务拉起时 cwd 可能是 `System32`**，会导致 Tauri 加载资源失败。**这个坑我们一定会踩**。

### 3.5 明确不适合（含理由）

| 不适合 | 理由 |

| **运行时强制 UAC 提权**（`main.rs:100-108`，拒绝即 `exit(0)`） | 我们要免安装 + 非管理员；MSIX 场景提权会失败。**反例价值高于借鉴价值** |
| `csp: null` + assetProtocol 全开 | 与 §5.8 直接冲突 |
| 硬件监控 / EcoQoS / 显示滤镜 / 系统优化整体 | 需提权、与游戏进程共存、有反作弊暴露面；**若做必须独立模块 + 独立进程 + 默认关闭** |
| `df_stats.rs` 的"独立 WebView2 数据目录 + `ExecuteScript` 每 2 秒轮询厂商网页采集" | **机制（独立 `data_directory` 隔离登录态，`df_stats.rs:255`）好**，但高频轮询第三方站点有 ToS 与稳定性风险，不照搬 |
| **红线类**：`crosshair.rs`/`crosshair_hold.rs`、`autoclicker.rs`、`anticheat.rs`、`vac_repair.rs`、`game_process_optimize.rs` | **正是我们红线逐条禁止的类别**。它们的实现（Win32 直接操作游戏进程/注入/叠加窗口）**说明这类功能与启动器共用同一进程是危险的**——要做必须完全隔离 |

仓库根目录虽带 `LibreHardwareMonitorLib.dll`，但**主路径未见 P/Invoke 加载**。
→ **若参考硬件监控实现，看 `wmi_query.rs` + `sensor_monitor.rs`，不要以 README 为准。**

1. **S9 的"路径 B（PE 导入表改写）"不需要再做风险评估——直接结论为"永久放弃"，并写进红线**。

3. **有两条设计知识仍然可借鉴**（不涉及代码）：
   - **UWP 的六个不可漫游目录必须排除**（`AC` / `LocalCache` / `SystemAppData` / `Settings` / `TempState` / `RoamingState`）；

| 方式 | 内容 | 成本 | 来源 |
|---|---|---|---|
| **A. 搬数据/规范** | 把对方的数据结构、命名体系、UID 规则、格式规范**原样转成我们的 JSON/TOML/Rust 常量表** | **最低**（几乎只是改写格式） | MultiMC 的 `mmc-pack.json` 组件 UID 体系；Trident 的 `profile.json` 字段集；HMCL 的 `JavaVersionConstraint` 枚举；Axolotl 的加载器清单 |
| **B. 搬算法** | 纯逻辑函数（版本比较、依赖解析、URL 改写、速度自适应、MOTD 解析）**按其设计用 Rust 重写** | 低 | Axolotl `download_manager.rs` 的自适应地板；HMCL 的 `MirrorRule`；LeviLauncher 的下载状态机 |
| **C. 搬设计规格** | 只取接口形状与状态机定义（不取实现） | 低 | Prism 的组件栈 API 形状；Axolotl 的事件目录；PCL 的 `Watcher` 事件表 |
| **D. 直接搬代码（仅限 L1）** | **真正复制代码**，需要：保留声明 + 记入 `docs/来源记录.md` + CI 防误粘贴检查 | **最低但需合规流程** | **目前只见 Polymerium/Trident 是 MIT**，且它是 C#——**语言不通，实际不可搬** |

**坦白结论**：**"直接搬代码"这条路在本项目里收益有限**——因为
① 可搬的 L1 项目（Polymerium/Trident、XMCL）分别是 **C# 与 TS/Electron**，与我们的 Rust 内核语言不通；
② 语言相通的（Axolotl、LeviLauncher）虽然**同许可可搬**，但一个是**巨型 monorepo**（搬进来要连它的 116 个迁移与 sqlx 耦合一起搬）、
一个是 **Go + Wails**（同样语言不通）。

→ **所以真正省开销的是"方式 A + B + C"（搬数据、算法、规格），而不是"方式 D"（搬代码）。**
→ **但这不等于"不用读"**：方式 A/B/C 的前提恰恰是**把对方的代码读懂**——你要求"先读了再说"，是对的。

### 7.1 ⚠️ 三处纠错（**两条直接影响我已写进方案的条款**）

#### 纠错 1：`Watcher` 不是"生命周期事件总线"，而是**日志监控驱动的启动进度模型 + 三机制并用**

我此前从本地化键反推"`Watcher` = 生命周期事件表"是**推测——方向对，内容错**。真实结构（`Modules/Minecraft/ModWatcher.cs`）：

| 机制 | 用途 | 证据 |
|---|---|---|
| **日志子串匹配** | **五步启动进度**全靠它：已出现日志输出 / 游戏用户已设置 / LWJGL 版本确认 / OpenAL 已加载 / 材质已加载 | `:476, 482, 487, 493, 500` |
| **窗口探测（拿到 HWND）** | 窗口就绪：`WindowLoaded` / `FmlWindowLoaded` / `LoadComplete` | `:593, 616, 548` |
| **独立一档** | `SecurityBlocked`（安全拦截） | `:578` |

**崩溃识别分三档语气**（不是"崩了/没崩"二元）：

| 事件 | 含义 |
|---|---|
| `Crash.Detected` | 已崩溃（2 秒后才分析） |
| `Crash.Suspected` | 尚未加载完成，**可能**已崩溃 |
| `Crash.AbnormalExit` | 返回值异常 |

且**日志先被分类为"崩溃的"或"关闭的"**（`Log.CrashDetected` / `Log.CloseDetected`）。
**强杀两级**：`TerminateProcess` → 超时后 `taskkill.exe`（`Kill.TaskkillAttempt/TaskkillResult/Timeout`）。

→ **修正方案 §4.4 的表述**：灵动岛 `Running` 态的数据源**应照这个真实结构设计**：
**日志匹配做进度 + 窗口 HWND 做就绪 + 独立一档做安全拦截**。
我原来写的"进程探测 / 窗口探测 / 日志观测**三法比选**"是错的——它们不是竞品，是**分工**。

#### 纠错 2：「镜像源用 ≥256 KB 实测探针测速」**不是 PCL 的做法**——那是我第一轮项目的做法

PCL 的真实策略是**"多源列表 + 顺序偏好"，两行逻辑，无探针**：

```
ModDownload.cs:2119  DlSourceOrder = DlSourcePreferMojang ? official.Union(mirror)
                                                        : mirror.Union(official)
```

→ **方案 §2 里"≥256 KB 实测探针"这一条的出处需要更正**：它**继承自我封存的第一轮项目**（且那条在本机实测过），
**不是 PCL 的做法，不应记为"PCL 对齐项"**。两套可以并存（我们有实测优势），但**归属要说对**。

#### 纠错 3：PCL 的默认下载线程是 **63**

`PCL.Core/App/Config.cs:79` 默认 **63 线程**；`FileDownloader.cs:14/15` 超时 30s、重试 3 次；
`:56-70` **外层重试 × 内层遍历全部源**。
→ 在**我们实测的 0.28 MB/s** 链路上，63 线程**没有收益**（NexBox 的自适应爬坡初值只要 4）。

## 10. 本轮被源码推翻的判断（**我此前的结论错在哪**）
> 集中记录，因为这些错都来自同一类坏习惯：**凭 README / 语言标签 / 本地化键 / 目录名做推断，而没读实现**。
> 每一条都写清"我当时怎么想的"与"实际是什么"，作为方法论教训。

| # | 我此前的判断 | 实际 | 我当时错在 |
|---|---|---|---|
| 1 | **LeviLauncher = TS + Rust** | **Go + Wails**（`go.mod` + `main.go` + `internal/` + `native/`） | 信了 GitHub 的 `language` 字段——**它只是按行数统计** |
| 2 | **Axolotl 无认可许可证，一行代码都不能用** | **仓库级 `NOASSERTION` = 多许可 monorepo**；启动器本体是 **GPL-3.0** | 只读了仓库级 API 字段，**没逐包打开 LICENSE** |
| 3 | **NexBox = GPL-3.0** | 主程序 GPL-3.0，但 **`nx-dl-engine` 是 AGPL-3.0**（逐字搬运自 FluxDown，经 GPL-3.0 §13 并入） | 同上，没读子 crate 的 `Cargo.toml:4` |
| 4 | **PCL 的 `Watcher` = 生命周期事件总线** | **日志子串匹配（五步进度）+ 窗口 HWND 探测（就绪）+ 独立一档（安全拦截）**——三机制**分工**，不是并列候选 | **从本地化键反推结构**，方向对内容错 |
| 5 | **链接降级链 `symlink > hardlink > junction > copy`** | **junction 必须排在 symlink 之前**——junction **不需要开发者模式**（Axolotl `util/symlink.rs:154-164`） | 凭"symlink 更强"的直觉排序，**没考虑权限门槛** |
| 6 | **XMCL 的"磁盘高效"靠硬链接去重** | **全包零命中创建链接的代码**；真实机制 = **SHA-1 内容哈希 + SQLite 引用** | 把**宣传语**当成了实现 |
| 7 | **ATLauncher 的 Servers 页 = 服务器列表** | 它是**"用启动器开一个 Minecraft 服务端"的实例模型**（`data/Server.java` 有 `loaderVersion`/`mods`/`ROOT`） | 从页面名推断功能 |
| 8 | **Portal 有 Vue 桌面前端** | `web/` 是**官网落地页**（Vue + SSG `prerender.mjs`，组件是 `HeroSection` 之类）；**桌面 UI 是 Avalonia** | 看到 `web/` 目录与 `.vue` 文件就下结论 |
| 9 | **Prism #1165（导出全塞 Overrides）是个要绕开的普遍问题** | 那**只是 Prism 自己的缺陷**；**Trident 的 Modrinth 导出已正确分流**（在线包进 `index.files[]`，仅离线模式才实体化进 `overrides/`） | 把某个项目的 bug 当成了领域难题 |
| 10 | **基岩版 UWP 隔离做不到**（"UWP 恒为 native"） | LeviLauncher 实现了 UWP 隔离，**版本边界 `1.19.70.2`**，机制是"重定向 `ApplicationData`"；与 Portal 的 ntdll Detour 是**两回事** | 只读了 Portal 一家的实现就下了全局结论 |
| 11 | **Portal 的 T2 属于"风险待评估"** | 读全后确认是**三重红线同时命中**（改 exe 导入表 + `CreateRemoteThread` 写他进程 + **8 个 ntdll 内联 Detour**）→ **技术性排除，不需评估** | 只读了 C# 侧，没读 preload DLL 与 Injector |
| 12 | **"镜像探针测速"是 PCL 的对齐项** | PCL 实际是**两行顺序偏好**（`ModDownload.cs:2119`），**无探针**；探针是**我第一轮项目**的做法 | **把自己的旧做法记成了别人的做法**（最危险的一类错） |
| 13 | **PCL 仓库里有可搬的规则表/数据文件** | **没有**——全部 >2 KB 的 JSON/TXT 只有 Wiki 条目与提示文本；规则**硬编码在源码里** | 假设"功能这么全，规则一定是数据驱动的" |
| 14 | **`Trident 支持 junction/hardlink 降级链`** | 全项目**只有 `CreateSymbolicLink` 两处**，靠 `allowed_symlinks.txt` 白名单 | 把它与 Axolotl 的实现混在一起了 |
| 15 | **"Electron 项目对我们没价值"** | **XMCL 是本轮最大资产来源**（`@xmcl/semver` 等零依赖纯逻辑包） | 按技术栈一票否决，**没看它把什么做成了可复用资产** |
