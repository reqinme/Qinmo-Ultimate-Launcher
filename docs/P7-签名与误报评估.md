# P7 · 签名与杀软误报评估

> P7 交付物之一。**这份评估的结论直接决定 P7.0 的更新选型是否成立**——
> 见 `P7.0-更新策略选型.md` §2.1 与 §6。

---

## 1. 结论

| 判断 | 内容 |
|---|---|
| **签名是 P7.0 选型的前提** | 自替换方案押在"自我修改自身映像"上。**未签名时这一动作的风险显著高于已签名**，因此不签名就不该启用自动更新 |
| **不签名时的唯一诚实选项** | 按 `P7.0` §6 改选**外部更新器**；或干脆先只提供"检查新版本 + 给出下载链接"，由用户手动替换 |
| **本机无法证伪误报率** | 真实误报需要已签名二进制 + 多引擎扫描 + 真实分发量。本机只能给出可执行的自测清单（见 §5） |
| **已做的减害措施** | 见 §4——这些不替代签名，但都降低被误判的概率 |

**给产品负责人的一句话**：如果短期内不打算买证书，那就**不要启用自动更新**，
把更新做成"提示 + 链接"。功能少一点，但不会让用户下载下来就被杀软拦掉。

---

## 2. 签名方案对比

价格随 CA 与年限差异很大，**这里不写具体数字**（那会变成随时间失效的假精确），只写相对量级与真正影响决策的三件事。

| 方案 | 相对成本 | 私钥存放 | SmartScreen 信誉 | 适用判断 |
|---|---|---|---|---|
| **EV 代码签名** | 最高 | 硬件 Token / 云 HSM（私钥不可导出） | **签发即获得信誉**，首次运行不弹"未知发布者" | 分发量小、又必须"下载即用"的场景，这是唯一能立刻见效的 |
| **标准 OV 代码签名** | 中等 | 本地文件或 Token | **需要积累**：下载量不够时仍可能被 SmartScreen 拦 | 便宜，但"下下来就被拦"的问题不一定解决 |
| **不签名** | 0 | — | 无 | 用户看到"未知发布者"；自替换风险最高 |

**决策要点**：本项目是绿色版、用户从网页直接下载，
所以真正要解决的是 **SmartScreen 首次运行的拦截**，而不是"文件有没有签名"这个形式问题。
按这一点，EV 是唯一立刻见效的；OV 需要时间积累，等于把问题推迟。

若走 EV，注意它会**改变构建流程**：签名需要硬件 Token 或云签名服务，
不能在 `dotnet publish` 里直接完成，P7 的发布步骤要相应调整。

---

## 3. 为什么"谁来做这件事"比"做不做"更关键

P7.0 里已经论证过：真正触发启发式的不是"谁来改文件"，而是**做了哪几类动作**。

| 动作模式 | 信号强度 |
|---|---|
| 把可执行文件写到临时目录并执行 | **高**（典型 dropper） |
| 修改 / 删除正在运行的自身映像 | 中 |
| 用另一个进程替换主程序并重启 | 中 |
| 下载一个 exe 放到它该在的位置 | 中 |

本项目**从不做第一类**（不自解压、不写临时目录、不打包壳）。自替换落在第二类——
这一类在**已签名**的前提下是 Chrome、VS Code 等大量正常软件的日常动作；
在**未签名**的前提下，它就是一个匿名程序在改自己的可执行文件。

同一段代码，签名与否，风险评估完全不同。这就是为什么签名是前提而不是可选优化。

## 4. 已实施的减害措施（不替代签名）

| 措施 | 状态 | 说明 |
|---|---|---|
| 补齐版本信息 | ✅ 已做 | 产品名 / 公司 / 版权 / 文件说明。一个没有任何元数据的 exe 更像可疑程序 |
| 应用图标 | ✅ 已做 | 由本项目自制品牌标识生成（7 个尺寸），不使用任何外部素材 |
| 不自解压、不写临时目录 | ✅ 一直如此 | 从设计上就没有 dropper 模式 |
| 不打包壳（无 UPX 等） | ✅ 一直如此 | 加壳是最强的误报信号之一 |
| 更新由用户显式发起 | ✅ 已做 | 不静默自我替换 |
| 下载物强制 SHA-256 校验 | ✅ 已做 | 清单里没有摘要就拒绝下载 |
| 零第三方运行时依赖 | ✅ 一直如此 | 不需要释放 DLL，也不会被"捆绑"启发式命中 |
| 私钥不出本机 | — | 走 EV 时由硬件 Token 保证 |

## 5. 可执行的自测清单

本机做不到的，写成清单，等有签名产物与分发渠道后逐项执行：

1. **多引擎扫描**：把发布产物提交 VirusTotal，记录命中引擎与报法（是启发式还是签名库）。
2. **SmartScreen 首运行**：在一台全新安装的 Win10 与 Win11 上，从浏览器下载后直接运行，
   记录是否弹"Windows 已保护你的电脑"。分别测未签名与已签名两个版本。
3. **更新流程自身**：在实时防护开启的情况下跑完整更新（下载 → 替换 → 重启），
   确认替换动作没有被当成可疑行为拦下。
4. **主流杀软实机**：至少在 Defender 之外挑两三家（含一家国产）各跑一遍安装、启动、更新。
5. **回退路径**：确认被拦或失败时，回退逻辑仍能运行（`P7-发布工程规范.md` §3.5 的演练已覆盖文件层面）。
6. **浏览器下载拦截**：Chrome / Edge 对未签名 exe 的下载拦截提示，记录用户需要点几次"仍要保留"。

---

## 6. 不签名时的处置

按 `P7.0-更新策略选型.md` §6 执行：

- **改选外部更新器**：主程序保持单文件，另发布一个独立小更新器，
  由它完成"等待主进程退出 → 校验 → 原子替换 → 启动新版 → 失败恢复"。
- **或者更保守**：先只做"检查新版本 + 打开下载页"，由用户手动替换文件。
  代价是体验，收益是**零自我修改行为**——在完全没有签名的情况下，这是风险最低的形态。

两条路都保留"更新失败可回退且用户数据无损"这一硬要求，
因为回退靠的是 `pending.json` 标记与 `.old` 备份，与由谁执行替换无关。
