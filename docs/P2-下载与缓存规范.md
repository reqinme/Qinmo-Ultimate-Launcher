# P2 · 下载与缓存规范

> 依据：《Minecraft 启动器 · 架构规划与路线图（v1.2 正式版）》P2 阶段交付物。
> 本文件合并了五份要求：**下载任务模型**、**缓存布局**、**重试与校验策略**、**来源策略**、**解压安全规范**、**网络环境处理**。
> 所有结论都对应到已落地的实现与测试，不是设计推演。

---

## 1. 分层与端口

| 关注点 | 归属 | 为什么在这里 |
|---|---|---|
| 下载任务模型 | `Qul.Domain.Downloads` | 纯数据，无 IO |
| 路径穿越判定规则 | `Qul.Domain.Security.ArchiveEntryPolicy` | **纯字符串逻辑**，放在领域层才能被穷举单测 |
| SHA-1 表示与比较 | `Qul.Domain.Security.Sha1Hex` | 纯逻辑 |
| HTTP 传输端口 | `Qul.Application.Ports.IHttpTransport` | 需要 `Stream`，领域层禁止引用 `System.IO` |
| HTTP 实现 | `Qul.Infrastructure.Net.HttpTransport` | 唯一能看到 `WebException` 细节的地方，错误分类在这里发生 |
| 下载引擎 | `Qul.Infrastructure.Downloads.DownloadEngine` | 续传/重试/校验/并发的全部语义 |
| 解压执行 | `Qul.Infrastructure.Archives.SafeZipExtractor` | 只负责照领域层的判定执行 |

> **对 P0 分层说明的修订**：P0 地基规范写的是"端口由领域层定义"。
> 实现时发现涉及 `Stream` 的端口无法放在领域层——那会迫使领域层引用 `System.IO`，与分层守卫直接冲突。
> 因此**带 IO 类型的端口定义在应用层**，领域层只保留纯数据与纯规则。分层方向不变：基础设施依赖应用层的端口接口。

**传输被做成端口，唯一目的是可测**：续传、重试、校验这些行为必须能被伪造传输完整验证。真实网络测不出"拔网线"。

## 2. 下载任务模型

```
DownloadPlan ── Items: DownloadItem[]
                  ├─ Kind        : 通道类别
                  ├─ Url
                  ├─ Sha1        : 十六进制摘要（**只能来自官方元数据**）
                  ├─ Size
                  ├─ RelativePath: 相对缓存根
                  └─ IsOptional
```

| 通道类别 | `DownloadItemKind` | 相对路径约定 |
|---|---|---|
| 版本清单索引 | `VersionManifest` | `meta/version_manifest_v2.json` |
| 版本详情 | `VersionDetail` | `meta/version-<id>.json` |
| 客户端 jar | `ClientJar` | `meta/client-<id>.jar` |
| 库 | `Library` | `libraries/<groupId 路径>/<artifact>/<version>/<artifact>-<version>.jar` |
| 库的 classifier 变体 | `LibraryClassifier` | 同上，文件名带 `-<classifier>` |
| 资源索引 | `AssetIndex` | `meta/assets-<assetIndexId>.json` |
| 资源对象 | `AssetObject` | `objects/<hash 前两位>/<hash>` |
| 日志配置 | `LoggingConfig` | `logging/<fileId>` |

**绝对路径一律不参与计划**：`RelativePath` 永远是相对路径，引擎用缓存根拼出最终位置。

### 缓存布局

```
data/cache/
  meta/          版本清单索引、版本详情、客户端 jar、资源索引
  libraries/     库（官方 groupId/artifactId 目录结构）
  objects/       资源对象（按哈希前两位分目录，与官方布局一致）
  natives/       natives 解压目标（P4 使用）
```

### 结果模型

`DownloadReport` 逐条给出 `DownloadItemState`：

| 状态 | 含义 |
|---|---|
| `Present` | 本地已存在且校验通过，**未产生任何网络请求** |
| `Downloaded` | 本次取回并通过校验 |
| `Failed` | 取回失败（携带错误码与尝试次数） |
| `RefusedNoChecksum` | 元数据未提供校验值，拒绝下载（`QUL-DL-0003`） |

`IsComplete` 只看**非可选**条目：可选资源的失败不阻断整体，但必须出现在 `Failures` 里。

## 3. 校验策略

### 3.1 校验基准的信任边界（硬约束）

`DownloadItem.Sha1` 是唯一的校验基准来源，而它由版本元数据解析产生。

**结构上的保证**：`IContentSource` 一类的来源抽象**没有任何能产出哈希的 API**。因此"信任镜像提供的哈希"不是靠纪律避免，而是无处安放。P10 接入镜像时，镜像只是 URL 的替换者。

配套约束：

1. MVP 阶段配置里不存在镜像开关（`contentSource.kind` 只能是 `official`，`mirrorBaseUrl` 必须为 null）。
2. 没有任何代码路径接受来自响应体或响应头的哈希。
3. 元数据未提供 SHA-1 时，条目**拒绝下载**而不是"先下下来再说"。

### 3.2 校验时机

| 时机 | 行为 |
|---|---|
| 启动前（缓存命中判断） | 目标文件存在 → 计算 SHA-1 → 匹配则标记 `Present`，不发请求；不匹配则删除并重下 |
| 落盘后（发布前） | 对 `.part` 计算 SHA-1 → 匹配才 `File.Move` 成正式文件；不匹配则丢弃 `.part` 与目标文件，重头再来 |

**只有校验通过的文件才会成为正式文件**，因此缓存里不会出现"看起来存在但内容是坏的"文件。

## 4. 续传与重试策略

### 4.1 续传

落盘写在 `<目标>.part`，其长度就是下一次的 Range 起点。

| 服务端响应 | 行为 |
|---|---|
| `206 PartialContent` 且 `RangeStart == .part 长度` | 追加写入 |
| `200 OK`（服务端忽略了 Range） | **覆盖重写**，绝不追加——追加会得到重复内容 |
| `416 RangeNotSatisfiable`（本地残留比远端还长） | 丢弃 `.part`，下一轮从头取 |

**传输中途断开时保留 `.part`**：这是断点续传成立的前提。断线、超时、连接重置都不清理残留。

### 4.2 重试矩阵

| 错误码 | 可重试 | 说明 |
|---|---|---|
| `QUL-NET-0001` 网络不可达 | 是 | |
| `QUL-NET-0004` 请求超时 | 是 | |
| `QUL-NET-0005` 服务器失败状态 | 是 | 5xx 与其他非成功状态 |
| `QUL-NET-0006` 资源不存在（404） | **否** | 重试三次是纯浪费：一次就定性 |
| `QUL-NET-0002` 代理配置无效 | **否** | |
| `QUL-NET-0003` 证书校验未通过 | **否** | 重试改变不了证书事实 |
| `QUL-DL-0001` 下载失败 | 是 | 含 416 丢弃残留后的重来 |
| `QUL-DL-0002` 校验和不匹配 | 是 | 丢弃损坏内容后重下 |
| `QUL-DL-0003` 元数据未提供校验值 | **否** | 元数据缺陷，重试无意义 |
| `QUL-IO-0002` 磁盘空间不足 | **否** | |
| `QUL-IO-0001` 数据目录不可写 | **否** | |

退避：`基数 × 2^(尝试序号-1)`，上限 8 秒，叠加确定性抖动（`尝试序号 × 37 % 120` 毫秒）。
抖动是确定性的而非随机——为了可复现，同时也能让多线程重试错开。

默认最多尝试 3 次。**单条目失败不牵连整体**：每个条目独立重试、独立定性。

### 4.3 并发

`MaxConcurrency`（默认 4）由信号量控制。任何单个条目的异常都在其工作单元内被吸收并转换成逐条结论，**编排层永不因单个条目抛出**。

## 5. 磁盘预检

下载开始前，用 `已知体积之和 + 安全余量（默认 256 MB）` 与缓存所在卷的可用空间比较。不足即整批标记 `QUL-IO-0002` 并**一个请求都不发**。

理由：下到一半才发现空间不够，用户得到的是"下了 3 GB 然后失败"，而正确的反馈是"空间不够，请先释放"。

`KnownTotalBytes` 在存在未知体积条目时是下界，仅用于预检与进度估算。

## 6. 解压安全规范

### 6.1 判定规则（领域层，纯逻辑）

对每个条目名求出结论：

| 结论 | 触发条件 |
|---|---|
| `EmptyName` | 空、全空白、或只有 `./` |
| `AbsolutePath` | 以 `/` 或 `\` 开头（含 UNC） |
| `DriveLetter` | 任意位置含 `:`（Windows 下本就是非法文件名字符） |
| `ParentTraversal` | 含 `..` 段 |
| `SymbolicLink` | 条目通过 Unix 外部属性把自己标成软链 |
| `TooLong` | 与根拼接后超过 240 字符的保守上限 |
| `OutsideTargetRoot` | 拼接结果不在受控根目录之下（纵深防御）；或根本没有给出根目录 |
| `Allow` | 其余 |

理由与做法：**不使用 `Path.GetFullPath` 做归一化后再比较**（领域层禁止引用文件系统），而是靠段扫描直接排除越界可能，再用前缀比较做第二道确认。

### 6.2 执行策略：整包拒绝

**先对全部条目做一遍判定，只要有一条越界，就一个字节都不写。**

先解压再补救是做不到的——恶意条目一旦落盘就已经生效。因此 `ZipEntryEscape`（`QUL-ZIP-0001`）的语义是"整包拒绝且零落盘"，而不是"跳过坏条目继续"。

`EmptyName` 是唯一的例外：无法映射到任何文件的条目直接忽略，不构成攻击。

### 6.3 排除项

`LibraryRef.ExtractExclude`（通常是 `META-INF/`）作为前缀排除。同时容忍写成不带斜杠的 `META-INF`。

## 7. 网络环境处理

### 7.1 代理

三种状态必须可区分，否则"关闭代理"这个用户意图无法表达：

| 配置 | `HttpFetchRequest.ProxyAddress` | 行为 |
|---|---|---|
| `ProxyMode.System` | `null` | 跟随系统代理 |
| `ProxyMode.Direct` | `""` | 显式直连 |
| `ProxyMode.Manual` | 代理地址 | 显式代理 |

代理地址畸形 → `QUL-NET-0002`，不重试。

### 7.2 证书

**绝不安装证书校验回调。** 这一点由单元测试断言 `ServicePointManager.ServerCertificateValidationCallback` 保持为 `null` 来守住。

证书类失败（`TrustFailure` / `SecureChannelFailure` / 内层 `AuthenticationException`）→ `QUL-NET-0003`，**不重试**。

分类顺序很关键：证书失败常被包在 `ProtocolError` 里，**必须先判证书再判状态码**，否则会被误当成"服务器错误"而重试三次。

同时显式补齐 TLS 1.2（net48 在部分机器上默认不启用），这只做"补上"，不做任何降低校验强度的动作。

## 9. 测试清单

全部用例走**伪造传输 + 真实临时目录**：网络是模拟的，磁盘是真的。

### 9.1 缓存与校验

| 用例 | 断言 |
|---|---|
| 首次下载后二次运行 | 第二次 `Present`，**请求数不增加** |
| 缓存文件损坏 | 被检出、重下、内容正确 |
| 元数据缺校验值 | `RefusedNoChecksum` + `QUL-DL-0003`，**连请求都不发** |
| 服务端内容与校验值不符 | 3 次尝试后失败，`.part` 与目标文件**都不残留** |

### 9.2 续传

| 用例 | 断言 |
|---|---|
| 传输中途断开 | 2 次尝试；第二次 `RangeFrom` **等于断点位置**；拼接后内容与源逐字节一致 |
| 服务端回 416 | 先带残留长度请求；残留被丢弃后第二次从头取 |
| 服务端忽略 Range 回 200 | **整体重写**而非追加；最终内容不重复 |

### 9.3 重试与隔离

| 用例 | 断言 |
|---|---|
| 网络不可达 | 重试后成功，`Attempts == 2` |
| 404 | `QUL-NET-0006`，**只有 1 次请求** |
| 证书失败 | `QUL-NET-0003`，**只有 1 次请求** |
| 三个条目中一个永久失败 | 另外两个正常完成，`Failures.Count == 1`，`IsComplete == false` |

### 9.4 预检与网络环境

| 用例 | 断言 |
|---|---|
| 空间不足 | `QUL-IO-0002`，**零请求** |
| 三种代理模式 | `null` / `""` / 地址三者互不相同 |
| 证书绕过 | `ServerCertificateValidationCallback` 为 null |

### 9.5 解压安全

| 用例 | 断言 |
|---|---|
| 正常压缩包 | 3 个文件全部解出，内容正确 |
| `../escaped.txt` | `QUL-ZIP-0001`，`ExtractedFiles == 0`，越界文件不存在，正常条目也**没被写出** |
| 绝对路径条目 | `QUL-ZIP-0001` + `AbsolutePath` |
| 盘符限定条目 | `QUL-ZIP-0001` + `DriveLetter` |
| 软链条目 | `QUL-ZIP-0001` + `SymbolicLink` |
| 排除前缀 | `META-INF/` 下的内容不落盘，其余正常 |

`ArchiveEntryPolicyTests` 覆盖：正常路径（含中文与空格目录）、各种 `..` 形态、绝对路径与 UNC、

## 11. 计划组装（P2 收尾）

`Qul.Domain.Downloads.DownloadPlanBuilder` 把一份已合并的版本元数据变成 `DownloadPlan`。
它是**纯逻辑**——不做网络、不碰文件系统，因此"某版本到底要下多少文件、每个文件的校验值是多少"
可以在没有网络、没有磁盘的条件下被完整断言。

### 11.1 四类通道的实际产出

| 版本 | 客户端 | 库 | 本地库变体 | 资源索引 | 日志配置 | 资源对象 |
|---|---|---|---|---|---|---|
| 1.7.10 | 1 | 规则过滤后 | 4 | 1 | 1 | 686 个逻辑名 → 674 个文件 |
| 1.12.2 | 1 | 规则过滤后 | 5 | 1 | 1 | 未纳入样本 |
| 1.16.5 | 1 | 规则过滤后 | 每平台恰好 1 组 | 1 | 1 | 未纳入样本 |
| 26.3 | 1 | 规则过滤后 | **0** | 1 | 1 | — |

### 11.2 计划的两条硬校验

**（一）每个条目都必须带可用的 SHA-1。** 引擎按设计会拒绝没有校验值的条目（`QUL-DL-0003`），
所以计划本身就不该产出这种条目。这条断言把 P1（解析）与 P2（执行）钉在了一起——
"元数据解析得对不对"在这里被"计划能不能真的被执行"再验证一次。

**（二）重复路径必须无害。** 计划按相对路径折叠重复项，但要区分两类：

| 类别 | 含义 | 处置 |
|---|---|---|
| 无害重复（`DuplicatePaths`） | 同一路径，且 **URL 与哈希都相同** | 折叠成一个条目，并如实记录 |
| **内容冲突（`ConflictingPaths`）** | 同一路径，但 URL 或哈希不同 | 并发下载会互相覆盖，留下哪个全看运气；真实元数据上必须恒为空，由测试守住 |

无害重复在真实数据里**普遍存在**，不是异常：

- **资源对象是内容寻址的**：实测 1.7.10 的 686 个逻辑名只对应 **674 份不同内容**，12 组同哈希必须折叠；
- **官方元数据里有指向同一 artifact 的重复库条目**：实测 1.12.2 的 `com.mojang:text2speech:1.10.3`
  出现两次（一次带 natives、一次不带），两者的 `downloads.artifact` 指向同一个文件。

### 11.3 补充实测结论

| 发现 | 影响 |
|---|---|
| **classifier 命名在同一版本内都不统一** | 1.16.5 里 LWJGL 用 `natives-macos`，而 `ca.weblite:java-objc-bridge:1.0.0` 用 `natives-osx`。因此**绝不能硬编码「平台 → classifier」映射**，必须始终走库自己的 `natives` 表——`NativeClassifierSelector` 正是这么做的 |
| **每个平台的本地库变体数量恰好相同** | 1.16.5 的元数据设计成「每平台恰好命中一个变体」，所以三平台的 classifier **数量相同**、差别在变体本身。不能用数量差异判断规则是否生效 |
| **规则过滤的是整个库条目** | 带 os 规则的条目连它的主 artifact 一起被排除。因此按 artifact 计数的库数量可能三平台相同，差异只体现在 classifier 上 |
| **`${arch}` 的取值是 32 / 64** | 不是 `x86_64` 这类架构名，必须显式映射（`NativeClassifierSelector.ArchToken`） |
| **机器架构不等于 JVM 架构** | `PlatformProbe` 给出的是**机器**架构；natives 需要匹配的是 **JVM** 架构（32 位 JVM 跑在 64 位 Windows 上要的是 `-32`）。P3 选定 Java 之后必须用它覆盖 |

### 11.4 资源索引解析

- 索引文件只有一个 `objects` 键；实测 1.7.10 与 1.16.5 的索引**都不含** `virtual` / `map_to_resources`，
  因此不建立任何虚拟目录映射，只保留「逻辑名 → 哈希 + 体积」。
- 缺哈希的对象被单独跳过（没有哈希就无法校验、也无法定位），而不是让整份索引失败。
- **交叉校验**：索引内体积求和与版本元数据声明的 `totalSize` 完全一致
  （1.7.10 = 112,396,854；1.16.5 = 334,438,503）。两份独立元数据互证，
  是元数据被截断或被篡改的天然警报。

### 11.5 相对路径约定

`RelativePath` 是**逻辑路径**，分隔符统一用 `/`（Windows 文件 API 同样接受 `/`）。
统一分隔符是启动计划骨架能逐字节比对的前提之一。绝对路径一律不参与计划。
