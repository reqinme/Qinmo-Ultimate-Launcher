# P4 · 启动计划规范

> 依据：《Minecraft 启动器 · 架构规划与路线图（v1.2 正式版）》P4 阶段。
> 本文件覆盖 **P4.0 离线身份** 与 **启动计划组装**；natives 解压与进程管理在后续小节补录。
> 全部结论都对应已落地的实现与测试。

---

## 1. P4.0 · 离线身份最小实现

### 1.1 它是什么、不是什么

| 是 | 不是 |
|---|---|
| 一个纯本地标识，由本机按固定规则派生 | 不是 Mojang 发放的账号标识 |
| 一个能带进启动参数的显示名与标识 | 不是会话，换不来任何在线能力 |
| 一个不依赖网络、不依赖任何外部服务的身份来源 | 不是"绕过正版验证"——它没有任何东西可以被绕过 |

**它不会向 Mojang 发送任何请求，不伪造官方会话，也不劫持任何官方接口。**

### 1.2 标识的派生规则

```
seed   = "OfflinePlayer:" + <名字>
digest = MD5(UTF8(seed))
digest[6] = (digest[6] & 0x0F) | 0x30        // UUID v3 版本位
digest[8] = (digest[8] & 0x3F) | 0x80        // RFC 4122 变体位
uuid   = 32 位小写十六进制
```

**为什么用社区通行的 `OfflinePlayer:` 约定**：离线模式服务端就是用同一规则算玩家标识的。
换一套规则会让客户端与服务端对不上，而这一约定本身不含任何秘密。

**为什么可以用 MD5**：这里的 MD5 不是安全原语，只是"把一个名字稳定地映射成一串十六进制"的哈希约定。
它不承担防篡改或防碰撞的安全职责——身份标识本身不含秘密，改了也只是换一个本地名字。

**如何与官方标识区分**：生成的是 **UUID v3**，Mojang 官方发放的是 **v4**，版本位不同，
结构上就不可能混淆。`OfflineIdentityFactory.IsDerivedUuid` 就是这条要求的可执行形式，由测试守住。

### 1.3 名字校验

| 规则 | 理由 |
|---|---|
| 非空，两端空白裁掉 | — |
| 长度 ≤ 16 | 游戏本身的限制 |
| 只允许 `[A-Za-z0-9_]` | 游戏与多数服务端只接受这套字符 |

非法名字抛 `QUL-AUTH-0006`，**绝不悄悄替换成一个能用的名字**——那样用户会以另一个身份进游戏却毫不知情。

### 1.4 强制告知（原文保留）

离线身份携带三条告知，界面必须展示且不可默认跳过：

1. 离线账户仅在本机有效，无法进入正版验证（online-mode）服务器。
2. 离线账户不带访问令牌，因此进入不了需要正版验证的服务器与 Realms。
3. 该身份标识由本机按固定规则生成，仅作本地标识，与 Mojang 官方发放的账号标识无关。

`AccessToken` 的取值是占位串 `"0"`：**它不是会话令牌，永远不会被送去 Mojang**，
正版验证服务器也不会接受它。

## 2. 启动计划的双平面模型

### 2.1 为什么要拆

原要求"同一输入两次生成的启动计划逐字节一致"在整份计划上**不可实现**：
计划里含访问令牌、UUID、用户名、实际绝对路径、构建时间戳。

### 2.2 平面划分

| 平面 | 内容 | 参与逐字节比对 | 导出处理 |
|---|---|---|---|
| **A 可复现骨架** | 版本 id、主类、Java 主版本要求、Java 位宽与架构、身份**来源种类**、工作目录与 natives 目录的**逻辑标识**、类路径**相对**条目、JVM/游戏参数**模板**、环境变量**键**、注入项**键** | **是** | 原样导出（本来就不含秘密） |
| **B 运行时秘密引用** | 全部占位符**取值**、解析后的绝对路径、Java 可执行文件路径、构建时刻 | **否** | 一律脱敏 |

**关键分工：模板进骨架，取值进秘密。**
骨架里只有 `${...}` 占位符，没有任何令牌、UUID、用户名或绝对路径——
因此换一个账户、换一台机器，骨架依然逐字节一致。测试里专门有一条用例锁这个性质。

### 2.3 规范化文本

逐字节比对以 `ToCanonicalText()` 为准：

- 换行固定 `\n`，不用 `Environment.NewLine`；
- 数字用不变文化；
- 字段顺序固定，列表按下标展开成 `jvm[0]=…`；
- 首行是 `planFormat=1`，字段增删时递增，让旧记录一眼可辨。

`ComputeHash()` 给出骨架指纹，日志里只记这一串，避免把整份计划灌进日志。

### 2.4 脱敏导出

`ToRedactedText()` = 骨架原文 + 解析后的命令行（敏感值以 `<名字>` 呈现）。

**默认拒绝**：只有白名单里的占位符（`clientid`、`user_type`、`version_name`、`version_type`、
`assets_index_name`、`classpath_separator`、`launcher_name`、`launcher_version`、分辨率）
可以明文出现，其余一律按敏感处理。

测试用一个**可辨识**的令牌断言导出不含它。
（早期版本用离线占位令牌 `"0"` 做这个断言——那段文本里到处是 0，断言永远不成立，等于没写。）

## 3. 占位符清单

清单是四个真实版本元数据里全部 `${...}` 的**并集**，不是拍脑袋列的：

| 版本 | 该版本用到的占位符 |
|---|---|
| 1.7.10 | assets_index_name, assets_root, auth_access_token, auth_player_name, auth_uuid, game_directory, path, user_properties, user_type, version_name |
| 1.12.2 | 同上，去 user_properties，加 version_type |
| 1.16.5 | 加 classpath, launcher_name, launcher_version, natives_directory, resolution_width, resolution_height |
| 26.3 | **加 auth_xuid, clientid, quickPlayPath, quickPlaySingleplayer, quickPlayMultiplayer, quickPlayRealms** |

**26.x 新增的 6 个占位符是硬性要求**：漏掉任何一个，参数组装都会以"未替换占位符"告终。
清单外出现新名字时抛 `QUL-PLAN-0001`，而不是把 `${...}` 原样喂给 JVM。

## 4. 参数组装规则

### 4.1 条目筛选与摊平

参数条目先按规则过滤（os 规则 + features），再摊平成 token 流。

摊平是安全的：真实元数据里 `--xuid` 与 `${auth_xuid}` 本来就是**两个独立条目**，
所以取值与交付都不依赖条目边界。

### 4.2 孤儿开关修复（**必须实现**）

值解析为空的 token，要**连同紧邻的前一个以 `-` 开头的 token** 一起丢弃。

> 为什么：`--xuid` 与 `${auth_xuid}` 是两个独立条目。若只丢值，`--xuid` 会孤零零留下，
> 游戏就会把**下一个参数**当成它的值——参数会整体错位，而且错得毫无提示。

这条规则对"独立条目"与"数组 value 的复合条目"两种形态都成立，因此不需要区分它们。

### 4.3 feature 门控（**最容易搞错的一处**）

一部分参数条目不是被 os 规则门控，而是被 `features` 门控：

| 参数 | 需要的 feature |
|---|---|
| `--demo` | `is_demo_user` |
| `--width` / `--height` | `has_custom_resolution` |
| `--quickPlayPath` | `has_quick_plays_support` |
| `--quickPlaySingleplayer` | `is_quick_play_singleplayer` |
| `--quickPlayMultiplayer` | `is_quick_play_multiplayer` |
| `--quickPlayRealms` | `is_quick_play_realms` |

**不声明 feature，这些参数根本进不了计划**——它们不是"取值为空所以被省略"，
而是压根没通过规则求值。把这两件事搞混，会让人对着一个永远不出现的 `--width` 查半天。

因此组装器的职责之一是**把请求翻译成 feature**：
用户设置了分辨率 → `has_custom_resolution = true`；其余显式置假，
让规则求值的输入是完整的而非缺省的。

### 4.4 旧式与元数据参数的取舍

| 情形 | 做法 |
|---|---|
| 元数据有 `arguments.jvm` | 直接用（规则过滤后） |
| 没有（1.7 / 1.12） | 自己补 `-Djava.library.path=${natives_directory}`、`-cp`、`${classpath}` |
| 元数据有 `arguments.game` | 直接用 |
| 没有 | 把 `minecraftArguments` 整串按空白切分 |

内存参数（`-Xmx`）排在最前，便于一眼看到。用户附加参数排在元数据参数之后。

**日志配置参数只在真的拿到配置文件时才加**：否则会产生一个指向空路径的 `-Dlog4j.configurationFile=`，
那比没有更糟。

### 4.5 恒为空的取值

| 占位符 | 离线取值 | 后果 |
|---|---|---|
| `auth_xuid` | 空串 | `--xuid` 连同开关一起省略（离线没有 Xbox 标识，不编假的） |
| `quickPlay*` | 空串 | 相关参数由 feature 门控，本就不出现 |
| `resolution_*` | 未设置时为空串 | 同上 |
| `user_properties` | `"{}"` | 官方启动器也是传空对象 |

## 5. 类路径

顺序：**规则过滤后的库，然后是客户端 jar**。

- 库来自 `downloads.artifact`，路径优先采用元数据给出的 `path`；
- **只有 classifier 内容的旧式 natives 容器不参与类路径**（它们会被解压到 natives 目录）；
- 26.x 的 natives 是坐标自带 classifier 的独立条目，有 artifact，会正常进入类路径；
- 骨架里存**相对**路径，秘密平面里存拼好的绝对路径串。

## 6. 资源布局修正（P2 → P4 的跨阶段发现）

游戏把 `--assetsDir` 指向的目录当作资源根，并在其下找
`indexes/<索引 id>.json` 与 `objects/<哈希前两位>/<哈希>`。

P2 最初把索引落在 `meta/assets-<id>.json`、对象落在 `objects/<hash>`——**这个布局游戏不认**，
后果是游戏找不到任何贴图与语言文件。已修正为：

```
data/cache/
  meta/                    版本清单、版本详情、客户端 jar
  libraries/               库
  assets/                  资源根 = --assetsDir
    indexes/<id>.json
    objects/<h2>/<hash>
  natives/                 natives 解压目标
```

这不是可以自由发挥的地方。P0 与 P2 的目录规范、路径约定与测试期望均已同步。
