## 0. 本机已核实的起点事实（**先读这一节，能省一天**）

M0 前已实测，下表是**事实**不是推测。写任务书时凡涉及本机环境，一律引用此表。

| 项 | 已核实的事实 |
|---|---|
| 系统 | Windows 11（构建 **26200**；`ProductName` 显示为 "Windows 10 Home China"，是注册表陈旧字段，以构建号为准）→ **Mica / Acrylic 系统材质可用** |
| 网络代理 | **PAC 自动配置**：`AutoConfigURL = http://127.0.0.1/pac.txt?S302`，规则为 `PROXY 127.0.0.1:80`；绕过名单 196 个域名，含 `github.com` / `raw.githubusercontent.com` / `codeload.github.com` |
| git 访问 GitHub | **需显式配置**：`git config --global http.https://github.com.proxy http://127.0.0.1:80`。命令行工具**不读 PAC**，不配就 21 秒超时 |
| GitHub API | `api.github.com` 直连可达，匿名限流 **60 次/小时** |
| Minecraft 环境 | **未安装任何 Minecraft**：无 `.minecraft`、无基岩版包、`minecraft://` 协议未注册 |
| **WebView2 运行时** | **本机已安装，版本 `154.0.4258.37`** → S3 的基线环境就绪；但 S10 **无法用本机验证"缺运行时"这条路径**，必须另找干净环境 |
| **网络实测带宽** | **国际源实际吞吐 ≈ 0.22–0.28 MB/s（1.8–2.3 Mbps）**；网卡链路为 681 Mbps WLAN → **瓶颈在跨境出口，不在本机**。走 PAC 代理（0.28 MB/s）与直连（0.22 MB/s）**差别不大** |
| 文档编码 | 三份文档均为 **UTF-8 无 BOM**（正确）——**但 `README.md` 有 BOM**，不统一（低优先，可顺手统一）。⚠️ **不要用 `Get-Content` 判断文档内容**——PowerShell 5.1 默认按 ANSI 读 UTF-8，会显示乱码，容易被误判为"文件损坏"（本轮已发生一次） |
| `repos/` | 已克隆 **18 个参考仓库**，均为只读参照 |

> **"浏览器能开 GitHub 但 git 连不上"这个现象本身就说明存在 PAC**。诊断网络先查
> `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `AutoConfigURL`，别只查环境变量与常见端口。

### ⚠️ 带宽实测带来的一个设计判断修正（**重要**）

**1.20.x 全量资源约 550 MB 以上。** 按实测 0.28 MB/s，**仅资源下载就要约 33 分钟**，加上库与客户端 jar 更久。

**这把 S5 要回答的问题改了：**

| 原以为的问题 | 实测后真正的问题 |
|---|---|
| "并发能不能打满带宽"（带宽假设是充裕的） | **"在 0.28 MB/s 的现实下，全量安装要几十分钟——产品能不能接受？"** |
| 打满带宽即算通过 | **打满 0.28 MB/s 毫无意义**；真正要优化的是**总时长**与**用户等待体验** |

**因此 S5 的通过标准相应改写**（见 S5），并追加三条设计输入：

1. **镜像源不是"可选优化"，而是可用性刚需**——本机实测官方源很快（第一轮项目实测"官方比 bmclapi 快约 8 倍"）是在**另一条网络路径**下的结论，**换环境后必须重测**。
2. **"按需下载"（只下启动必需资源）优先级上升**：先能进游戏，资源后台补。这从"优化项"变成"核心体验"。
3. **进度可见性成为硬要求**：几十分钟的等待里，**必须有可信的剩余时间估算与可中断/可恢复**，否则用户会以为卡死。

### 1.1 一句话目标

**用最低成本，把"会让后面返工"的假设全部证伪或证实，并交出材质方案、性能预算、官方对标基线与技术栈结论。**

### 1.3 硬纪律

1. **不为尖刺写产品代码**——尖刺代码写在 `spikes/` 下，**结论出来后可以整体删除**，不进主工程。
   > **例外（v1.3 修正）**：**材质获取与窗口配置那段不能删**——那是 M4 的地基，应**抽进 `qul-infra`**。
   > 删的是**演示界面**，不是能力本身。
2. **每项尖刺必须"可复现"**：留下命令、环境、数字、截图路径。**"我试过了没问题"不算结论。**
3. **失败不掩盖**：结论槽只允许填 `通过` / `不通过` / `降级：<具体降级方式>`，**不允许"基本可行"这种措辞**。
4. **不达标就砍功能，不改预算**（除非 S3 证明预算本身需要按实测重定，那是允许的——但要写明依据）。

#### ⭐ 纪律 5：**每次收工必须留下"可运行状态"**（碎片化时间的前提下的第一条纪律）

> **背景**：本项目的时间**碎片化、不可承诺**（"有空就开"）。
> 这种节奏下，项目最常见的死法**不是做不完，是"下次打开不知道从哪继续"**。

| 收工前**必做** | 说明 |
|---|---|
| **① 提交（commit）** | 不管做到哪，**代码必须是能编译/能跑的状态**。宁可回退到上一个绿色状态，也不要留着半截 |
| **② 更新 `SESSION.md`**（仓库根目录，新建） | 三行就够：**① 我上次做到哪 ② 下一步第一件事是什么 ③ 有没有卡住的地方** |
| **③ 不留"我记得要改 X"** | 想起来的事**立刻写进 `SESSION.md` 或 issue**，不要靠脑子——碎片化节奏下必忘 |

**`SESSION.md` 模板**（新建仓库时直接建这个文件）：

```markdown
# 上次收工（YYYY-MM-DD HH:MM）

## 上次做到哪
<一句话 + 相关文件/里程碑>

## 下一步的第一件事
<必须具体到"打开哪个文件、改什么"——这是为了下次坐下 30 秒内能开工>

## 卡住的 / 待查的
- <没有就写"无">

## 这次决定的（避免下次重新纠结）
- <例如"§7.2 的自适应爬坡初值用 4，因为 …">
```

**为什么这条比其它纪律都重要**：**碎片化时间的成本不在"做得慢"，在于每次重新进入状态**。
没有 `SESSION.md`，每次开工会花 20–30 分钟回忆——**一年 200 个单元，那就是 60–100 小时白扔**。

#### ⭐ 纪律 6：**只做清单里的活**（AI 连续推进的前提，v1.4 新增）

> **本项目的开发方式是"AI 连续推进 + 人按需介入"。** 这带来一个特有的失败模式：
> **在你没看的那些小时里，我会自行扩大范围**——加个"顺手做的小功能"、改一处"看起来更好的设计"、
> 引一个"更方便的依赖"。**每一次都不大，累积起来就是范围失控。**

**三条硬约束**：

| # | 约束 |
|---|---|
| **1** | **只从已定清单取活**（M0 即 U0–U12）。**清单外的活只准做两件事**：写进 `SESSION.md` 的"**候选**"区，或问你。**不准自行开工。** |
| **2** | **失败即停**：任一验收没过 / 测试变红 / 发现方案矛盾 → **停下并写进 `SESSION.md` 的"卡住"区**，不许"先绕过它做后面"。 |
| **3** | **重大决策不自行拍板**：不改红线、不改已定 ADR、不引方案外依赖、不加新功能。拿不准的写进仓库的 `docs/待决.md`，**等我看**。 |

**再加一条**：**每完成一个里程碑必须停下等人评审**，不允许连续跨过两个里程碑。

**为什么**：**连续推进省的是你的时间，代价是少了你的判断。** 这三条就是把代价显式设上限——
否则省下来的时间会以**返工**的形式还回去，而且还更多。

### S1 · DWM 窗口材质可达性

**假设**：net48 时代 WPF 拿不到的东西，Tauri 2 + WebView2 能在本机（Win11 26200）拿到 Mica / Acrylic 系统材质。

**为什么必须验**：材质是本方案界面语言的**第一层**。拿不到，"三层材质"直接塌成两层，全部界面设计要重做。

**怎么验**（**v1.2 改为 4×2 矩阵——这才是真正的风险点**）：

> **⚠️ 我最初把重点搞错了**：一直在追"材质能不能拿到"，但**真正的风险是**
> **无边框自绘窗口（`decorations: false`）与 DWM 系统材质能否共存**。
> 因为我们要自绘标题栏（灵动岛要浮在顶部），而**无边框窗口正是历史上材质不生效的高发场景**。
> **如果"无边框 + 材质"不成立，整个界面语言的形状要改**——这比"材质能不能拿到"重要得多。

| | **有系统边框** | **无边框自绘**（我们要的形态） |
|---|---|---|
| `apply_mica` | ? | **? ← 真正要知道的** |
| `apply_acrylic` | ? | **?** |
| `apply_tabbed` | ? | **?** |
| 不施加（纯色兜底） | ? | ? |

1. 新建最小 Tauri 2 工程（`pnpm create tauri-app`，Vanilla TS 模板即可）。
2. 加官方 vibrancy 能力（`window-vibrancy` / `tauri-plugin-vibrancy`）。
3. **把 8 个格子逐个跑出来并截图**：4 种材质 × 有/无边框（`decorations: true/false`）。
4. 全程保持 **`transparent: false`（非透明窗口）**——因为 S2 会证明透明不可用。
5. 检查窗口拖动、最大化、还原、Snap Layouts、多显示器（若有第二屏）下材质是否稳定。
6. **额外记录**：不同材质走的是哪个 API（`DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE)` 还是 `SetWindowCompositionAttribute`）——**这决定材质在 Win10 上是否可用**。

**通过标准**：8 个格子都有明确截图；**至少"无边框 + 某一种材质"成立**（这是我们要的形态）；纯色兜底可用。

**不通过怎么办**：

| 情形 | 降级方案 |
|---|---|
| **无边框下材质全部失效** | ⚠️ **最需要预案的情形**：二选一 —— ①**保留系统边框**，灵动岛改为浮在内容区顶部（不占标题栏）；②**放弃材质**走纯色 + 层次。**M4 的布局设计必须先知道走哪条** |
| 只有 Acrylic 可用 | 用 Acrylic，视觉参数按 Acrylic 特性重调 |
| 只在深色主题可用 | 主题系统按"深色有材质、浅色纯色"设计，且必须好看 |
| 全部不可用 | **退回纯色 + 层次设计**，并把"纯色也必须高级"升级为核心设计约束（靠留白、描边、排版、字重） |

**取证**：8 张截图（`spikes/S1/screens/`）+ 材质 API 调用日志（含用的是哪个 API）+ 窗口操作录屏。

**结论槽**：

```
判定：☑通过（2026-10-01，U1）—— **A 档成立**
有边框可用材质：☑Mica / Acrylic / Tabbed 三者 OK    无边框可用材质：☑同上（三者在无边框下均 OK）← 关键
走的是哪个 API：☑DWMWA_SYSTEMBACKDROP_TYPE（由 window-vibrancy 封装调用）
  实测调用：apply_mica / apply_acrylic / apply_tabbed，**全部返回 Ok 且可见**
无边框下材质是否成立：☑成立（→ 布局预案取 A 档：保留自绘标题栏 + 材质）
适用主题：☑浅色与深色均可用（另行记录：深色 Mica 下**测试页的深色字不可读**，
  但那是测试页的问题，不是材质的问题 —— 主题令牌四态已在 UI 规格 §5.2 定）
⚠️ **前提（比结论更重要）**：**窗口必须 `transparent(true)`**。
  不加它时三个 apply_* 都返回 `Ok` 但**毫无可见效果** —— 因为 WebView2 默认以不透明背景填满窗口，
  把 DWM 材质整个盖住。**只信 `apply_ok` 会得出完全错误的结论。**
  证据：8 张截图 + 像素分析（`docs/_artifacts/S1/`、`spikes/s1-material/out/`）
```

### S2 · 窗口透明与 CSS `backdrop-filter` 能否共存

**假设（预判为否）**：Windows 上 WebView2 的窗口级透明会破坏 CSS `backdrop-filter` 的模糊（社区已记录的平台缺陷）。

**为什么必须验**：这决定**要不要用 CSS 模糊做卡片毛玻璃**。若误判，会在做了几十个组件后才发现效果全是坏的。

**怎么验**：

1. 在同一最小工程里，开 `transparent: true` + 页面背景半透明 + 一个 `backdrop-filter: blur(20px)` 的卡片。
2. 关闭 `transparent`，重复同一页面。
3. 两种状态各截图，**肉眼比对卡片是否真的模糊了背景**。
4. 附带测：`backdrop-filter` 在**不透明窗口**内是否正常工作。

> **⚠️ 本步骤原文已按 S1 实测更正（v1.6）**
>
> 原写作："**（这是我们要的方案：窗口不透明、材质走 DWM）**"。
> **这句话与 S1 的实测结论矛盾**，故删除，理由如下：
>
> | 来源 | 说法 |
> |---|---|
> | 本步骤原文（推测） | 窗口不透明 + 材质走 DWM |
> | **S1 实测结论** | **材质需要 `transparent(true)`** —— 它是**前提**，不是可选项 |
>
> **为什么必须改而不是"两种都留着"**：留着它，后面按任务书办事的人会去试一条
> **已经被证伪的路线**，而失败现场看起来像"材质坏了"，不像"我按错的文档做了"。
> **一份同时写着两种互斥说法的文档，比一份写错的文档更贵**——
> 因为它让人无法判断该信哪一句。
>
> 因此本步骤改为**只做对照测量**（不透明窗口下 CSS 模糊是否可用），
> 而**不再声称"这是我们要的方案"**——采用方案由 S1 + S2 的联合结论决定，
> 记在下面的结论槽里，不写在这一步的步骤描述里。

**通过标准**：得到明确结论——三者组合（透明窗口 + CSS 模糊 + DWM 材质）**能否共存**；

**取证**：两组对比截图（含局部放大）+ 结论说明。

### S3 · WebView2 性能基线（**本尖刺决定预算是否成立**）

**假设**：Tauri 2 + WebView2 的冷启动与内存落在可接受范围，能让 §7 的三项预算成立。

**怎么验**（**必须分两阶段，否则"材质的开销"和"平台的成本"会混成一个数**）：

> **⚠️ v1.2 修正**：原写法直接在带材质的窗口上测，量到的是"**平台 + 材质 + 演示界面**"的混合值。
> 必须**先量裸窗口拿到真基线**，再量带材质的窗口得出**材质自身开销**——否则 S3 无法回答"是材质贵还是 WebView2 贵"。

**阶段 A · 裸窗口基线**（不放任何材质、不放演示界面）：
1. **release 构建**（不是 debug）：`pnpm tauri build`。
2. **冷启动**：脚本启动进程并计时到窗口首帧可交互；**跑 30 次取中位数与 P95**。

4. **体积**：release 产物总体积；**明确区分**是否含 WebView2 运行时。
5. **帧率**：窗口内做一个持续滚动的长列表（含图片），用 DevTools Performance 或自埋点记录帧时间，**跑在核显机器上**。

6. 重复阶段 A 的第 2、3 项，**得出"材质的增量"**（冷启动 +Δms、内存 +ΔMB）。

### S5 · 下载引擎：**总时长与等待体验**（原"能否打满带宽"，已按实测修正）

> **问题已被 §0 的带宽实测改写**：本机国际源实际吞吐 ≈ 0.28 MB/s。**"能不能打满带宽"不再是关键问题**——
> 0.28 MB/s 打满也是 33 分钟。**真正要回答的是"几十分钟的等待，产品能不能让用户接受"。**

**假设**：在 0.28 MB/s 的现实吞吐下，我们能通过**并发 + 镜像 + 按需下载 + 可恢复**，把"能进游戏"的时间压到可接受范围。

**为什么必须验**：这是全链路最大的失败源与最大的体验风险。

**怎么验**：

1. **先建立真实的吞吐基线**（三档，各测 3 次取中位）：
   - 官方源（`piston-meta` / `libraries.minecraft.net` / `resources.download.minecraft.net`）
   - 镜像源（BMCLAPI 等）
   - 并发 8 / 16 / 32 三档下的吞吐变化
   > **注意**：并发在**跨境受限带宽**上常常**没有提升甚至变差**。要用数据决定，不要凭直觉。
2. **测"能进游戏的最短路径"**：只装启动必需的文件（客户端 jar + 必需库 + natives + log4j），
   不下全量资源（`--assetsDir` 缺失时的降级行为要实测），记录**从零到进主菜单的耗时**。
3. **测全量安装耗时**：完整资源（≥550 MB），记录总时长与各阶段占比（元数据 / 库 / jar / 资源）。
4. **测可中断可恢复**：下载到 40% 杀进程，重启后能否续传，**续传是否真的不重下已完成部分**。
5. **测镜像源切换**：把主源改成不可达地址，观察是否自动换源、任务是否中断、已下部分是否保留。
6. **测界面在长时间下载中的表现**：连续 20 分钟全速下载 + 万行日志滚动，窗口可拖动、可取消、**进度与剩余时间不跳变**。
7. **测校验开销**：边下边校验 vs 下完再校验，比较吞吐（SHA-1 在 0.28 MB/s 下几乎不构成瓶颈，但需数据确认）。

**通过标准**（**改写版**）：

| 项 | 标准 |
|---|---|
| **"能进游戏"耗时** | 在 0.28 MB/s 基线下，**按需下载 ≤ 15 分钟** |
| 全量安装 | 无硬线，但**剩余时间估算按分段目标**（见下），**不许给假精度** |
| 并发有效性 | 有数据证明最优并发数；**若无提升，如实记录"跨境受限下并发无收益"** |
| 续传 | 断点续传后哈希正确，且**不重下已完成部分** |
| 换源 | 主源不可达时自动切源，任务不失败 |
| 长时间运行 | 20 分钟连续下载中窗口可交互；**进度不跳变、不假死** |
| 镜像价值 | 如实对比官方源与镜像源吞吐，**产出"默认源优先级"的数据依据** |

**不通过怎么办**：

- 时长不可接受 → **提高"按需下载"的默认范围**（先只下必需，资源后台补）+ **首启引导"先能玩"**。
- 并发无收益 → **降并发**，把资源用在稳定性（重试、校验、镜像）上。
- 镜像也慢 → 引入**用户可配置的多源**并明示"当前源与测速结果"（默认关闭模式见方案 §1.4 的边界表与 §7.2 的差异表）。

**取证**：三源 × 三并发档的吞吐表、按需下载与全量安装的耗时分解、续传验证记录、20 分钟稳定性录屏。

**剩余时间估算的分段目标**（评审修正：原"误差 ≤30%"不现实，因为实测波动本身就有约 27%）：

| 时段 | 目标 | 呈现 |
|---|---|---|
| 下载前 30 秒 | **只显示区间**（"约 25–50 分钟"） | 不给单点数字 |
| 30 秒后 | 最近 60 秒滑动窗口均值，**误差 ≤ 50%** | 单点 + "剩余约 X 分钟" |
| 过半后 | **误差 ≤ 30%** | 同上 |

**纪律**：**错误的小数字比正确的区间更让用户愤怒。**

**结论槽**：

```
⚠️ **仅第 1 项（吞吐基线）已完成；第 2–7 项未做，故本槽不得视为 S5 通过。**
官方源吞吐：0.382（conc 1）→ **0.832 MB/s**（conc 16）    镜像源吞吐：0.000–0.124 MB/s
  两轮中位数（4 MB/格）：官方 0.382 / 0.623 / 0.776 / 0.832（conc 1/4/8/16）
                         BMCLAPI 0.000 / 0.021 / 0.124 / 0.000
  官方源错误数**恒为 0**；BMCLAPI 的**失败数恰好等于并发数**（conc 16 → 16 失败）
最优并发：**8**（官方源）；8 与 16 差异（0.776 vs 0.832）在噪声内 → 取更保守的 8
并发是否有收益：☑**有**（官方源 0.382 → 0.832，**×2.18**）—— **与任务书"跨境受限下常无收益"的预判相反**
默认源优先级结论：**官方优先**。本机的 BMCLAPI 不是"慢"而是"经常失败"，
  故它只能是可选后备，且**不要给它开并发**（应按单连接 + 长超时 + 快速失败切回官方）。
  ⚠️ 反面对照：任务书记的"第一轮项目实测官方比 bmclapi 快约 8 倍"是**另一条网络路径**下的结论，
  本条**只在当前网络下成立，必须带环境一起引用**。
时间波动：同一格（官方 conc 1）两轮 0.481 vs 0.282（差 1.7 倍）→ **只能当量级与趋势读**，
  与任务书"实测波动本身约 27%"的那条修正一致。
```

### S6 · Java 版本探测与多版本选择

**假设**：能可靠发现本机全部 Java，并按游戏版本要求选对（1.17+ 需 Java 16+，1.20.5+ 需 Java 21）。

**为什么必须验**：选错 Java 是"游戏起不来"的头号原因，且用户看不懂报错。

**怎么验**：

1. 扫描并列出本机全部 Java：注册表（`HKLM\SOFTWARE\JavaSoft`、`...\WOW6432Node`）、`JAVA_HOME`、`PATH`、常见安装路径（Oracle / Adoptium / Microsoft / Zulu / Liberica）、各启动器自带 JRE 目录。
2. 对每个候选执行 `<java> -version` 与 `<java> -XshowSettings:properties -version`，解析出版本号、位数、厂商、路径。
3. 构造选择场景：给一批游戏版本（1.8.9 / 1.12.2 / 1.16.5 / 1.20.1 / 最新正式版），验证选出的 Java 是否符合要求。
4. 负面场景：本机**没有**符合条件的 Java 时，界面给什么提示？（必须是"需要 Java 21，未找到；已找到 Java 8 与 17"这种可操作提示）

**通过标准**：本机全部 Java 被找出（无漏、无误报）；五个版本场景选择全对；缺 Java 时有可操作提示。

**不通过怎么办**：对扫不到的安装方式（如绿色版解压不注册）明确记录为已知限制，并提供**手动指定路径**作为兜底（该能力本轮必须可用）。

**取证**：探测结果与真实 `java -version` 的逐条对照表。

**结论槽**：


### S7 · Java 启动链路端到端（**产品地基，不通就没有产品**）

**假设**：能独立完成"取元数据 → 下载 → 校验 → 解压 natives → 组装参数 → 拉起游戏 → 进主菜单"。

**为什么必须验**：这是产品的存在理由。**第一轮项目已完整走通这条链路，但本轮换栈，必须重新确认**（尤其是参数组装与 `mainClass` 处理）。

**怎么验**：

1. 取 `version_manifest.json`，选一个正式版（建议 **1.20.1**，结构现代且稳定）。
2. 下载：客户端 jar、全部 libraries、asset index 与 objects、log4j 配置。
3. 校验：逐文件 SHA-1 比对；**故意篡改一个文件，验证能被发现并重下**。
4. natives：按平台解压到**实例目录内**（不落系统 `%temp%`）。
5. 组装参数并**逐参数与官方启动器的实际命令行比对**。**工具链要落实（不能靠肉眼）**：

   ```powershell
   # 第一步：用官方启动器启动一次游戏，抓它的真实命令行作为基准
   (Get-CimInstance Win32_Process -Filter "caption='javaw.exe' OR caption='java.exe'" |
      Select-Object -First 1).CommandLine | Set-Content baseline.txt -Encoding UTF8

   # 第二步：用我们的启动器启动一次，同样抓一份
   (Get-CimInstance Win32_Process -Filter "caption='javaw.exe'" |
      Select-Object -First 1).CommandLine | Set-Content ours.txt -Encoding UTF8

   # 第三步：把两条命令行按空白切分为参数数组，排序后 diff
   #   （排序是为了消除顺序差异造成的噪声；classpath 那一段单独整段比对）
   $norm = { param($p) ((Get-Content $p -Raw) -split '\s+') |
             Where-Object { $_ } | Sort-Object }
   Compare-Object (& $norm baseline.txt) (& $norm ours.txt) |
     Format-Table SideIndicator, InputObject -AutoSize
   ```

   **比对纪律**：`-cp` 后的 classpath 是**长串**，排序会打乱它，所以**整段取出单独比对顺序**；
   其余参数按集合比对。**每一处差异都要在报告里写清"为什么不同、是否可以接受"**，不允许"看起来差不多"。

6. 用**离线身份**拉起游戏，确认进入主菜单。
7. 采集 stdout/stderr，确认日志可读、退出码可回收。
8. **`launcher_profiles.json` 是否必需——实测。**
   背景：wiki 称 Forge 安装检验需要该文件，但**HMCL 全仓不写**（3 处提及全是导出黑名单），Portal 也不写。
   做法：装一次 **Forge 官方 installer**，先**不写** `launcher_profiles.json`，观察安装是否成功；
   失败则在 `versions/` 旁补写最小 `launcher_profiles.json`（格式见官方教程）再试一次。
   通过标准：得出明确结论——**Forge installer 是否检查该文件**。
   结论槽：`需要写：□是 □否   依据：__________`
   **该结论回填 `ADR-0012` 的状态。**

**通过标准**：

| 项 | 标准 |
|---|---|
| 完整链路 | 进到游戏主菜单 |
| 参数比对 | 与官方命令行的差异**逐项有解释**（允许合理的无关差异，不允许悄悄不同） |

**怎么做**：

1. 建 `docs/来源记录.md`：任何"借鉴自某项目"的设计，写明来源、链接、借鉴的是什么。**本任务书与 `参考项目笔记.md` 即此机制的起点。**

3. 加**参照代码防误粘贴**检查：对 `repos/` 下源码做行哈希，与 `src/`、`crates/` 比对，命中即失败。
4. 明确红线：**AGPL 与无许可的项目，一行代码都不能进仓库。**

**通过标准**：三项机制可运行（哪怕规则很粗），且**能故意踩红**。

**取证**：扫描脚本输出 + 一次故意踩红的记录。

**结论槽**：


```markdown
### S10 干净机器分发

> **判定：⏸ 环境降级（不可完整完成）** —— 用户明确答复：**「我没有一台干净 Windows，我只有这一台电脑」**

**可以做的降级验证**（利用"全新用户配置"这条次选路径）：

| 检查项 | 能否用"新建本地用户配置"覆盖 | 说明 |
|---|---|---|
| release 产物能否直接运行 | ✅ 能 | 新用户没有 `%USERPROFILE%\.cargo`，也读不到本机的 PATH 配置 |
| 是否依赖开发环境（Rust / Node / pnpm） | ✅ 能 | 新用户下这些命令不存在，可直接验证 |
| **是否缺 WebView2 运行时的行为** | ❌ **不能** | **WebView2 是机器级安装**（由 Edge 更新器装在系统里），新用户不会让它消失 |
| 缺运行时的提示是否可接受（非白屏/闪退） | ❌ 不能 | 同上 |

**⚠️ 必须如实记录这一点**：**"新用户配置"与"干净机器"不是一回事**，
差额恰好落在**最需要验证的那一项**上（WebView2 缺失）。
把降级验证当成完整验证，会得到一个"我们验过了"的假结论，
而 M4/M7 的分发设计会建立在这个假结论上。

**因此本项的处置是**：

1. **做能做的部分**（产物可直接运行 / 不依赖开发环境），**并把范围写清**；
2. **WebView2 缺失路径标为"未验证"**，在方案 §7 的"带运行时版本"决策里**按未验证对待**；
3. **补一条不需要干净机器的替代验证**（见下）。

**替代验证（可利用现有环境，成本低）**：
```

## 6. 推进顺序（**按单元，不按天**）

> **v1.3 修正**：原来排的是"Day 1 / Day 2 / …"，**这个前提是错的**——本项目时间碎片化、不可承诺。
> 改成**单元序列**：**每个单元只做一件事**，做完就收工（收工三条硬要求见 §1.3 纪律 5）。
> **不预设一个单元多长**——1 小时能做完 S2 就是一个单元，S7 花三个单元也正常。

| 序 | 单元目标 | 产出 | 为什么排这个位置 |
|---|---|---|---|
| **U0** | **环境就绪**：`git init` + `.gitignore` + `SESSION.md` + CI 骨架 + 装 Rust/Node/pnpm + 确认 JDK 三套 | 一个空仓库，`cargo test` 与前端 lint 能跑 | **这三样没备齐，后面每个单元都会卡**。先做它，因为它是纯机械活，碎片时间也能做 |
| **U1** | **S1 · 材质 4×2 矩阵** | 8 张截图 + 材质 API 记录 | **阻塞全部界面工作**；也是**最快能看到东西**的一步 |
| **U2** | **S2 · 透明 × blur × 材质** | 两组对比截图 + 结论 | 极快（1 小时级），可与 U1 同一次时段做完 |
| **U3** | **S3 阶段 A · 裸窗口基线** | 冷启动 / 内存 / 体积 / 帧率数字 | **唯一能推翻预算的尖刺**，必须早出数字 |
| **U4** | **S3 阶段 B · 加材质增量** | 材质的 Δms / ΔMB | 决定"如果超预算该砍什么" |
| **U5** | **S4 · 分层骨架 + 三条护栏踩红** | 骨架 + 三张"踩红"证据 + CLI 输出 | 决定纪律能否被强制 |
| **U6–U8** | **S7 · Java 启动链路**（预计跨 2–3 个单元） | 能进主菜单 + 参数比对表 + S7 第 8 步结论 | **产品地基**，含脚本调试，最易超时 |

| **U12** | **S9 隔离评估 + 流程 B + 写报告** | 风险评估 + 扫描机制 + `docs/M0-尖刺报告.md` | 都是轻量项，合成一个单元收尾 |

**可压缩 / 可并**：S2、S6、S9、流程 B 都是"1 小时级"；**同一个时段能塞两个就塞**。
**保底优先级**：若进度紧张，**优先保 S1 / S3 / S7**——其余可顺延。

**U0 必须备齐的三样（否则后面每个单元都会卡）**：JDK 8/17/21 三套 · 商店安装基岩版 ·
一台干净虚拟机或全新用户配置。**这三样是纯机械活，适合在碎片时间里先做完。**

> **注意**：**U1 之后你就能看到材质与一个空壳窗口的真实观感**——这是整个项目里最早、最有价值的"看见东西"时刻。
