## 5. 被打断的那一步（恢复后从这里继续）

原本要验证的是 P6 验收里"**能力限制告知每次启动前出现且不可跳过**"这一条——
不能只靠肉眼看截图，要**直接读控件的真实可用状态**：勾选那个确认框之前，「启动」按钮必须不可用。

思路是用 UI 自动化（`UIAutomationClient`）读出按钮的 `IsEnabled`。上一步失败了两次：

1. 第一次抓整屏，抓到了前台别的窗口 → 改成按窗口矩形抓。
2. 第二次 `SetWindowPos` 置顶后 `GetWindowRect` 返回 `0x0`，`AutomationElement.FromHandle` 报"无法识别的错误"
   → 截图退化成 0 字节。

**下次换个更稳的做法**：不要依赖 `Process.MainWindowHandle` + 置顶，
直接用 UI 自动化从根元素（`AutomationElement.RootElement`）按窗口名找，
或者在应用里加一个仅供测试的开关，把 `CanLaunch` 在勾选前后的取值打到会话日志里——
后者更省事，也更容易在无人值守时复现。

## 附：一条工具链教训（会静默毁掉文档）

**在 PowerShell 里对含中文的 UTF-8 文件做"读-改-写"，必须显式指定编码。**

```powershell
# 会毁文件：Get-Content -Raw 默认按 ANSI 代码页读，Set-Content 再把乱码写回去
$t = Get-Content $f -Raw; Set-Content $f $t

# 正确：显式 UTF8，且不做多余的解码往返
$enc = New-Object Text.UTF8Encoding($false)
$t = [IO.File]::ReadAllText($f, $enc)
[IO.File]::WriteAllText($f, $t, $enc)
```

这条已经真实发生过一次：`docs/P7-发布工程规范.md` 被写成 0 字节、随后又被写成乱码，
两次都提交了进去，靠 `git checkout HEAD~1 -- <path>` 才捞回来。

**另外两条同源教训：**

1. **PowerShell 函数名不要撞内置命令**（`Measure` 撞 `Measure-Object` 让脚本静默走错分支）。
   用之前先 `Get-Command <名字>` 确认。
2. **命令用法的 here-string 不能与方法调用的参数共用一行**
   （`Rep @'…'@ @'…'@` 能跑，`.Replace(@'…'@ @'…'@)` 不能）。
