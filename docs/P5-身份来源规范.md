### 为什么"未与真实服务联调"必须写在这里

微软链路的请求形状（端点、授权类型、请求体字段、错误分类）按公开文档实现，
结构测试也覆盖了它们。但**结构测试用的是我自己预置的响应**——
它只能证明"我按文档发了请求"，不能证明"服务端接受这些请求"。

拿一个未注册的 client_id 去撞授权端点，得到的永远是一个笼统的失败，
无法区分"我的请求写错了"与"这个 client_id 本就不可用"。
因此：**在 C1–C4 满足并完成一次真实登录之前，本实现不得被视为已验证。**

## 2. 前置条件门禁（决策 11）

| # | 前置项 | 置真者 |
|---|---|---|
| C1 | 已在微软平台完成应用注册 | 产品负责人 |
| C2 | client_id 已确定；所需权限范围已确认 | 产品负责人 |
| C3 | 回调 URI 或设备码流程已确定 | 产品负责人 |
| C4 | 第三方启动器相关条款已核对 | 产品负责人 |

这四项都是**外部事实**，本程序无从验证，只能逐项确认后置真。

**任一未满足，`Authenticate` 直接返回 `QUL-AUTH-0005` 并逐条说明缺什么，且一个请求都不发。**

拿未注册的 client_id 去撞授权端点，得到的是一个让人查半天的错误，
而真正的原因是前置条件根本没满足——这种"排查成本转移给用户"的行为必须避免。
门禁的这一条由测试直接断言请求数为 0 来守住。

## 3. 令牌加密存储

`DpapiTokenStore`：写盘前经 `ProtectedData.Protect` 加密，作用域 `CurrentUser`。

| 契约 | 由什么守住 |
|---|---|
| 明文绝不落盘 | 测试**直接扫描文件字节**，断言密文里不含访问令牌、刷新令牌、用户名、账号标识的 ASCII 序列 |
| 读不出来不得抛异常 | 密文被改坏时 `Load` 返回 null 并删除残留，而不是崩掉 |
| 换 Windows 账户后优雅降级 | 解密失败 → 当作"没登录过，请重新登录"，且清掉解不开的残留 |
| 列表读取不因单个坏文件失败 | `ListAccounts` 跳过读不出来的文件 |

文件名取账户键的 SHA-1，避免账户名里的字符影响文件系统。

**登出不做服务端撤销**：消费级微软账户没有面向本场景的公开撤销端点，
而刷新令牌本身有有效期。这一点如实说明，不假装做了。

## 5. 微软链路的失败分类

| 情形 | 错误码 | 说明 |
|---|---|---|
| 前置条件未满足 | `QUL-AUTH-0005` | 逐条列出缺失项，且不发任何请求 |
| 用户在浏览器里拒绝 | `QUL-AUTH-0001` | 与网络故障区分开 |
| 设备码过期 | `QUL-AUTH-0002` | 需要重新发起 |
| client_id 不被接受 | `QUL-AUTH-0005` | 几乎总是前置条件问题，不报成网络错误 |
| 账户没有 Xbox 档案（XErr 2148916233） | `QUL-AUTH-0003` | 给出"请先在 Xbox 端创建"的指引 |
| 未成年账户（XErr 2148916238） | `QUL-AUTH-0003` | 指引加入家庭组 |
| 所在地区不支持（XErr 2148916235） | `QUL-AUTH-0003` | — |
| 档案 404 | `QUL-AUTH-0003` | 该账户不拥有游戏 |

**轮询期间把 OAuth 的错误信息读出来再判断**：OAuth 把最有用的错误放在 400 的响应体里，
提前按状态码抛异常会把那部分信息丢掉。

`XErr` 的取值超过 `int` 范围（2148916233 > int.MaxValue），必须按 64 位读——
按 32 位读会得到一个负数，然后落到"未知错误"分支上。

## 7. 界面接线的两态实测

账户恢复接进界面之后，用 UI 自动化跑了两种状态（按控件类型精确定位下拉框，
避免把整个桌面其它窗口的内容也扫进来）：

```
场景 A（存储里有一份有效会话）
  当前选中 = 微软正版账户（EndToEndProbe）
  离线账户 可用=True / 微软正版账户（EndToEndProbe） 可用=True / 第三方 可用=False

场景 B（存储已清空）
  当前选中 = 离线账户
  离线账户 可用=True / 微软正版账户 可用=False（退回门禁）/ 第三方 可用=False
```

**场景 A 下微软来源可用，尽管 C1–C4 仍未满足**——
门禁管的是"发起新的登录"，而已有一份有效会话不该被它拦住。这一点是刻意的。

会话日志同时记录了恢复动作：

```
restored a valid session for Microsoft / EndToEndProbe / 069a79f4… / 到期 …
```

## 8. 首次真实联调（应用注册已就位后）

拿到 client_id 后第一次真正打微软端点，记录实测结果。

### 8.1 一个把真因藏起来的诊断缺陷（已修）

首次失败时程序只显示：

```
登录失败：AuthPrerequisiteMissing
  微软正版登录当前不可用。
```

听起来像前置条件没满足，会把排查引向完全错误的方向。真因是：
`AuthPrerequisiteMissing` 这个错误码被复用在了**设备码请求失败**上，
而 `Send` 与 `Authenticate` 两处 `catch` 都把原始消息替换成了笼统提示——
**Azure 写在 401 响应体里的 `error` / `error_description` 被彻底丢掉**。

修好后一眼看到真因：

```
HTTP 401 invalid_client：
AADSTS70002: The provided client is not supported for this feature.
The client application must be marked as 'mobile'.
```

教训：**错误码可以复用，错误说明不能丢。** 回归用例断言 `Explanation` 里
必须出现 `invalid_client` 与 `AADSTS70002`。

### 8.2 逐端点实测（决定性证据）

同一个应用注册，只换租户段：

| 端点 | 结果 |
|---|---|
| `/consumers/oauth2/v2.0/devicecode` | ✗ HTTP 401 AADSTS70002 |
| `/common/oauth2/v2.0/devicecode` | ✗ HTTP 401 AADSTS70002 |
| `/organizations/oauth2/v2.0/devicecode` | ✅ 成功，返回 user_code |
| `/<目录租户 ID>/oauth2/v2.0/devicecode` | ✅ 成功，返回 user_code |

**结论**：这个应用注册当前只能让**工作/学校账户**完成设备码流程，
面向个人账户的两个端点都被拒。而 Minecraft 绝大多数用的是**个人微软账户**，
所以应用注册缺少的是「**移动和桌面应用程序**」平台配置
（对应错误里那句 "must be marked as 'mobile'"），
外加设备码流程必需的「**允许公共客户端流**」。

这不是启动器侧能绕过的：换租户段绕不开，因为个人账户端点本身被拒。

### 8.3 端点选为 common

在 `MicrosoftAuthEndpoints` 里把租户段固定为 `common`：

- 应用注册声明的是"所有 Microsoft 帐户用户"，对应的正是 `common`
- `consumers` 只认个人账户、`organizations` 只认工作账户，两者都比注册声明的范围窄
- 没有 Xbox 档案的账户会在后面的 Xbox 步骤得到明确说明（`AuthNoOwnership`），
  所以放宽入口不会把问题藏起来，只会让更多账户有机会走完

有回归用例锁死这三点，免得被人顺手改窄。
