# P3 · Java 运行时规范

> 依据：《Minecraft 启动器 · 架构规划与路线图（v1.2 正式版）》P3 阶段交付物。
> 本文件合并四份要求：**Java 探测规则表**、**候选排序策略**、**不可用时的提示文案**、**运行时来源能力矩阵**。
> 所有结论都有本机实测支撑——这台机器上恰好有 7 套 Java，覆盖了三代命名与多种厂商。

---

## 1. 分层与端口

| 关注点 | 归属 |
|---|---|
| 版本号解析、输出解析、选择策略 | `Qul.Domain.Runtime` —— 纯逻辑，可穷举单测 |
| 运行时来源端口与能力声明 | `Qul.Application.Ports.IJavaRuntimeProvider` |
| 多来源合并与手动覆盖语义 | `Qul.Application.Java.JavaRuntimeResolver` |
| 实际执行 java.exe 确认身份 | `Qul.Infrastructure.Runtime.JavaExecutableProbe` |
| 安装位置枚举 | `Qul.Infrastructure.Runtime.JavaInstallationScanner` |
| 两个 MVP 实现 | `DetectedJavaRuntimeProvider` / `ManualJavaRuntimeProvider` |

**为什么探测算基础设施、解析算领域**：领域层被禁止引用进程 API，所以"跑不跑进程"在外面；
但"跑出来的文本是什么意思"是纯字符串逻辑，放在领域层才能被穷举验证。

## 2. 运行时来源能力矩阵

| 实现 | 阶段 | 默认 | 可枚举 | 可获取 | 需许可告知 | 可卸载 |
|---|---|---|---|---|---|---|
| `detected` 本机探测 | **MVP** | 启用 | 是 | 否 | 否 | 否 |
| `manual` 手动指定 | **MVP** | 启用 | 否 | 否 | 否 | 否 |
| 自动下载 | **P10** | **关闭** | 否 | 是 | **是** | 是 |

能力是**声明**而不是假设：调用方按能力决定界面与流程，而不是按实现类型写 `if`。
自动下载那一行的"需许可告知 / 可卸载"两个 true，就是它必须满足的额外约束（只选许可允许再分发的构建、附许可文本、可卸载）。

## 3. 探测规则表

### 3.1 覆盖的位置

| 来源 | 具体位置 |
|---|---|
| 环境变量 | `JAVA_HOME\bin\java.exe` |
| 环境变量 | `PATH` 的每一项 `<dir>\java.exe` |
| 厂商根目录（一级与二级子目录） | `%ProgramFiles%` 下的 `Java`、`Eclipse Adoptium`、`Zulu`、`Microsoft`、`Amazon Corretto`、`BellSoft`、`Semeru`、`AdoptOpenJDK`、`RedHat`、`SapMachine` |
| 厂商根目录 | `%ProgramFiles(x86)%` 下的 `Java`、`Zulu`、`Eclipse Adoptium` |
| 厂商根目录 | `%LOCALAPPDATA%\Programs\Eclipse Adoptium` |
| 官方启动器运行时 | `%APPDATA%\.minecraft\runtime\<组件>\<平台>\<组件>\bin\java.exe` |

候选路径去重后**按路径序排序**再探测，保证候选顺序可复现。

### 3.2 本机实测（可作为验收基线）

| 目录 | `java.version` | `os.arch` | `sun.arch.data.model` | 厂商 |
|---|---|---|---|---|
| `Zulu\zulu-25` | `25.0.4.1` | amd64 | 64 | Azul Systems |
| `Java\jdk-25.0.4.1` | `25.0.4.1` | amd64 | 64 | Oracle |
| `Java\jdk-21.0.12.1` | `21.0.12.1` | amd64 | 64 | Oracle |
| `Java\jdk-17.0.20` | `17.0.20` | amd64 | 64 | Oracle |
| `Java\jdk-11.0.32` | `11.0.32` | amd64 | 64 | Oracle |
| `Java\jre1.8.0_503` | `1.8.0_503` | amd64 | 64 | Oracle |
| `Java\jdk1.7.0_80` | `1.7.0_80` | amd64 | 64 | Oracle |
| `Java\latest` | — | — | — | **空壳目录，不含 java.exe** |
| `%APPDATA%\.minecraft\runtime` | — | — | — | 不存在 |

最后两行就是必须"跳过而不是报错"的情形：目录在、但里面没有可跑的运行时。

### 3.3 判定依据：实际执行，不看目录名

尖刺 S5 的结论被落成了硬规则：**目录名只用于快速筛选候选，从不用于判定版本或架构。**

反例就在本机：`jdk-25.0.4.1` 是四段版本号、`latest` 是个空壳目录、`jre1.8.0_503` 是 JRE 而非 JDK。
只看目录名，这几种都会判错。

## 4. 版本号解析规则

三代命名必须在同一个解析器里共存：

| 形态 | 样例（均为本机实测值） | 规则 |
|---|---|---|
| 旧式 | `1.7.0_80`、`1.8.0_503` | 第一段是 1 → **主版本取第二段**；下划线后是 update 号 |
| 现代 | `11.0.32`、`17.0.20` | 主版本就是第一段 |
| 四段 | `21.0.12.1`、`25.0.4.1` | 多出的第四段记为 build |

归一化规则：

- 截掉构建元数据：`1.8.0_503-b01`、`17.0.20+7-LTS-191`、`25.0.4.1+7-LTS` 都要能处理；
- 去掉首尾空白与成对引号；
- **`1` 与 `1.0` 一律拒绝**——孤零零一个 `1` 没有主版本可言，当成 Java 1 是错的。

排序按 主 / 次 / 修订 / 构建 / update。实际使用几乎只会比主版本，其余段是为了让同主版本的多个安装有稳定次序。

## 5. 输出解析

### 5.1 命令与流

探测统一跑 `java.exe -XshowSettings:properties -version`。

**实测：该输出全部走 stderr，stdout 为 0 字节。** 只读 stdout 会得到一个空字符串。

属性输出直接给出三个权威值，不必从文案里猜：

```
    java.version = 17.0.20
    os.arch = amd64
    sun.arch.data.model = 64
```

### 5.2 回落

不支持属性开关的运行时，回落到 `-version`，从 `java version "1.8.0_503"` 这类行里取版本号。
此时 `os.arch` 拿不到——**如实为 null，不瞎猜**；位宽退一步从整段文本里的 `64-Bit Server VM` 字样推断。

### 5.3 双流并发读

属性输出约 5 KB，超过管道默认缓冲区。顺序读完一个流再读另一个会**死锁**，
因此必须用 `ReadToEndAsync` 并发读两个流，读完再 `WaitForExit` 之后的 `Task.WaitAll`。

超时（默认 8 秒）后杀掉进程并返回 null，绝不挂住界面。

## 6. 三个"架构"概念，别混

这是 P3 最容易出错的地方，也是 P2 交接过来的问题：

| 概念 | 来源 | 用途 |
|---|---|---|
| **机器架构** | `PROCESSOR_ARCHITECTURE` / `PROCESSOR_ARCHITEW6432` | 仅作默认值（`PlatformProbe.DetectArchitecture`） |
| **JVM 的 CPU 架构** | `os.arch`（`amd64` / `x86` / `aarch64`） | `rules` 里的 `os.arch` 匹配 |
| **JVM 位宽** | `sun.arch.data.model`（32 / 64） | **元数据里 `${arch}` 占位符的取值** |

关键点：

1. natives 要匹配的是 **JVM** 的架构，不是机器的架构。32 位 JVM 跑在 64 位 Windows 上时需要的是 `natives-windows-32`。
2. `${arch}` 要的是 `32` / `64`，**不是** `x86_64` 这类架构名——这个映射由 `sun.arch.data.model` 直接给出，不必从架构名反推。
3. `PlatformProbe.ForJavaRuntime(candidate)` 就是这两者的接合点：用选定的 JVM 的 `os.arch` 覆盖机器架构，产出给 `RuleEvaluator` 与 `NativeClassifierSelector` 用的环境画像。

## 7. 候选排序策略

### 7.1 过滤

依次判掉：版本号无法识别 → 主版本低于要求 → 架构不符 → 位宽不符。
**位宽未知（0）不构成拒绝理由**：那是"探测不到"，不是"不匹配"。

### 7.2 排序

| 策略 | 规则 | 默认 |
|---|---|---|
| `SmallestSatisfying` | 先比"比要求高多少"（越接近越优先，**精确匹配排最前**），再取更高版本，再偏好 64 位，最后按路径序收尾 | **是** |
| `Latest` | 满足要求里最新的 | 否 |

**全序收尾必须有**：没有路径序，并列候选的选出结果会随输入顺序漂移，破坏可复现性。测试里专门有一条用例锁这个。

### 7.3 对规划文档的一处有意偏离

文档写的是"自动选中满足该版本要求的**最新可用者**"。本实现默认取 **`SmallestSatisfying`**，理由：

> Minecraft 元数据里的 `javaVersion.majorVersion` 是**下界**，不是"随便多新都行"。
> 1.16.5 声明需要 Java 8，而用 Java 17 / 25 去跑会因为模块系统与 LWJGL 本地库的限制直接失败。
> 选"最新的"在本机场景下会稳定地选中 Java 25，然后稳定地启动失败。

`Latest` 策略保留下来是为了可测与可切换，但不作默认。
**该偏离需要产品负责人确认**；若确认要按文档原文，改一个默认参数即可。

## 8. 多来源合并与手动覆盖

合并顺序：`manual` → `detected`，按可执行文件路径去重（同一文件只算一次）。

覆盖语义：

| 情形 | 行为 |
|---|---|
| 手动路径可跑且满足要求 | **采用手动指定的 Java**，并记一条"已采用手动指定" |
| 手动路径不可用（不存在 / 无法执行） | 回落到本机探测，并记一条"已回落到本机探测" |
| 手动路径可跑但版本不够 | 回落到本机探测，并**记下不满足的具体原因** |

**回落必须留痕。** 静默回落会让用户以为自己的设置生效了，然后对着一个"我明明指定了 Java 17"的界面百思不得其解。

## 9. 不可用时的提示文案

三档，都以"可执行指引"结尾，而不是丢一堆堆栈：

| 情形 | 错误码 | 文案要点 |
|---|---|---|
| 一个 Java 都没找到 | `QUL-JAVA-0001` | "本机未找到可用的 Java。请安装 Java N 或更高版本，或在设置中手动指定 java.exe 的路径。" |
| 找到了但版本都不够 | `QUL-JAVA-0002` | "本机有 N 个 Java，但没有一个满足主版本 ≥ M（最低的是 X）。请安装符合要求的 Java，或在设置中手动指定。" |
| 指定的路径不可用 | `QUL-JAVA-0003` | 携带路径与失败原因 |

另外每个候选都会得到一条**判定理由**（`JavaCandidateAssessment`）：为什么选它、为什么没选别人。
这是验收里"说得清"那一条的落点，也是排障时最有用的东西。

## 11. 测试清单

| 类别 | 覆盖 |
|---|---|
| 版本号解析 | 本机 7 个真实版本串 + 带构建元数据/引号/空白的变体 + 9 种畸形输入拒绝 |
| 输出解析 | 三份**真实抓取的** java 输出（17 / 8 / 7）逐字段断言；纯 `-version` 回落；双流来源；垃圾输入 |
| 位宽判定 | `sun.arch.data.model` 优先 → vm name 推断 → 未知返回 0，绝不用架构名猜 |
| 选择策略 | 默认取最小满足；可切 Latest；无精确匹配时取最小的更大者；不满足时的文案；架构约束；位宽偏好与显式要求；**输入顺序无关的确定性**；每个候选都有判定理由 |
| 多来源合并 | 手动优先；手动无效/版本不够时回落且留痕；跨来源去重 |
| 真实探测（端到端） | 枚举位置去重有序；执行真实 java 得到版本/架构/位宽；**全量扫描跳过空壳目录而不报错** |

## 附：为 26.3 选中 Java 25 的出处

验收表记有"为 26.3 选中 Java 25"，而本文档正文某处仍写着"还没跑过真实启动"。
后者是更早的状态。**26.3 的真实启动已经跑通**，界面与日志里都留下了选择结果：

```
选定 Java 25 (x86_64 / 64-bit)
```

随后 26.3 真实启动成功（窗口 `Minecraft 26.3`，8.3 秒出现），
