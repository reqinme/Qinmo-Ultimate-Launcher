## NexBox 源码实证（**同栈先例，且这里的发现文档里没有**）

> 本节是**读源码**得到的，不是读 README。位置：`repos/NexBox/src-tauri/`。
> NexBox 的技术栈与我们**逐项一致**：Tauri 2.10 + `tauri-build` 2.5 + Rust 1.77.2 + 无边框自绘窗口。

### 发现 1：WebView2 内存可以通过**官方 API** 主动压低（**直接救我们的内存预算**）

`src/lib.rs:260-294`，作者注释写得很清楚：

```rust
// 设置主窗口 WebView 的内存目标级别（Windows，微软官方 API）。
// Low：允许 Chromium 丢弃缓存数据、将内存页换出到 pagefile（隐藏/最小化时）；
// Normal：恢复完整性能。对应 MemoryUsageTargetLevel 的 1 / 0。
fn set_main_webview_memory_level<R: tauri::Runtime>(app: &tauri::AppHandle<R>, low: bool) {
    use webview2_com::Microsoft::Web::WebView2::Win32::{
        COREWEBVIEW2_MEMORY_USAGE_TARGET_LEVEL_LOW,
        COREWEBVIEW2_MEMORY_USAGE_TARGET_LEVEL_NORMAL,
        ICoreWebView2_19,
    };
    // …
    if let Ok(c19) = core.cast::<ICoreWebView2_19>() {
        let level = if low { COREWEBVIEW2_MEMORY_USAGE_TARGET_LEVEL_LOW }
                    else    { COREWEBVIEW2_MEMORY_USAGE_TARGET_LEVEL_NORMAL };
        let _ = c19.SetMemoryUsageTargetLevel(level);
    }
}
```

**它的策略**（值得照抄）：

| 时机 | 动作 |
|---|---|
| 窗口隐藏 / 最小化 | `SetMemoryUsageTargetLevel(LOW)` —— 允许 Chromium 丢缓存、把页换出到 pagefile |
| 窗口恢复可见 | 切回 `NORMAL` |
| 防抖动 | **延时 3 秒**才降级，避免"刚最小化又恢复"的反复切换 |
| 作用范围 | **只对主窗口**（占用最大），切换频率低，用户无感知 |
| 配套 | 隐藏时同时开 Windows **效率模式**（`set_efficiency_mode`） |

**对我们的意义（三条）**：

1. **这是官方 API**（`ICoreWebView2_19::SetMemoryUsageTargetLevel`），不是 hack——**不违反任何红线**，也不属于本方案排除的"修改游戏二进制"类。
2. **它把 §7 的内存预算从"只能被动测量"变成"可以主动优化"**：launcher 长时间挂在后台是常态，
   后台时压低内存恰恰是用户最在意的时候（游戏正在跑，启动器在后台占内存最讨厌）。
3. **依赖两个 crate**：`webview2-com = "0.38"` 与 `windows-core = "0.61"`（NexBox 的精确版本，同 wry 版本）。

**→ 应写进 M0 的 S3**：测内存时**分"可见 / 隐藏后 5 秒"两个状态**，并把 `SetMemoryUsageTargetLevel` 列为 M4 的实现项。

### 发现 2：WebView2 可以关掉一大堆用不上的 Edge 特性（**降内存 + 降攻击面**）

`tauri.conf.json` 的 `additionalBrowserArgs` 是一份很长的手工清单：

```
--disable-features=MediaSessionService,HardwareMediaKeyHandling,msWebOOUI,msPdfOOUI,
  msSmartScreenProtection,msEdgeAutofill,msEdgeShopping,msEdgeWallet
--autoplay-policy=no-user-gesture-required
--disable-background-networking --disable-client-side-phishing-detection
--disable-component-update --disable-default-apps --disable-extensions --disable-sync
```

**对我们的意义**：这份清单**同时服务两件事**——
① **降内存**（Edge 的购物/钱包/自动填充组件对启动器零价值）；
② **降攻击面与降后台网络**（与我们 §5.8 安全基线的"不加载远端、最小权限"同向）。
**可直接作为我们 `additionalBrowserArgs` 的起点**，再按需增删。

### 发现 3：DevTools 的关闭被当作**安全与内存**措施（不是省事）

`Cargo.toml` 注释原文：

> "不含 devtools：release 构建中 wry 会 SetAreDevToolsEnabled(false)，关闭 F12/右键「检查」
> （**DevTools 打开会额外占 100~300MB 且可以任意调用本地 IPC 命令**）；dev 构建用 debug_assertions 兜住。"

**这条直接印证我们 §5.8 安全基线的第 1、3 条**（CSP 不放开、命令白名单）：
**DevTools 能在页面里任意调用本地 IPC 命令 = 如果被打开，命令白名单形同虚设**。
`tauri.conf.json` 里确实写了 `"devtools": true`，但那是 dev 配置；**release 必须确保关闭**。

### 发现 4：主窗口 `decorations: false` + 第二个 `transparent: true` 的托盘菜单窗口

`tauri.conf.json` 里有两个窗口：

| 窗口 | 关键配置 | 说明 |
|---|---|---|
| `main` | `decorations: false`、`visible: false`、`resizable: true`、最小尺寸 1140×715 | **主窗口不透明 + 无边框自绘** → 印证我们"非透明窗口走 DWM 材质"的路线 |
| `tray-menu` | **`transparent: true`**、`decorations: false`、`skipTaskbar`、`shadow: false`、独立页面 `/tray-menu` | 托盘菜单用**透明小窗口**做 |

**对我们的意义**：**透明窗口不是完全不能用**——它适合**小的、不做毛玻璃的浮层**（托盘菜单），
只是不能用来做"窗口级材质 + 卡片毛玻璃"（§2 的结论）。**这细化了我们的设计约束**，不是推翻它。

## LeviLauncher 源码实证（**推翻了我此前两条判断**）

> ⚠️ **先更正一条**：本笔记早先凭 README 的语言标签写"LeviLauncher = TS + Rust"。
> **实际是 Go + Wails**（`go.mod` + `main.go` + `internal/` + `native/` + `frontend/`），加 VCLibs 原生依赖。
> **教训：语言标签来自 GitHub 的统计（按行数），不能当架构结论用。**

### 发现 1：**UWP 形态的实例隔离是做出来的**（我此前判它不可能）

`internal/versions/isolation.go` 全文只有 11 行，但信息量很大：

```go
const UWPIsolationMinVersion = "1.19.70.2"

// SupportsIsolation leaves GDK unchanged and requires a known supported UWP version.
func SupportsIsolation(packageType, gameVersion string) bool {
	if NormalizePackageType(packageType) != PackageTypeUWP {
		return true
	}
	return gameVersionAtLeast(gameVersion, UWPIsolationMinVersion)
}
```

`internal/mcservice/versions.go:185-189` 的注释写了机制：

> `// Isolated UWP redirects ApplicationData into the instance's data folder,`
> `// named per channel to match GDK. Non-isolated instances share the Windows package family's LocalState.`

而 `isolationDirName()` 的注释点明了它与 GDK 的**根本差别**：

> `// isolationDirName is the per-instance data folder. UWP names it per channel`
> `// because the launcher owns the redirect target; GDK mirrors the game's sAppName,`
> `// which only distinguishes preview from release.`

**三种隔离机制现在能分清（这才是关键）**：

| 机制 | 谁做的 | 原理 | 版本约束 | 我们 |
|---|---|---|---|---|
| **GDK 原生** | 游戏自己 | 游戏读普通文件路径，**启动器只需指对路径** | 无 | ✅ 一期做（T1 的加强版） |
| **UWP 重定向** | **启动器** | 把包的 `ApplicationData` **重定向进实例数据目录** | **≥ 1.19.70.2** | ⚠️ **列为 S9 的评估项之一**（不是"不可能"） |
| **PE 导入表改写** | Portal | 改游戏 exe 导入表 + preload DLL | GDK only | ⛔ 触碰红线，不做 |

**→ 对 §6.2 的修正**：原文写"UWP 恒为 `native` → 隔离做不到"**是错的**。
正确表述是：**UWP 隔离存在，但有版本下限（1.19.70.2），且机制是"启动器重定向 ApplicationData"而非"原生命令行参数"**。

### 发现 2：UWP 的内容根与 GDK **结构不同**（印证并强化我的矩阵分列判断）

`service_uwp_test.go` 与 `versions.go` 证实两套路径：

| 形态 | `ComMojangRoot` | 隔离时 |
|---|---|---|
| **UWP 非隔离** | `%LOCALAPPDATA%\Packages\<family>\LocalState\games\com.mojang` | 与包族共享 LocalState |
| **UWP 隔离** | `<版本目录>\<verName>\Minecraft Bedrock[ Beta\| Preview]\games\com.mojang` | **启动器拥有重定向目标** |
| **GDK 隔离** | `<版本目录>\<verName>\Minecraft Bedrock[...]\Users\<user>\games\com.mojang` | 镜像游戏自己的 `sAppName` |

**注意 UWP 隔离路径少一层 `Users/`**——与我从 Portal 读到的结论一致（UWP 无多用户层）。
**两套路径必须分别处理**，这条已在方案 §6.2 的"分 GDK/UWP 两列"里，现在有了第二份独立证据。

### 发现 3：实例备份带**冲突检测与备份路径**（M6 可直接借鉴）

`internal/mcservice/instance_backup.go` 实现了相当完整的实例备份/还原：

- `GetInstanceBackupInfo` → 产出 `Conflicts` 列表，每条含 `ConflictID` / `BackupPath` / `CurrentPath`；
- 还原时**逐项比对**（包目录、配置文件、世界），冲突项不直接覆盖，而是记录"备份路径 vs 当前路径"；
- `buildInstanceBackupScopeWarnings(!roots.IsIsolation)` —— **非隔离实例的备份会带警告**（因为共享数据）；
- 归档结构是**可读的相对路径**（`gameData/Users/<user>/games/com.mojang/minecraftWorlds/<world>/levelname.txt`），便于人工核对。

**对我们的意义**：这套"**备份 → 冲突检测 → 逐项还原决策**"正是方案 §5.5 里"整包更新与重置都不触碰 `persist/`"的落地形态。
**它的 `Conflicts` 结构值得直接照抄形状**，且它印证了"还原不是覆盖"这条纪律。

### 发现 4：它有完整的测试覆盖（**说明这些机制是被验证过的，不是纸面设计**）

`instance_backup_test.go` 有 **1000+ 行**，`uwp_integration_test.go` 直接跑 UWP 集成路径，
`content_roots_uwp_test.go` 测 UWP 隔离根，`TestUWPIsolationVersionBoundaryAppliesToRootsAndSavedSettings`
甚至验证了**版本边界同时作用于"内容根"与"已保存的设置"**（读盘时若版本不支持隔离，**不重写文件但禁用隔离**）。

**这条本身是方法论借鉴**：它的"不支持隔离的版本读到 `enableIsolation:true` 时不改文件、只在读出的元数据上禁用"
正是我们 §4.7 数据迁移链需要的**"失败不阻断、不破坏用户数据"**的同一思路。

## Polymerium（d3ara1n/Polymerium）· MIT · C# / .NET 10 / Avalonia 12

**一句话**：一个把"实例"当**声明式配置**而不是"一堆拷贝文件"的 Minecraft 启动器。

### 核心机制：实例 = 描述，不是文件堆

> 原文："An instance in Polymerium is a description, not a pile of copied files."
> "Polymium — treat your instance as a recipe, not a pile of copied files."

| 能力 | 机制 | 为什么值钱 |
|---|---|---|
| **换加载器不重建** | Forge → NeoForge、Fabric → Quilt：改描述后 **redeploy**，mod 保留 | 我们 M7 的痛点正是"加载器换版本/换类型要重装"；声明式模型把这件事变成改配置 + 重新部署 |
| **整包原地升级** | 丢入新版整合包，存档/设置/世界**自动带过去** | 解决"升级整合包=重装+搬存档"这个老大难 |
| **快照与回滚** | 每次变更可快照；出问题一键还原，**并给出"到底变了什么"的 diff** | 我们 M7 已规划"事务与回滚"，但**回滚后展示 diff** 这一层是它的亮点 |
| **文件链接而非复制** | 用符号链接共享同名 mod → 十个整合包共用一套 mod，不占十倍磁盘 | 直接回答"多实例磁盘爆炸" |
| **依赖图可视化** | 每个 mod、每层依赖可视化成图；**启动前就能看出冲突与缺失** | 我们只规划了"重复/冲突提示"；**图**比列表强得多 |
| **整合包 = 可版本控制的配置文件** | 实例本身就是配置文件，能进 git、能协作、能跨机迁移 | 与"导出整合包"完全不同的思路：**导出的是描述，不是内容** |
| **干净卸载** | 删两个文件夹即彻底移除，无残留 | 与我们"模块可整体移除"纪律同源，但它是端到端承诺 |

### 技术栈与结构

- `.NET 10` + `Avalonia 12` + **MVVM** + 依赖注入 + Reactive Extensions
- 目录：`src/`、`website/`、`submodules/`、`notes/`、`changelogs/`、`scripts/`、`plans/`（**有 plans 目录 = 先写方案再写代码**）
- **内建 CLI**，且**提供 MCP 模式供 AI Agent 调用**
- 内置 CurseForge + Modrinth 市场，可按游戏版本与加载器筛选后直接装进实例
- Windows **必须开启开发者模式**（因为要创建符号链接，否则需要管理员权限）

### 真实架构：外壳 + 独立核心引擎（源码实证，本笔记最重要的一节）

克隆后读它的 `AGENTS.md` 才看清：**本仓库只是外壳，真正的逻辑在子模块里。**

| 层 | 项目 | 职责 |
|---|---|---|
| **核心引擎** | `submodules/Trident.Net`（`TridentCore.*`） | **全部真实逻辑**：数据模型、部署与运行引擎、包仓库（Modrinth / CurseForge）、账户认证（Microsoft / Xbox Live / Mojang / 离线）、整合包导入导出（Trident / Modrinth / CurseForge / MultiMC / Packwiz） |
| **外壳** | `src/Polymerium.Avalonia` | MVVM 界面、主题、本地持久化（FreeSql）、自更新（Velopack）、崩溃上报（Sentry）、HTTP 缓存 |

**关键约束（原文）**："Polymerium **does not re-implement** instance management, deployment, repositories, accounts, or import/export — it drives Trident's managers."

**同一个核心有多个宿主**：`trident` **CLI**（独立分发的产品）+ Polymerium 桌面端 + **MCP 服务模式**（`--mcp`，供 AI Agent 调用）。
所以"一个实例被 CLI 建的，桌面端能直接读写"。

**五个 manager 构成核心门面**：`ProfileManager`、`InstanceManager`、`RepositoryAgent`、`ImporterAgent`、`ExporterAgent`。

**对我们的直接意义**（已写入方案 §5.6）：
1. **引擎与外壳分离不是洁癖，是可落地的架构** —— 它用"CLI 与桌面端共用同一份 `profile.json`"证明了这件事。
2. **CLI 值得进一期**：能跑 CLI 就证明业务逻辑真的不在界面里，我们的"前端零逻辑"护栏多一道实证；顺带得到脚本化与 CI 冒烟测试能力。
3. **MCP 是当代桌面工具的现实需求**，但它属于后续模块位，不进内核。

### 目录布局与三层模型（`Trident.Net/README.md` 原文）

```text
.trident/
├── cache/          assets / libraries / packages / runtimes   ← 共享
├── instances/{key}/
│   ├── profile.json      声明式实例元数据
│   ├── data.lock.json    部署锁定态（用于重建与 diff）
│   ├── data.pack.json    整合包层数据
│   ├── patches/          外部部署声明：patches/import/（随整合包分发）+ patches/users/（本机，不随包分发）
│   ├── build/            投影出的 .minecraft 运行目录
│   ├── import/           整合包源
│   └── persist/          用户保留（存档/截图/options.txt）
```

**术语表（`GLOSSARY.md`）里几条定义精确到可以直接抄**：

| 术语 | 定义要点 |
|---|---|
| instance | 受管理的 MC 环境，**含 profile 与受管目录** |
| profile | **定义实例的元数据**（版本/加载器/包/规则）—— "profile"不是"instance"的同义词 |
| package | **对仓库内容的受管引用**（mod/资源包/光影/数据包/世界）；**package ≠ mod** |
| asset | **受管的物理文件**（配置/截图/日志/库/版本文件）；asset ≠ package |
| recipe | 用户整理的**可分享包引用清单**，只含引用、不含文件与版本/加载器信息；**与整合包不同** |
| collection | 实例内的包分组，仅由共享的 `collection://by-name/<name>` 标记定义，**无外部引用产物** |
| **deploy（部署）** | **把描述变成可运行的游戏目录；不启动游戏** |
| **launch（启动）** | 启动 Minecraft；**可触发部署，但两者是不同操作** |
| reset instance | **永久清空运行目录与部署锁**；可能删掉存档/截图/日志/配置。**"绝不要描述成无害的清理"**（原文） |
| update modpack | 替换整合包源并刷新工作副本，**保留本地保留层**；与 reset 不是一回事 |
| snapshot | 可还原状态，含 profile 与受管数据；**不自动等于运行目录的完整备份** |
| shared cache | 下载的包、资源、库等可复用文件；**缓存条目不是用户数据** |
| promote（提升） | 把易失数据移入更持久的受管层：`build→persist`、`live→import` 两个方向 |
| symlink | **中文用"符号链接"，不用"软链接"**（原文） |

**三条纪律原文摘录**（值得直接采纳为我们的产品文案规范）：
1. **"State data-loss boundaries explicitly."** —— 明确写出数据丢失边界。
2. **"Distinguish preparation from execution."** —— 部署与启动必须分清。
3. **"Distinguish logical references from physical files."** —— package 是引用，asset 是文件。

### 它自陈的已知问题（对我们有直接价值）

| 问题 | 说明 | 对我们的启示 |
|---|---|---|
| 渐变带状色阶 | Avalonia 画刷渲染在渐变过渡处有可见色阶，**是所有 Avalonia 应用的框架级问题** | **这正是我们选 Tauri + CSS 而非 Avalonia 的一条实证**：材质/渐变是我们的核心诉求，框架级渐变缺陷不可接受 |

### 基岩版实例隔离的真实实现（源码实证，本笔记第二重要的一节）

> 读的是 `src/Portal.Bedrock.Windows/BedrockDataIsolation.cs`、`src/Portal.Bedrock.Standard/Manifest/BedrockInstanceConfig.cs`、
> `src/Portal.Core/Minecraft/Instance/Bedrock/BedrockDataPathResolver.cs`。
> **这一节推翻了本方案早先"基岩版隔离大概率做不到"的判断。**

**它做的事，四步：**

1. **从嵌入资源里提取一个 preload DLL**（`Portal.Preload.dll`）到本机目录，再拷进实例目录
   （`ExtractPreloadDll` / `DeployPreloadDll`；拷贝失败时还会生成一个备用文件名重试）。
2. **用 PE 解析器改写游戏主程序的导入表**，让它启动时自动加载这个 DLL：
   `GetPreloadImportName(gameExecutable)` 读现有导入项，`AddPreloadImport(...)` 以 **`FileAccess.ReadWrite` 打开游戏 exe** 写入新的导入项。
3. **写一份 `config.json` 告诉 DLL 把数据目录重定向到哪**：
   `folderPolicyString` 取值 **`native` / `portal` / `shares` / `independence`**，另有 `isVersionIsolated`、`versionType`（正式版/预览版）。
4. **只在 GDK 形态生效**：`GetFolderPolicy` 里 `BedrockBuildType.UWP` **直接返回 `"native"`**——UWP 在 MSIX 沙箱内，做不了。

**数据根解析的完整决策树（`BedrockDataPathResolver.GetDataRoot`）：**

| 条件 | 数据根 |
|---|---|
| `BuildType == UWP` | `%LOCALAPPDATA%\Packages\<包名>\LocalState`（沙箱内） |
| Linux | Proton prefix 下的 `pfx/drive_c/users/steamuser/AppData/Roaming/Minecraft Bedrock` |
| `EnableIndependentInstance == true` | `EnableLauncherSharedData ? <实例目录>\Minecraft Bedrock : <实例目录>\config\Portal\isolation` |
| 否则 | `EnableLauncherSharedData ? %APPDATA%\Minecraft Bedrock : %APPDATA%\cc.tiouo.Portal\Bedrock` |

**两个开关的语义**（`BedrockInstanceConfig` 原文）：

- `enableIndependentInstance`（默认 `false`）——是否让该实例独立数据；
- `enableLauncherSharedData`（默认 `false`）——是否与官方启动器共用数据目录。
  两者组合出上表四种策略，命名与 `folderPolicyString` 一一对应。

**我们的结论（已写入方案 §6.2）：**

| 档 | 内容 | 我们一期是否做 |
|---|---|---|
| **T1** | 不碰游戏本体，只对数据目录做读写管理（列出/导入/导出/备份）；**不承诺隔离** | ✅ 做（=`isolation:false`，界面不渲染隔离开关） |
| **T2** | 真隔离：PE 导入表改写 + preload DLL + 配置驱动重定向 | ❌ 不做。**它触到我们"不修改游戏二进制"的红线**，且引入原生注入的杀软与维护风险（游戏一更新就可能失效，且改写后如何干净卸载需自证）。列为探针 S9：**先做风险可行性评估，不写实现；任一项不可接受即永久放弃并写进红线** |

**同时它也证明了几件正当的事**（这些不踩红线，值得抄）：

- **GDK 形态的数据目录树是**：`<数据根>/Users/<userId>/games/com.mojang/<behavior_packs|resource_packs|skin_packs|minecraftWorlds|Screenshots|world_templates|development_*>`；
  **UWP 形态则是** `<LocalState>/games/com.mojang`（**少一层 `Users`**）——两套路径必须分别处理。
- **世界按用户分目录**：`GetWorldUserIds` 枚举 `Users/` 下的子目录并保证 `Shared` 存在，世界路径为 `<mojangRoot>/minecraftWorlds`。
- **`EnableLauncherSharedData` 这个开关本身是个好设计**：默认用自己的目录，用户可选择与官方启动器共用——这直接对应我们 §4.4"默认关闭、可显式启用、明示限制"的模式。
- **启动信息回传**：`enableLaunchInfo` 开关 + 原生日志文件（`logs/native-<时间戳>-<guid>.log`）——**这正是灵动岛 `Running` 态需要的"游戏已启动/已退出"信号来源**，与 §12.1 从 PCL 挖到的 `Watcher` 事件表是同一类需求的两种实现。

## 环境限制（重要，影响后续所有抓取）

| 通道 | 状态 |
|---|---|
| 系统代理 | **PAC 自动配置**：`AutoConfigURL = http://127.0.0.1/pac.txt?S302`，PAC 规则为 **`PROXY 127.0.0.1:80`**（本地 PAC 服务兼作代理），绕过名单含 196 个域名，覆盖 `github.com` / `raw.githubusercontent.com` / `codeload.github.com` / `objects.githubusercontent.com` |

## Axolotl = Modrinth 启动器的衍生仓库（**重要更正**）

> **更正（v3.7）**：本笔记早先据 GitHub API 的 `spdx_id: NOASSERTION` 判定"Axolotl 无认可许可证，不得复制任何代码"。
> **这个判定是错的**，根因是**仓库级许可证字段读不出 monorepo 的分包许可**。逐包实测后事实如下。

### 证据：它就是 Modrinth 启动器的完整衍生

Axolotl（`Mystic-Stars/Axolotl`，Rust）与 `modrinth/code` 的根结构**逐项对得上**：

| 根条目 | modrinth/code | Axolotl |
|---|---|---|
| `apps/` | ✅ | ✅（`app` / `app-frontend` / `installer-ui` / `website` / `telemetry-*`） |
| `packages/` | ✅ | ✅（含 `ui`、`utils`、`daedalus`、`async-minecraft-ping`、`api-client`） |
| `patches/`、`standards/`、`scripts/` | ✅ | ✅ |
| `COPYING.md`、`crowdin.yml`、`tombi.toml`、`.nvmrc`、`pnpm-workspace.yaml`、`turbo.jsonc` | ✅ | ✅ |
| Axolotl 额外目录 | — | `.claude/`、`docs/`、`netlify/`、`nix/`、`third-party/`、`tools/` |

它的 README 直接用 `apps/app/icons/128x128.png` 作 logo（与上游同路径），
且 `.gitmodules` 里挂着 `Axolotl-Launcher/blockbench-skin-standalone`——**是二次开发而非从零重写**。

### 逐包许可证实测（这才是有效读法）

| 包 | 许可证 | 文件 |
|---|---|---|
| `apps/app`（**启动器本体**） | **GPL-3.0** | `apps/app/LICENSE`（34.3 KB GNU GPL v3） |
| `apps/app-frontend` | **GPL-3.0** | 同上 |
| `packages/ui`、`packages/utils`、`packages/assets` | **GPL-3.0** | 各自 `LICENSE` |
| `apps/website` | **AGPL-3.0** | `apps/website/LICENSE` |
| `packages/api-client` | **LGPL-3.0** | `packages/api-client/LICENSE`（7.5 KB） |
| `packages/async-minecraft-ping` | MIT / Apache-2.0 双许可 | `LICENSE-MIT` + `LICENSE-APACHE` |
| `packages/daedalus` | 自定义（`Copyright © 2024 Rinth, Inc.`） | `packages/daedalus/LICENSE` |
| 多个包另有 `COPYING.md` | **逐包附加条款**（须逐个读，不能只看 LICENSE） | — |

上游 `modrinth/code` 的 `COPYING.md` 原文即：

> "All packages in this repository are licensed under their respective licenses. For more information, refer to the LICENSE file in each package."

**所以仓库级 `NOASSERTION` 的含义是"多许可 monorepo"，不是"无许可"。**

### 对项目的实际结论（三条）

1. **Axolotl 的启动器本体是 GPL-3.0，与我们同为 GPL-3.0** → 许可上**可兼容**，技术上可作为参考甚至借鉴对象（须遵守 GPL 与原作者版权声明）。
2. **但它反过来是更强的证据**：**Modrinth 启动器（Rust）已实现完整的"实例 + 加载器 + 内容 + 整合包"链路，且是 Rust**——
   与我们选的栈**语言级同栈**。它对 **M1（内核）/M6（实例）/M7（加载器）/M8（内容与整合包）** 的参考价值，
   高于此前列为"首批"的任何仓库。
3. **读法纪律**：凡读到 monorepo 参照仓库，**必须逐包打开 `LICENSE` / `COPYING.md`，不能只看仓库级返回值**。
   这条已写进任务书流程 B。
