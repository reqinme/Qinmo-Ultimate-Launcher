# P1 · 版本元数据规范

> 依据：《Minecraft 启动器 · 架构规划与路线图（v1.2 正式版）》P1 阶段交付物。
> 本文件是三样东西的合体：**版本元数据模型说明**、**继承与规则求值规则书**、**兼容性测试清单**。
> 其中绝大部分结论不是设计推演，而是从四个真实版本的官方元数据里实测出来的——凡实测项都标注了样本证据。

---

## 1. 分层与职责边界

| 关注点 | 归属 | 说明 |
|---|---|---|
| 元数据模型 | `Qul.Domain.Metadata` | 纯数据 + 纯规则。无文件、无网络、无进程 |
| 规则求值 | `Qul.Domain.Metadata.RuleEvaluator` | 纯函数，可在任意平台上完整单测 |
| 继承合并 | `Qul.Domain.Metadata.VersionResolver` | 纯函数，同上 |
| JSON → 模型 | `Qul.Infrastructure.Metadata.VersionMetadataParser` | 唯一的解析入口 |

**解析与合并严格分离**：`ParseVersion` 只产出"未合并"的原始形态，绝不隐式展开 `inheritsFrom`。
理由：排障时必须能回答"这个字段到底来自子版本还是父版本"，隐式合并会永久抹掉这个信息。

## 2. 版本清单索引

来源：官方版本清单（`version_manifest_v2.json`）。

| 字段 | 模型属性 | 可空 | 实测说明 |
|---|---|---|---|
| `latest.release` / `latest.snapshot` | `LatestRelease` / `LatestSnapshot` | 否（缺省为空串） | — |
| `versions[].id` | `VersionSummary.Id` | 否 | 缺 id 的条目被跳过 |
| `versions[].type` | `VersionSummary.Type` | 否 | `release` / `snapshot` / `old_beta` / `old_alpha`，未知 → `Unknown` |
| `versions[].url` | `VersionSummary.Url` | 否 | 缺 url 的条目被跳过 |
| `versions[].sha1` | `VersionSummary.Sha1` | 是 | 实测 40 位 |
| `versions[].size` | `VersionSummary.Size` | **是** | **实测 917 个条目一个都没有该字段**。解析器必须容忍缺失，不得据此报错 |
| `versions[].releaseTime` | `VersionSummary.ReleaseTime` | 是 | 原样字符串，不解析成时间类型（解析失败会造成无谓的失败面） |
| `versions[].complianceLevel` | `VersionSummary.ComplianceLevel` | 是 | — |

**容错策略**：单条坏数据（缺 id / 缺 url / 不是对象）**跳过该条**，其余版本照常可用；
只有整个数组缺失或一条可用条目都没有时，才抛 `QUL-META-0001`。
理由：一份清单里出现个别异常条目，不应该让用户完全无法启动游戏。

## 3. 版本详情

| 字段 | 模型属性 | 实测差异 |
|---|---|---|
| `id` | `VersionDetail.Id` | 若调用方传入 `expectedId`，两者必须完全一致，否则 `QUL-META-0002`（防串号/防被替换的元数据） |
| `mainClass` | `MainClass` | 四个样本均为 `net.minecraft.client.main.Main` |
| `assets` | `Assets` | 1.7.10 → `1.7.10`；1.16.5 → `1.16`；26.3 → `34`（命名规则随年代变化，不得假定是版本号） |
| `assetIndex` | `AssetIndexRef` | `id` / `sha1` / `size` / `totalSize` / `url`；`totalSize` 会超出 int，必须用 64 位 |
| `downloads.client` | `ClientDownload` | `downloads` 的键随年代变化（1.7.10 有 `windows_server`，1.16.5 有 `*_mappings`，26.3 只有 `client`+`server`）；只取 `client` |
| `javaVersion.majorVersion` | `JavaVersion.MajorVersion` | 1.7.10/1.12.2/1.16.5 → 8；26.3 → **25** |
| `libraries` | `Libraries` | 33 / 39 / 57 / 114（四样本） |
| `arguments` | 三个参数组 | 见 §6 |
| `minecraftArguments` | `MinecraftArguments` | 仅 1.7.10 / 1.12.2 |
| `logging.client` | `LoggingConfig` | 四个样本都有；`argument` 为 `-Dlog4j.configurationFile=${path}` |
| `inheritsFrom` | `InheritsFrom` | 四个原版样本都为 null；加载器版本才会用到 |
| `minimumLauncherVersion` | `MinimumLauncherVersion` | 记录但不作判断——它约束的是官方启动器，与本项目无关 |

**未知字段**：忽略，并通过可选参数 `unknownTopLevelFields` 上报顶层未知字段名（`QUL-META-0004`，只记日志，绝不失败）。
已知顶层字段集合见解析器中的 `KnownVersionFields`。

**校验（`VersionResolver.Validate`）**：合并后必须满足

1. `Id` 非空
2. `MainClass` 非空
3. `ClientDownload.Url` 非空
4. **不得同时**声明 `minecraftArguments` 与 `arguments.game` —— 两套写法互斥，同时存在说明元数据异常

任一不满足即 `QUL-META-0002`，拒绝该版本。

## 4. 继承合并规则书

### 4.1 字段回落

以子版本为主，字段为空则回落到父版本：`MainClass`、`Assets`、`AssetIndex`、`ClientDownload`、`JavaVersion`、`Logging`、`MinecraftArguments`、`MinimumLauncherVersion`。
`Type` 为 `Unknown` 时取父版本。合并结果不再保留 `InheritsFrom`。

### 4.2 链折叠

先沿 `inheritsFrom` 收集 叶→根 的链，再按 根→叶 顺序逐层合并。

- 链上出现**环** → `QUL-META-0003`
- **父版本缺失** → `QUL-META-0003`
- 超过深度上限（16 层）→ `QUL-META-0003`

三者都是明确拒绝，不是静默降级：畸形元数据必须暴露，而不是产生一个"看起来能用"的版本。

### 4.3 库列表合并（**这一节踩过坑，务必按此实现**）

规则：

1. **子列表原样保留**，顺序与内容一个字节都不改，整体排在最后；
2. **父列表里凡是身份已被子列表覆盖的条目丢弃**；
3. 其余父条目按原顺序排在前面。

去重键是 `LibraryRef.IdentityKey` = `group:artifact` + 变体判别（坐标自带的 classifier、`natives` 键集合、`classifiers` 键集合），**刻意不含版本号**——版本号正是子版本要覆盖的东西。

**为什么不能用 Maven 坐标做键**：1.12–1.16 时代的元数据里，同一坐标会按 OS 出现多条。
实测 1.16.5 有 **16 组**、1.12.2 有 **2 组**，例如 `org.lwjgl:lwjgl:3.2.1` 同时存在通用变体与 `natives-macos` 变体，坐标字符串一模一样。
（1.16.5：57 条库只对应 41 个唯一坐标；1.12.2：39 条对应 37 个。）
只按坐标去重会把一半本地库变体静默吃掉，症状要到运行时缺本地库才暴露。

**为什么禁止在单份列表内部去重**：1.16.5 里 `org.lwjgl:lwjgl:3.2.1`（osx 专用）与 `3.2.2`（win/linux 专用）服务不同平台，在**同一份库列表里合法共存**。
它们的 `IdentityKey` 相同（版本号不参与身份），所以按身份在列表内部去重会误杀。
**身份键只能用于跨父/子边界判断覆盖关系。**

> 未决项：该覆盖语义在 P1 没有真实继承样本可验（四个原版样本的 `inheritsFrom` 均为 null）。
> **P9 接入 Fabric / Forge 时必须以真实数据复核**，尤其是类路径顺序是否需要"子条目插到父位置"。

## 5. 规则求值规则书

### 5.1 列表语义

| 情形 | 结果 |
|---|---|
| 无规则 / 规则为空 | **允许** |
| 有规则 | 初始为**拒绝**；按顺序求值，命中的规则覆盖结论；以**最后一条命中的规则**为准 |
| 有规则但一条都没命中 | **拒绝** |

对应 `RuleEvaluator.IsAllowed`。常见形态 `[{allow, os:osx}]` 在 Windows 上即因"一条未命中"而被拒。

### 5.2 单条规则匹配

全部条件为"与"关系，任一不满足即不命中：

| 条件 | 语义 |
|---|---|
| `os.name` | 大小写不敏感相等（`windows` / `linux` / `osx`） |
| `os.arch` | 相等；**额外接受一条兼容规则**：要求 `x86` 时 `x86_64` 也算命中（32 位规则在 64 位 JVM 上仍应生效）。反向不成立 |
| `os.version` | **正则匹配**运行环境版本；模式非法或环境版本未知时判为**不命中**，绝不抛穿 |
| `features.*` | 每个键都必须等于环境声明的值；环境未声明的键按 `false` 处理 |

**动作无法识别时整条规则跳过**：既不能当 `allow`（会放行不该放行的），也不能当 `disallow`（会拦掉本该生效的），只能判定该规则不可用。

### 5.3 环境画像

`EnvironmentProfile` 是**纯数据**（os 名 / arch / 版本 / 特性表）。
探测真实环境属于基础设施职责——领域层被禁止引用进程与系统 API，因此规则求值本身可在任意平台被完整单测。

四个样本实际用到的规则形态：`os.name` = windows / linux / osx；`features` = `is_demo_user` 等；**`os.arch` 与 `os.version` 在样本中未被使用**，这两条分支由单元测试单独锁定。

## 6. 两套参数写法

| 写法 | 出现版本 | 模型 | 解析要点 |
|---|---|---|---|
| `minecraftArguments` | 1.7.10 / 1.12.2 | `MinecraftArguments`（整串） | 空格分隔成词；不含带规则的项 |
| `arguments.game` / `arguments.jvm` / `arguments.default-user-jvm` | 1.16.5 起 | `GameArguments` / `JvmArguments` / `DefaultUserJvmArguments` | 元素是**字符串**或**对象**；对象的 `value` 是**字符串或字符串数组** |

要点：

- **`value` 的两种形态都必须摊平**。实测 1.16.5 的 `arguments.jvm` 中存在 `{"rules":[{"action":"allow","os":{"name":"osx"}}],"value":["-XstartOnFirstThread"]}`（数组形态）。
- **`default-user-jvm` 是 26.x 新增的键**。P1 只负责原样解析，不在这一层决定它怎么用——但必须存下来，否则会在 P4 悄悄丢掉一组参数。
- 未知的参数组键一律忽略（前向兼容）：26.x 已经证明 Meta 会新增键。
- 1.7.10 / 1.12.2 走 `minecraftArguments`；1.16.5 / 26.3 走 `arguments`。两套写法在真实样本里从未同时出现，因此"同时存在"被判定为元数据异常（见 §3）。

## 7. natives 的两代机制与已知缺陷

**这是 P1 最重要的产出。** P4 的 natives 处理必须同时支持两代机制，并容忍官方元数据自身的缺陷。

### 7.1 第一代（1.7–1.16 时代）：`natives` 映射 + `downloads.classifiers`

```
"natives": { "linux": "natives-linux", "windows": "natives-windows", ... }
"downloads": { "artifact": {...}, "classifiers": { "natives-windows": {...}, ... } }
"extract": { "exclude": ["META-INF/"] }
```

- 1.7.10：4 个库有此形态，且**只有 classifier 内容、没有主 artifact**
- 1.16.5：16 个库有此形态，**同时带主 artifact 与 classifier 内容**

### 7.2 第二代（26.x）：坐标自带 classifier 的独立库条目

26.3 **完全没有 `natives` 映射**（实测 0 个），而是把 natives 做成独立条目，classifier 直接写在 Maven 坐标里：

```
"name": "com.mojang:jtracy:1.14.38:natives-linux"
"downloads": { "artifact": {...} }        // 有主 artifact，没有 classifiers
"rules": [ { "action": "allow", "os": { "name": "linux" } } ]
```

因此 `LibraryName` **必须保留 classifier**，`LibraryRef` 必须能表达"坐标自带 classifier"。

### 7.3 官方元数据自身的缺陷（实测，必须在 P4 容忍）

| 缺陷 | 实测证据 | P4 的正确行为 |
|---|---|---|
| **natives 值是模板** | `tv.twitch:twitch-platform:5.16` 与 `tv.twitch:twitch-external-platform:4.5` 的 `natives[windows]` = `natives-windows-${arch}` | 先按 JVM 架构替换 `${arch}` 再查 classifier；不做替换永远查不到 |
| **悬空引用** | `tv.twitch:twitch-platform:5.16` 声明 `natives[linux] = natives-linux`，但其 `classifiers` 只有 `natives-osx` / `natives-windows-32` / `natives-windows-64` | 变体不存在就**跳过该库**，不抛异常、不取到 null 静默继续 |
| **32/64 位分叉** | 同一库的 classifiers 只有 `natives-windows-32` 与 `natives-windows-64`，没有笼统的 `natives-windows` | 必须按 JVM 架构在两者间选择，不能假定存在通用键 |

`ExtractExclude` 保留原样（通常是 `META-INF/`），供 P4 解压时排除。

## 8. 兼容性测试清单

### 8.1 黄金样本覆盖矩阵

样本为**未经修改的官方元数据**，冻结在 `tests/Qul.Tests/Golden/`，测试离线可跑。

| 维度 | 1.7.10 | 1.12.2 | 1.16.5 | 26.3（当前正式版） |
|---|---|---|---|---|
| 参数写法 | `minecraftArguments` | `minecraftArguments` | `arguments` | `arguments` |
| `arguments` 键 | — | — | game, jvm | game, jvm, **default-user-jvm** |
| 库条目数 | 33 | 39 | 57 | 114 |
| 唯一坐标数 | 33 | 37 | 41 | 114 |
| Java 主版本要求 | 8 | 8 | 8 | **25** |
| `assets` | `1.7.10` | `1.12` | `1.16` | `34` |
| natives 机制 | 第一代（无主 artifact） | 第一代 | 第一代（带主 artifact） | **第二代（坐标带 classifier）** |
| natives 库数 | 4 | 5 | 16 | 0 |
| `downloads` 键 | client, server, windows_server | client, server | client, server, 两个 mappings | client, server |

### 8.2 必须持续为真的断言

| 断言 | 锁定的风险 |
|---|---|
| 版本清单可解析出 500+ 条目，`latest` 非空，四个样本版本可被 `Find` 到 | 索引解析回归 |
| 不存在版本返回 null 而不是抛异常 | 界面侧应能安全查询任意 id |
| 1.7.10 走 `minecraftArguments`、`GameArguments` 为空 | 两套写法识别错误 |
| 1.7.10 的 natives 值 = 字面可命中 ∪ 模板值 ∪ 已登记悬空引用，且**模板与悬空引用都被计数断言覆盖** | 靠"恰好没触发"通过的空断言 |
| 1.12.2：39 条库 / 37 个唯一坐标 / `com.mojang:text2speech:1.10.3` 存在 2 个变体 | 同坐标多变体被误合并 |
| 1.16.5：57 条库 / 41 个唯一坐标 / 16 个 natives 库 / 每条都有主 artifact | 同上 |
| 1.16.5 的 `-XstartOnFirstThread` 带 osx 规则，在 Windows 上判为不生效 | 规则求值失效会直接导致启动失败 |
| 26.3：114 条库 / 0 个 `natives` 映射 / 存在坐标自带 classifier 的条目 / `default-user-jvm` 非空 | 第二代机制与新增参数组被漏掉 |
| 三个平台（windows / linux / osx）在 1.7.10 / 1.12.2 / 1.16.5 上得到**不完全相同**的可用库集合 | 规则根本没生效 |
| `MergeLibraries` 在任一侧为空时**不改变条目数**（57 / 57 / 114） | 列表内部误去重 |
| 单份列表内部绝不去重，且 `3.2.1` 与 `3.2.2` 的 `IdentityKey` 相同 | 上述误杀的成因 |
| 子版本覆盖父版本同身份库，子条目排在最后 | 继承覆盖语义 |
| 解析两次结果完全一致（库顺序与参数序列） | 启动计划骨架要做逐字节比对，解析必须可复现 |
| 四个样本全部通过 `Validate` | 必备字段校验过严或过松 |

### 8.3 解析器边界用例

畸形 JSON、根不是对象、缺 id、id 与 `expectedId` 不一致、清单缺 `versions`、清单条目全坏、
未知顶层字段被收集但不失败、单条坏清单条目被跳过、无法识别的规则动作被丢弃、
`arguments.value` 的字符串与数组两种形态、Maven 坐标的 3 段 / 4 段 / `@ext` / 各种畸形形态。
