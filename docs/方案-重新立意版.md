## 1. 定位重置

### 1.1 一句话

**一个可扩展的启动器平台，首个产品是 Minecraft 双版本（Java 版 + 基岩版）。**

> **措辞修正（v3.6）**：早先写的是"多游戏启动平台"，与 §12.4"不为无关游戏新增 Provider"**自相矛盾**——
> 前者承诺泛化，后者禁止泛化。正确表述是**平台能力可扩展，但产品边界明确**：
> 能扩展的是**「同一个游戏的不同版本/形态」与「与游戏无关的工具模块」**，不是"什么游戏都能启动"。

这个转折不是措辞游戏，它决定了三件事：

| 决定 | 若定位是"MC 启动器" | 定位是"可扩展平台" |
|---|---|---|
| 内核数据模型 | 版本 / 加载器 / mod 可以直接写进模型 | 必须是 **Game / Instance / Provider** 通用模型，MC 概念降为**某个 Provider 的实现细节** |
| 界面导航 | 左侧写死"模组 / 资源包 / 光影 / 存档" | 导航由**能力描述符**动态生成，扩展不需要改界面代码 |
| 扩展方式 | 加功能 = 加分支 | 加功能 = **注册一个模块**，不改内核 |

**如果一开始按第一种做，第二种永远长不出来。** 所以下面的架构是按第二种设计的。

### 1.2 差异化：我们比第一梯队强在哪（**这条是资源分配依据，不是营销文案**）

评审指出：方案通篇在讲"不比别人差"，却**没有一句话说清"我们比 PCL / HMCL / Prism / Polymerium 各自强在哪"**。
**这不是营销问题——不知道强在哪，就会平均用力**（后果举例：M4 花两周打磨下载进度条动画，而不是灵动岛与材质层次）。

**三条差异化，按优先级：**

| 序 | 差异化 | 为什么是它 | 相对谁 |
|---|---|---|---|
| **1** | **界面质感**：DWM 系统材质 + 三层层次 + 灵动岛 | **唯一"看一眼就知道不同"的维度**；也是我们放弃旧技术栈换来的东西 | 全部（PCL/HMCL 基于 WPF/JavaFX，材质与动效是天花板级的差距） |
| **2** | **Java + 基岩同一外壳** | 省掉"装两个启动器"的心智负担（官方现在也在走这条路） | PCL / HMCL（只做 Java）；Portal 已做但桌面质感不及我们目标 |
| **3** | **实例声明式模型 + 快照回滚 + diff** | 把"重装 / 搬存档"从根上消灭 | Prism / HMCL（目录隔离，但无声明式与回滚） |

**其余能力（下载、加载器、整合包、账户、诊断）追平第一梯队即可，不追求超越。**

**这条如何指导资源分配**：

| 该多花时间 | 追平即可，不多花 |
|---|---|
| 材质层次、灵动岛、动效、主题四态 | 下载进度条的动画细节 |
| 基岩版与 Java 版的**心智模型一致性**（含 §6.2 的共享世界告知） | 加载器支持的**数量**（对齐 PCL 即可，不追新） |
| 声明式实例、快照、diff、用户数据安全 | 整合包格式的**数量**（对齐主流即可） |

### 1.3 产品能力面

| 域 | 内容 |
|---|---|
| **产品** | Java 版（含全部加载器）、基岩版（GDK / UWP 双形态）、未来其它游戏 |
| **实例** | 创建 / 复制 / 删除 / 迁移 / 隔离；实例级参数（内存、Java、窗口、强调色、身份偏好） |
| **内容** | 模组 / 资源包 / 光影 / 行为包 / 皮肤包 / 存档：列表、启停、拖入安装、冲突提示、信息读取 |
| **整合包** | Modrinth、CurseForge、通用压缩包 |
| **账户** | 离线（含强制告知）、微软正版（Java 与基岩共用同一微软身份，但**授权与启动路径不同**） |
| **下载** | 全量 / 按需 / 续传 / 校验 / 自愈 / 缓存 / 多源与测速 |
| **运行时** | Java 探测与选择（自动下载默认关闭）；基岩版依赖组件检测（Gaming Services / GameInput） |
| **调优与诊断** | 内存推荐（可解释）、JVM 预设、崩溃归因、日志关键词、脱敏导出 |
| **后续扩展位** | 与 MC 无关的功能模块（工具类、内容管理类、平台服务类）——**走插件位，不进内核** |

### 1.4 不做（红线与边界） `[REDLINES]`

**"红线"不是"建议"**——所以每条都写明**违反会怎样**。这不只是给读者看，也是为了将来有人提"就做一点点"时能立刻终止讨论。

| 不做 | 理由 | **违反的后果（为什么它是红线）** |
|---|---|---|
| 任何"不登录也能进正版服"的路径 | 永不实现 | 法律风险（绕过技术措施）+ 用户账号封禁 + 项目被下架 |
| 内建任何游戏内容（jar / 资源 / 整合包 / 世界） | 只做编排与下载 | 侵犯版权方分发权 → 收到下架通知、仓库被封 |
| 伪造官方会话、劫持官方验证接口、逆向混淆代码 | 红线 | 同上，且触及《数字千年版权法》类反规避条款 |
| 自行运营中继联机服务 | 与本地工具定位冲突 | 长期后端成本拖垮单人项目（已有三家联合停用的前车之鉴） |
| 修改游戏二进制 / 自研模组加载器 | 不做游戏逻辑 | 破坏游戏完整性；更新即失效；用户环境不可复现 |
| **为与 MC 无关的游戏新增 Provider** | 只服务 MC 两个版本（§12.4） | 范围失控 → "tries too many things" → 每个方向都做不深 |
| **任何影响游戏内胜负判定的功能**（准星 / 瞄准 / 自动点击 / 宏） | 整体否决（§12.7） | **用户被封号**——这是唯一会直接伤害用户的类别，比法律风险更不能碰 |
| **读写其它进程内存、干预反作弊组件** | 侵入性行为（§12.7） | 被反作弊判定为绕过 → 用户封号 + 法律风险 |
| 冒用 Mojang / Microsoft / Minecraft 品牌 | 红线 | 商标侵权 → 下架 + 法律函 |

**这张表的用法**：任何新需求**先过这张表**，命中即拒绝，不需要讨论收益或实现成本。

## 3. 架构：窄 trait + 两层能力描述符（本篇核心）

### 3.1 三层抽象

```
┌── 产品层 Product ────────────────────────────────────────────┐
│  Minecraft Java 版  |  Minecraft 基岩版  |  未来其它产品        │
│  每个产品 = 一个 GameProvider 实现                            │
└──────────────────────────────────────────────────────────────┘
┌── 实例层 Instance ───────────────────────────────────────────┐
│  平台的通用概念：一个可启动的、有独立数据的游戏安装单元         │
│  Instance { id, product, name, dataDir, params, isolation }   │
└──────────────────────────────────────────────────────────────┘
┌── 内核层 Core（完全与游戏无关）──────────────────────────────┐
│  下载引擎 | 校验与解压 | 任务队列与进度 | 凭据存储 | 日志脱敏    │
│  配置层级合并 | 错误码体系 | 诊断导出 | 更新 | 材质 | 界面外壳   │
└──────────────────────────────────────────────────────────────┘
```

**关键约束**：内核层**不得出现任何 Minecraft 词汇**（没有 `Version`、`Loader`、`Asset`、`Mod`）。
这些概念只允许出现在 MC 的两个 Provider 内部。**这条由架构测试强制**（对内核 crate 做关键词扫描 + 依赖方向断言）。

### 3.2 Provider 抽象：**拆成小 trait**，不做一个大接口

> **修订（v3.6）**：早先设计成单个 `GameProvider` 承载九个成员，**接口定得太大**——
> 后果是每加一个能力，所有 Provider 都要实现一遍占位空方法，且测试要构造全量假对象。
> 改为**按能力拆分的窄 trait**，Provider 只实现自己真正具备的那些。

| 窄 trait | 职责 | 谁实现 |
|---|---|---|
| `ProductIdentity` | 产品标识与展示信息（名称、图标、版本形态） | 全部（唯一必需） |
| `Discoverable` | 发现本机已有安装 | Java / 基岩 / 将来其它 |
| `Installable` | 可安装的版本来源 | Java（官方清单 + 加载器元数据）/ 基岩（GDK 分发通道 + 商店已装版本） |
| `Launchable` | 产出可复现启动计划 + 执行启动并回收进程 | 全部 |
| `ContentManageable` | 内容仓库集合（扫描/启停/导入/移除） | Java（mod/资源包/光影/存档）/ 基岩（行为包/资源包/皮肤包/世界，**仅 GDK**） |
| `Importable` | 可导入的包格式 | Java（Modrinth/CurseForge/zip）/ 基岩（`.mcpack`/`.mcaddon`/`.mctemplate`） |
| `Diagnosable` | 崩溃与日志归因规则 | 全部（规则集不同） |

**内核对形状的依赖**：`ProductRegistry` 按 trait 能力**查询**，而不是要求每个 Provider 都实现全部。
界面同理（见 §3.3）。

#### 拆分时机（评审修正：**不要一次抽全 7 个**）

> 评审指出：**M1–M8 只有 Java 一个实现**，基岩要到 M9。一个实现的时候拆 7 个 trait，
> 收益是 0，成本是"M1 就要定下全部形状，把错误抽象固化"。
> **这个判断成立，我采纳推迟策略**——但保留按能力拆分的设计意图，不回到一个大接口。

| 里程碑 | 实现哪些 trait | 理由 |
|---|---|---|
| **M1** | `ProductIdentity` + `Launchable` | 真正必需的两个；也是最小可验证的 CLI 调用链（M1 出口条件） |
| **M2** | 加 `Discoverable` + `Installable` | 元数据与 Java 运行时到位时，**它们各自出现第二个使用场景**（多版本发现、多来源安装） |
| **M3** | 加 `Diagnosable` | 启动链路的失败面出现，日志归因成为真实需求 |
| **M6 / M8** | 加 `ContentManageable` + `Importable` | 实例与内容管理落地时才需要 |
| **M9** | 用基岩版**验证前六个 trait 的形状**；此时才判定是否需要再拆或合并 | **第二实现是抽象的第一个真实检验者**——在此之前任何调整都不算数 |

**纪律**：**每个 trait 在"出现第二个使用场景"时引入**，不在纸面上预抽。
**但 §3.3 的能力描述符与 `reason` 机制从 M1 就要有**——它的形状不依赖第二个 Provider（它只是键值对）。

**收益**：新增一个产品 = 新增一个 Provider crate，**只实现它真有的能力**；内核与界面代码零改动。

### 3.3 能力描述符：**产品级 + 实例级**，且必须带原因 `[CAPABILITIES]`

> **修订（v3.6）**：早先只有产品级能力表，**无法表达"同一产品的不同形态能力不同"**。
> 最典型的反例就在我们自己的 §6.2：**基岩版 GDK 支持内容管理，UWP 不支持**。
> 旧设计会逼出 `if (buildType == UWP)` 这种分支——正是我们想消灭的东西。

**两层能力，缺一不可：**

```
ProductCapabilities     产品级：这个产品整体上能做什么（静态、随 Provider 编译期确定）
InstanceCapabilities    实例级：这个具体实例此刻能做什么（动态、带原因）

Capability = { key, enabled: bool, reason: Option<String> }
```

**实例级能力的判定依据是实例自身属性**（形态、版本、加载器、账号类型、系统环境），例如：

| 能力键 | Java 版实例 | 基岩版 GDK 实例 | 基岩版 UWP 实例 |
|---|---|---|---|
| `content.behavior_packs` | ✗（不适用） | ✅ | **✗ `reason: "UWP 形态位于系统沙箱内，无法管理内容包"`** |
| `content.shader_packs` | ✅ | **✗ `reason: "基岩版不支持光影"`** | ✗（同上） |
| `instance.isolation` | ✅ | ✗ `reason:"需要改写游戏二进制，本项目不做"` | ✗（同上） |
| `params.memory` | ✅ | ✗ `reason:"基岩版无 JVM 内存参数"` | ✗（同上） |
| `identity.offline` | ✅ | ✗ `reason:"基岩版仅支持微软账户"` | ✗（同上） |

**界面规则（三条，都要遵守）**：

1. **产品相关区**只渲染 `enabled == true` 的项 → Java 有"光影"，基岩没有，天然不出现。
2. **百宝箱工具区**入口固定、全部可见（§4.3），但**不适用的工具以禁用态 + `reason` 呈现，不隐藏**。
   → 用户看到的是"光影管理（基岩版不支持光影）"，而不是"找不到光影管理"。
3. **`reason` 是必填项**：任何 `enabled == false` 都必须给出人话原因。
   **没有原因的禁用态一律视为缺陷**——这比"渲染一个灰按钮"要求更高，但它把"为什么不能用"变成了产品信息。

这条规则彻底消灭了"界面里到处是 `if (product == "java")` / `if (buildType == UWP)`"这类必然腐化的写法。

#### 新增能力的变更流程（**防止能力注册混乱**）

能力描述符是**跨内核、Provider、界面三层的契约**，所以"加一个新能力"必须有固定流程，不能随手加：

| 步 | 动作 | 谁做 |
|---|---|---|
| 1 | 在 `qul-core` 注册新的 `CapabilityKey`（**枚举/常量集中在一处，不许散落字符串**） | 内核 |
| 2 | 声明它是**产品级**还是**实例级**；实例级必须定义判定依据（形态/版本/加载器/账号类型/系统环境） | 内核 |
| 3 | 相关 Provider 在 `InstanceCapabilities` 中返回 `{ enabled, reason }`；**`reason` 在 `enabled == false` 时必填** | Provider |
| 4 | 界面按 §3.3 三条规则渲染（产品区只渲染 enabled；百宝箱渲染禁用态 + reason） | 界面 |
| 5 | **加架构测试**：① 未注册的 key 不允许出现在界面渲染路径；② 任何 `enabled == false` 必须带非空 `reason` | 内核 |

**纪律**：**能力是"声明"，不是"判断"**。Provider 不许在界面里做运行时判断来决定显示什么——
判断属于 Provider，显示属于界面，中间只隔一层描述符。这条由第 5 步的测试强制。

### 3.4 基岩版与 Java 版的差异如何被吸收

| 差异点 | 吸收方式 |
|---|---|
| 版本来源不同（元数据 vs GDK 分发通道） | `Installable` 各自实现 |
| 启动方式不同（子进程 + 参数 vs URI/包激活） | `Launchable` 各自实现 |
| 数据目录不同（`gameDir` 参数 vs 固定路径 + 目录重定向） | `Discoverable` 与实例数据目录策略各自实现 |
| **形态不同（GDK vs UWP）导致能力不同** | **靠实例级能力描述符 + `reason` 表达**（§3.3），不在界面里写分支 |
| 隔离能力不同（Java 原生支持 vs 基岩需改二进制） | 能力描述符里如实声明 `isolation:false` 并给原因 |
| 身份相同但授权完全不同 | 共用**微软账户层**；**授权层各自独立**（Java 走 XBL→XSTS→MC 令牌，基岩走 Xbox/商店授权）——详见 §11.4 |

**结论：差异全部关在 Provider 内部，内核与界面完全无感。** 这正是"可扩展平台"定位能落地的唯一方式。

### 3.5 模块化目录结构

```
qul/
  crates/
    qul-core/            内核：通用模型 + 规则（零 IO、零 Tauri、零 MC 词汇）
    qul-infra/           网络 / 文件 / 解压 / 哈希 / 进程 / 凭据 / 更新
    qul-app/             用例编排 + 注册表（Provider 与模块在此注册）
    qul-provider-java/   MC Java 版 Provider
    qul-provider-bedrock/MC 基岩版 Provider
    qul-mod-<name>/      与 MC 无关的扩展模块（百宝箱工具、后续功能）
  src-tauri/             Tauri 命令层（薄壳）+ 界面外壳
  src/                   前端（React + TS）
  tests/                 集成测试 + 架构约束测试（关键词扫描 + 依赖方向）
```

**纪律（比"独立接口 crate"更朴素、也更有用）**：功能代码只调用**内核公共模型与服务**，不 import 别的功能的内部实现。
这就是 §5 说的"分好格子"——**一期不需要一个稳定的插件接口 crate**，等真要开放第三方时再抽。

### 4.2 产品切换的两种交互

| 方式 | 场景 | 实现 |

### 4.3 导航结构：仿 PCL 的两段式（2026 修订）

PCL 的导航有两个特征值得直接照搬（实测 `repos/PCL-CE/Plain Craft Launcher 2/Pages/`）：

1. **一级导航是"启动 + 内容 + 工具"三段**：版本/实例、下载、**百宝箱**，加上主页与设置。
2. **百宝箱是一级入口，不是设置里的子页**（PCL 的设置里只有一个"百宝箱可见性"开关 `UiHiddenPageTools`）。

本方案的左导航据此定为：

```
主页 | 实例 | 内容 | 下载 | 存档 | 百宝箱 | 账户 | 设置
                              └── 工具集合：联机 / 测速 / 日志与诊断 / 皮肤 / 截图 /
                                  崩溃分析 / 依赖与组件检查 / 数据包 / 服务器 / 磁盘清理
```

**这里必须修正 v3 的一个判断。** v3 说"导航由能力描述符完全生成"。改成：

| 区域 | 生成方式 | 理由 |
|---|---|---|
| **产品相关区**（内容、存档、下载的类型列表） | **能力描述符生成** | Java 版有"光影"、基岩版有"行为包"，这个差异必须自动消化 |
| **工具区（百宝箱）** | **入口固定在导航里，全部可见** | 百宝箱的意义就是"我想找个工具，能看见它"。藏进二级甚至按能力过滤掉，就失去了百宝箱的作用 |

于是规则变成：**产品能力决定"渲染什么"，百宝箱决定"东西放哪儿"。**
不适用的工具以**禁用态 + 一句原因**呈现（例：基岩版实例上"光影管理"显示为不可用并注明"基岩版不支持光影"），
**而不是直接消失**——用户找不到东西的挫败感，比看到一个带解释的禁用按钮更糟。

#### 百宝箱的可用性上限（评审补：全可见会膨胀）

"全部可见"解决的是**可发现性**，但工具会越来越多（M4.5 六件 → M10 十几件 → 未来模块位更多）。
所以"可见"不等于"平铺一次列完"：

| 机制 | 要求 |
|---|---|
| **二级分组** | 按域分组：`诊断与日志` / `性能与测速` / `文件与清理` / `内容工具` / `联机` / `帮助` |
| **搜索** | 百宝箱内有搜索框，可按工具名与关键词过滤（**复用全局搜索的同一索引**） |
| **最近使用** | 顶置最近 3–5 个用过的工具；这是"新用户翻列表、老用户直接进"的分界 |
| **收藏** | 可固定常用工具到顶部（本地偏好，随配置备份迁移） |
| **默认展开策略** | 一级分组展开，组内**默认显示前 N 个 + "展开全部"**；避免单页几十项 |

**纪律**：**入口永远可见（不错过），列表永远可收缩（不淹没）。** 两者不是矛盾的，是同一件事的两面——
藏起来会让用户找不到，平铺会让用户找不到**别的**。

**空状态**（首次使用 / 尚未用任何工具）：**不显示空列表**，改为：
① 一张引导卡（"百宝箱里放的是启动之外的工具：日志诊断、测速、依赖检查、磁盘清理……"）；
② 推荐 3 个最常用工具（**内建帮助 / 日志与诊断 / 依赖与组件检查**）；
③ 一行"全部工具"入口。
**理由**：百宝箱的价值靠"被发现"实现，冷启动时的空列表等于把这个价值藏起来。

### 4.4 灵动岛的产品无关性

岛的状态机（`Idle / Probe / Download / Install / Launch / Running / Error / Update`）**全部是产品无关的**——"下载中""安装中""运行中"对任何游戏都成立。
产品差异只在**展开面板的细节**：

- Java 版 `Running` → 显示 JVM 内存、局域网状态。
- 基岩版 `Running` → 显示进程存活探测、依赖组件状态（无 JVM 概念）。

实现方式：岛内内容由 `Provider.ui_hints(instance)` 返回的字段清单驱动，**不写分支**。

> **前置依赖 + 实测结构修正（v3.9）**：Java 版 `Running` 态需要"已启动 / 已进入世界 / 已退出"的信号源。
> **我此前写"进程探测 / 窗口探测 / 日志观测三法比选"，这是错的——它们不是竞品，是分工。**
> PCL 的真实实现（`PCL-CE Modules/Minecraft/ModWatcher.cs`）是三机制**分工并用**：
>
> | 机制 | 负责 | 证据 |
> |---|---|---|
> | **日志子串匹配** | **五步启动进度**：已出现日志输出 / 游戏用户已设置 / LWJGL 版本确认 / OpenAL 已加载 / 材质已加载 | `:476, 482, 487, 493, 500` |
> | **窗口探测（拿 HWND）** | **窗口就绪**：`WindowLoaded` / `FmlWindowLoaded` / `LoadComplete` | `:593, 616, 548` |
> | **独立一档** | `SecurityBlocked`（安全拦截） | `:578` |
>
> **崩溃识别还要分三档语气**（不是"崩了/没崩"二元）：
> `Crash.Detected`（已崩溃，2 秒后分析）/ `Crash.Suspected`（尚未加载完成，**可能**已崩溃）/ `Crash.AbnormalExit`（返回值异常）；
> 且**日志先被分类为"崩溃的"或"关闭的"**（`Log.CrashDetected` / `Log.CloseDetected`）——避免把用户正常退出报成崩溃。
> **强杀两级**：`TerminateProcess` → 超时后 `taskkill.exe`。
>
> → **实现按这个结构做**：**日志匹配做进度 + 窗口 HWND 做就绪 + 独立一档做安全拦截**。
> 基岩版对应的信号源由 M0 的 **S8.2** 实测决定。

### 4.5 前端技术栈（**评审指出的最大缺口，本节补齐**）

> **问题**：方案把 Rust 侧定得很细（7 个窄 trait、三层目录、能力描述符），前端却只有"React + TS"五个字。
> 到了 M4 会发现**状态管理、路由、CSS 方案、无头组件、数据缓存**这五件必须当场定，否则 M4 前两天全在选型。
> **落点**：作为 **M4 的前置门禁**——比 M4 开工早一周定下。

| 项 | 选择 | 为什么是它（针对我们的具体约束） |
|---|---|---|
| **语言 / 构建** | TypeScript 严格模式 + Vite | Vite 是 Tauri 官方模板默认，冷启动与 HMR 都最快 |
| **UI 框架** | React 19 | 生态最厚；Framer Motion 的弹簧动画是灵动岛的关键依赖 |
| **状态管理** | **Zustand** | 灵动岛状态机、实例切换、下载进度都是**长生命周期跨组件状态**；Zustand 无 Provider 地狱、无样板，**与"前端零逻辑、数据单向从 Rust 流入"的架构天然契合**。不选 Redux（样板过重）与 Context（跨组件性能差） |
| **路由** | **TanStack Router** | 两段式导航 + 百宝箱二级分组 + 实例详情，路由是"能力描述符如何被消费"的落点；类型安全路由与 TS 严格模式搭配能**在编译期挡住"跳转到未注册的能力页"** |
| **CSS 方案** | **纯 CSS Modules + 令牌文件（CSS 自定义属性）** | 见下方专门说明——**这是本节最需要解释的一条** |
| **无头组件库** | **Radix Primitives** | 按钮/开关/弹窗/滚动容器约 20 个基础组件；Radix **无样式、可访问性已做好、与设计系统完全解耦**——我们只取行为与 a11y，样式全部自己写（我们的设计语言不允许现成皮肤） |
| **数据获取与缓存** | **TanStack Query** | 版本清单、模组列表、下载进度都需要缓存与失效策略；**缓存 key 直接用实例 id / 版本 id**，与内核的实例模型一一对应 |
| **动画** | Framer Motion | 灵动岛两态切换用弹簧；**只用 `transform` / `opacity`**（§4.4 纪律） |
| **图标** | 自绘 SVG 集合（`lucide` 风格线稿） | 沿用"素材自制、来源可追溯"的既有纪律 |

#### 为什么 CSS 用纯 CSS Modules + 令牌，而不用 Tailwind / CSS-in-JS

**这一条值得单独说明，因为它直接关系到"三层材质"能否被严格执行。**

| 方案 | 判断 | 理由 |
|---|---|---|
| **纯 CSS Modules + CSS 自定义属性令牌** | ✅ **选它** | 我们的设计语言是"**语义化的层次**"：`surface.panel` / `stroke.subtle` / `elev.2`。CSS 变量让"改一处、全站生效"成为物理事实；**主题四态（Full/Reduced/None 材质 × 深/浅）只需切换一组变量**。组件样式是**手写的、有名字的**，层次能被审阅 |
| Tailwind | ❌ 不选 | **大量 utility 类会掩盖"材质层次"这个核心语义**——当样式写成 `bg-white/10 border border-white/15` 时，"这是第几层"就查不出来了；且从类名无法回答"这个组件用了哪一档 elevation"。**它不是不能用，而是会主动对抗我们的设计纪律** |
| CSS-in-JS | ❌ 不选 | 运行时开销与 WebView2 冷启动预算冲突（§7），且我们不需要动态主题计算——CSS 变量已经解决了 |

**配套纪律（由测试/lint 强制）**：

1. **组件样式不得出现字面颜色值** —— 只能引用语义令牌（沿用"界面代码永不写十六进制"的既有纪律）。
2. **每个组件必须声明它在哪一层**（`panel` / `card` / `raised`），不允许"随便调透明度"。
3. 令牌文件是**唯一真源**；组件目录里不允许出现第二处定义颜色/圆角/间距的地方。

#### M4 前置门禁（开工前必须齐备）

| # | 交付 | 内容 |
|---|---|---|
| 1 | 令牌文件 | 完整的语义令牌（颜色/圆角/间距/时长/elevation）+ 四态主题变量 |
| 2 | 约 20 个基础组件的骨架 | 只做样式与 a11y，不做业务；含 6 个必要状态（默认/悬停/按下/聚焦/禁用/加载） |
| 3 | 路由骨架 | 两段式导航 + 百宝箱二级分组的可跑通空壳 |
| 4 | 数据层骨架 | 一个完整的 Tauri 命令 → TanStack Query → 组件渲染的贯通示例 |
| 5 | 三条 lint 规则 | 无字面颜色值 / 组件声明层级 / 令牌唯一真源 |

**这五项不齐，M4 不开工**——否则会在做界面时反复回头改基础设施。

### 4.6 设计令牌：**两层结构 + 成阶中间色**（v3.9 补，来自 ATLauncher 源码实证） `[TOKENS]`

> **§4.5 定的令牌系统只有"语义层"，缺"成阶中间色"**——这一节补齐，且已有可直接映射的现成表。

**两层结构**（ATLauncher `themes/ATLauncherLaf.properties:26-91`，已对着源码核实）：

```
第一层 · 调色板（成阶）
  primary.100 … primary.900      ← 9 阶，从最浅到最深
  secondary.100 … secondary.900
  gray.100 … gray.900
  red / yellow / black / white / transparent

第二层 · 语义令牌（引用调色板，不写死色值）
  Button.background = $buttonBackground
  BottomBar.dividerColor = $Separator.foreground
  @selectionBackground = $primary.200
```

**为什么必须有成阶层**：语义令牌解决"改一处全站生效"，但**解决不了"我需要一个比 panel 亮一点点、又比 hover 暗一点点的色"**。
没有成阶层时，这种需求会退化成"随手调一个透明度"——**而那正是我们要禁止的写法**。

**17 套主题复用同一套令牌**（`CatppuccinLatte.properties:92-96`、`OneDark.properties:50-54` 等）
→ **主题只提供调色板，语义层不动**。这正是"主题四态（深/浅/跟随系统/跟随实例）"该有的组织方式。

#### 日志分级色的令牌化（**直接可搬**）

ATLauncher `:112-117` 的写法，五档语义名 + 主题无关：

```
Console.fontSize = {float}12
Console.LogType.debug   = #9f7aea
Console.LogType.error   = $red
Console.LogType.info    = $primary.500
Console.LogType.warn    = $yellow
Console.LogType.default = @foreground
```

**配套一个值得抄的设计**（`evnt/LogEvent.java:33-37`）：
用 `meta` 区分日志来源 **`CONSOLE=0xA` / `LOG4J=0xB`** —— **能分清"启动器自己的输出"与"游戏进程的输出"**。
→ 日志抽屉必须支持**按来源过滤**，否则诊断时两种日志混在一起无法阅读。

**Console 页的四个操作**（`ConsoleBottomBar.java:48-51`）：`Clear` / `Copy Log` / `Upload Log` / **`Kill Minecraft`（`:134` 带二次确认）**。
→ 直接采纳；注意 `Kill` **必须二次确认**。

### 4.7 实例数据格式的版本化与迁移（**评审补：数据安全义务**） `[MIGRATION]`

§5.5 采纳了声明式 `profile.json` + 锁定态，但**必须回答"格式变了怎么办"**——
否则用户从 v1.2 升到 v1.3 时，老实例会直接崩。**这是用户数据安全的一部分，不是可选项。**

| 条款 | 要求 |
|---|---|
| **版本字段** | `profile.json` 与锁定态**顶部强制 `version` 字段**；缺失视为 v1 |
| **迁移链** | 内核启动时扫描全部实例，遇旧版本走**迁移链**（v1→v2→v3 逐步升级，**不允许跳版本**） |
| **迁移前备份** | **强制备份整个实例元数据层**（`profile.json` + 锁定态 + `patches/`，**不含 `build/`**）到实例的备份区 |
| **失败不阻断** | 迁移失败**不阻断启动器启动**：把该实例标为「需手动处理」，界面给出**可执行说明**（含备份位置与回滚方式） |
| **不可逆操作** | 任何会自动改写用户文件的迁移，**必须可回滚**；不可回滚的迁移需要用户显式同意 |
| **测试** | 每个历史版本各留一个样本实例作为回归 fixture，**新版本必须能迁移全部样本** |

**这条的验收方式**：造 3 个不同历史版本的样本实例，跑一次新版启动器，验证全部迁移成功且备份存在。
**M1 出口条件包含此三项**（迁移链 + 迁移前备份 + 失败不阻断）。

#### M1 阶段的 fixture 怎么来（操作定义）

项目此时**还没有历史版本**，所以"三个历史版本样本"必须**人为构造**：

1. 定稿 v1 格式后，**立刻把一份完整实例目录冻结进 `tests/fixtures/instances/v1/`**（提交进仓库，只读）。
2. 每次改格式（v1→v2→v3），**冻结一份新的**，且**同时保留旧的**。
3. M1 的验收只针对**当时已有的** fixture：实现 v1→v2 时，验收是"v1 fixture 能升级到 v2"。

**纪律**：fixture 一旦提交**永不修改**——它就是"用户的老数据"的替身。

### 4.8 启动器自身的更新与回滚（**评审补**）

方案原来只写了"更新"，没有设计**更新形态、失败回滚、与运行中游戏的关系、与用户数据的边界**。

| 项 | 条款 |
|---|---|
| **更新形态** | **Tauri 应用内自动更新**（差量优先）。理由：§7.1 实测带宽仅 ~0.28 MB/s，**差量下载不是优化而是必需** |
| **检查时机** | 启动后台检查，**不阻塞首帧**（见 §7 的冷启动口径） |
| **不强制** | 发现新版本**只提示，不自动装**；用户可推迟 |
| **与游戏互斥** | **用户正在游戏中或正在下载/安装时，更新推迟到任务结束**，并说明原因（Minecraft 不能被打断） |
| **失败回滚** | **保留上一版本可执行文件**；更新失败自动回滚，界面明示"已回滚到 vX.Y"（含失败原因） |
| **数据契约** | **更新绝不修改用户数据**；数据格式演进一律由 §4.7 的迁移链承担。**这两件事必须物理分离**：更新只动程序文件，迁移只动元数据且先备份 |
| **签名** | **个人自用：不需要任何代码签名证书**（自编译自运行，SmartScreen 不会拦本地构建）。**仅当决定对外分发时才需要**——那时才回到本节：更新包必须验签，且需要 OV/EV 证书（见 §9.1 成本表） |

**M11 出口条件包含**：更新失败能自动回滚 + 游戏运行中不打断 + 更新不动用户数据。

#### 4.8.1 版本与通道策略（个人自用场景，刻意从简）

| 项 | 决定 |
|---|---|
| 版本号 | **SemVer**（`0.x.y`）；**0.x 期间不承诺兼容**，破坏性变更进 minor |
| 发布通道 | **不设 nightly/beta/stable 三通道**——个人自用，只有"最新 tag"一条线 |
| 更新检查 | 只检查最新 tag；不做灰度、不做分批 |
| 回滚 | 本节已定：保留上一个版本可执行文件，失败自动回滚 |
| **何时才需要引入通道** | 若将来决定分发（见 §1.4 与 ADR），**那时再引入**，现在不做 |

**理由**：多通道是为"大量用户灰度"设计的；一个人的项目引入它只会增加发布负担。

## 5. 扩展方式：先"分好文件夹"，别急着做插件

> **修订说明（v3.2）**：v3 的 §5 用了"插件 / 编译期注册 / 运行时动态加载"这套词，属于把简单问题说复杂了。
> 本节重写为可执行的结论：**一期不做插件系统，只做代码分区。**

### 5.1 我们要的能力，其实就是"分好格子"

把新增功能想成往柜子里放东西。要解决的是三件事：

| 想要的效果 | 具体做法 |
|---|---|
| 加一个新功能（比如"联机"）**不用动主程序别的地方** | 代码放在自己的文件夹里，主程序只在一处登记它 |
| 这个功能**能整个删掉**，删了别的地方不报错 | 它只调用公共接口，不直接碰别人的内部代码 |
| 每个功能**自己管自己的界面和后台任务** | 界面和后台服务都由这个格子自己带进来 |

**这就是"模块化"，不需要"插件系统"。** PCL 就是这么做的：`Modules/` 下按 `Base / Event / Minecraft / UI / Network / Updates` 分目录，`Pages/` 按 `PageHomepage / PageInstance / PageDownload / PageTools / PageSetup` 分目录。没有插件 API，也没有第三方插件——但它照样长出了百宝箱、联机、测速、崩溃分析这么多功能。

### 5.2 一期（M0–M11）怎么做：平铺写，不搞抽象

| 项 | 一期结论 |
|---|---|
| 第三方插件 | **不做** |
| 稳定 API / ABI | **不定**（不定就不会错；定早了将来每次改动都要兼容包袱） |
| 动态加载 `.dll` | **不做** |
| 界面主题 / 图标包 / 语言包 | **做成数据**（JSON + 资源目录），这是唯一值得运行时加载的东西——因为它零代码风险 |
| 代码组织 | 每个功能一个独立目录（Rust 侧一个模块、前端侧一个页面目录），主程序只有一张**登记表** |

**"登记表"长什么样**（这是唯一需要提前约定的事，且它只是内部约定，不是对外 API）：

```
模块登记项 = { 标识, 显示名, 图标, 导航条目, 后台服务, 依赖的公共能力 }
```

主程序启动时读这张表生成导航；新增功能 = 加一行 + 加一个文件夹。

**代价**：一期加功能要重新编译主程序（这对单人项目完全无所谓——你本来就要自己编译）。
**收益**：没有 ABI 兼容包袱、没有沙箱逃逸风险、没有信任链问题，开发速度快一大截。

### 5.3 什么时候才真的需要插件系统

只在一个条件下需要：**让别人（第三方开发者）在不改我们代码的前提下加功能。**

到那天再决定的，是"用什么技术把外部代码装进来"，候选三条：

| 方案 | 优点 | 代价 |
|---|---|---|
| C ABI 动态库 | 性能好、能力最强 | ABI 脆弱、崩溃能带走主进程、要签名与信任链 |
| WASM 沙箱 | 安全、跨平台 | 能力受限、要写宿主函数桥接 |
| 独立子进程 + JSON-RPC | 崩溃隔离、语言无关 | 通信开销、要定协议与生命周期 |

**现在不选，也不为它做设计。** 唯一现在要留的位是：**功能代码必须放在自己的目录里、只调用公共接口**——这条不管将来走哪条路都用得上，而且它本身就是好习惯。

### 5.4 三条纪律（替代原来的"插件三条纪律"）

1. **功能不与功能直接耦合**：A 功能要 B 功能的数据，走公共模型，不 import B 的内部实现。
2. **功能不绕过内核服务**：下载必须走内核下载引擎（否则没有校验、没有脱敏、没有统一进度）。
3. **功能可整体移除**：删掉它的目录与登记项那一行，主程序照常编译与运行（由集成测试强制）。

### 5.5 实例数据模型：声明式 profile + 三层目录（源码实证） `[INSTANCE-DATA]`

> 来源：Trident.Net（Polymerium 的核心引擎，已克隆到 `repos/Polymerium/submodules/Trident.Net`）。
> 它的 `profile.json` 是**声明式单一数据源**，部署时由引擎把它"解析"成一个可启动的 `.minecraft`。

**它的目录布局（原文）**：

```text
.trident/
├── cache/          assets / libraries / packages / runtimes   ← 共享，不属于任何实例
├── instances/{key}/
│   ├── profile.json      声明式实例元数据（版本/加载器/包/规则/运行时覆盖）
│   ├── data.lock.json    部署锁定态 —— 用于重建与 diff
│   ├── data.pack.json    整合包层数据
│   ├── patches/          外部部署声明（import/ 与 users/ 两层）
│   ├── build/            投影出的 .minecraft 运行目录
│   ├── import/           整合包源（整合包带来的权威文件）
│   └── persist/          用户保留数据（存档/截图/options.txt）
```

**我们直接采纳这个三层模型**，因为它解决了我们原方案最大的一个漏洞——我原来把"版本 + 存档 + 配置"混在一层里，
于是**"更新整合包"必然要碰用户数据**（这正是 Polymerium README 里承诺"升级整包，存档设置自动带过去"的原因）：

| 层（我们的目录名） | 语义 | 整包更新时 | 重置时 | 删除实例时 |
|---|---|---|---|---|
| `import/` | **整合包源**：分发内容、权威版本 | **可被替换** | 保留 | 删 |
| `persist/` | **用户保留**：存档、截图、`options.txt`、mod 配置 | **永不触碰** | **保留** | 删（但删前强制确认 + 可导出） |
| `build/` | **运行目录**：游戏实际读写的 gameDir | 由前两层重建 | **清空并重建** | 删 |

四条随之而来的纪律：

1. **共享缓存与实例目录严格分离**（沿用原设计）：`cache/` 里的任何东西都不是用户数据。
2. **`build/` 里同时存在"可复现文件"和"不可替代的用户数据"** —— 这是它最危险的地方。
   **只有用户显式"提升"（promote）到 `persist/` 的文件才受保护。**
   **但用户根本不知道 `build/` 里哪些文件是存档** —— 所以不能靠自觉（修订 v3.6）：

   | 时机 | 强制动作 |
   |---|---|
   | 部署 / 重置 / 整包更新 **之前** | **扫描 `build/` 中未被 `data.lock.json` 管理的文件**（= 游戏运行时新产生的、非部署产物），列出为「待提升」清单 |
   | 清单呈现 | 按类型分组（存档 / 截图 / 配置 / 日志 / 未知），标明大小与修改时间 |
   | 用户选择 | **默认勾选"备份到 `persist/` 的临时区"**；可逐项确认；**不勾选的项在重置时需要二次确认** |
   | 安全阀 | 即使用户全部跳过，**重置仍自动把整个 `build/` 快照到临时区**（默认上限 10 GB / 保留 7 天，见下方容量表），给一次后悔的机会 |

   **一句话**：**"用户数据可能丢失"这件事不能靠用户的知识来防，只能靠工具主动发现。**

   > **为什么不做"一期简化版"（评审建议，我不采纳）**：评审建议一期只硬编码 `worlds/` 与 `screenshots/` 两个已知路径，
   > 其余在日志里 warn，把"通用扫描 + 用户确认"推到二期。**我明确拒绝，理由三条**：
   > ① **硬编码路径覆盖不全**——整合包常有自定义目录、mod 自己写的数据目录、`config/` 与 `options.txt` 之外的游戏文件，
   > "已知路径"这个前提本身就是错的；
   > ② **这正是数据丢失最容易发生的地方**，而我们刚在 §6.2 为基岩版加了"共享目录上必须默认假设用户在别处也在用这份数据"的纪律——
   > Java 版的 `build/` 有同样性质，**同一份纪律不能在两个地方给两种强度**；
   > ③ "扫描未被 `data.lock.json` 管理的文件"**并不复杂**——锁定态本来就记录了部署产物清单，做一次集合差即可，
   > 成本远低于评审估计的"5 个 UI 状态"；UI 上只需要一张清单 + 默认全选。
   >
   > **可以简化的部分我接受**：**"按类型分组"与"逐项确认"可以降级**——一期只做
   > **"清单 + 默认全选 + 一键备份"，不要求用户逐项决策**。这样既保住安全阀，又不引入五个 UI 状态。
3. **部署 ≠ 启动**。部署是"把描述变成可运行的游戏目录"，启动是"运行游戏"；启动可以触发部署，但两者是**两个操作、两个状态、两个进度**。这直接决定灵动岛的 `Install` 与 `Launch` 两个状态不能合并。
4. **"重置实例"必须如实描述后果**：它会清空运行目录，可能删掉存档——**不许包装成"清理一下"**。

**共享 mod 的实现要降级链，不能只有符号链接**（**v3.9 按源码实证修正顺序**）：

Windows 上**符号链接需要开发者模式**（否则要管理员权限），而 **junction（目录联接）不需要**。
因此**正确顺序是把 junction 放在 symlink 之前**——这正是 Axolotl 的实现顺序：

```
junction（目录级，免开发者模式）  >  symlink（保底，需开发者模式）
      >  hardlink（文件级）        >  copy（兜底，占磁盘）
```

> **修正依据**（此前本方案把顺序写反了）：
> Axolotl `packages/app-lib/src/util/symlink.rs:136 create_link_blocking` ——
> **Windows 目录优先 `junction::create`（`:154`）→ 退 `symlink_rs::symlink_dir`（`:160`）→ 文件 `symlink_file`（`:164`）**。
> 另有提权路径 `:177 create_link_elevated`。
>
> 另两处独立实证：
> - **Trident（MIT）没有降级链**——全项目只有 `Directory/File.CreateSymbolicLink` 两处，靠 `allowed_symlinks.txt` 白名单解决链接安全
>   → **Windows 场景不能照它的方案**。
> - **XMCL 的"磁盘高效"根本不靠链接**——全包检索 `hardlink|symlink|junction` **零命中创建链接的代码**，
>   真实机制是 **SHA-1 内容哈希 + SQLite 元数据引用**（`resource/core/ResourceManager.ts`）→ **见下方"主路径"修正**。

#### ⭐ 主路径修正：**"哈希 + 引用"优先于"建链接"**

XMCL 的实证改变了优先级：**内容寻址（哈希 + 引用）不依赖开发者模式、不受跨卷限制、无权限门槛**，
而链接方案全都受这些约束。因此：

| 位置 | 方案 |
|---|---|
| **主路径** | **共享缓存按内容哈希寻址**（`objects/<hash[:2]>/<hash>`，与 git 同构），实例侧只存**引用** |
| **可选加速** | 需要"文件必须真实出现在游戏目录里"的场景（如 mod 目录），才用上面的降级链落地 |

> **Trident 的快照也是内容寻址**（`snapshots/objects/<hash[:2]>/<hash>`，见 `PathDef.cs`）——两个独立项目都收敛到同一形态。

| 要求 | 说明 |
|---|---|
| 自动探测 | 探测开发者模式、目标卷是否同卷、目标文件系统（NTFS/ReFS/FAT32） |
| 自动选择 | 按上表顺序选**可用的最强方案**，无需用户干预 |
| 可见性 | 实例存储页显示"本实例的共享方式：内容引用 / 目录联接 / 符号链接 / 硬链接 / 复制（占 X MB）" |
| 兼容性提示 | 检测常见杀软与备份软件是否可能干扰链接；**文件数异常增多时提示可能已降级为复制** |
| 移除 | 删实例时**只删链接本身，绝不跟随链接删除共享缓存里的真实文件**（必须由测试强制） |

**快照分三层，语义必须写清**（修订 v3.6）：

| 层 | 内容 | 用途 |
|---|---|---|
| **元数据快照** | `profile.json` + 锁定态 | 换加载器/改配置后后悔 |
| **部署快照** | `build/` 中由部署产生的那部分 | 装坏一个 mod 后还原 |
| **用户数据快照**（可选） | `persist/` | 存档级回滚；**体积大，默认不自动做，需显式选择** |

**回滚前三件事**：显示 diff（变了什么）→ 明确标注「`persist/` 不受本次回滚影响」→ 让用户确认。
**快照不等于运行目录的完整备份**——这句话必须出现在界面上。

**容量上限与保留期（v3.10 补具体默认值）**：

| 类型 | 上限 | 保留期 | 回收 |
|---|---|---|---|
| 元数据快照（`profile` + 锁定态） | 不限（体积极小） | 永久 | 不自动删 |
| 部署快照（`build/` 的部署产物） | **2 GB** | **7 天或最近 2 份**（取先到者） | LRU |
| 用户数据快照（`persist/`） | **5 GB** | **30 天或最近 3 份** | LRU |
| 重置安全阀（整份 `build/` 临时快照） | **10 GB** | **7 天** | 到期自动删 |

**以上为默认值，用户可在设置页调整**；**"磁盘与缓存"面板必须把四类占用分别可视化**
（因为用户一定会问），**提供一键清理与"清理前预览"**。

**另外三项顺手采纳**：

| 采纳项 | 内容 | 落点 |
|---|---|---|
| **包引用格式 `pref://`** | `pref://repository/projectId[@versionId]`，如 `pref://modrinth/aC3cM3Vq@9I21YYxf`。稳定、可分享、可写进配置。**完整语法**（Trident `Parser.cs:115`）：`pref://<repo>[/<ns>]/<identity>[@<version>][?k=v]`，**`@version` 取路径段里最后一个 `@`**（identity 自身可能含 `@`） | M8（我们设计自己的等价格式） |
| **部署规则**（selector + action） | Trident 的 **selector 7 维**（`And` / `Or` / `Not` / `Pref` / `Repository` / `Tag` / `Kind`）+ **动作仅 3 个**（`Destination` / `Skipping` / `Normalizing`）——把"这个包在某些实例里不部署"变成声明而不是代码 | M8 |
| **导入导出格式面** | 它支持 Trident / Modrinth / CurseForge / MultiMC / **Packwiz** 五种；迁移支持 MultiMC / Prism / CurseForge App / ATLauncher / Modrinth App | M8（我们的格式面从"三种"提到"对齐这些"） |

**v3.9 新增两项（源码实证）**：

| 采纳项 | 内容 | 依据 |
|---|---|---|
| **配置覆盖用 `Override*` 双层语义** | **"是否覆盖"与"覆盖成什么"是两件独立的事**：`OverrideMemory=false` + `MaxMemory=4096` 表示"本实例不改内存，用全局值"；重置只需关 `Override*`，**不必删值**。**比"有值就优先"清晰**——后者无法表达"我显式想用全局值" | MultiMC `MinecraftInstance.cpp:82-135` |
| **组件栈（Component Stack）作为版本合成模型** | 版本合成不该是"版本 + 加载器两层"，而是一个**有序组件列表**：加载器、jar mod、Java agent、自定义主 jar、资源覆盖**都是组件**，统一支持 `move / enable / disable / remove`，且每个组件**自带依赖、冲突与问题**（见 `docs/MultiMC-源码调研.md` 的依赖模型） | Prism `minecraft/PackProfile.h:59`、`Component.h:52-99` |

### 5.6 引擎与外壳分离（架构纪律）

Trident 的定位是"**内部核心 + CLI 产品 + MCP 工具入口**"，而 Polymerium 桌面端只是它的**同级外壳**，
两者**共用同一份 `profile.json` 与同一套 manager**——"一个实例被谁建的，另一个都能直接读写"。

我们采纳这条，并把 CLI 从"以后再说"提到**一期规划内**：

| 收益 | 说明 |
|---|---|
| 架构被强制干净 | 能跑 CLI 就证明业务逻辑确实不在界面里（我们的"前端零逻辑"护栏多了一道实证，而不只是靠测试） |
| 可自动化 | 脚本化安装/启动、CI 冒烟测试、批处理 |
| 成本低 | §3.5 的 Tauri 命令层本来就是薄壳，把它复用成 CLI 是最省力的做法 |
| 为 MCP 留位 | AI Agent 可通过 CLI/协议调用我们——**这是当代桌面工具的现实需求**，但属于后续模块位，不进内核 |

**新增工程纪律**：**内核逻辑不得依赖界面层与 Tauri**，且必须能被一个 CLI 入口完整调用。写不出 CLI 的功能，说明它与界面耦合了。

### 5.7 错误严重级别表（**评审补：M1 必须有，否则每模块自行造弹窗**）

M1 已定"错误码 + 原因 + 建议 + 可点击按钮"（对齐 PCL 两段式），但**没写什么时候用哪种呈现**。
不补这张表，每个模块会各造各的弹窗，最终界面风格不统一、用户也无法形成"一看就知道多严重"的肌肉记忆。

| 级别 | 触发条件 | 呈现 | 举例 |
|---|---|---|---|
| **静默** | 可自动恢复、用户无感 | **只写日志**，界面零提示 | 单文件重试成功、镜像自动切换成功、已存在文件跳过 |
| **微提示** | 用户可继续，但需知情 | **状态条一行，3 秒自动消失** | 已切换到镜像源、已跳过 N 个已存在文件、已自动修复 1 个坏文件 |
| **面板** | 用户**须处理才能继续** | **灵动岛展开 + 可点击操作按钮** | 校验失败需要重下、Java 缺失、某 mod 依赖缺失 |
| **阻断** | 无法继续 | **模态框：错误码 + 原因 + 建议 + 操作按钮** | 实例损坏、磁盘空间不足、实例数据格式迁移失败 |
| **崩溃报告** | 应用自身崩溃 | **重启后首次进入时呈现**（不在崩溃瞬间弹窗） | 内核 panic、WebView2 异常退出 |

**两条纪律**：

1. **同一级别内所有错误共享同一个视觉容器**——不许各模块自造弹窗。用户看到某个容器就知道严重程度。
2. **级别由"用户能否继续"决定，不由"我们觉得多严重"决定**。
   - 一个技术上的致命错误，如果已自动恢复，那就是**静默**级（比如重试成功）。
   - 一个技术上的小问题，如果挡住用户，那就是**阻断**级。

**实现约束**：级别是**错误码的属性**（在 §M1 的错误码表里标注），不是调用点的临场判断——
**否则同一个错误码在不同地方会有不同呈现，第 1 条纪律就守不住。**

#### 崩溃归因：**有现成资产可直接搬**（v3.9 补，源码实证）

> **PCL 的规则与文案全部硬编码在源码里**（仓库里没有任何可搬的数据文件——已核实）。
> 但**它们的可用性完全不同，必须分三档**——**原创中文文案受著作权保护，不能直接搬**。

**PCL 崩溃资产的可用边界（三档，必须分清）**：

### 5.8 安全基线（评审补：Tauri 应用不能只靠自觉）

"前端零业务逻辑"是**设计意图**，不是**安全边界**。WebView2 里的页面一旦被注入内容（例如渲染了不可信的
mod 描述、公告、Markdown、外部图标），攻击面就是**整个 Tauri 命令层**。所以必须有强制手段：

| # | 措施 | 具体要求 |
|---|---|---|
| 1 | **CSP 不放开** | 生产环境禁止 `unsafe-inline` / `unsafe-eval`；外链资源一律白名单；**不加载任何远端脚本** |
| 2 | **Tauri capabilities 最小权限** | 按窗口/按模块授予权限；**默认不授予 `fs` / `shell` / `http` 的宽泛能力**；需要文件操作的功能走**自定义命令**而不是通用 fs 插件 |
| 3 | **命令白名单** | 只有显式注册的 `#[tauri::command]` 可被调用；每个命令做**参数校验与路径约束**（禁止任意路径读写） |
| 4 | **前端禁止直连网络与文件系统** | ESLint / lint 规则：禁止在 `src/` 中直接 `fetch` / `XMLHttpRequest` / `import('fs')` / `invoke` 之外的 IPC；**所有业务必须走命令层** |
| 5 | **不可信内容沙箱化** | mod 描述、公告、README 等外部文本：**一律当纯文本或受净化 Markdown 渲染**，禁止内联 HTML 与脚本 |
| 6 | **路径穿越防护** | 所有接受路径的命令：解析为绝对路径后**必须校验仍在允许根目录内**；沿用解压侧同一套策略 |
| 7 | **架构测试强制** | 与"内核零 MC 词汇"同样做成测试：**前端源码中出现网络/文件系统调用即失败** |

**一句话**：**"零逻辑"靠测试强制，"零权限"靠配置强制。两者都不是文档里写一句就算数。**

## 6. 基岩版可行性（按 GDK 迁移重做）

> 本节取代 `_archive/docs/…` 里"基岩版只调研、默认不接"的旧结论。旧结论基于"UWP 沙箱内可操控空间极小"这一前提，**该前提在 1.21.120 之后已失效**。

### 6.1 决定性事实

Minecraft 基岩版 Windows 自 **1.21.120** 起从 **UWP 迁移到 GDK**，数据目录随之搬家（[Microsoft Learn](https://learn.microsoft.com/en-us/minecraft/creator/documents/gdkpcprojectfolder?view=minecraft-bedrock-experimental)）：

| 形态 | 数据目录 | 启动器可及性 |
|---|---|---|
| **UWP（旧，≤1.21.120 前后的商店版）** | `%localappdata%\Packages\Microsoft.MinecraftUWP_8wekyb3d8bbwe\LocalState\games\com.mojang` | 受限：位于 MSIX 包沙箱内，受虚拟化与权限影响 |
| **GDK（新，1.21.120 起）** | `%appdata%\Minecraft Bedrock\users\shared\games\com.mojang` | **可达**：普通文件系统路径 |

子目录（两套结构相同）：`behavior_packs` `resource_packs` `skin_packs` `development_*` `worlds`，日志在 `%appdata%\Minecraft Bedrock\logs\`。

**所以基岩版的内容管理与世界管理是可做的**：行为包、资源包、皮肤包、世界都是普通文件。

### 6.2 能力矩阵（**必须分 GDK / UWP 两列**）

> **修订（v3.6）**：早先矩阵只有一个"基岩版"列，但它把 GDK 与 UWP 混在一起——
> 而这两者能力**根本不同**（UWP 在 MSIX 沙箱内，GDK 是普通文件）。混列的后果是 M9 会写出错误的能力判定。

| 能力 | Java 版 | 基岩版 **GDK** | 基岩版 **UWP** |
|---|---|---|---|
| 检测已装实例 | ✅ | ✅ 查普通路径 | ✅ 查 `Get-AppxPackage` + 包数据目录 |
| 启动（含直接进服务器/世界） | ✅ | ✅（通道待 S7 实测） | ⚠️ 受限（沙箱内，通道待 S7） |
| 依赖组件检测与引导（Gaming Services / GameInput） | — | ✅ | ✅ |
| 内容管理（行为包/资源包/皮肤包 导入·移除） | ✅ mod/资源包/光影 | ✅ 普通文件 | ⛔ **`reason:"UWP 位于系统沙箱内，无法管理内容包"`** |
| 世界管理（列表/备份/还原/导入导出） | ✅ | ✅ | ⛔ 同上（只读受限） |
| 版本管理（可装版本列表） | ✅ | ⚠️ 取决于 GDK 分发通道（**S8**） | ⚠️ 仅能管理商店已装版本 |
| **多实例隔离** | ✅ 原生 | ⚠️ **待评估**：GDK 可指对路径即可；UWP 有"启动器重定向 `ApplicationData`"机制（LeviLauncher 实证，版本 ≥ 1.19.70.2） | ⚠️ 同 GDK |
| 模组框架（LeviLamina 类） | — | ⛔ 外部集成位 | ⛔ 不做 |
| 修改游戏二进制 | — | ⛔ 红线 | ⛔ 红线 |

#### T1 的**数据安全**要求（评审指出的真实事故风险）

T1 不隔离 = **我们直接读写的是官方启动器也用的那份共享数据目录**（`%APPDATA%\Minecraft Bedrock\`）。
这意味着**我们的破坏性操作会波及用户在官方启动器里的游戏**。因此：

| 操作 | 强制要求 |
|---|---|
| 移除内容包（行为包/资源包/皮肤包） | **先自动备份到实例的 `persist/` 备份区**，再执行；操作前明示"这会同时影响官方启动器中的该内容包" |
| 还原/导入世界 | 同名世界存在时**不覆盖**，改为「备份原世界 → 写入新世界」；明示影响范围 |
| 删除世界 | **二次确认 + 强制备份**，且文案必须写明"官方启动器中也将不再出现" |
| 所有写操作 | 记入实例操作日志（可回溯"谁在什么时候动了什么"） |

**一句话纪律**：**在共享目录上操作，默认假设"用户还有另一个启动器也在用这份数据"。**

#### 必须向用户明说的心智模型差异（评审补：**这不是"少一个功能"**）

T1 不隔离的真实后果不只是"少一个开关"，而是：

> **所有基岩版实例共享同一份世界池。** 用户在"实例 A"里建的世界，"实例 B"里也看得见、也能删。

| | Java 版 | 基岩版（T1） |
|---|---|---|
| 世界归属 | **一实例一世界池**，互不可见 | **全局一份世界池，所有实例共享** |
| 内容包归属 | 一实例一份 | **全局一份** |
| 用户预期 | "我在 A 里做的事不影响 B" | **需要被明确告知，否则必然误解** |

**强制界面要求**：基岩版实例的**世界管理页与内容管理页顶部常驻一行**（不可折叠、不可关闭）：

> "基岩版所有实例共用同一份世界数据；在此处的修改会影响其他实例与官方启动器。"

**理由**：不写这句，M9 交付后**一定会**收到"我在 A 实例删了世界，B 实例的世界也没了？"——
那不是 bug 报告，是我们没把心智模型讲清楚。**这条是产品文案的硬要求，不是可选提示。**

**验收口径（K3 定稿）**：基岩版的验收标准就是**与官方启动器逐项对照**——

```
官方启动器能做的，我们要能做：找到已装游戏 → 启动（含直接进服务器/世界）
                              → 内容导入与移除 → 世界列表与备份/导入导出
官方启动器没有的，我们不假装有：模组注入、加载器、JVM 参数、多实例隔离
做得比它好的地方（如实宣传）：下载与校验策略、镜像与测速、诊断与日志、界面与质感
```

**一句话**：基岩版做到"**比肩官方启动器**"即可，不追 Java 版的深度。多实例隔离一期不做且如实告知，
界面自动把它渲染成带原因的禁用态（§3.3 的机制正是为此准备的）。

#### T1 / T2 两档的完整定义（源码实证 ×2，修正早先"隔离大概率做不到"的判断）

| 档 | 内容 | 一期 |
|---|---|---|
| **T1** | 不碰游戏本体，只对数据目录做**读写管理**（列出/导入/导出/备份），**隔离不承诺** → 能力描述符声明 `isolation:false` 并给原因 | ✅ 做（**含上文的数据安全要求**） |
| **T2** | 真隔离，**有两种实现路径（见下）**，均先评估不实现 | ❌ 一期不做 |

**T2 的两条路径（必须分清，此前混为一谈——v3.9 已读全源码）**：

| 路径 | 谁实现过 | 原理 | 版本约束 | 判定 |
|---|---|---|---|---|
| **A · UWP 重定向** | **LeviLauncher**（Go） | 把包的 `ApplicationData` **重定向进实例数据目录**（启动器拥有重定向目标）。**不碰游戏本体** | **≥ 1.19.70.2**（`versions/isolation.go`） | ⚠️ **不触碰红线**，风险显著低于路径 B → **列为 S9 的评估项** |
| **B · ntdll 内联 Detour** | **Portal**（AGPL） | **三重侵入**：① 改写游戏 exe **导入表**注入 preload DLL；② 启动后用 **`CreateRemoteThread`** 在他进程里远程调用其导出函数；③ 该函数**内联 hook `ntdll` 的 8 个文件 API** 改写路径 | GDK | ⛔ **同时命中三条红线**（改二进制 / 写他进程内存 / hook 他进程），**技术性排除，无需再评估** |

**路径 B 的证据链**（`repos/Portal/src/Portal.Bedrock.*`）：
`BedrockDataIsolation.cs`（`AddPreloadImport` 以 `FileAccess.ReadWrite` 打开游戏 exe）→

## 7. 性能预算（**口径必须写清**）

> **修订（v3.6）**：早先"空闲内存 ≤150 MB / 体积 ≤25 MB"**没写口径**——
> 是否含 WebView2 子进程、是否含运行时，直接决定预算成不成立。
> 参考实证：同栈的 NexBox 只自述"内存占用极低"，**没有数字**——所以基线只能我们自己测。

| 项 | 硬预算 | 口径（必须按此测量） |
|---|---|---|
| 冷启动到可交互 | ≤ 700 ms | **精确定义见下方"口径补充"** |
| **内存 — 主进程** | ≤ 60 MB | 我们自己的进程工作集 |
| **内存 — WebView2 进程树** | ≤ 90 MB | `msedgewebview2.exe` 全部子进程之和 |
| **内存 — 合计** | ≤ 150 MB | 以上两者之和（**这才是"空闲内存 ≤150 MB"的含义**） |
| 发行体积 | ≤ 25 MB | **不含** Evergreen WebView2 运行时（系统级依赖，另行检测与引导）；若出"带运行时"版本，该版本单列预算 |
| 界面帧率 | 滚动与动画不掉出 60 fps | 核显机器（无独显）实测 |
| 下载中可交互 | 万行日志 + 全速下载并存时不假死 | 窗口可拖动、可取消 |
| 材质降级 | 高对比度 / 省电 / 远程桌面 / Win10 四场景 100% 正确 | 逐项实测 |
| **高分屏** | **150% / 200% 缩放下不模糊、不裁切**（实现条款见 `docs/UI设计规格.md` §3.3） | 本机改缩放逐档实测 |
| **里程碑审计** | **每个里程碑出口评审时已跑过一次全量审计**（检查清单见 §12.10；机制见 §8.2.4） | 审计结论（P0/P1/P2 分级）留档 |

**M0 必须先出一份 WebView2 基线实测**（空壳窗口的进程树内存与冷启动耗时）。
**若基线本身就把预算顶穿，则预算需按实测重定——不许假装它成立。**

#### 口径补充：**700 ms 期间允许发网络请求，但不许等它**（评审补）

原口径只写了"到可交互"，**没写主窗口是否阻塞在网络调用上**。如果首屏要检查更新、拉版本清单、查镜像源，700 ms 必然爆掉。

```
700 ms 的定义 = 主窗口渲染出「首帧可交互」的时间。
期间【允许】发起网络请求，但【不得等待其完成】。
所有网络结果回来后通过事件更新 UI，不阻塞首帧。
```

**因此以下三件事一律不得出现在首帧路径上**：

| 不得阻塞首帧的事 | 正确做法 |
|---|---|
| 检查启动器更新 | 后台发起，结果回来后在灵动岛/状态条提示（§4.8） |
| 拉取版本清单 | 后台发起；首屏先用**本地缓存**渲染，清单回来后刷新 |
| 探测镜像源速度（≥256 KB 实测探针） | **后台串行探测**，不参与首帧；探针结果只影响后续下载的源序 |

> **⚠️ 归属更正（v3.9，源码实证）**：这条例在方案与归档文档里一直被描述成"**比 PCL 更严谨**"，
> 容易被读成"PCL 也这么做、我们做得更好"。**实际是**：
> - **"≥256 KB 实测探针"是我们第一轮项目自己的做法**（且在本机实测过）；
> - **PCL 没有探针**——它是**两行顺序偏好**：`ModDownload.cs:2119`
>   `DlSourceOrder = DlSourcePreferMojang ? official.Union(mirror) : mirror.Union(official)`；
> - 另有 **HMCL 的"镜像 = URL 前缀改写表"**（`HMCLDownloadProvider.java:62-116,124-149`），
>   **比"多源列表 + 测速"更易维护**，且规则表天然覆盖 Modrinth / CurseForge 的 API 与 CDN。
>
> **结论**：探针保留（它是我们的优势，且有实测依据），但**归属必须写对**；
> 并且**镜像机制升级为"前缀改写表 + 速度判定选当前规则"**（详见 `docs/下载引擎设计规格.md` §5）。

**纪律**：**首帧只做"读本地状态 + 渲染"，任何 I/O 与网络都异步。**
这条与 §3 的"Provider 懒加载"是同一条纪律的两个面——**内核自身的启动阶段也适用**（原来只约束了 Provider）。

#### 口径补充：内存要分"可见 / 隐藏"两个状态测（**源码实证带来的优化**）

同栈先例 NexBox（`src-tauri/src/lib.rs`）用**微软官方 API** 主动压低后台内存：

```rust
// ICoreWebView2_19::SetMemoryUsageTargetLevel
// 窗口隐藏/最小化 → COREWEBVIEW2_MEMORY_USAGE_TARGET_LEVEL_LOW（允许丢缓存、换页到 pagefile）
// 窗口恢复可见   → ..._NORMAL
// 配套：延时 3 秒防抖动；同时开 Windows 效率模式；只对主窗口做
```

**这对我们尤其重要**：启动器最典型的使用形态就是**挂在后台、游戏在前台**——
用户最在意内存的时刻，恰恰是我们能主动压低内存的时刻。

因此 §7 的内存预算**增加两个测量状态**：

| 状态 | 预算 | 说明 |
|---|---|---|
| 窗口可见、空闲 | ≤ 150 MB（合计，原口径） | 用户正在操作启动器 |
| **窗口隐藏/最小化后 5 秒** | **≤ 100 MB（合计）** | 后台常态，应明显低于可见态 |

**M0 的 S3 需同时测这两个状态**；**M4 需实现 `SetMemoryUsageTargetLevel` + 效率模式**（成本极小，收益在用户最敏感的时刻）。

另外两项可从 NexBox 直接借鉴的实现细节（已记入参考笔记 §NexBox 源码实证）：

| 借鉴项 | 内容 |
|---|---|
| **WebView2 特性裁剪** | `additionalBrowserArgs` 关掉 Edge 的购物/钱包/自动填充/同步/扩展/后台网络等——**同时降内存与降攻击面**，与 §5.8 安全基线同向 |
| **release 必须关 DevTools** | NexBox 注释原文："DevTools 打开会额外占 100~300MB **且可以任意调用本地 IPC 命令**" → **DevTools 开着，§5.8 的命令白名单形同虚设**。这是安全项，不只是体积项 |

### 7.1 一个已实测的、会改变设计判断的数字（**带宽**） `[BANDWIDTH]`

M0 前已实测本机国际源吞吐：

| 目标 | 实测 |
|---|---|
| Cloudflare 测速（走 PAC 代理） | **0.28 MB/s（2.3 Mbps）** |
| Cloudflare 测速（直连） | 0.22 MB/s（1.8 Mbps） |
| Mojang `piston-meta` 版本清单 | 0.24 MB/s（1.9 Mbps） |
| 网卡链路速率 | 681 Mbps WLAN |

**瓶颈在跨境出口，不在本机。** 直接后果：**1.20.x 全量资源约 550 MB，仅资源下载即需约 33 分钟。**

这把三件事从"优化项"提升为"核心体验"：

| 项 | 原定位 | 新定位 |
|---|---|---|
| **镜像源** | 可选加速（默认关闭） | **可用性刚需**——必须实测对比官方源与镜像源，并给出默认优先级 |
| **按需下载** | 优化 | **核心**：先只下启动必需，资源后台补。目标"能进游戏 ≤ 15 分钟" |
| **进度与剩余时间** | 有就行 | **硬要求**：但"误差"要按实际波动设，见下 |

#### 剩余时间估算：**分段目标**（评审修正，已接受）

**原写"误差 ≤ 30%"是不现实的**——§7.1 的实测本身就有 0.22–0.28 MB/s 的波动（约 27%），
在此基础上再要求估算误差 ≤30%，等于**要求估算器预知未来**。改为分段：

| 时段 | 目标 | 呈现方式 |
|---|---|---|
| **下载前 30 秒** | 样本不足，**只显示区间** | "约 25–50 分钟" + 已下载量与速度；**不显示单点数字** |
| **30 秒后** | 用最近 60 秒滑动窗口均值，**误差 ≤ 50%** | 显示单点 + "剩余约 X 分钟" |
| **下载过半后** | 样本充分，**误差 ≤ 30%** | 同上 |

**纪律**：**错误的小数字比正确的区间更让用户愤怒。** 样本不足时宁可给区间，不给假精度。
（这条直接改进 M0 的 S5 判据。）

> **注意**：第一轮项目曾在**另一条网络路径**下实测"官方源比 bmclapi 快约 8 倍"。
> **该结论不可直接继承**——换环境后必须重测（已写入 M0 的 S5）。

### 8.1 执行节奏：**按"单元"推进 + 与你 1:1 配对的关键路径**（v3.11 新增）

> **前提变化**：本项目由 AI 协助开发，**可连续推进**（不依赖人的连续大块时间）。
> **于是瓶颈移了位**：不再是"你的手"，而是**"你的眼 + 你的决策"**。
> 因此执行方式的核心不是"排期"，而是**把必须由人做的事与可全自动的事分开**。

#### 8.1.1 两类工作必须分开

| 类别 | 内容 | 谁来 |
|---|---|---|
| **可全自动推进**（大部分） | 纯逻辑内核、下载引擎、元数据解析、加载器合成、测试、重构、文档维护 | **AI 连续推进**，以"测试全绿 + 验收通过"为收敛条件 |
| **必须人参与的四类**（少数但关键） | ① **看第一帧/手感**（材质观感、灵动岛动画）② **产品决策**（文档里没定的）③ **人工验证**（装基岩版、干净虚拟机、真实 Forge installer）④ **里程碑边界评审** | **你**，按需介入 |

**所以"24 小时运行"的实际价值是把这张表右边的第 1 类吃掉**，让你只在第 2 类出现。

#### 8.1.2 单元序列与配对点（以 M0 为例）

| 单元 | 内容 | 能否全自动 | 需要你做什么 |
|---|---|---|---|
| **U0** | `git init` + `SESSION.md` + CI 骨架 + 工具链 | ✅ 全自动 | 无（只需一句"开始"） |
| **U1** | **S1 材质 4×2 矩阵** | ⚠️ 我能跑出 8 张截图 | **必须你看**——"这个材质观感能不能接受"是审美判断，我替代不了 |

**规律**：**每 3–4 个单元才需要你出现一次**。这就是这套分工的收益。

#### 8.1.3 每次收工的三条硬要求

> **本条已抽为单一真源，见 [`docs/M0-尖刺任务书.md`](M0-尖刺任务书.md) 的「纪律 5：每次收工必须留下可运行状态」**
> （含 `SESSION.md` 模板与"为什么它值钱"的说明）。
>
> **为什么不在这里重复**：本条此前在本节与任务书**完整重复**——而"同一件事两个真源会漂移"
> 正是本方案反复强调要避免的（见 §5.5 对 `patches/` 双真源的批评、§6.3 对尖刺编号撞车的处理、§8.2 的引用锚点规范）。
> **纪律：一份内容只在一个地方写全文，其它地方只留指针。**

#### 8.1.4 ⚠️ 无人值守的四条风险纪律（**v3.11 新增，最重要的一节**） `[UNATTENDED]`

> **连续推进的最大风险不是"做错"，是"做多"**——在你没看的那些小时里，我会**自行扩大范围**。
> 所以下面四条是硬约束，**每条都必须在仓库里有物理载体**（不能只是口头约定）。

| # | 纪律 | 物理载体 |
|---|---|---|
| **1** | **任务单一真源**：我只从**已定清单**里取活做。**清单外的活，只准做两件事：写进 `SESSION.md` 的"候选"区，或问你。不准自行开工。** | `docs/任务清单.md`（M0 有 U0–U12；后续里程碑的清单按 §8 路线图展开） |
| **2** | **失败即停**：任一验收标准没过、测试变红、或发现方案有矛盾 → **停下，写进 `SESSION.md` 的"卡住"区，不继续往下推**。绝不允许"先绕过它做后面" | 收工前必须 `cargo test` + 前端 lint 全绿，否则不留 commit |
| **3** | **重大决策不得自行拍板**：不改红线、不改已定 ADR、不引入方案外依赖、不加新功能。**拿不准的写进 `docs/待决.md`，等我看** | `docs/待决.md`（格式：问题 / 备选 / 我的建议 / 影响谁） |
| **4** | **每单元一个 commit**，且 commit message 写明"完成哪个单元的哪个验收点" | git 历史本身 |

**再加一条防跑偏的**：**每完成一个里程碑（M0/M1/…），必须停下来等我做一次边界评审**——不允许连续跨过两个里程碑。

**为什么把这条单独写出来**：**AI 连续推进的价值是"省你的时间"，代价是"少了你的判断"。**
上面四条就是把这笔代价**显式设上限**——否则省下来的时间会以"返工"的形式还回去，而且还更多。

### 8.2 引用锚点规范：**用不会变的 ID，不用会变的章节号**（v3.13 新增）

> **触发原因（诚实交代）**：我在文档开头写了"当前不拆分"，理由是"拆开会让每次改动跨多文件改写引用，
> 成本高于收益"。**这个判断的前半段对、后半段错**——成本没有消失，它**转移**了：
>
> | 轮次 | 实际发生的引用腐烂 |
> |---|---|
> | v3.7 | §12 的九个子节标题仍停留在 `13.x`（只改了主标题） |
> | v3.10 | 插入"设计令牌"后 **§4.6 被挤占**，6 份文档里的旧引用全部指错 |
> | v3.10 | §7 出现 **7.1 → 7.3 跳号**，4 处 `§7.1` 引用悬空 |
> | v3.12 | 补正后 §7.3 又改为 §7.2，任务书里的对应引用同步失效 |
> | v3.13 | 审计发现**方案里 Portal 的许可证仍写着 GPL-3.0**（应为 AGPL-3.0）——**这是内容腐烂，不是引用腐烂，但同样致命** |
>
> **结论**：**"章节号"是会变的东西，不能用来当标识。** 被引用超过 2 个文档的章节，一律加锚点。

#### 8.2.1 锚点格式与现有锚点

**格式**：写在章节标题行末尾，方括号大写短名，全文档唯一。

| 锚点 | 位置 | 为什么它需要锚点 |
|---|---|---|
| `[TOKENS]` | §4.6 设计令牌 | 被 3 份文档引用过；且**已被挤占过一次编号** |
| `[DOWNLOAD]` | §7.2 下载引擎 | 被任务书 + 下载规格 + ADR 三处引用；**编号改过两次**（7.3→7.2） |
| `[BANDWIDTH]` | §7.1 带宽实测 | 被 4 处引用；**编号曾是"无编号悬空"** |
| `[MIGRATION]` | §4.7 数据格式与迁移 | 曾是 §4.6，**被挤占过一次** |
| `[REDLINES]` | §1.4 不做（红线与边界） | 被 ADR 与任务书引用 |
| `[CAPABILITIES]` | §3.3 能力描述符 | 被多份文档引用，是架构支点 |
| `[INSTANCE-DATA]` | §5.5 实例数据模型 | 被资产清单、代码笔记、MultiMC 报告引用 |
| `[COST]` | §9.1 成本表 | 决策依据 |
| `[UNATTENDED]` | §8.1.4 无人值守四条纪律 | AI 协作的硬约束 |
| `[UI]` | §4 界面 | 被 `docs/UI设计规格.md` 引用；**是唯一被单独展开成规格的层** |

#### 8.2.2 三条使用纪律

1. **新写跨文档引用时**：**锚点优先**，形如"见 `方案 [DOWNLOAD]`"。章节号可以附带写（方便人读），但**锚点是判定依据**。
2. **只在"被 ≥2 份文档引用"时才加锚点**——不要给每一节都加，那会让标题变脏。
3. **改了带锚点的章节**：**锚点跟着走，章节号随便改**；同时把该锚点的位置更新到本表。

#### 8.2.3 关于"要不要拆分"

**仍然不拆**，但理由变了（不是"拆了更贵"，而是"锚点已经解决了主要问题"）：

| 方案 | 判断 |
|---|---|
| **现在拆分**（方案只留决策+索引） | ❌ 方案仍在频繁整体修订；此刻拆开，**每次改动要跨 4–5 个文件**，且拆分本身会引入一轮新的引用迁移 |
| **立锚点（已做）** | ✅ 成本几行字，**直接消除"章节号漂移"这一类问题**；内容腐烂（如许可证写错）由**定期审计**兜底 |
| **拆分触发条件（更新）** | **M1 结束时**——那时架构冻结、进入按模块并行，且文档体系已被锚点稳定过一轮 |

**新增一条配套机制**：**每个里程碑结束时跑一次全量审计**（本次那种：引用完整性 + 数字一致性 + 悬空承诺 + 许可证）。
**理由**：锚点治不了"内容腐烂"，只有**定期审计**能治。本次审计抓出的 Portal 许可证错误就是证据。

#### 8.2.4 审计机制的**落点**（v3.13 补：此前立了机制、无任务承载 → 悬空承诺）

审查确认：这条机制**在全文没有任何任务条目或验收标准**。现补齐：

| # | 项 | 内容 |
|---|---|---|
| **1** | **触发时机** | **每个里程碑的出口评审时**（与 §8.1.4 的"每完成一个里程碑必须停下等人评审"同一次） |
| **2** | **执行方式** | 按 **§12.10 那次的检查清单**：① 引用完整性（`§X.Y` 与锚点逐个核"存在 + 语义相符"）② 数字一致性（尖刺编号 / 里程碑数 / 工时表加总 / 性能预算 / 带宽 / 成本）③ **悬空承诺**（搜"待实测/待定/见某文档"并逐条核落点）④ **许可证与来源**（与 `docs/来源记录.md` 台账逐项对齐）⑤ 结构与围栏（重复标题 = 0、围栏成对）⑥ **标题守恒**（见下） |
| **2b** | **⚠️ 标题守恒（每次编辑的**前置**检查，不是审计时才做）** | **成因**：用 `edit` 时若 `old_string` 里**含一个标题行**，而 `new_string` 忘了把它抄回去，**这个标题就被"吃掉"，正文留下来并挂到上一个标题下**——文档语法完全合法、结构校验也过（重复标题仍是 0、围栏成对），**所以任何自动校验都抓不到它**。本项目已发生 **4 次**：§4.4 灵动岛、§7.1 跳号、§6.5 缺失、§5.4 日志分级色。<br>**规则**：**`old_string` 与 `new_string` 的标题行数必须相等**（除非就是要增/删标题）。<br>**做法**：改完立刻数一次 `grep -c '^#{2,4} '`，**编辑前后标题总数必须一致**（有意增删则记录差值）——这一步 5 秒钟，能抓住全部 4 次事故。 |
| **3** | **产出** | 一份审计结论，问题按 **P0 / P1 / P2** 分级（P0 = 会导致错误实现或合规风险） |
| **4** | **归属** | **M0 由 `M0-尖刺任务书.md` 的「流程 C · 里程碑审计」承载**；**M1 起由各里程碑的出口条件承载** |

> **与 §8.2 的关系**：**锚点治"引用漂移"，审计治"内容腐烂"——两者治的是不同的病，都要有。**
> **证据**：v3.13 这次审计抓出"Portal 许可证被写成 GPL-3.0（实为 AGPL-3.0）"，
> 而它**不是引用漂移、是内容错误**——锚点对它无效。

## 11. 与官方教程的对照（Java 版）

> 依据：[中文 Minecraft Wiki · 教程:编写启动器](https://zh.minecraft.wiki/w/Tutorial:%E7%BC%96%E5%86%99%E5%90%AF%E5%8A%A8%E5%99%A8?variant=zh-cn)（该教程**仅适用于 Java 版**，且 wiki 自身标注"仍需完善"）。
> 本节做三件事：确认方案与你给的教程一致、找出教程没覆盖而我们必须补的、把教程里的流程性硬要求变成路线图事件。

### 11.1 教程的七环节 ↔ 本方案落点

| 教程环节 | 教程要点 | 本方案落点 | 状态 |
|---|---|---|---|
| 1 基本原理 | "启动器 + 游戏文件"分离；库与资源由启动器补全；**离线登录仅由启动器完成** | 与 `GameProvider` 抽象天然同构（游戏本身 = 启动器架构） | ✅ 一致 |
| 2 准备 | JSON 解析 / 解压 / 网络 IO 三件套；Java 8 与 Java 21/25 双线 | 内核基础设施（M1） | ✅ 一致 |
| 3 启动参数 | `-X/-XX`、`-D`、`-cp`（Windows `;` 分隔）；Minecraft 参数以 `mainClass` 开头 | M3 参数组装；**`mainClass` 取自 JSON，加载器会覆盖它** | ✅ 一致 |
| 4 游戏文件 | 版本清单 / 版本 JSON / 资源索引 / `launcher_profiles.json` / 主文件 / 普通库 / natives / 资源 | M2 元数据 + M3 组装 | ⚠️ 见 §11.2（补 4 项） |
| 5 正版验证 | 设备代码流 与 授权代码流；XBL → XSTS → MC 令牌 → 校验拥有 → 取 UUID | M5 微软身份 | ⚠️ 见 §11.3（三条硬要求） |
| 6 启动游戏 | 拉起 `java.exe`/`javaw.exe` 并传入参数 | M3 进程管理 | ✅ 一致 |
| 7 支持 Mod 加载器 | **额外版本 JSON**（`inheritsFrom`）；教程给了 Fabric 与 NeoForge | M7 加载器合成 | ✅ 与设计一致 |
| 8 优化下载 | 教程仅提"可优化"，未展开 | M1 下载引擎（第一轮已验证的源策略更强） | ✅ 我们更完备 |
| 9 皮肤管理 | `sessionserver` 取皮肤/披风（base64 解 `textures`）；`PUT`/`DELETE` 上传与重置 | M11 皮肤 | ⏸ 延后（教程里唯一与我们排期不同的环节） |

**结论：教程覆盖的 9 个环节里，7 个与本方案完全一致，1 个（下载）我们做得更深，1 个（皮肤）我们排期在后。**
**最重要的一点**：教程开篇的"启动器 + 游戏文件"分离模式，**本身就是 provider 架构**——Minecraft Java 版是"游戏把自己拆成元数据 + 文件"设计的。
这反过来证明 §3 的抽象不是我们发明的，而是贴着游戏本身的形状长的。

### 11.2 教程没覆盖、但我们必须补的（4 项）

| 缺口 | 为什么必须补 |
|---|---|
| **`launcher_profiles.json` 兼容** | ⚠️ **v3.9 降级为"待实测项"**：wiki 说它可用于与官方启动器数据互通、**以及 Forge 安装检验**，我据此写过"M7 必须写"。**但源码实证推翻了"必须"**：**HMCL 全仓不写它**（3 处提及全是**导出黑名单**，如 `ModAdviser.java:47`、`ModrinthModpackExportTask.java:157`），Portal 也不写。**处置**：降级为 **M0 尖刺的实测项**——装一次 Forge 官方 installer，实测它是否真的检查该文件；若检查再补写，不检查就不做**（实测步骤见 `docs/M0-尖刺任务书.md` 的 S7 第 8 步）** |
| **安装器模式（installer jar）** | 教程第 7 节只讲"额外版本 JSON"的合并方式，但 Forge 1.13+ 走的是 `--installClient` 安装器流程（会写 libraries 与 versions）。NeoForge 同理。**这条是 M7 最大的工作量项** |
| **跨年代结构差异** | 教程以 1.19/22w24a 为例。旧版用 `minecraftArguments`（字符串）而非 `arguments`（对象）、natives 走 `classifiers` 而非 `downloads`、无 `rules.features`。**M2 必须按版本年代分支处理** |
| **失败面与边界** | 教程不写失败路径。我们需要补：Java 版本不匹配（1.17+ 需 Java 16+，1.20.5+ 需 Java 21）、库缺失、`rules` 判定错误、assets 索引更新、natives 被清理软件删除、启动计划不可复现等 |

### 11.4 一处必须修正的设计（Java 与基岩的身份不能混为一谈）

v3 §3.4 写的是"身份相同但授权路径不同"。**按教程细化后要改得更准确**：

| 维度 | Java 版 | 基岩版 |
|---|---|---|
| 凭据链 | 微软 OAuth → **XBL → XSTS** → `login_with_xbox` → MC 令牌 | 微软账户 + **Xbox Live / 商店授权** |
| 校验 | `GET /entitlements/mcstore` 检查 `product_minecraft` / `game_minecraft` | 商店授权与 Gaming Services |
| 玩家标识 | `GET /minecraft/profile` 取**Java 版 UUID + 用户名** | **Xbox 玩家标识**（与 Java UUID 不是同一体系） |
| 启动凭据 | `--accessToken` 传入游戏 | 不向进程传令牌 |

**结论：可以共用同一个微软账户，但必须各自独立持有凭据链与校验结果**，且界面要区分显示"Java 版授权 / 基岩版授权"两种状态。
抽象上：`IAuthProvider` 拆为**账户层（微软，共用）**与**授权层（各产品独立）**。这是 M5 的设计输入。

> **📌 Java 版这条链的具体规格已独立成文** → **`docs/身份与授权规格.md`**（锚点 `[IDENTITY]`）。
> 那儿有：**已实测可用的应用注册（`client_id` / 流程 / 范围）**、端点全表、令牌链四段、
> 错误码、令牌存储安全基线，以及**前置条件门禁 C1–C4 的当前状态**。
> **本方案不再重复这些内容**（§8.2 的单一真源原则）。
>
> **一条要特别留意的事实**：封存的第一轮项目**在这条链上真的卡死过**
> （`AADSTS70002: must be marked as 'mobile'`，个人账户端点全被拒），
> 而 **2026-10-01 复测三个租户段全通 → 注册已补齐配置**。
> 也就是说：**这条链此前没有任何版本走通过一次真实登录**——M1 要做的第一件事就是把它走通。

### 11.5 官方端点清单（M1–M3 的契约依据）

```
版本清单     https://piston-meta.mojang.com/mc/game/version_manifest.json
版本详情     https://piston-meta.mojang.com/v1/packages/<sha1>/<id>.json
资源索引     https://piston-meta.mojang.com/v1/packages/<sha1>/<index>.json
资源对象     https://resources.download.minecraft.net/<hash[0..2]>/<hash>
             → 落盘 .minecraft/assets/objects/<hash[0..2]>/<hash>
             → 并在 assets/virtual/legacy/ 留一份拷贝（旧版资源路径依赖）
库           https://libraries.minecraft.net/...  （按 version.json 内 url，勿硬编码）
日志配置     https://launcher.mojang.com/v1/objects/<sha1>/client-1.12.xml
皮肤/披风    GET    https://sessionserver.mojang.com/session/minecraft/profile/<uuid>   （base64 解 textures）
上传皮肤     PUT    https://api.minecraftservices.com/minecraft/profile/skins
重置皮肤     DELETE https://api.minecraftservices.com/user/profile/skin/active
```

**纪律**：所有 URL 与哈希**一律取自元数据，不硬编码**（教程示例中的地址仅作形状参照）。
`assets/virtual/legacy/` 这份拷贝是**旧版本资源查找路径的硬依赖**，不是可选项——M2 的验收要覆盖它。

> 调研方式：本地实测 PCL / PCL-CE / PCLHelp 仓库（`repos/`）+ 外部启动器实证调研 + 两个同栈同定位先例（Polymerium / Portal，见 [`docs/参考项目笔记.md`](参考项目笔记.md)）。
> 每条给四项：**抄什么 → 解决什么问题 → 成本量级 → 落点**。

### 12.1 从 PCL 自己身上抄（本地仓库实测，一手证据）

> 方法：`repos/PCL-CE` 的本地化文件共 **3030 个键**，等于 PCL 的完整功能地图。
> 命名空间分布：`Setup(652)`、`Instance(582)`、`Download(420)`、`Minecraft(338)`、`Launch(230)`、
> `Tools(205)`、`Crash(141)`、`Select(118)`、`Watcher(27)`、`Link(53)`。

**从这份地图里挖出三处我原方案漏掉的结构性设计：**

| 挖到什么 | 证据 | 为什么重要 | 落点 |
|---|---|---|---|
| **游戏生命周期事件表** | `Watcher` 命名空间：`Start / WindowLoaded / FmlWindowLoaded / LoadComplete / Exited / ProcessExited / Crash / Kill / SecurityBlocked` | 这正是**灵动岛 `Running` 态的数据源**。我原来只写"进程探测/窗口探测/日志观测三法比选"，PCL 已把这套状态机定义清楚——照搬即可 | M3 / M4 |
| **崩溃分析是"原因 + 建议"两段式** | `Crash` 命名空间：`Reason(62)` + `Suggestion(39)` + `Report(26)` | 比我写的"错误码 + 人话提示"更进一层：**结论必须带可执行建议** | M11 |
| **工具区含服务器查询** | `Tools` 命名空间：`GameLink(102)` + `Test(84)` + **`ServerQuery(14)`** | 不只是"服务器列表"，而是能查在线状态/玩家/MOTD | M10 |

**另外六条可抄（含我上一轮猜错、已排除的一项）：**

| # | 抄什么 | 解决什么问题 | 成本 | 落点 |
|---|---|---|---|---|
| 1 | **帮助系统内建在启动器里，且是"可点击的操作卡片"**（卡片里直接带"打开注册表编辑器""备份注册表"这类按钮） | 用户卡住时去搜网页，搜到的教程版本对不上；PCL 的帮助**跟着启动器一起发布** | 中 | M4.5 增加"帮助"一格：Markdown/JSON 内容 + **可绑定动作的按钮**；内容与程序分离，可随版本更新 |

| 3 | **设置备份与还原（含凭据本机限定）** | 重装系统/换机时配置全丢。PCL 分两处存（程序文件夹 + 注册表），并明说"账号密码只能同机还原" | 小 | 我们天然更好：配置全在 `data/`、凭据 DPAPI 加密。要做的是"一键导出/导入配置包"并标注凭据不可跨机 |
| 4 | **整合包导出（把个性化设置一起打包）** | 做整合包的人希望连外观一起分发 | 小 | M8 增加导出方向：实例 → 压缩包（含可选外观配置） |
| 5 | **本地化的"你知道吗"提示** | 空界面时提供信息密度，且是**可自定义的本地文本**（`hints.txt`） | 极小 | 灵动岛 `Idle` 态或主页空白区轮播提示；内容做成可替换的数据文件 |
| 6 | **第三方验证做成显式可选项** | 让不同来源的用户都能进来，但**不明示就有合规风险** | 小 | 统一按 **§1.4 的"不做/边界"表**处理（**默认关闭、显式启用、明示限制**三件套），这里补上**具体来源清单**：Authlib-Injector（外置皮肤站）、统一通行证 |

> **一处纠正**：我早先猜 PCL 有独立的"资源管理页"——查证后 `Assets` 并未构成独立本地化组，**该猜测不成立，已排除**。

### 12.3 同栈 / 同定位的直接先例（本地实证，价值最高）

这三个项目不是"别家启动器"，是**直接验证或推翻我们设计决策的证据**。

| 项目 | 定位 | 对我们的价值 |
|---|---|---|
| **Polymerium**（C#/Avalonia，MIT） | "**实例是一份描述，不是一堆拷贝的文件**"（元数据驱动） | ① **实例声明式模型**：换加载器只改描述后重建、mod 保留；整包原地升级，存档设置自动带过去 ② **快照回滚 + "到底变了什么"的 diff** ③ **符号链接共享 mod**（十个整合包不占十倍磁盘）④ **依赖图可视化**，启动前看出冲突 ⑤ 实例即配置文件，**可进 git** |
| **Portal**（C#/Avalonia，**AGPL-3.0**——只读设计，代码零引用） | "**同时支持 Java 版与基岩版**"，含游戏安装、账户、资源查找、文件整理 | ① **它是"Java + 基岩同一启动器"的活先例**，证明 §3 架构方向可行 ② 含 `Portal.Bedrock.Hook` / `Portal.Bedrock.Preload` / `Portal.XUserHook.dll`，且 README 自陈支持基岩版 **DLL 模组、预加载、可配置键盘** → **说明基岩版可操控空间比我们保守估计的更大**（**S8** 要实测的正是这个）③ `portal://` 协议 + 命令行调用安装与启动 ④ 游玩时长与最近游玩记录 ⑤ **`.litematic` / `.nbt` 结构预览 + 材料清单导出**——典型的"MC 相关但与启动无关"工具，**正好验证百宝箱的必要性** |

**其中一条是选型对照表里最硬的一手证据**：Polymerium 在 README 的 Known Issues 里自陈，**Avalonia 的画刷渐变渲染有可见色阶（banding），是所有 Avalonia 应用的框架级问题**，它无法在自己层面修复。
而**材质与渐变正是我们的核心诉求** → 这条实证直接支撑了 §2 的 K1 选型（Tauri + CSS 而非 Avalonia）。

### 12.4 吸收纪律与边界（防止"百家之长"变成大杂烩）

调研报告给出的一条警告必须单独写下来，因为它**直接约束我们的架构边界**：

> **"多游戏抽象泛化"是陷阱。** Lutris / Playnite 类"什么游戏都管"被用户明确抱怨 "tries too many things"；
> 而 **HMCL 与 Prism 至今都坚持只做 Minecraft**，没人靠"什么游戏都管"赢过。

因此把 K7 的边界说得更准（修正原表述）：

| 层 | 允许扩展 | 禁止扩展 |
|---|---|---|
| **产品 Provider**（§3.2） | **只服务 Minecraft 的两个版本：Java 版、基岩版**。将来若出现"同引擎多产品/多版本"才考虑增加 | **不为无关游戏新增 Provider**。GTA / 独立游戏 / 模拟器不进来 |
| **功能模块**（§5） | **与 MC 无关的功能一律走百宝箱模块位**（工具、管理、平台服务） | 不许把这类功能塞进内核或 Provider |

**两句话记住**：
**Provider 抽象服务"同一个游戏的不同版本"，百宝箱服务"与游戏无关的功能"。两者不许互相渗透。**

其余五条纪律（只抄机制不抄外观、只抄能落点的、冲突时以"减少用户决策"为准、不抄需要长期后端运营的、不抄可能踩红线的）保持不变。

### 12.5 明确不吸收（含理由）

| 不吸收 | 理由（实证） |
|---|---|
| **内建联机** | 2022-11-05 PCL2 / HMCL / BakaXL **三方联合公告停用内建联机**，理由是提供商"高度商业化、强制付费"（[来源](https://www.taptap.cn/moment/338056872613380736)）；此后 PCL 走 EasyTier 仍出现"因强制付费而暂时关闭"。**只留外部集成位，绝不承诺免费联机**（K11） |
| **泛化到无关游戏** | 见 §12.4 |
| **完全暴露 JVM 参数** | 对普通玩家是负担；保留但默认折叠 + 预设 + 可解释 |
| **自造私有包格式** | HMCL 的"HMCL 数据包"是它的生态包袱，不跟 |
| **追求"超小体积单文件"** | GDLauncher 已 EOL、XMCL 活跃度存疑——**体积不是护城河**，架构与维护节奏才是（这条也确认了我们放弃旧方案"≤5 MB"约束是对的） |

### 12.6 设计资源参考库（三个已克隆的 UI 项目）

| 仓库 | 它到底是什么 | 我们能取什么 | 不能取什么 |
|---|---|---|---|
| **taste-skill**（91k★，MIT，4.7 MB） | 不是 UI 库，是**一份给 AI Agent 的前端设计技能包**：13 个技能（`taste-skill` 86 KB 的 SKILL.md、`image-to-code-skill`、`soft-skill`、`minimalist-skill`、`brutalist-skill`、`brandkit`、`redesign-skill`、`stitch-skill`…） | **设计裁决规则**：它把"什么算俗气、什么算高级"写成了可执行的检查项与判据。M4 开工前读它的 `taste-skill/SKILL.md`，用来**校准我们的三层材质与动效规范**，并作为设计评审的对照清单 | 它的产出目标是"营销站/落地页"（Persuade 模式），我们的界面是"操作型应用"（Operate 模式）——**判据要重映射，不能直接照搬审美结论** |
| **galaxy**（13k★，MIT，10 MB） | **UI 组件与样式库**：Buttons(1231)、Cards(726)、loaders(718)、Toggle-switches(260)、Inputs(226)、Forms(180)、Checkboxes(171)、Patterns(103)、Radio-buttons(102)、Tooltips(62)、Notifications(23) —— **约 4200 个社区提交的组件成品** | **视觉参考与交互范式库**：做按钮/开关/加载/空态/骨架屏时**先在这里找既有解法**，避免自己发明平庸方案。纯 CSS / Tailwind 实现，可直接读代码 | 它的组件风格杂（社区投稿质量不均），**只当参考不当依赖**；我们的组件必须走自己的语义令牌 |
| **impeccable**（73k★，Apache-2.0，66 MB） | 一个**设计语言 + 反模式检测器**（Rust 编写，编译为 wasm + CLI + 浏览器扩展）：24 个设计命令（`audit` / `polish` / `critique` …），**确定性检测"AI 味"界面**；自带一套 `DESIGN.md`（Neo kinpaku：金箔 + 铜绿 + 黑漆，全 OKLCH 令牌） | **① 反模式规则集**（Rust 里的 `check_*` / `scan_*`）——这是**可直接拿来做我们验收清单的"AI slop"检查表**（通用 AI 味配色、紫色渐变、发光粒子、玻璃拟态堆砌、SaaS 落地页套路）→ **已接入 M4 出口条件（见 M4）**；**② OKLCH 令牌组织方式**（语义层 + 中性阶 + 发丝线 hairline 的写法）；**③ 它的自我戒律**："每个视觉元素都必须挣得自己的位置，不为装饰而装饰" —— 与我们"纯色兜底也必须好看"同源 | 它的产物是"给 AI 用的设计技能包"，不是组件库；**我们借鉴规则与令牌组织，不引入它的运行时** |

**一条有意思的对照**：impeccable 明确把 **glassmorphism（玻璃拟态）与紫色渐变、青黑霓虹**列为要避免的"通用 AI 工具味"。
而我们的设计（窗口 DWM 材质 + **界面层零模糊** + 描边/留白分层）恰好绕开了它点名的那些俗套——
**这与 §2 因 WebView2 平台限制被迫放弃 CSS 模糊的决定，方向是一致的**。限制与品味在这里刚好同向。

### 12.7 扩展接口预留：NexBox 类功能模块（K13）

**NexBox（`MuLiuSaMa/NexBox`，GPL-3.0，476★，124 MB）** 是一款"为 PC 游戏玩家打造的一站式性能工具箱"，
技术栈 **Tauri 2.10 + React 19 + Rust 1.77 —— 与我们选择的栈完全相同**。

**它为什么值钱（三条）：**

1. **它是"用 Tauri 做系统级工具"的可行性实证**：硬件监控（LibreHardwareMonitorLib 级）、系统优化、显示滤镜、
   悬浮叠加面板、系统托盘、全局热键、自动更新、视频壁纸——这些都被 WebView2 壳跑通了，
   说明我们"Tauri 做 Windows 桌面启动器"的选型在能力面上没有天花板问题。
2. **它把"百宝箱"做成了一个完整的盒子**：README 原话是"PC 玩家常常需要同时运行七八个工具软件，NexBox 把这一切装进一个盒子"
   ——**这正是 K7 百宝箱的产品逻辑**，而且它已在 `Tools` 意义上验证了可行。
3. **它的"叠加面板"已经内置了灵动岛样式**（README：支持**灵动岛** / 竖排面板 / 默认三种样式）——
   与我们的灵动岛设计撞在同一处，值得当实现参考读。

**但它同时暴露了我们必须提前划清的三条线（这是本次调研最有价值的发现）：**

| NexBox 的做法 | 我们的判断 |
|---|---|
| **准星叠加**（6 种样式、自定义 PNG、职业选手预设） | ⛔ **不吸收**。这就是瞄准辅助类工具，在竞技射击游戏里属违规且可能致封号。**红线：不做任何影响游戏内胜负判定的功能** |
| **从游戏内存读取每日密码** | ⛔ **不吸收**。读游戏进程内存属侵入性行为。**红线：不读写其它进程内存** |
| **ACE 反作弊引擎优化**（改反作弊进程优先级与 CPU 亲和性） | ⛔ **不吸收**。干预反作弊是高风险行为，可能被判定为绕过。**红线：不触碰任何反作弊组件** |
| 系统托盘 / 全局热键 / 自动更新 / 主题定制 / 视频壁纸 / 内置工具集成（检测外部工具并启动） | ✅ 可吸收，成本小。**"检测外部工具并一键启动"与我们百宝箱的定位完全一致**（我们不打包第三方工具，只做检测与启动） |
| 硬件监控 / 显示滤镜 / 悬浮信息面板 | ⚠️ 可吸收但有前提：**必须放独立模块、独立进程、默认关闭、明示风险**（详见下） |

**边界结论（K13）：**

```
与 MC 无关的功能一律走模块位（K7），且必须遵守三条：
  1. 模块不获得内核特权：不得访问内核的凭据、实例数据、启动计划
  2. 高风险能力（系统级、驱动级、进程级）必须独立进程 + 默认关闭 + 明示风险
  3. 模块可整体移除，且移除后主程序不报错、功能不缺失（§5.4 纪律）
```

**同时新增两条全局红线**（写进 §1.3）：

| 永不实现 | 理由 |
|---|---|
| **任何影响游戏内胜负判定的功能**（准星叠加/瞄准辅助/自动点击/宏） | 会致用户封号，且与"启动器"定位无关 |
| **读写其它进程内存、干预反作弊组件** | 侵入性行为，法律与账号风险双高 |

### 12.8 "集百家之长"能不能实现：能，但靠的是筛选而不是堆叠——筛选规则在此

**结论先行：技术上完全可实现，风险是范围失控，而范围失控是这类产品的第一死因。**

反面实证：Lutris / Playnite 类"什么游戏都管"被用户抱怨 "tries too many things"；
而 **HMCL 与 Prism 至今只做 Minecraft，反而活得最稳**。**聚合的价值在"深度"不在"广度"。**

**因此设一道准入门槛。任何来源的功能要进入我们的方案，必须同时通过四条：**

| # | 门槛 | 反例（会被挡住） |
|---|---|---|
| **① 落位明确** | 归入三个位置之一：**产品 Provider**（MC 的 Java/基岩）／**百宝箱模块**（与 MC 相关但非启动）／**独立功能模块**（与 MC 无关） | 说不清属于哪一档的功能 |
| **② 频次达标** | **≥80% 的用户、≥每周一次**会用；否则进 backlog 不进里程碑 | 一次性工具、极客向开关 |
| **③ 可独立移除** | 拿掉它，主程序照常编译运行、其它功能不缺失（§5.4 纪律） | 与内核或别的模块缠在一起的功能 |
| **④ 可写验收** | 能写出"怎么验、验到什么算过" | 只有感受没有判据的功能 |

**两句话总结**：
- **纵向（同一个游戏）做深**：同一件事在多家有不同解法时，取**最省用户决策**的那一种，并写清为什么。
- **横向（与游戏无关的功能）做隔离**：全部走模块位，绝不让它们影响启动主链路的稳定性、启动时间与内存预算。

> 记住一句话：**集百家之长 ≠ 什么都做。集的是"每一处的最佳解法"，不是"每一家的全部功能"。**

### 12.9 模块预留：一件事现在不做，但接口现在留

你提到"后续可能加上 NexBox 那类功能"。**本方案不承诺实现其中任何一项**，但预留如下（避免将来推倒重来）：

| 预留项 | 现在要做的事 | 成本 |
|---|---|---|
| 模块注册与移除机制 | §5.2 的"登记表 + 独立目录"——已在一期（M4.5 就绪） | 已计入 |
| 独立进程能力 | 内核需要能拉起并托管一个**受限子进程**（不是随便起进程） | M1 预留接口，不实现 |
| 高风险能力的开关框架 | "默认关闭 + 显式启用 + 明示风险"三件套——已有（镜像源/第三方验证/Java 下载同一模式） | 已计入 |
| 权限声明 | 模块需声明自己要什么能力（系统信息/文件/进程），内核据此做提示与裁剪 | M10（工具补全阶段） |

**明确不预留的**：进程内存访问、反作弊交互、驱动级调优——**这三类的接口一个都不留**，因为它们属于红线。
