# 性能与体积实测记录

> 硬约束来自制作规划：主程序 ≤5 MB、冷启动 ≤800 ms、空闲内存 ≤80 MB。
> **这些数字不能只在 Debug 下"应该没问题"——本文件是实测结果。**

测量环境：Windows，显示器物理 2560×1600 @ 150% 缩放（1706×1067 设备无关单位），
WPF 渲染层级 Tier 2（硬件加速），Release 构建，数据目录为便携模式。

---

## 1. 结论摘要

| 约束 | 预算 | 实测 | 判定 |
|---|---|---|---|
| 主程序体积 | ≤ 5 MB（目标 1–3 MB） | **252 KB** | ✅ 大幅优于预算 |
| 冷启动（窗口可见） | ≤ 800 ms | **330 / 343 / 377 ms** | ✅ |
| 冷启动（可交互） | ≤ 800 ms | **389 / 449 ms** | ✅ |
| 空闲内存 | ≤ 80 MB | **约 154 MB**（其中约 138 MB 是 WPF 基线） | ❌ **预算在该技术栈上不可达** |

**我们的界面自身只占约 16 MB**——预算不可达的原因是运行时基线，不是实现浪费。详见 §4。

---

## 2. 体积：不需要 Costura

Release 发布产物只有三个文件：

```
QinmoUltimateLauncher.exe          258,560 B   (252 KB)
QinmoUltimateLauncher.pdb           87,644 B   (调试符号，不随发布)
QinmoUltimateLauncher.exe.config       174 B
```

**没有任何第三方 DLL。** 原因是项目从 P0 起就坚持零第三方运行时依赖：
HTTP 用 `HttpWebRequest`、ZIP 用 `System.IO.Compression`、JSON 是自己写的 DOM。

因此"单文件"不需要 Costura.Fody 或 ILMerge——**把一个 exe 单独拷到空目录就能跑**，已实测：
目录里只有 `QinmoUltimateLauncher.exe` 时正常启动，并自动生成 `data/` 与 `game/`。

那 174 字节的 `.config` 只是 `supportedRuntime` 声明，删掉不影响运行。

## 3. 冷启动

从 `Start-Process` 到主窗口句柄可用（窗口可见），以及到 UI 自动化能按名称找到「启动游戏」按钮
（即布局完成、绑定生效，用户真的可以点了）：

| 运行 | 窗口可见 | 可交互 |
|---|---|---|
| 第 1 次（含首次运行写入配置与目录） | 377 ms | 449 ms |
| 第 2 次 | 330 ms | 389 ms |
| 第 3 次 | 343 ms | — |

清单读取、Java 探测等耗时工作都在后台线程上跑，不阻塞窗口出现。

## 4. 空闲内存：预算在该技术栈上不可达

### 4.1 对照实验一：空的 net48 WPF 窗口

写了一个**只有一句 `TextBlock` 的 net48 WPF 程序**，同样 1120×820、
同样挂 PerMonitorV2 清单、同样 Release 构建：

| | 工作集 |
|---|---|
| **空 WPF 窗口（基线）** | **137.7 MB** |
| 我们的启动器 | 153.6 MB |
| **我们的界面自身** | **+15.9 MB** |

**空窗口就已经 137.7 MB，远超 80 MB 预算。**
net48 的 WPF 运行时（PresentationFramework / PresentationCore / WindowsBase / System.Xaml）
本身的装载成本就超过这个数。

### 4.2 对照实验二：启动工作占多少

把"启动即刷新"临时关掉（不读 917 条清单、不探测 19 个 `java.exe`），同一次会话内 A/B 对照：

| | 工作集 | 私有 |
|---|---|---|
| A 无启动工作（不刷新、不探测） | 153.9 MB | 135.6 MB |
| B 完整启动（917 条 + 19 个 JVM） | 153.6 MB | 136.2 MB |

**两者一致（差值在噪声内）。** 说明清单解析与 19 次 JVM 探测**不留下长期内存**——
CLR 用完就还了。不需要为此做任何"探测后 GC"之类的小动作。

### 4.3 内存不随窗口尺寸变化

| | 正常 1120×820 | 最小化 | 缩到 400×300 |
|---|---|---|---|
| 空 WPF 窗口 | 137.7 MB | 137.8 MB | 123.4 MB |
| 启动器 | 220.5 MB※ | 220.2 MB※ | 227 MB※ |

空窗口缩小只省 14 MB。**这些内存不是渲染表面，而是运行时与托管对象图本身。**

※ 这一组读数是同一构建在更早会话里测到的，明显偏高（见 §4.4）。

### 4.4 测量方法本身会骗人

同一个 Release 构建，空闲工作集在不同会话里测到过 **153.6 / 220.5 / 222.9 / 227 MB**——
跨度 70 MB 以上。可信的是 **§4.2 那种"同一次会话内 A/B 对照"**，不是跨会话的单点读数。

已知的两个干扰源：

1. **UI 自动化客户端连着窗口会抬高读数。** WPF 在被 UIA 查询时会实例化整个可视树的
   automation peer，这部分内存会一直留着。做过 `AutomationElement.FindAll` 的那次会话读数最高。
   这一条同时是个产品事实：**接上屏幕阅读器后内存会涨**，值得在无障碍场景下单独测一次。
2. **PowerShell 默认 DPI 不敏感**，`GetWindowRect` 给逻辑坐标而 `CopyFromScreen` 用物理坐标，
   截图会只取到窗口一角（详见 `P6.5-界面现代化规范.md` §8）。这条不影响内存读数，但同样属于
   "工具默认行为把人带沟里"。

**以后报内存数字，必须写明：同一会话内的对照值、是否接过 UIA。**

## 5. 结论与待决策

**80 MB 这个预算在 net48 + WPF 上不可能达成**——什么都不做的空窗口就 137.7 MB。
这不是实现缺陷，而是**规划阶段技术选型与内存预算没有对齐**：
规划同时固定了 "C# + WPF + net48"，又要求 "空闲内存 ≤80 MB"。

而且我们的实现几乎没有浪费：**界面自身只占 15.9 MB，启动工作占 0。**

| 方案 | 影响 | 代价 |
|---|---|---|
| **A. 修正内存预算**（例如改为 ≤200 MB） | 承认 net48+WPF 的现实；仍优于多数 WPF 启动器 | 需要产品负责人认可 |
| **B. 换 UI 栈**（如 WinForms） | 空闲内存可降到 ~40 MB | 与既定技术栈冲突；界面现代化方案要重做 |
| **C. 换运行时**（net8.0-windows） | 单文件 70 MB+ | 体积预算崩掉，与"轻量单文件"直接冲突 |
| **D. 维持 80 MB 不放松** | — | 需要换栈，否则该验收项永远无法通过 |

**建议 A。** 理由：体积 252 KB、冷启动 330 ms 两项都大幅优于预算，
而内存这一项的成本几乎全部来自既定技术栈本身；
为它换栈会同时毁掉体积与界面方案，收益不成比例。

**如果选 A，建议把预算写成"≤200 MB（空窗口基线 + 60 MB）"**——
这样它衡量的是**我们的实现**，而不是 WPF 的固有成本，将来也不会因为换个运行时就失效。

## 下载提速：照搬 PCL2 的全局网络配置（实测 2.1 倍）

### 起因

用户要求"下载速度与 PCL2 比肩"。于是读 `repos/PCL/` 的源码，
并由子代理整理出 PCL2 下载实现的关键参数（附文件:行号）。

### 决定性的一条

PCL2 在 `Application.xaml.vb:100-104` 启动时设置：

```
Expect100Continue = False
DefaultConnectionLimit = 10000
UseNagleAlgorithm = False
```

**`DefaultConnectionLimit` 是 .NET Framework 每主机连接上限，默认值实测为 2。**
不改它，无论把并发开到多少，同一个主机上真正并行的连接最多只有 2 条。

我自己的数据也印证了这一点：同一批真实资源对象（1.7.10 资源索引抽样 60 个）

| 条件 | 吞吐 |
|---|---|
| 未设该项 | 232 KB/s |
| 设为 10000 | 662–815 KB/s |

### 改动

| 项 | 改前 | 改后 |
|---|---|---|
| `DefaultConnectionLimit` | 框架默认 2 | 10000 |
| `Expect100Continue` | 框架默认 true | false |
| `UseNagleAlgorithm` | 框架默认 true | false |
| 下载并发 | 8 | 32 |
| 下载调度 | 每条目一个 Task + 阻塞等信号量 | 固定 worker 从共享游标取活 |

### 实测结果（同一台机器、同一网络）

方法：全新目录冷装 1.7.10，量 120 秒；**同时间段另跑一次 8 并发裸脚本作为网络基准**，
用来校准网络漂移。

| | 改前 | 改后 |
|---|---|---|
| 吞吐 | 337 KB/s | **705 KB/s** |
| 文件/秒 | 1.2 | **5.7** |
| 120 秒下载量 | 35 MB | **83 MB** |
| 线程数 | 57→80 且持续增长 | 稳定 43–46 |
| 达到网络基准的比例 | 0.42 | **0.87** |

**吞吐 2.1 倍，文件速率 4.75 倍，已跑到裸脚本基准的 87%。**

### 两条被我自己推翻的错误结论（留作记录）

1. **"瓶颈是连接数上限"→ 我先前用 100 秒窗口做过一次 A/B（上限 2 得 359 KB/s、
   上限 16 得 313 KB/s），据此认为该项无效并撤销了改动。那个 A/B 是在网络漂移的
   噪声里做的，结论不可靠。** 用更严谨的方法（同时间段插入基准、更大样本）重测后，
   该项是 3 倍级的因素。**
2. **"引擎比裸脚本慢 12 倍"→ 错误对比**：裸测反复下载同一个文件命中了 CDN 边缘缓存
   （769–1380 KB/s 是虚高的），而引擎下的是各不相同的冷对象（真实单连接 293 KB/s）。

教训：**在会漂移的环境里做 A/B，必须把基准放进同一个测量窗口，否则量到的是环境不是改动。**

## 提速之后暴露的缺陷链：源探测基于噪声排序（已修）

按 PCL2 配置提速后跑了一次完整冷装，结果是
**691 成功、19 失败**，其中包含 **lwjgl** 这类必需库——安装"完成"却报失败。

### 排查

直接取那 19 个失败资源的官方 URL：**全部返回 200**。资源根本没丢。

而日志里的探测记录是：

```
source probe: bmclapi2.bangbang93.com = 36 KB/s
source probe: bmclapi2.bangbang93.com = 11 KB/s
source probe: libraries.minecraft.net =  4 KB/s   ← 官方被排到最后
```

**这些数字毫无意义。** 探测用的是计划里**体积最小的条目**（几 KB），
量到的是**延迟**不是吞吐：3 KB 的文件 0.1 秒返回被记成 "30 KB/s"、
0.3 秒被记成 "10 KB/s"。拿它排序，结果把镜像排到了首位。

而实测镜像对库文件返回 **403**（PCL2 源码里明确写着
"403/429 对 bmclapi 豁免"，说明这是它的已知行为）。于是 19 个条目失败。

### 修法

1. **给样本加下限 256 KB**：体积未知或太小的一律不做样本。
   没有合适样本就返回 null，**宁可不排序，也不要基于噪声排序**。
2. **改掉那句把来源说死的提示**：`QUL-NET-0006` 原文是
   "该资源在**官方源**上不存在或已被移除"——不管实际失败的是哪个源都这么说，
   把排查引向了错误的方向。改为说明可能是镜像缺件并提示换回官方源。

### 附：PCL2 并没有下载测速选源

子代理读源码的结论：PCL2 的源顺序由**用户设置**与
"拉官方 version_manifest 是否够快（< 4 秒）"决定，另有失败禁用与分段轮换。

**"源码中未发现"任何下载测速选源。** 我先前那层探测比 PCL2 更激进，而且在害事。

## 19 个失败的真因：一个源的 404 让条目直接判死（已修）

上一节把 19 个失败归因于"源探测基于噪声排序"。**那只说对了一半，而且是次要的一半。**

### 真正让条目失败的地方

重试循环里：

```csharp
catch (LauncherException ex)
{
    if (!IsRetryable(ex.Code))
    {
        _log.Failure("download", ex.Code, ex, item.RelativePath);
        break;   // ← 404 在这里跳出整个循环
    }
}
```

`NetResourceMissing`（404）不在可重试之列，于是**一旦某个源报 404，条目立刻判死，
连第二个源都不会去试**。而镜像上缺的文件，官方源上往往是有的。

探测把镜像排到首位只是让这个缺陷更容易触发；**即使探测完全正常，
只要首选源缺件，条目照样会失败。**

### 修法

```csharp
bool anotherSourceMayHaveIt =
    ex.Code == ErrorCode.NetResourceMissing && attempt < sourceCount;

if (!anotherSourceMayHaveIt) { _log.Failure(...); break; }

_log.Warn("download", "this source reports missing; trying another", ...);
```

并把重试上限改为 `max(options.MaxAttempts, sourceCount)`——
**每个源至少要被试过一次**，这个保证不该依赖重试次数的配置。

### 两个方向的用例都补上了

| 用例 | 断言 |
|---|---|
| 第一个源 404、第二个源有 | 换源并成功，落盘内容正确 |
| 所有源都 404 | 结论是"资源不存在"，两个源各试一次就收手，不多试 |

### 教训

上一节我把结论下得太快：看到"探测把镜像排首位"就收工了。
**真正的问题在更下面一层——重试循环把"这个源没有"和"这个资源不存在"当成了同一件事。**

## 并发数的确定：8 → 32 是 2.88 倍，32 → 64 只有 1.15 倍

方法：两个 120 秒冷装窗口，**前后各插一次 8 并发裸脚本作网络基准**以校准漂移。

### 8 vs 32（网络基准 1175 → 1321 KB/s）

| 并发 | 结果 |
|---|---|
| 8 | 473 个文件 / 36.0 MB / 120 秒 = **307 KB/s** |
| 32 | **710 个文件全部下载** / 103.6 MB / 120 秒 = **884 KB/s** |

**2.88 倍。** 32 并发达到了网络基准的约 71%。

### 32 vs 64（网络基准 828 → 947 KB/s）

| 并发 | 结果 |
|---|---|
| 32 | 713 个文件 / 103.1 MB / 120 秒 = **880 KB/s** |
| 64 | 713 个文件 / 119.1 MB / 120 秒 = **1016 KB/s** |

**1.15 倍。** 注意 32 并发得到的 880 KB/s 已经**超过**了 8 并发裸脚本基准（828–947 KB/s），
因为引擎用的连接数更多。

### 为什么停在 32 而不是 PCL2 的 64

PCL2 的上限是 64（`ToolDownloadThread` 默认 63 + 1），但它是**自适应**的：
先给每个文件各起 1 线程，**只有全局速度掉到阈值以下**才给进行中文件追加分段线程
（`ModNet.vb:1747、1763`），并且对 bmclapi 有专门的节流（起线程后 sleep 100）。

我们目前是固定并发，没有这套调度。取 32 拿到 64 的约 87% 收益、连接数只有一半，
是更稳妥的中间点。**若将来照搬了自适应调度与镜像节流，再提到 64 是有依据的。**

### 一次被网络噪声误导的记录

同期还跑过一次完整冷装：900 秒仍未结束、131.5 MB、平均 150 KB/s，
而本次探测却显示网络很快（270–1295 KB/s）。同一套配置在 120 秒窗口里能跑 884 KB/s——
**说明那 900 秒里网络塌过。** 又一次印证：不把基准放进同一个测量窗口，量到的是环境不是代码。

## 又一个被实测推翻的映射：launcher.mojang.com 没有 bmclapi 对应路径

排查 `logging/client-1.7.xml` 为什么失败时，顺手验证了我们为它造出的镜像 URL：

| URL | 结果 |
|---|---|
| `https://launcher.mojang.com/v1/objects/50c9…/client-1.7.xml` | **200**（966 B） |
| `https://bmclapi2.bangbang93.com/v1/objects/50c9…/client-1.7.xml` | **404** |

bmclapi 根本没有 `/v1/objects/` 这个路径。而映射表里 `https://launcher.mojang.com`
被替换成 `BmclapiBase + 空后缀`，于是**每一条这个域名的下载都会多出一个必然 404 的"备用源"**。

危害不是"下载失败"（官方源是好的，会成功），而是：

1. 白占一次重试机会——如果官方源真出问题，这一轮重试就浪费在一个不可能成功的地址上
2. **日志里的"换源"看起来发生过，其实是假的**——这比不做更糟

`AddIfMapped` 的注释写着"绝不凭空造一个备用源"，
但它能挡住"没匹配到主机时原样返回"，**挡不住映射表里的路径本身不存在**。

**已从映射表移除该主机**，并加用例锁住：这个域名必须映射不出任何镜像候选，
且即便在 `MirrorFirst` 偏好下，唯一候选仍是官方地址。

## 决定性的一条：一条静默连接会把整次安装永久挂死（已修）

前几次"完整安装跑不完"我都归因于网络慢。**错了——是卡住了。**

### 现场

```
在途 .part : assets/objects/47/47800737…5a.part
大小       : 0 B          ← 文件建好了，一个字节都没收到
停滞       : 20.3 分钟
线程       : 只剩 7 个（其余 worker 早已退出）
CPU 累计   : 3.7 秒
```

`RequestTimeout` 是 60 秒，`ReadWriteTimeout` 也按它设了，
**但没有触发**。于是那个唯一的在途读取永久阻塞，
`Task.WaitAll` 永远等下去——其余 31 个 worker 都做完了，整次安装却结束不了。

### 修法：自己盯"多久没有新数据"

新增 `IdleTimeoutStream`：每次读取前武装计时器、读到数据就解除，
超时则 `Abort()` 那条请求，让阻塞的读取抛出来，**落进引擎既有的重试与换源路径**。

空闲上限取请求超时本身，但**最多 60 秒**、不低于 5 秒。
**"挂死"与"失败后重试"的分界就在这一点上。**

### 回归用例复现的就是这个场景

本地起一个服务器，**发完响应头就沉默**：

- 这样 `GetResponse()` 会立刻返回，走不到 `HttpWebRequest.Timeout`
- 阻塞只可能发生在读正文上——也就是空闲看门狗唯一能救的场景
- 断言：必须抛出、且必须在 20 秒内放弃

**没有这个修复，这条用例会真的挂 30 秒。**

### 教训

网络慢和"卡住"在现象上都是"进度不动"，但**处理方式完全相反**：
慢要等，卡住要掐断重试。我把两者混为一谈了整整两轮，
期间每次测出来的"平均吞吐"里都混着挂死的时间。

## 换源的成本：反复试一个注定缺件的源（已按 PCL2 的做法修）

第一次完整成功的冷装（710/710、0 失败）之后，平均吞吐只有 **142 KB/s**，
而同一窗口内的能力是 884 KB/s。差在哪？

日志给出了答案：**大量 `this source reports missing; trying another`**——
命中 `trove4j`、`jinput`、`commons-io`、`netty`、`commons-logging`… 一长串库。

原因是探测这次测出 **bmclapi 1441 KB/s、官方 452 KB/s**，于是把镜像排到首位；
镜像对**资源对象**确实快得多，但它**缺很多库文件**——
于是每个库都要先失败一次再换源。**时间花在了一次次注定失败的尝试上。**

### 修法：本次运行内的来源健康度

新增 `SourceHealth`，按 **主机 + 条目类型** 记录缺件次数，达到阈值（3）就本轮跳过该组合。

键里带条目类型是刻意的：**同一台镜像对资源对象齐全、对库却常缺**，
只按主机计数会把它的资源提速一起误伤掉。

只把 `NetResourceMissing`（404）与 `NetHttpStatus` 算在来源头上；
超时与连接中断属于传输故障，记上去会误伤好源。

这是 PCL2 的同一个思路（按来源记录失败、超阈值禁用，`ModNet.vb:1084`）。

## 全程分阶段采样：慢的不是网络，是"少数大文件 + 单连接"

第一次完整成功之后，平均 142–155 KB/s 而窗口内能跑 884 KB/s。
我一直归因于"网络退了"，**这次用全程采样把它查清了。**

方法：每 10 秒记录缓存各子目录的体积（正好对应阶段），
并在几个时间点插入一个很小的网络基准（12 个真实资源对象，约 1 秒）。

### 采样结果（1.7.10 冷装）

```
  时间   合计MB  资源MB  库MB  区间吞吐KB/s  网络基准KB/s
   10s    27.6     2.1  20.3         2821          506
   32s    32.2     6.3  20.6           31
  145s    80.6    54.3  21.0         2580
  215s   122.9    96.6  21.0          418
  225s   122.9    96.6  21.0            0
  392s   122.9    96.6  21.0            0     ← 167 秒零进展
  402s   128.2   101.9  21.0          540
  649s   128.2   101.9  21.0            0     ← 又是 237 秒零进展
  689s   133.4   107.1  21.0  完成
```

**决定性的一点：那两段零进展期间，网络基准是 550、231、530、396 KB/s——网络完全健康。**
而且日志里那 474 秒**没有任何错误、超时或换源记录**。

### 真因：资源对象的体积分布

| 体积 | 个数 | 合计 | 占比 |
|---|---|---|---|
| **≥256 KB** | **39 个** | **95.06 MB** | **89%** |
| <256 KB | 647 个 | 12 MB | 11% |

最大的那些是 Minecraft 的**音乐文件**：`end.ogg` 9.68 MB、`credits.ogg` 5.92 MB、
`creative5.ogg` 5.4 MB……（686 个对象共 107.19 MB）

**而这 39 个大文件各自只在一条连接上下载，没有任何分段能力。**

时间线因此完全解释得通：
- 前 100 秒下完 647 个小文件——连接多、聚合吞吐高（830 KB/s）
- 剩下的大文件越来越少，**干活连接数塌到个位数**，
  每个文件还是一条慢连接 → 22 KB/s 的尾巴

### 结论：下一步就是 PCL2 的多线程分段下载

这不是"再调调参数"能解决的，是**缺少一个能力**。
PCL2 对 ≥1 MB 的文件按 256 KB 粒度切分、多连接并行拉
（`ModNet.vb:674-678、772、861-863`）。

**39 个大文件占了资源字节的 89%**——把它们分段并行，
那段 474 秒的尾巴是首先要被消掉的。

## 大文件分段下载（照 PCL2 的做法实现）

上一节把慢尾归因于"39 个大文件各占一条连接"。这一节是实现。

### 参数（照 PCL2）

| 项 | 值 | 出处 |
|---|---|---|
| 分段阈值 | **1 MB** | `ModNet.vb:674-678` |
| 单文件最多几段 | 4（PCL2 是自适应，受 64 全局上限约束） | — |
| 段请求 | 非首段带 `Range`；**本实现给所有段都带上有界 Range** | `ModNet.vb:917` |
| Range 被忽略时 | 回 200 且从 0 开始 → 非首段必须判为不支持并回退单连接 | `ModNet.vb:964-971` |

### 与既有不变量的关系（这是关键）

分段**只负责把字节完整写进 `.part`**，之后仍走原来的
**SHA-1 校验 + 原子发布**。完整性保证一点没打折。

分段失败时删掉整个 `.part` 并**回退单连接重试**。

### 为什么必须给 Range 终点

只给起点的话每一段都会一直下到文件末尾——**N 段就变成 N 倍的流量**，比不分段还糟。
为此给 `HttpFetchRequest` 加了 `RangeTo`。

写入时也**绝不越过本段边界**：服务端忽略 Range 时会回整个文件，
多写的部分会覆盖邻段已经下好的数据。**拼错了就是静默损坏。**

### 一个必须防住的静默损坏

新增的用例里有一条专门验证：让假的服务端**忽略 Range**（回 200 + 整个文件），
断言最终落盘内容仍然逐字节一致。

如果实现里没有"非首段遇到 200 就判为不支持"这条判断，
错位的数据会被拼进文件——而 SHA-1 校验**本来能拦住它**，
但代价是整份重下，而且失败原因会显得莫名其妙。

## 分段下载的净效果：同一时段 A/B，24 倍

先前那次比较（689 秒 → 101 秒）**不能全算给分段**——网络基准同期从 506–1321 升到了 1528 KB/s。
所以做了严格的时间窗内 A/B：**同一时段、前后各插一次基准、只切换分段开关。**

| | 用时 | 平均吞吐 |
|---|---|---|
| 分段**关闭** | **848.3 秒（14.1 分钟）** | 161 KB/s |
| 分段**开启** | **34.9 秒** | **3903 KB/s** |
| 期间网络基准 | 2006 → 1949 KB/s（稳定） | |

**24 倍。**

最关键的一点是"关闭"那一臂：**在网络基准 2006 KB/s 的情况下，它仍然要跑 14 分钟。**
这彻底证实了慢尾**不是网络问题**——先前我两次把它归因于"网络退了"，两次都错了。

分段开启时 3903 KB/s 高于 8 并发基准（1949 KB/s）是预期的：
引擎此时能用远多于 8 条的连接。

## 并发数定稿：64（与 PCL2 一致），三明治式对照

先前在 1.7.10 上量过 32 → 64 只有 1.15 倍，据此把默认定在 32。
但那是在**分段之前**、而且工作负载里没有 26.3 那种几千个小文件。

在 26.3 上重量（5224 项 / 586 MB）：

```
并发 32（第一次）: 1667 KB/s
并发 64          : 2215 KB/s      ← 夹在两次 32 之间
并发 32（第二次）: 1760 KB/s
```

**32 的两次是 1667 与 1760（稳定在 ±5%），64 夹在中间拿到 2215。**
这是个**三明治式对照**——64 的前后都是 32，所以 1.3 倍**不能归因于网络漂移**。

之所以要这么排，是因为同一时段测出的网络基准波动极大（前 5761、后 642 KB/s）。
**单看两臂先后跑的数字是不可信的，这正是我先前栽过的坑。**

### 顺带把分段闸门与并发数解耦

分段闸门取 32（不跟并发数同值）：单文件最多 8 段，但**只有大文件才分段**
（26.3 的 5224 项里只有 87 项 ≥1MB），所以闸门几乎不会成为瓶颈，
而它把最坏情况下的总连接数摁在 **96** 以内（64 worker + 32 分段），
不至于出现"每个 worker 再各开 8 段"。

#### 这 85 MB 是什么？——**只有假设，没有定论**

窗口出现时约 138 MB，之后涨到 222 MB。而日志显示版本清单是**缓存命中**，
`version_manifest_v2.json` 只有 **271 KB**。

271 KB 的 JSON 解析不出 85 MB 的常驻结构（那相当于每个叶子节点 13 KB，不可能）。
**因此最可能的解释是：这 85 MB 里绝大部分是尚未回收的垃圾**——

**但这是假设，不是结论。** 要证实它需要强制 GC 后对比工作集，

而预算是 ≥80 MB。也就是说，**什么也不做的空窗口就已经超标 1.7 倍**。

建议把该项改为**相对基线的增量指标**（例如"空窗口基线 + 60 MB 以内"），
而不是绝对值——这也是我一直等产品负责人确认的那条。

## 空闲内存：从 222 MB 降到 37.5 MB（并且这次真的落进预算）

上一节把 85 MB 的去向标为"假设、未证实"。这一节把它证实了，并据此改掉。

### 证实方法：清空工作集，看它长回多少

用 `EmptyWorkingSet` 把工作集清空，再观察它**只长回真正被再次触碰的页**：

```
清空前工作集  226.9 MB
清空后立即     11.9 MB
空闲 20 秒后   23.7 MB   ← 只长回这么多
私有内存       201.3 -> 200.7 MB（未变）
```

**227 MB 里只有约 24 MB 是启动后真正还会被触碰的页。**
其余约 200 MB 是启动期分配、之后再也没碰过的页——**假设成立：那不是活跃状态，是没被回收的垃圾与没交还的堆。**

### 修法

新增 `WorkingSetTrimmer`：**先真正回收一次垃圾，再把空闲页交还系统**。

两步缺一不可：只交还不回收，交还的只是"暂时没碰"的活对象页，下一次 GC 前后又会长回来。

只在**启动完成且界面进入空闲后做一次**，绝不放在热路径上，也不在游戏运行期间反复做。

### 结果

| | 交还前 | 交还后 |
|---|---|---|
| 工作集（启动后 2 秒） | 225.8 MB | — |
| 工作集（4 秒起） | — | **28.3 MB** |
| 工作集（40 秒） | 222 MB | **37.5 MB** |
| 私有（已提交） | 200 MB | **200 MB（未变）** |

**37.5 MB < 80 MB —— 这项预算现在真的达标了。**

### 必须说清楚它改了什么、没改什么

- **改进了**：常驻物理内存（工作集）222 → 37.5 MB。这才是真正与其他程序争抢 RAM 的部分，
  也是任务管理器那一列显示的数字。
- **没改进**：已提交的私有内存仍是约 200 MB——那是 GC 保留下来备用的堆段。
  它占的是系统的提交量，不占物理页。

**这不是把数字做小的花招**：页被移到系统的备用链表，应用再次需要时由系统重新调入
（代价是一次缺页）。真正省下的是"启动器开着不动时对其他程序的内存压力"——
而启动器恰恰常年就是开着不动。这也正是把它放在"启动完成后一次"而不是热路径上的原因。
