## 1. 结论（先说结果）

| 问题 | **答案** |
|---|---|
| **无边框窗口能不能用 Mica** | ✅ **能**。`decorations: false` + `apply_mica` 返回 `Ok`，且**有可见效果** |
| **无边框窗口能不能用 Acrylic** | ✅ **能**（同上） |

| **有没有出现黑边/白边/渲染破裂** | ✅ 没有。所有色块边缘干净 |
| **走哪一档预案** | **A 档**（`docs/UI设计规格.md` §11.2）：岛贴顶居中、浮在自绘标题栏之上 |

**因此 §4 的布局可以按 A 档冻结**——这是 S1 要解开的那个阻塞。

## 2. ⚠️ 一个必须先说的前提：**光调 API 是不够的**

**第一次跑矩阵时，8 格全部 `apply_ok: true`，但像素分析显示它们与"完全不调材质"的对照组数值一模一样。**

第一轮的实测数据（**窗口内部中心区**）：

```
cell                     ctr_mean  ctr_sd
mica-bare-auto                255       0
none-bare-auto   ← 对照组      255       0      ← 与 Mica 完全相同
tabbed-bare-auto              255       0
```

**纯白 255、标准差 0，且 Mica 那格与对照组无差别** → 材质**没有任何可见效果**。

**根因**：**Tauri 的 WebView2 默认以不透明背景填充窗口**，把 DWM 材质整个盖住。
`apply_mica` 改的是**窗口**属性，而窗口被一层不透明内容填满 → 看不见。

**修法**：窗口构建时加 **`transparent(true)`**。

```rust
tauri::WebviewWindowBuilder::new(...)
    .decorations(decorations)
    .transparent(true)      // ← 少了这个，材质看得见才怪
    .build()?;
```

> ### 🔴 这条是本尖刺最重要的产出，比"材质能用"本身更重要
>
> 如果我只信 `apply_ok: true`，结论会是"材质可用"，而**实际现象是完全不可见**。
> **`apply_*` 返回 `Ok` 只说明 Windows 接受了这个调用，不说明它产生了任何可见效果。**
>
> 这与本项目已经栽过两次的失效模式**同源**：
> 用比真实条件宽松的证据（`HTTP 200`、带 flag 的截图、`apply_ok`）替代"看到结果"。
> **所以本次的判据被强制为：像素分析 + 看图，`apply_ok` 只作参考。**

## 3. 完整矩阵实测数据

**环境**：Windows 11 家庭版 中文版 **Build 26200** ｜ 系统主题**浅色**（`AppsUseLightTheme=1`）｜
透明效果**开**（`EnableTransparency=1`）｜ 显示缩放 **150%**（请求 1100×760 → 实得 1650×1140）｜
`tauri 2.12.1` · `window-vibrancy 0.8.1` · WebView2 154.0.4258.37

**像素统计口径**：屏幕截图中**窗口内部中心区**（水平 30–70%、垂直 60–80%）的亮度均值。
**对照组** `none-bare-auto` = **不调用任何材质 API**。

| 格子 | 材质 | 边框 | `dark` | `apply_ok` | **中心均值** | 与对照组差 | 判定 |
|---|---|---|---|---|---|---|---|
| `none-bare-auto` | **无（对照）** | 无 | — | — | **12.0** | — | 基线（窗口近乎全透） |
| `mica-bare-auto` | Mica | **无** | 未指定 | ✅ | **242.5** | **+230.5** | ✅ **生效** |
| `mica-deco-auto` | Mica | **有** | 未指定 | ✅ | **242.5** | +230.5 | ✅ 生效（与无边框同值） |
| `mica-bare-light` | Mica | 无 | `false` | ✅ | **242.5** | +230.5 | ✅ 生效（与 auto 同值，自洽） |
| `mica-bare-dark` | Mica | 无 | `true` | ✅ | **31.1** | +19.1 | ✅ **生效，且明显更暗** |
| `acrylic-bare-auto` | Acrylic | 无 | — | ✅ | **144.4** | +132.4 | ✅ 生效，整体偏暗（含着色） |
| `acrylic-deco-auto` | Acrylic | 有 | — | ✅ | **139.0** | +127.0 | ✅ 生效 |
| `tabbed-bare-auto` | Tabbed | 无 | 未指定 | ✅ | **216.2** | +204.2 | ✅ 生效，观感**可区分** |

**读法**：**只要某一格的中心均值显著偏离对照组 `12.0`，就说明材质产生了可见效果。**
六种材质配置给出**六个互不相同、且可复现**的数值 → 材质确实在起作用。

**边框维度（有/无）对材质没有影响**：Mica 两格都是 242.5，Acrylic 两格 144.4 / 139.0（差 5.4，属截图噪声量级）。
**这正是要紧的那一点**：`decorations: false` **不会**让材质失效。

**未定论的一项**（见 §5）：**窗口四周边缘是否透出桌面**。本次数据不足以判定，
因为截图把窗口外 12px 也框进来了，边缘读数混入了窗口外的像素。

# 附：S2 · 透明 × CSS `backdrop-filter`（**2026-10-01，U2**）

> **预判被推翻。** 任务书原文的假设是"Windows 上 WebView2 的窗口级透明**会破坏** CSS
> `backdrop-filter`（社区已记录的平台缺陷）"，**预判为否**。**实测：两者共存，且完全无差异。**

## 1. 结论

```
判定：✅ 通过（得到明确结论）
透明窗口 + CSS 模糊：✅ 可共存
采用方案：保持"窗口 DWM 材质 + 界面零 CSS 模糊"不变（但理由从"做不到"变成"不这么做"）
```

**三个事实，每个都有独立证据**：

| # | 事实 | 证据 |
|---|---|---|
| **1** | **不透明窗口里 `backdrop-filter` 正常模糊** | `opaque-blur` 对比度比值 **0.379**（判据：≤0.5 为"已模糊"） |
| **2** | **透明窗口里同样正常模糊** | `trans-blur` 比值 **0.379**（与上一格**完全相同**） |
| **3** | **透明与不透明，卡片区像素逐字节相同** | 独立复算：卡片内 / 对照内 / 两卡之间**平均差 0.00、最大差 0**（各 28500 采样点） |

**第 3 条最有力**：透明作为自变量**没有改变卡片内部的任何一个像素**。这比"两次测得同一个比值"更强——
比值相同可能是巧合，**逐像素为 0 不是**。

## 2. 矩阵与数据

（`--material none` 恒定：DWM 材质在**窗口**层合成，会整体染色，混进来就分不清"被 CSS 模糊"与"被 DWM 染色"。
材质另有单独两格。）

| 格 | 透明 | blur | 卡片对比度 | 对照对比度 | 比值 | 判定 |
|---|---|---|---|---|---|---|
| `opaque-noblur` | ✗ | ✗ | 5.93 | 5.29 | 1.122 | **NO-BLUR**（对照组自洽，§3） |
| `opaque-blur` | ✗ | ✓ | 4.33 | 11.42 | **0.379** | **BLURRED** |
| `trans-noblur` | ✓ | ✗ | 9.05 | 4.83 | 1.875 | **NO-BLUR**（对照组自洽，§3） |
| `trans-blur` | ✓ | ✓ | 4.33 | 11.42 | **0.379** | **BLURRED** |
| `opaque-mica` | ✗ | ✗ | 5.95 | 5.22 | 1.141 | NO-BLUR |
| `trans-mica` | ✓ | ✗ | 5.66 | 4.58 | 1.235 | NO-BLUR |

**度量**：测试页铺高频黑白棋盘格；`R = 亮度通道相邻像素差的均值`（`0.299R+0.587G+0.114B`）。
模糊必然把锐利边缘抹平 → 卡片内 `R` 显著低于对照卡内的 `R`。

**判据先于数据确定**（避免"看着数字凑结论"）：比值 ≥0.8 = 未模糊；≤0.5 = 已模糊；之间 = 不明确。

**截图证据**：`spikes/s1-material/out/shot-{opaque,trans}-{blur,noblur}.png`（+ `crop-*` 与 `result-*.json`）。
`shot-opaque-blur.png` **肉眼即可判读**：卡片内是一块平滑灰面，而同页其余部分是锐利棋盘格。

## 3. 两处必须记下的方法学教训（**都是我自己犯的**）

| # | 教训 | 具体经过 |
|---|---|---|
| **1** | **测试页自称的颜色，必须等于它真渲染出来的颜色** | 第一版测试页写的是"红/黑棋盘格"，实测渲染成**白/近黑**（R255 vs R16）。而我的度量**恰好用的红通道**——也就是说"红通道度量灰白图案"这件事**碰巧能用**，但它是一处**自己骗自己的巧合**。改法：**度量换成与颜色无关的亮度**，测试页**只声明它真的渲染出来的**黑白。 |
| **2** | **对照组必须与受测区在图案相位上可比** | 对照卡片与受测卡片水平相距 420 px，**棋盘格相位不同**，所以"对照的对比度"并非同相位的基准（这解释了为何 `opaque-noblur` 的比值是 1.122、`trans-noblur` 是 1.875——**两者都是"未模糊"，比值却差很远**）。**结论不受影响**（效应量大：0.379 vs ~1.1–1.9），但**比值只能当序数量级读，不能当精确基准**。要精确基准应改用"同心留白"布局，让对照与受测**同相位**。 |

> **第 2 条同时解释了 §3 表格里那个"对照组自洽"的标注**：
> 那两格的对照与受测都锐利（比值为 1 量级），说明该格**没有别的因素在模糊**，
> 因此"这一格没开 blur"这个前提**被验证过**，而不是假定。

## 4. 对设计的影响：**结论是"可以，但不做"**

**S2 通过的含义要读准**——它不是"我们该用 CSS 模糊"，而是：

> **零 CSS 模糊从"平台做不到"变成了"我们主动不这么做"。**

| 项 | 变化 |
|---|---|
| **UI 规格 §4 的三层材质** | **不变**（层次仍由不透明度阶梯 + 1px 描边 + 留白承担） |
| **理由** | **从"唯一可行"改为"主动选择"**——这更稳固，因为它是**设计判断**而非**能力妥协** |
| **新增的能力** | 现在可以**在个别位置**用适度模糊做强调（例如浮层/抽屉/岛的展开态），**但必须过评审**，不得变成"到处毛玻璃" |
| **未改的红线** | **材质仍然走 DWM，不是 CSS 模拟**——CSS 模糊只是**补充**，不能替代材质（材质是窗口级的，CSS 进不到那层） |

**一句话**：**S2 把一堵"墙"变成了一扇"可选的门"，但没有理由因此改变房间的布局。**

**⚠️ 复现时的一个坑（已修，但值得记）**：`Start-Process -ArgumentList` **不会给含空格的参数加引号**，
而本仓库路径含 `DeepSeek desktop`。于是 `--result` 的路径被**从空格处切断**，
尖刺把 JSON 写到别处、取图脚本一直等到超时——**看起来像"尖刺坏了"，实际是取图脚本的 bug**。
修法：所有含空格的参数**逐个加引号**，而不是靠"把路径挪到没空格的地方"。

## 6. ⚠️ S2 顺手暴露的一处**文档自相矛盾**（**未私自改，请裁决**）

**矛盾双方**：

| 出处 | 说法 |
|---|---|
| **S1 报告 §2 + UI 规格约束 0** | **`transparent(true)` 是材质能不能看见的前提**（少了它，`apply_mica` 返回 `Ok` 但毫无效果）|
| **M0 尖刺任务书 · S2 怎么验 · 第 4 步** | "这是我们要的方案：**窗口不透明**、材质走 DWM" |

**这两句不能同时成立**：材质走 DWM 就需要窗口透明；窗口不透明则材质看不见。

**我的判断（推断，非实测）**：任务书那句里的"窗口不透明"**大概本意是"页面背景不透明"**——
即"不要靠 CSS 半透明背景 + 模糊去伪造材质"，而不是"窗口层关掉 transparent"。
**佐证**：S2 这一步是在验 `backdrop-filter`，与"窗口要不要透明"是两件事；
而"窗口层 `transparent(true)`"已经被 S1 用像素证据定死为前提。

**但它也可能真的是另一个设计**（页面铺满不透明内容、材质只当窗口动画期的过渡），
**那就要重验**。**故此处只记录、不修改**，等确认后再回填任务书与规格。

**顺带修正一处措辞**：`goals` 里若引用"采用方案：窗口 DWM 材质 + 界面零模糊"，
应明确是 **`transparent(true)` 的窗口 + DWM 材质 + 页面零 CSS 模糊**，
**不是**"不透明窗口 + DWM 材质"。


| **§11.2 A / B1 / B2 三档** | **确定走 A 档**。B1 / B2 保留为**降级预案**（用户手动关闭材质、或高对比度模式时仍走 B2 的参数） |
| **§3.4 材质降级链** | 保持四级；实测确认 **`tabbed` 也可用**，故"Tabbed"作为第三级是有依据的 |
| **§2 硬约束** | **新增一条**：**窗口必须 `transparent(true)`**，否则材质不可见。这条不是"实现细节"，是**材质能不能存在的前提** |
