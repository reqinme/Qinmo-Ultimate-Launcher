## 1. 结论（先说结果）

| 问题 | **答案** |
|---|---|
| **无边框窗口能不能用 Mica** | ✅ **能**。`decorations: false` + `apply_mica` 返回 `Ok`，且**有可见效果** |
| **无边框窗口能不能用 Acrylic** | ✅ **能**（同上） |
| **第三种材质 Tabbed** | ✅ 也能，且观感与 Mica/Acrylic **可区分**（中心亮度 216.2 vs 242.5 / 144.4） |
| **材质是否随系统主题自动明暗** | ✅ 是。系统浅色时 `dark=None` 与 `dark=false` 结果**完全一致**（均为 242.5） |
| **有没有出现黑边/白边/渲染破裂** | ✅ 没有。所有色块边缘干净 |
| **走哪一档预案** | **A 档**（`docs/UI设计规格.md` §11.2）：岛贴顶居中、浮在自绘标题栏之上 |

**因此 §4 的布局可以按 A 档冻结**——这是 S1 要解开的那个阻塞。

## 2. ⚠️ 一个必须先说的前提：**光调 API 是不够的**

**第一次跑矩阵时，8 格全部 `apply_ok: true`，但像素分析显示它们与"完全不调材质"的对照组数值一模一样。**

第一轮的实测数据（**窗口内部中心区**）：

```
cell                     ctr_mean  ctr_sd
mica-bare-auto                255       0
none-bare-auto   ← 对照组      255       0      ← 与 Mica 完全相同
tabbed-bare-auto              255       0
```

**纯白 255、标准差 0，且 Mica 那格与对照组无差别** → 材质**没有任何可见效果**。

**根因**：**Tauri 的 WebView2 默认以不透明背景填充窗口**，把 DWM 材质整个盖住。
`apply_mica` 改的是**窗口**属性，而窗口被一层不透明内容填满 → 看不见。

**修法**：窗口构建时加 **`transparent(true)`**。

```rust
tauri::WebviewWindowBuilder::new(...)
    .decorations(decorations)
    .transparent(true)      // ← 少了这个，材质看得见才怪
    .build()?;
```

> ### 🔴 这条是本尖刺最重要的产出，比"材质能用"本身更重要
>
> 如果我只信 `apply_ok: true`，结论会是"材质可用"，而**实际现象是完全不可见**。
> **`apply_*` 返回 `Ok` 只说明 Windows 接受了这个调用，不说明它产生了任何可见效果。**
>
> 这与本项目已经栽过两次的失效模式**同源**：
> 用比真实条件宽松的证据（`HTTP 200`、带 flag 的截图、`apply_ok`）替代"看到结果"。
> **所以本次的判据被强制为：像素分析 + 看图，`apply_ok` 只作参考。**

## 3. 完整矩阵实测数据

**环境**：Windows 11 家庭版 中文版 **Build 26200** ｜ 系统主题**浅色**（`AppsUseLightTheme=1`）｜
透明效果**开**（`EnableTransparency=1`）｜ 显示缩放 **150%**（请求 1100×760 → 实得 1650×1140）｜
`tauri 2.12.1` · `window-vibrancy 0.8.1` · WebView2 154.0.4258.37

**像素统计口径**：屏幕截图中**窗口内部中心区**（水平 30–70%、垂直 60–80%）的亮度均值。
**对照组** `none-bare-auto` = **不调用任何材质 API**。

| 格子 | 材质 | 边框 | `dark` | `apply_ok` | **中心均值** | 与对照组差 | 判定 |
|---|---|---|---|---|---|---|---|
| `none-bare-auto` | **无（对照）** | 无 | — | — | **12.0** | — | 基线（窗口近乎全透） |
| `mica-bare-auto` | Mica | **无** | 未指定 | ✅ | **242.5** | **+230.5** | ✅ **生效** |
| `mica-deco-auto` | Mica | **有** | 未指定 | ✅ | **242.5** | +230.5 | ✅ 生效（与无边框同值） |
| `mica-bare-light` | Mica | 无 | `false` | ✅ | **242.5** | +230.5 | ✅ 生效（与 auto 同值，自洽） |
| `mica-bare-dark` | Mica | 无 | `true` | ✅ | **31.1** | +19.1 | ✅ **生效，且明显更暗** |
| `acrylic-bare-auto` | Acrylic | 无 | — | ✅ | **144.4** | +132.4 | ✅ 生效，整体偏暗（含着色） |
| `acrylic-deco-auto` | Acrylic | 有 | — | ✅ | **139.0** | +127.0 | ✅ 生效 |
| `tabbed-bare-auto` | Tabbed | 无 | 未指定 | ✅ | **216.2** | +204.2 | ✅ 生效，观感**可区分** |

**读法**：**只要某一格的中心均值显著偏离对照组 `12.0`，就说明材质产生了可见效果。**
六种材质配置给出**六个互不相同、且可复现**的数值 → 材质确实在起作用。

**边框维度（有/无）对材质没有影响**：Mica 两格都是 242.5，Acrylic 两格 144.4 / 139.0（差 5.4，属截图噪声量级）。
**这正是要紧的那一点**：`decorations: false` **不会**让材质失效。

**未定论的一项**（见 §5）：**窗口四周边缘是否透出桌面**。本次数据不足以判定，
因为截图把窗口外 12px 也框进来了，边缘读数混入了窗口外的像素。

# 附：S2 · 透明 × CSS `backdrop-filter`（**2026-10-01，U2**）

> **预判被推翻。** 任务书原文的假设是"Windows 上 WebView2 的窗口级透明**会破坏** CSS
> `backdrop-filter`（社区已记录的平台缺陷）"，**预判为否**。**实测：两者共存，且完全无差异。**

### A1. 结论

```
判定：✅ 通过（得到明确结论）
透明窗口 + CSS 模糊：✅ 可共存
采用方案：保持"窗口 DWM 材质 + 界面零 CSS 模糊"不变（但理由从"做不到"变成"不这么做"）
```

**三个事实，每个都有独立证据**：

| # | 事实 | 证据 |
|---|---|---|
| **1** | **不透明窗口里 `backdrop-filter` 正常模糊** | `opaque-blur` 对比度比值 **0.379**（判据：≤0.5 为"已模糊"） |
| **2** | **透明窗口里同样正常模糊** | `trans-blur` 比值 **0.379**（与上一格**完全相同**） |
| **3** | **透明与不透明，卡片区像素逐字节相同** | 独立复算：卡片内 / 对照内 / 两卡之间**平均差 0.00、最大差 0**（各 28500 采样点） |

**第 3 条最有力**：透明作为自变量**没有改变卡片内部的任何一个像素**。这比"两次测得同一个比值"更强——
比值相同可能是巧合，**逐像素为 0 不是**。

### A2. 矩阵与数据

（`--material none` 恒定：DWM 材质在**窗口**层合成，会整体染色，混进来就分不清"被 CSS 模糊"与"被 DWM 染色"。
材质另有单独两格。）

| 格 | 透明 | blur | 卡片对比度 | 对照对比度 | 比值 | 判定 |
|---|---|---|---|---|---|---|
| `opaque-noblur` | ✗ | ✗ | 5.93 | 5.29 | 1.122 | **NO-BLUR**（对照组自洽，§3） |
| `opaque-blur` | ✗ | ✓ | 4.33 | 11.42 | **0.379** | **BLURRED** |
| `trans-noblur` | ✓ | ✗ | 9.05 | 4.83 | 1.875 | **NO-BLUR**（对照组自洽，§3） |
| `trans-blur` | ✓ | ✓ | 4.33 | 11.42 | **0.379** | **BLURRED** |
| `opaque-mica` | ✗ | ✗ | 5.95 | 5.22 | 1.141 | NO-BLUR |
| `trans-mica` | ✓ | ✗ | 5.66 | 4.58 | 1.235 | NO-BLUR |

**度量**：测试页铺高频黑白棋盘格；`R = 亮度通道相邻像素差的均值`（`0.299R+0.587G+0.114B`）。
模糊必然把锐利边缘抹平 → 卡片内 `R` 显著低于对照卡内的 `R`。

**判据先于数据确定**（避免"看着数字凑结论"）：比值 ≥0.8 = 未模糊；≤0.5 = 已模糊；之间 = 不明确。

**截图证据**：`spikes/s1-material/out/shot-{opaque,trans}-{blur,noblur}.png`（+ `crop-*` 与 `result-*.json`）。
`shot-opaque-blur.png` **肉眼即可判读**：卡片内是一块平滑灰面，而同页其余部分是锐利棋盘格。

### A3. 两处必须记下的方法学教训（**都是我自己犯的**）

| # | 教训 | 具体经过 |
|---|---|---|
| **1** | **测试页自称的颜色，必须等于它真渲染出来的颜色** | 第一版测试页写的是"红/黑棋盘格"，实测渲染成**白/近黑**（R255 vs R16）。而我的度量**恰好用的红通道**——也就是说"红通道度量灰白图案"这件事**碰巧能用**，但它是一处**自己骗自己的巧合**。改法：**度量换成与颜色无关的亮度**，测试页**只声明它真的渲染出来的**黑白。 |
| **2** | **对照组必须与受测区在图案相位上可比** | 对照卡片与受测卡片水平相距 420 px，**棋盘格相位不同**，所以"对照的对比度"并非同相位的基准（这解释了为何 `opaque-noblur` 的比值是 1.122、`trans-noblur` 是 1.875——**两者都是"未模糊"，比值却差很远**）。**结论不受影响**（效应量大：0.379 vs ~1.1–1.9），但**比值只能当序数量级读，不能当精确基准**。要精确基准应改用"同心留白"布局，让对照与受测**同相位**。 |

> **第 2 条同时解释了 §3 表格里那个"对照组自洽"的标注**：
> 那两格的对照与受测都锐利（比值为 1 量级），说明该格**没有别的因素在模糊**，
> 因此"这一格没开 blur"这个前提**被验证过**，而不是假定。

### A4. 对设计的影响：**结论是"可以，但不做"**

**S2 通过的含义要读准**——它不是"我们该用 CSS 模糊"，而是：

> **零 CSS 模糊从"平台做不到"变成了"我们主动不这么做"。**

| 项 | 变化 |
|---|---|
| **UI 规格 §4 的三层材质** | **不变**（层次仍由不透明度阶梯 + 1px 描边 + 留白承担） |
| **理由** | **从"唯一可行"改为"主动选择"**——这更稳固，因为它是**设计判断**而非**能力妥协** |
| **新增的能力** | 现在可以**在个别位置**用适度模糊做强调（例如浮层/抽屉/岛的展开态），**但必须过评审**，不得变成"到处毛玻璃" |
| **未改的红线** | **材质仍然走 DWM，不是 CSS 模拟**——CSS 模糊只是**补充**，不能替代材质（材质是窗口级的，CSS 进不到那层） |

**一句话**：**S2 把一堵"墙"变成了一扇"可选的门"，但没有理由因此改变房间的布局。**

### A5. 复现

```powershell
cd spikes/s1-material
cargo build
powershell -File capture-s2-blur.ps1     # 6 格矩阵 + 裁剪
powershell -File analyze-s2-blur.ps1     # 亮度对比 -> 判定
```

**产物**：`out/s2-summary.json`、`out/s2-analysis.json`、`out/shot-*.png`、`out/crop-*.png`。

**⚠️ 复现时的一个坑（已修，但值得记）**：`Start-Process -ArgumentList` **不会给含空格的参数加引号**，
而本仓库路径含 `DeepSeek desktop`。于是 `--result` 的路径被**从空格处切断**，
尖刺把 JSON 写到别处、取图脚本一直等到超时——**看起来像"尖刺坏了"，实际是取图脚本的 bug**。
修法：所有含空格的参数**逐个加引号**，而不是靠"把路径挪到没空格的地方"。

### A6. ⚠️ S2 顺手暴露的一处**文档自相矛盾**（**未私自改，请裁决**）

**矛盾双方**：

| 出处 | 说法 |
|---|---|
| **S1 报告 §2 + UI 规格约束 0** | **`transparent(true)` 是材质能不能看见的前提**（少了它，`apply_mica` 返回 `Ok` 但毫无效果）|
| **M0 尖刺任务书 · S2 怎么验 · 第 4 步** | "这是我们要的方案：**窗口不透明**、材质走 DWM" |

**这两句不能同时成立**：材质走 DWM 就需要窗口透明；窗口不透明则材质看不见。

**我的判断（推断，非实测）**：任务书那句里的"窗口不透明"**大概本意是"页面背景不透明"**——
即"不要靠 CSS 半透明背景 + 模糊去伪造材质"，而不是"窗口层关掉 transparent"。
**佐证**：S2 这一步是在验 `backdrop-filter`，与"窗口要不要透明"是两件事；
而"窗口层 `transparent(true)`"已经被 S1 用像素证据定死为前提。

**但它也可能真的是另一个设计**（页面铺满不透明内容、材质只当窗口动画期的过渡），
**那就要重验**。**故此处只记录、不修改**，等确认后再回填任务书与规格。

**顺带修正一处措辞**：`goals` 里若引用"采用方案：窗口 DWM 材质 + 界面零模糊"，
应明确是 **`transparent(true)` 的窗口 + DWM 材质 + 页面零 CSS 模糊**，
**不是**"不透明窗口 + DWM 材质"。

# 附：S3 阶段 A · 裸窗口性能基线（**2026-10-01，U3**）

> ## 🔴 **结论：基线本身就把预算顶穿。按方案 §7 的预先授权，预算需按实测重定。**
>
> 方案 §7 原文已写明这条路：**"若基线本身就把预算顶穿，则预算需按实测重定——不许假装它成立。"**

### B1. 数字（30 次，release 构建，裸窗口）

**测量配置**：`--material none --no-page`（最小页面）、无边框、release 构建、150% 缩放、核显。

| 项 | 硬预算 | **实测中位数** | P95 | 判定 |
|---|---|---|---|---|
| 冷启动到可交互（WebView2 热） | ≤ 700 ms | **924.6 ms** | 950.4 ms | ❌ **超 32%** |
| 内存 — 主进程（可见） | ≤ 60 MB | **27.3 MB** | 27.4 MB | ✅ **仅用 45%** |
| 内存 — WebView2 进程树（可见） | ≤ 90 MB | **342.3 MB** | 346.9 MB | ❌ **超 3.8 倍** |
| 内存 — 合计（可见） | ≤ 150 MB | **369.6 MB** | 374.1 MB | ❌ **超 2.46 倍** |
| 内存 — 合计（隐藏后 5s） | ≤ 100 MB | **369.8 MB** | 374.4 MB | ❌ **超 3.7 倍**，**且不降** |
| 发行体积（不含运行时） | ≤ 25 MB | **8.28 MB** | — | ✅ **仅用 33%** |
| 滚动帧率（核显） | 不掉出 60 fps | **未测** | — | ⏸ 本阶段不做 |

**首次启动（WebView2 冷）**：`935.1 ms`。
**关键发现**：**它和热启动的中位数 924.6 ms 几乎相同**——
也就是说 WebView2 的"冷/热"差别在这台机器上**可以忽略**，
方案 §7 为它们分列两行是**多虑的**（但分列的**方法**是对的，见 §4 方法学）。

### B2. 罪魁祸首是 **WebView2 平台本身**，不是我们的代码

| 证据 | 数字 |
|---|---|
| WebView2 进程树占合计内存的比例 | **342.3 / 369.6 = 92.6%** |
| 我们主进程只用了预算的 | **45%**（27.3 MB / 60 MB） |

**尖刺是否给 Tauri 加了额外负担？** 已核实**没有**：
release 二进制里 `tao` 出现 48 次、`wry` 23 次、`tauri` 152 次，
而材质库只留下 **2 个符号名**（`apply_mica` / `apply_acrylic`）。

> **也就是说：这 342 MB 是"一个最小的 Tauri 2 应用"的代价，不是我们写多了什么。**

**因此**：**在 Tauri + WebView2 这条技术栈上，内存预算 150 MB 是做不到的**——
不是"优化不够"，而是**平台下限就在那里**。
（对照：Electron 应用常在 200–400 MB；369.6 MB 属该量级，**并不反常**。）

**唯一能真正压低内存的手段是"不用 WebView2"**，那等于换技术栈
（方案选型 ADR 已定 Tauri）。**这条路要动的是 ADR，不是优化项**，
所以本文**只报数、不提议换栈**。

### B3. 按实测重定的预算建议（**待用户确认，尚未回填方案**）

**方法**：**实测中位数 + 约 15% 余量**，理由是本尖刺是**最小实现**，

**保留一个已知做不到的数字，才是真正的不诚实。**

| # | 纪律 | 理由 |
|---|---|---|
| **1** | **内存不得随功能增长而显著增长**：新增 Provider / 工具模块必须**整体可移除**（方案已有此条），且**默认不预加载** | 既然平台已经吃掉 92.6%，**我们唯一能控的就是"别再加"** |

### B7. U13 补测：滚动帧率（**S3 第 5 项**）

> **结论：3/3 全部 PASS。p95 帧间隔 4.30 ms，最差 20.8 ms。**

| 采样 | 帧数 | mean | p50 | **p95** | worst | 判定 |
|---|---|---|---|---|---|---|
| 1 | 1195 | 4.18 ms | 4.2 | **4.3** | 16.7 ms | PASS |
| 2 | 1192 | 4.20 ms | 4.2 | **4.3** | 20.8 ms | PASS |
| 3 | 1194 | 4.19 ms | 4.2 | **4.3** | 12.5 ms | PASS |

**判据**：预算行是"不掉出 60 fps"。**决定性的数是 p95 帧间隔**，而不是均值 ——
均值好可以掩盖周期性卡顿，**而周期性卡顿恰好是用户看得见的东西**。
阈值取 17.0 ms（而非 16.67）以容忍测量抖动；**掉一帧会落在约 33 ms**，远高于两者，
所以**切点不承担结论**。

**测试内容**：240 项、每项含一张图片的长列表，**页面自己滚动、自己用 `requestAnimationFrame` 计时**。

| 设计决定 | 理由 |
|---|---|
| **页面自己滚** | 由外部脚本注入滚动事件会把输入注入的抖动混进帧时间，**而"噪声源就是测量工具"正是本项目反复踩到的坑** |
| **图片用内联 SVG data URI** | 不依赖网络：**尖刺不该因为网络慢而测出假的低帧率** |
| **> 250 ms 的间隔当暂停、不计入** | 首帧之后、或窗口未被合成时会出现长间隔，计进去会让 p95 失去意义 |

### ⚠️ 这个数的口径限制（必须写明，否则会被误读）

**中位数 4.2 ms ⇒ 约 239 fps**，说明**这台机器上 `requestAnimationFrame` 没有被刷新率节流**。
因此这个测量证明的是：

> **"我们的渲染管线在滚动时能跟上"**（p95 远低于 16.7 ms），
> **而不是"合成器最终不掉帧"** —— 后者由 DWM 在 60 Hz 上呈现决定，**本尖刺测不到**。

**要测"最终呈现的帧率"需要 CDP 的 `Page.startScreencast` 之类的合成器级观测**，
那属于 M4 的验收。**本项只对"管线跟不跟得上"负责，并如实这样标注。**

**worst 20.8 ms 说明确实出现过一次掉帧**，但它落在 p95 之外
（3 次采样共约 3580 帧中的 1 帧），**不构成"掉出 60 fps"**。

### 四个通道，前三个都不通（**这一段是本轮最值得留的经验**）

结果最初只发到 `console.log`；不通。改成窗口标题；仍不通。
**两次症状完全一样（"没有结果"），两次真因都是通道，不是测量。**

| # | 通道 | 结果 |
|---|---|---|
| 1 | `console.log` | ❌ **WebView2 的 console 不会到达父进程 stdout**（除非加日志开关，而**加开关就改变了被测对象**） |
| 2 | `document.title` | ❌ 尖刺里标题**始终没变**（同一个页面在 headless Edge 下却执行正常、DOM 里出现了结果 → 差异在 WebView2 这一侧） |
| 3 | 跨线程 `eval` 读全局 | ❌ **`WebviewWindow` 不是 `Sync`**，无法交给读线程 |
| 4 | **页面 `fetch` POST → Rust 协议处理器写文件** | ✅ **通了**，且不需要新依赖（Tauri 2 自带 `register_uri_scheme_protocol`） |

**并且这一轮我自己制造了两个假象**，都值得记下来：

| 假象 | 真因 |
|---|---|
| "尖刺卡住了"（每次报 TIMEOUT） | 我把 `$exited = $proc.WaitForExit(...)` 改成了 `$null = ...`，**而后面仍在判断 `$exited`** → 未定义变量让超时分支**每次都触发**，**进程其实早已正常退出** |
| "退出计时没生效" | 我调的是 `window.close()`，而 **Tauri 默认在所有窗口关闭后仍保持进程存活** → 改用 `app.exit(0)`，且**不再依赖页面**（页面脚本出错也不再留下僵尸进程） |

> **一条一般化教训**（与 S2 / S4 的那条同源）：
> **"没有结果"和"结果不对"是两类问题，而通道故障会长得像测量故障。**
> 所以：**① 让结果同时走多条便宜通道；② 让失败出声。**

# 附：S3 阶段 B · 材质增量（**2026-10-01，U4**）

> ## ✅ **结论：材质的增量基本为零。超预算**不是**材质造成的。**

### C1. 为什么是**三格**而不是两格

**S1 已确立：DWM 材质只有窗口透明时才可见。**
所以"材质开"**必然蕴含"透明开"**——只跑一格"透明 + 材质"，
量到的是**透明度与材质一起**的代价。

**这正是任务书 S3 反复警告的那种混淆**（它警告的是"材质与平台混成一个数"，
这里是同一种错误换了个变量）。故本阶段**必须三格**：

```
A   不透明 + 无材质   ← 阶段 A，30 次：369.6 MB / 924.6 ms
B1  透明   + 无材质   ← 隔离"透明本身"的代价
B2  透明   + 材质     ← B2 − B1 = 材质自己的代价
```

### C2. 数字

| 配置 | 合计（可见） | 主进程 | WebView2 | 冷启动（热） |
|---|---|---|---|---|
| **A** 不透明 + 无材质（n=29） | 369.6 MB | 27.3 MB | 342.3 MB | 924.6 ms |

| **B2** 透明 + 材质 mica（n=8） | 379.4 MB | 34.6 MB | 344.7 MB | 922.9 ms |

| **材质**（B2 − B1） | **+0.5 MB** | **±0.0 MB** | +0.5 MB | −1.2 ms |

**读法**：
- **材质几乎不花钱**（+0.5 MB、−1.2 ms，都在噪声范围内）
- **真正花钱的是"把窗口做成透明"**（+9.3 MB，且几乎全在我们自己进程里：
  27.3 → 34.6 MB，**+27%**，因为透明迫使 WebView2 走一条支持合成的渲染路径）

**刻意让两阶段共用同一个 harness**——若用两个脚本测，
**脚本之间的差异与材质的代价将无法区分**。

任务书 S3 结论槽最后一行问的是"若超预算，**优先砍的是**：□材质档位 □演示界面 □WebView2 特性 □其它"。

# 附：S4 · 分层骨架与"护栏能红"（**2026-10-01，U5**）

> ## ✅ **结论：三条护栏都能被故意踩红，且清理后重新变绿、树无残留。**

### D1. 任务书要求的不是"护栏能绿"，而是"**护栏能红**"

原文通过标准：

> **上述三条护栏都能故意踩红；CLI 与界面调用同一套内核逻辑。**

**"能绿"与"能红"是两件事。**
**一个永远绿的检查，和没有检查是一样的**——而且更坏，因为它**给人"已经守住了"的错觉**。

本项目此前已吃过一次同形状的亏：架构测试最初扫整份文件文本，
于是**注释里的产品名也触发**（假红），而**真正该拦的依赖问题被文本淹没**。
**假红会被当成噪声忽略，接着真红也被忽略。**

### D2. 做法：把"判定"从"断言"里拆出来

每个护栏都是一个**纯函数**：`输入 → 违规清单`。于是可以对它做两件独立的事：

| # | 断言 | 证明的是 |
|---|---|---|
| 1 | 对**干净输入**清单为空 | 护栏**不误报** |
| 2 | 对**脏输入**清单非空 | 护栏**能报** |

**第 2 条就是"踩红"，而它不需要把仓库改坏**——
因为脏输入是**构造出来的**，不是**注入到真实文件里的**。

> **这是本节最重要的设计决定**：若真往 `Cargo.toml` 里写个 `reqwest` 来踩，
> `cargo test` 就再也跑不起来，得到的"证据"是**一次性的、不可回归的**。
> 用构造输入踩，则这条证明**每次 CI 都会重跑一遍**。

### D3. 但只用构造输入还不够——所以另有一个"原位金丝雀"

构造输入证明的是**判定函数**对。它**不能**证明：
配置真的生效了、文件真的被扫描了、lint 真的跑到那个目录了。

所以另做 `tools/s4-guardrail-canary.ps1`，做**原位**踩红，六步：

```
1. 对要碰的每个产物做哈希快照（或"确认不存在"）
2. 造出必须被拒的东西
3. 跑真实检查，把失败输出存为证据
4. 删掉金丝雀
5. 重跑同一检查，要求变绿
6. 校验每个产物与快照一致
```

**第 5、6 步是通常被跳过的两步**：
没有第 5 步，你分不清"**护栏拦住了**"与"**我把构建弄坏了**"；
没有第 6 步，你会**留下金丝雀文件**，下一个人看到红的护栏而不知道原因。

### D4. 实测结果

| 护栏 | 金丝雀 | 命令 | 期望 | **实测** |
|---|---|---|---|---|
| **A** 内核不许依赖 IO/界面框架 | 往 `crates/qul-core/Cargo.toml` 追加 `reqwest` | `cargo test -p qul-core --test architecture` | 失败 | **exit=101 ✅ TRIPPED** |
| **B** 组件不许直接 `fetch` | `web/src/__canary__.ts` 调 `fetch()` | `pnpm run lint` | 失败 | **exit=1 ✅ TRIPPED** |
| **C** 组件不许直接 import IPC | 同一文件 `import { invoke } from "@tauri-apps/api/core"` | `pnpm run lint` | 失败 | **exit=1 ✅ TRIPPED** |
| 恢复 | — | `sha256(Cargo.toml) == 快照` | 逐字节相同 | **✅ 一致** |
| 清理后 | — | 重跑两条检查 | 变绿 | **✅ 都 exit=0** |
| 树无残留 | — | 校验哈希 + 文件不存在 | 通过 | **✅ 通过** |

**产物**：`docs/_artifacts/S4/s4-guardrail-canary.json`（摘要）+
`s4-guardrail-canary.log`（**完整失败输出，这才是证据本体**）。

**并且它进了 CI**（新增 `canary` 作业），所以这条纪律**每次提交都会被重新验证**。

### D5. 三条护栏分别落在哪一层

**它们拦的是同一类越界（"不该碰外部世界的地方碰了"），在两层各拦一次**：

| 层 | 不许碰什么 | 手段 |
|---|---|---|
| **`qul-core`** | 文件系统、网络、进程、界面框架 | Rust 架构测试（读 `Cargo.toml` 依赖名 + 扫源码路径） |
| **`qul-app`** | 界面框架、`infra`、`provider` | Rust 分层测试 |
| **`web/src`（`api/` 之外）** | `fetch`、`invoke`、`@tauri-apps/api/core` | ESLint |

**`web/src/api/` 是唯一被允许碰外部世界的目录**：
它拿豁免不是特权，而是**它就是那道边界**。

### D6. CLI 与界面复用同一套逻辑（任务书第 4 条）

新增两个 crate：

| crate | 角色 |
|---|---|
| **`qul-app`** | **编排层**：界面与命令行共用的那一份逻辑的落点 |
| **`qul-cli`** | 命令行入口（bin 名 `qul`） |

**共用的那一次调用**是 `AppService::capability_overview()`：

```
界面侧：  Tauri 命令 capability_overview  ->  AppService::capability_overview()
命令行侧：qul（CLI）                     ->  AppService::capability_overview()
```

**CLI 实跑输出**（这就是"复用"的证据）：

```
秦墨 · 能力概览
可用 1 项 / 不可用 1 项

可用：
  + launch

不可用：
  - mods   （沙箱形态下内容包不可管理）
```

**注意最后一行**：**禁用项必须把原因打出来**。
只说"不可用"而不说为什么，是方案 §5.7 明确禁止的（"结论必须带可执行建议"）。
**CLI 是最需要正确输出这一段的地方**——用户看命令行就是为了知道为什么不行。

### D7. 一处还没做的（**不许当成已达标**）

任务书第 5 条要求"**MockProvider 能走通调用链**"（M1 出口条件依赖它）。

**故本阶段只做"链路的骨架"，不做 provider 抽象。**
**M1 开工第一件事就是把 MockProvider 补上**，并在此处回填结论。

### D9. 一个值得记的操作细节

**金丝雀脚本第一次跑，报"恢复不是逐字节相同"，树不干净。**

查下去发现：**不是这次恢复错了，而是上一次被中断的运行留下了改动**——
脚本在第一次运行时因为 `cargo` 不在 `PATH` 上而**中途抛错退出**，
`finally` 里的清理没能把它改过的 `Cargo.toml` 还原（那次 run 的恢复步骤根本没执行到）。

**两条都修了**：
1. **脚本自己解析 cargo 路径**（查 `PATH`，再查 `%USERPROFILE%\.cargo\bin`），
   而不是假设调用者已经配好环境——**一个因为环境而失败的金丝雀教不了任何东西**。
2. 重跑后一切正常。

**但更重要的是这次的排查过程本身**：
"恢复不逐字节相同"这个**告警是对的**，而它指向的是**上一次的残留**而不是**这一次的 bug**。
**如果我当时把那条 FAIL 解释成"脚本没问题"，就会把一个真实的清理漏洞留在 CI 里。**

### D10. 顺带产出：`Overview` 进了内核

链路要有个"计算结果"，选的是**能力概览**。它被放在 `qul-core` 而不是界面里，理由是：

> **"哪些能力可用、不可用的原因是什么"是**规则**，不是排版。**
> 这个判断与窗口、与渲染无关，所以它属于内核；界面只负责把返回的结构画出来。

`Capabilities::overview()` 返回**已排序的普通数据**（`Overview` / `DisabledItem`），
两个类型都进了 `qul-core` 的公开导出——**对外契约只该有一份**，
所以 `qul-app/tests/layering.rs` 里有一条断言：**编排层不许新增公开结构体**
（它现在只暴露 `AppService`）。
