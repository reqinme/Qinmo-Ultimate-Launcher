# S5 · 下载吞吐基线（**本轮只做可自测的那部分**）

> **执行**：`bench-s5-throughput.ps1` · 2026-10-01 · M0 尖刺 S5 的第 1 项
> **产物**：`s5-throughput.json` · `asset.json`（真实可下资产，从官方清单取）
>
> ⚠️ **本文件只覆盖 S5 的第 1 项（吞吐基线）。**
> 第 2、3 项（"能进游戏"耗时 / 全量安装耗时）**需要真实版本清单与大量下载，本轮未做**；
> 第 4、5、6、7 项（续传 / 换源 / 长时间界面 / 校验开销）**同样未做**。
> **不许把本文当成 S5 通过。**

## 1. 结论（吞吐部分）

| 源 | conc 1 | conc 4 | conc 8 | conc 16 |
|---|---|---|---|---|
| **官方** `piston-data.mojang.com` | 0.382 | 0.623 | **0.776** | **0.832** MB/s |
| **BMCLAPI** | 0.000 | 0.021 | 0.124 | 0.000 MB/s |

**官方源的错误数在两轮所有并发下恒为 0；BMCLAPI 的失败数恰好等于并发数**
（conc 16 → 16 个失败）。

### 三条结论

| # | 结论 | 依据 |
|---|---|---|
| **1** | **基线大体成立**：官方源单连接 0.382 / 0.282 MB/s，与任务书 §0 记的 0.28 MB/s 同量级 | 两轮 1 并发：0.481 与 0.282 |
| **2** | **并发在这条链路上确实有收益**——与任务书"跨境受限下常无收益"的**预判相反** | 官方源 0.382 → 0.832（**×2.18**），且错误数恒为 0 |
| **3** | **本机的 BMCLAPI 不可用**，不是"慢"而是"经常失败" | 8 个格子中 6 个有失败；两轮里一次 conc 1 直接 90 秒超时 |

### 由此得出的**默认源优先级**（S5 要求"产出数据依据"）

> **官方优先。镜像不是"更快的那个"，在本机它是"更常失败的那个"。**

**并且要写明它的反面**：任务书 §0 记着"第一轮项目实测官方比 bmclapi 快约 8 倍"，
那是在**另一条网络路径**下的结论。**本条结论只在当前网络下成立，必须带环境一起引用。**

## 2. 并发建议

**官方源：conc 8–16 均可**（0.776 / 0.832），两轮里 8 与 16 各赢一次 → **差异在噪声内**。

**建议取 8**：16 只高 7%，而并发越高对端与本地资源的压力越大，
**在没有更多数据前取保守值**。（这正是任务书那句"要用数据决定，不要凭直觉"的用法：
数据说"8 与 16 没差别"，于是选更保守的那个。）

**镜像源：并发毫无意义**（0.000–0.124 且高失败率）。若真的启用镜像，
应按"**单连接 + 长超时 + 快速失败后切回官方**"处理，**不要给它开并发**。

## 3. 一处必须记下的方法学问题：**时间波动很大**

同一格（官方 conc 1）两轮分别是 **0.481** 与 **0.282 MB/s**（差 1.7 倍）；
conc 16 是 1.182 与 0.482（差 2.5 倍）。

**所以这个矩阵只能当"量级与趋势"读，不能当精确数字用。**
任务书自己也算过这点：剩余时间估算原定"误差 ≤30%"不现实，**因为实测波动本身就有约 27%**。
**本文的观察与那条修正一致。**

**未做的**：本文没有取更多轮次去压小这个波动。理由与 S3 阶段 B 相同——
要看的是**源之间的差**（官方 0.83 vs 镜像 0.12，差 7 倍），
而那个差**远大于**格内波动；继续加轮次只会拉长时间而不改变结论。

## 4. 方法：用**真实**资产，而不是猜一个 URL

两个"官方源"根（`libraries.minecraft.net` / `resources.download.minecraft.net`）是 **404**：
它们是**存储桶根，不是可浏览的索引**。

所以 `find-download-asset.ps1` 走官方元数据链：

```
version_manifest_v2.json  ->  <version>.json  ->  downloads.client.url
```

并同时构造 BMCLAPI 的镜像形式，**让两边下的是同一份字节**。

**副产品**：这条链**正是 M1/M2 要用的东西**，所以它不是一次性脚本。

### 用 HTTP Range 而不是整文件

真实的客户端 jar 39.6 MB，而这条链路可能很慢；2×4 矩阵下整文件会跑几小时。
于是每格只拉固定预算（默认 6 MB，本轮 4 MB）并报 MB/s。
**预算写在输出里**，免得有人把它当成整文件安装耗时。

## 5. ⚠️ 一个必须上报的发现：**官方最新正式版是 `26.3`，不是 1.21.x**

从官方清单读到：

```
version 26.3  (release)
version_url https://piston-meta.mojang.com/v1/packages/4fe1aa.../26.3.json
client.jar 41,483,720 字节
```

**我们的文档里到处假设"最新正式版"是 1.21.x 系列**（例如 S3 的滚动测试页写着 `1.20.1`，
S6 的场景用了 `1.21.4`，方案与规格里也大量出现 1.21.x）。

**这意味着**：**版本号不能硬编码，也不能假定"1.2x"这个形态**。
本项目的 VERSION 解析（`GameVersion::parse`）已经能处理任意 `主.次.修订`，
所以**代码侧没有假设**；**但文档里的示例版本号会过期**，
而**这正是 S3 那条"界面稿只放事实性占位"的纪律要防的事**——
版本号是事实，而**写进文档的事实会腐烂**。

**处置**：本文件只记录该事实，**不改其它文档里的示例版本号**——
因为那些示例在写作时是事实，**改动历史记述等于篡改**（与流程 C 审计里 §13 那 10 条的判据一致）。
**M1 起，任何"最新版本"都必须来自清单，不许来自文档。**
