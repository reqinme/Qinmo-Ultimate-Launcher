# 附：S4 · 分层骨架与"护栏能红"（**2026-10-01，U5**）

> ## ✅ **结论：三条护栏都能被故意踩红，且清理后重新变绿、树无残留。**

## D1. 任务书要求的不是"护栏能绿"，而是"**护栏能红**"

原文通过标准：

> **上述三条护栏都能故意踩红；CLI 与界面调用同一套内核逻辑。**

**"能绿"与"能红"是两件事。**
**一个永远绿的检查，和没有检查是一样的**——而且更坏，因为它**给人"已经守住了"的错觉**。

本项目此前已吃过一次同形状的亏：架构测试最初扫整份文件文本，
于是**注释里的产品名也触发**（假红），而**真正该拦的依赖问题被文本淹没**。
**假红会被当成噪声忽略，接着真红也被忽略。**

## D2. 做法：把"判定"从"断言"里拆出来

每个护栏都是一个**纯函数**：`输入 → 违规清单`。于是可以对它做两件独立的事：

| # | 断言 | 证明的是 |
|---|---|---|
| 1 | 对**干净输入**清单为空 | 护栏**不误报** |
| 2 | 对**脏输入**清单非空 | 护栏**能报** |

**第 2 条就是"踩红"，而它不需要把仓库改坏**——
因为脏输入是**构造出来的**，不是**注入到真实文件里的**。

> **这是本节最重要的设计决定**：若真往 `Cargo.toml` 里写个 `reqwest` 来踩，
> `cargo test` 就再也跑不起来，得到的"证据"是**一次性的、不可回归的**。
> 用构造输入踩，则这条证明**每次 CI 都会重跑一遍**。

## D3. 但只用构造输入还不够——所以另有一个"原位金丝雀"

构造输入证明的是**判定函数**对。它**不能**证明：
配置真的生效了、文件真的被扫描了、lint 真的跑到那个目录了。

所以另做 `tools/s4-guardrail-canary.ps1`，做**原位**踩红，六步：

```
1. 对要碰的每个产物做哈希快照（或"确认不存在"）
2. 造出必须被拒的东西
3. 跑真实检查，把失败输出存为证据
4. 删掉金丝雀
5. 重跑同一检查，要求变绿
6. 校验每个产物与快照一致
```

**第 5、6 步是通常被跳过的两步**：
没有第 5 步，你分不清"**护栏拦住了**"与"**我把构建弄坏了**"；
没有第 6 步，你会**留下金丝雀文件**，下一个人看到红的护栏而不知道原因。

## D4. 实测结果

| 护栏 | 金丝雀 | 命令 | 期望 | **实测** |
|---|---|---|---|---|
| **A** 内核不许依赖 IO/界面框架 | 往 `crates/qul-core/Cargo.toml` 追加 `reqwest` | `cargo test -p qul-core --test architecture` | 失败 | **exit=101 ✅ TRIPPED** |
| **B** 组件不许直接 `fetch` | `web/src/__canary__.ts` 调 `fetch()` | `pnpm run lint` | 失败 | **exit=1 ✅ TRIPPED** |
| **C** 组件不许直接 import IPC | 同一文件 `import { invoke } from "@tauri-apps/api/core"` | `pnpm run lint` | 失败 | **exit=1 ✅ TRIPPED** |
| 恢复 | — | `sha256(Cargo.toml) == 快照` | 逐字节相同 | **✅ 一致** |
| 清理后 | — | 重跑两条检查 | 变绿 | **✅ 都 exit=0** |
| 树无残留 | — | 校验哈希 + 文件不存在 | 通过 | **✅ 通过** |

**产物**：`docs/_artifacts/S4/s4-guardrail-canary.json`（摘要）+
`s4-guardrail-canary.log`（**完整失败输出，这才是证据本体**）。

**并且它进了 CI**（新增 `canary` 作业），所以这条纪律**每次提交都会被重新验证**。

## D5. 三条护栏分别落在哪一层

**它们拦的是同一类越界（"不该碰外部世界的地方碰了"），在两层各拦一次**：

| 层 | 不许碰什么 | 手段 |
|---|---|---|
| **`qul-core`** | 文件系统、网络、进程、界面框架 | Rust 架构测试（读 `Cargo.toml` 依赖名 + 扫源码路径） |
| **`qul-app`** | 界面框架、`infra`、`provider` | Rust 分层测试 |
| **`web/src`（`api/` 之外）** | `fetch`、`invoke`、`@tauri-apps/api/core` | ESLint |

**`web/src/api/` 是唯一被允许碰外部世界的目录**：
它拿豁免不是特权，而是**它就是那道边界**。

## D6. CLI 与界面复用同一套逻辑（任务书第 4 条）

新增两个 crate：

| crate | 角色 |
|---|---|
| **`qul-app`** | **编排层**：界面与命令行共用的那一份逻辑的落点 |
| **`qul-cli`** | 命令行入口（bin 名 `qul`） |

**共用的那一次调用**是 `AppService::capability_overview()`：

```
界面侧：  Tauri 命令 capability_overview  ->  AppService::capability_overview()
命令行侧：qul（CLI）                     ->  AppService::capability_overview()
```

**CLI 实跑输出**（这就是"复用"的证据）：

```
秦墨 · 能力概览
可用 1 项 / 不可用 1 项

可用：
  + launch

不可用：
  - mods   （沙箱形态下内容包不可管理）
```

**注意最后一行**：**禁用项必须把原因打出来**。
只说"不可用"而不说为什么，是方案 §5.7 明确禁止的（"结论必须带可执行建议"）。
**CLI 是最需要正确输出这一段的地方**——用户看命令行就是为了知道为什么不行。

## D7. 一处还没做的（**不许当成已达标**）

任务书第 5 条要求"**MockProvider 能走通调用链**"（M1 出口条件依赖它）。

**本阶段没做**，理由：**`provider` 这个概念要到 M1 才出现**——
现在造一个 `MockProvider` 就得先定下 provider 的 trait，
而**那个 trait 的形状属于 M1 的设计**（`discover()` 的签名、错误类型、异步与否）。
提前定它，等于**用一个 M0 的猜测去约束 M1 的设计**。

**故本阶段只做"链路的骨架"，不做 provider 抽象。**
**M1 开工第一件事就是把 MockProvider 补上**，并在此处回填结论。

## D8. 复现

```powershell
# 判定函数的"能红"证明（构造输入，CI 每次跑）
cargo test -p qul-core --test guardrails
cargo test -p qul-app --test layering

# 原位金丝雀（真改文件、真跑检查、真清理）
powershell -File tools/s4-guardrail-canary.ps1

# CLI 复用证据
cargo run -q -p qul-cli
```

## D9. 一个值得记的操作细节

**金丝雀脚本第一次跑，报"恢复不是逐字节相同"，树不干净。**

查下去发现：**不是这次恢复错了，而是上一次被中断的运行留下了改动**——
脚本在第一次运行时因为 `cargo` 不在 `PATH` 上而**中途抛错退出**，
`finally` 里的清理没能把它改过的 `Cargo.toml` 还原（那次 run 的恢复步骤根本没执行到）。

**两条都修了**：
1. **脚本自己解析 cargo 路径**（查 `PATH`，再查 `%USERPROFILE%\.cargo\bin`），
   而不是假设调用者已经配好环境——**一个因为环境而失败的金丝雀教不了任何东西**。
2. 重跑后一切正常。

**但更重要的是这次的排查过程本身**：
"恢复不逐字节相同"这个**告警是对的**，而它指向的是**上一次的残留**而不是**这一次的 bug**。
**如果我当时把那条 FAIL 解释成"脚本没问题"，就会把一个真实的清理漏洞留在 CI 里。**

## D10. 顺带产出：`Overview` 进了内核

链路要有个"计算结果"，选的是**能力概览**。它被放在 `qul-core` 而不是界面里，理由是：

> **"哪些能力可用、不可用的原因是什么"是**规则**，不是排版。**
> 这个判断与窗口、与渲染无关，所以它属于内核；界面只负责把返回的结构画出来。

`Capabilities::overview()` 返回**已排序的普通数据**（`Overview` / `DisabledItem`），
两个类型都进了 `qul-core` 的公开导出——**对外契约只该有一份**，
所以 `qul-app/tests/layering.rs` 里有一条断言：**编排层不许新增公开结构体**
（它现在只暴露 `AppService`）。
