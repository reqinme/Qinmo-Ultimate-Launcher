> 纪律：**本次尖刺不产生任何产品代码**，只验证假设、记录观察、给出结论与处置建议。
> 环境：Windows，.NET SDK 10.0.401，目标框架 net48，C# + WPF；无 Visual Studio / msbuild，全部经 `dotnet` CLI。
> 结论去向：汇入 P7 软预算与依赖选择；涉及 OAuth 的结论汇入 P5 前置条件门禁；涉及路径与凭据的结论汇入 P2/P4/P5 安全基线。

## S1 · 单文件资源合并

**假设**：把依赖合并为单文件后，首启不应落地临时目录，也不应额外拖慢启动。

**观察**

| 项 | 结果 |
|---|---|
| Release 发布产物 | `QinmoUltimateLauncher.exe` **7,168 字节**；另有 `QinmoUltimateLauncher.exe.config`（174 字节）与 `.pdb` |
| Debug 构建产物 | `QinmoUltimateLauncher.exe` 7,680 字节 |
| 第三方运行时依赖 | **0 个**（`dotnet new` 生成的 WPF 模板 + net48 本体） |
| 是否出现临时目录解压行为 | 无 —— 因为不存在需要加载的附属程序集 |

**结论：可行。** 当前形态下"单文件"不是一个需要合并技术去达成的目标，而是零依赖架构的自然结果。net48 的 `dotnet publish` 不支持 `PublishSingleFile`，因此**单文件本质上等价于"把依赖数量压到 0"**。

**处置建议**

1. 把"依赖数量"当作一等架构指标：每引入一个 NuGet 包，都必须先回答"能否用 net48 本体替代"。这与文档第 7 节的依赖策略一致。
2. 只有当确实无法避免第三方包时才评估合并方案。届时优先选择**内存加载型**方案，明确排除任何"解压到临时目录再加载"的方案——后者直接违反首启约束。
3. `.exe.config` 在 net48 下无法内嵌，属于该框架的固有产物。"单文件"的验收口径应表述为**"单 exe + 一纸 .config"**，这是 PCL2 同路线下的客观形态。P7 需在预算报告中明确这一口径，避免验收争议。
4. P7 需重新执行本尖刺（届时依赖清单可能已变化）。

## S2 · 冷启动基线

**假设**：目标形态下冷启动能否接近 ≤ 800 ms。

**方法**：Release 产物连续启动 5 次，测量"进程创建 → 主窗口句柄可用"，每次测量前结束上一实例并静置 400 ms。

**观察**

| 次序 | 耗时 |
|---|---|
| 1（冷） | 440 ms |
| 2 | 251 ms |
| 3 | 236 ms |
| 4 | 251 ms |
| 5 | 236 ms |

**结论：可行，余量充足。** 稳态约 **236–251 ms**，距 ≤ 800 ms 软预算有约 3 倍余量；首次运行明显偏慢（+190 ms），与文件系统缓存冷启动一致。

**处置建议**

1. 软预算数值维持文档原值，不因骨架表现优异而下调——骨架尚未包含配置读取、缓存扫描、版本元数据装载、UI 数据绑定等真实成本。
2. **首次运行与稳态运行的差值必须分别验收**：文档中"首启与二次启动差异 ≤ 200 ms"这一指标在骨架阶段已达 **204 ms**（440 − 236），处于临界。P7 需重点关注首启路径，禁止在启动热路径上引入同步网络请求或全量缓存扫描。
3. 把 `elapsedMs` 日志字段（见《P0 地基规范》§5.1）作为常态回归手段，避免 P7 才发现退化。

## S3 · 手写 JSON 映射是否足够稳定

**假设**：不用第三方 JSON 库，用手写映射能稳定处理跨年代版本元数据。

**观察**：本阶段无法完成端到端验证——版本元数据结构需要在 P1 采集真实样本。已确认的边界条件：

| 边界 | 说明 |
|---|---|
| 字段缺失 | 旧版本缺少 `javaVersion`、`downloads`、`arguments` 等字段 |
| 新旧参数写法 | 同时存在 `minecraftArguments`（旧）与 `arguments`（新） |
| 多态字段 | `arguments` 的条目可能是字符串或对象（带 `rules`） |
| 嵌套与继承 | `inheritsFrom` 合成后的库与参数需要去重与顺序保持 |
| 未知字段 | 未来版本可能新增字段，解析器不得崩溃 |

**结论：有条件可行。** 手写映射在**结构稳定、可忽略未知字段**这个前提下是可行且体积最优的选择；"稳定"不是靠假设成立，而是靠 P1 的黄金样本回归来证实。

**处置建议**

1. P1 必须为四个代表性版本（1.7.10 / 1.12.2 / 1.16.5 / 最新正式版）建立**黄金样本回归**：样本落盘，断言解析结果的库列表、主类、参数、Java 主版本要求。
2. 解析器采取"宽松读、严格用"：未知字段忽略（`QUL-META-0004` 仅记日志），但关键字段缺失即拒绝该版本（`QUL-META-0002`）。
3. 若 P1 中手写映射的维护成本显著超出预期，允许在 P1 结束时重新评估；**不得在 P1 中途引入 JSON 库**，以免同时改变两个变量。

## S4 · 微软 OAuth 可行性

**假设**：回调 URI 与设备码两条路径在本工程形态下是否均可落地；应用注册前置条件是否可满足。

**观察（分析性，未做端到端验证）**

| 路径 | 可行性判断 | 主要风险 |
|---|---|---|
| 设备码流程 | **风险最低** | 用户需在浏览器输入代码；无本地监听端口，无防火墙问题，无 URI 注册冲突 |
| 回调 URI（本地回环监听） | 可行但更脆弱 | 需要占用本地端口（可能被占用）、可能被本机安全软件拦、需要与应用注册中的重定向 URI 精确匹配 |

**结论：有条件可行，且技术不是阻塞点。** 真正的阻塞点是**前置条件**：OAuth 应用注册、`client_id` 与权限范围、回调 URI 或设备码流程的登记、以及第三方启动器相关条款限制。本机无法在尖刺阶段完成任何一项。

**处置建议**

1. 决策维持：**P5 的 C1–C4 前置条件未全部满足，微软正版登录不得进入开发完成态**（`QUL-AUTH-0005`）。
2. 实现顺序建议：**先设备码流程，后回调流程**。设备码不依赖本地端口，与"绿色版、无安装、无服务"的产品形态更契合，也更容易在无管理员权限环境下工作。
3. 令牌存储方案已在 S6 验证可用，不构成风险。
4. 本项结论汇入 P5 前置条件门禁，需产品负责人对 C1–C4 逐项确认。

## S5 · Java 探测与版本解析

**假设**：常见安装形态与旧/新版本号是否都能被覆盖。

**观察**：本机 Java 布局（直接作为 P3 的真实测试床）：

| 来源 | 路径 | 备注 |
|---|---|---|
| PATH | `C:\Program Files\Zulu\zulu-25\bin\java.exe` | Azul Zulu 25 |
| 厂商目录 | `C:\Program Files\Java\jdk-11.0.32` | 新式命名 |
| 厂商目录 | `C:\Program Files\Java\jdk-17.0.20` | 新式命名 |
| 厂商目录 | `C:\Program Files\Java\jdk-21.0.12.1` | 新式命名 + 四段版本号 |
| 厂商目录 | `C:\Program Files\Java\jdk-25.0.4.1` | 新式命名 + 四段版本号 |
| 厂商目录 | `C:\Program Files\Java\jdk1.7.0_80` | **旧式命名**（1.7） |
| 厂商目录 | `C:\Program Files\Java\jre1.8.0_503` | **旧式命名 + JRE（非 JDK）** |
| 厂商目录 | `C:\Program Files\Java\latest` | **符号/转发目录，非真实安装** |
| 官方启动器运行时 | `%APPDATA%\.minecraft\runtime` | **本机不存在**（未安装官方启动器） |

**结论：可行，盲区已定位。**

| 盲区 | 处置 |
|---|---|
| 旧式版本号（`1.7.0_80` / `1.8.0_503`） | 必须按"`1.x` → 主版本 x"规则归一，否则 1.8 会被误判为 1 |
| 四段版本号（`25.0.4.1`） | 版本解析取前三段即可判定主版本，不得因段数不同而失败 |
| 转发/别名目录（`latest`） | 必须以**实际执行 `-version` 的结果**为准，不得仅凭目录名判断 |
| JRE 存在但缺 JDK | MVP 只要求能运行游戏（JRE 即可），不要求编译；不得因"不是 JDK"而拒绝 |
| 非标准厂商目录 | 探测列表必须包含 Azul / Adoptium / Microsoft / Oracle 等常见位置，而非只有 Oracle 默认路径 |
| `.minecraft\runtime` 缺失 | 探测结果可能为空，必须能优雅降级到 PATH 与厂商目录 |

**处置建议**：P3 的探测顺序定为 **用户手动指定 → `javaVersion` 要求匹配 → PATH → 厂商目录 → `.minecraft\runtime`**；所有候选一律以实际执行结果作为版本与架构依据，目录名仅用于快速筛选。

## S6 · DPAPI 凭据保护可用性

**假设**：系统凭据保护可用于令牌加密存储。

**方法**：`CurrentUser` 作用域下对标量做 Protect → Unprotect 往返。

**观察**：往返成功（`roundtrip ok = True`）；密文为当前用户绑定，其他用户账户无法解密。

**结论：可行。**

**处置建议**

1. P5 令牌存储采用 `DataProtectionScope.CurrentUser`，密文落在 `data/secrets/`，明文永不落盘。
2. 作用域限定的副作用是**便携性受限**：把 `data/` 目录整体拷到另一台机器或另一个 Windows 账户后，密文不可解密。这属于预期行为，不是缺陷。
3. 必须实现优雅降级：解密失败 → 清除该密文 → 以"需要重新登录"（`QUL-AUTH-0002`）提示用户，**不得崩溃，也不得静默使用空身份**。
4. 本机未测试漫游配置与域账户场景，P5 需在验收中补一条记录。

## S7 · 中文 / 空格 / 超长路径

**假设**：关键路径（游戏目录、缓存、natives、Java 路径）在中文、空格、超长场景下可正常处理。

**观察**

| 项 | 结果 |
|---|---|
| 中文 + 空格目录创建与访问 | 通过 |
| 本机 `LongPathsEnabled` | `1`（已启用） |

**结论：可行，但长路径必须自带处置。** 中文与空格路径本身不构成风险；真正的风险是**本机已启用长路径支持，因此测试环境会掩盖未启用机器上的失败**。

**处置建议**

1. **不得依赖 `LongPathsEnabled`**。P2/P4 的所有路径拼接必须走统一封装，超长时给出 `QUL-IO-0003` 并给出可执行的缩短建议。
2. 所有路径处理统一使用原生路径 API，禁止字符串拼接路径。
3. P7 验收必须在**未启用长路径**的配置下补一次实测记录，否则"兼容"项验收不成立。
4. natives 解压目录名保持短且固定（避免版本号 + 用户名 + 深目录叠加出超长路径）。

## S8 · 杀软误报初判

**假设**：目标形态是否触发常见误报。

**观察（静态初判，未做多引擎扫描）**

| 触发误报的高危行为 | 当前形态 |
|---|---|
| 自解压到临时目录 | 无（零依赖，无需解压自身） |
| 自我替换 / 自我修改 | 无 |
| 注入其他进程 | 无 |
| 启动时联网 | 无（骨架无任何网络行为） |
| 隐藏窗口 / 无界面运行 | 无（标准 WPF 窗口） |
| 未签名可执行文件 | **是** —— 当前未签名 |

**结论：初判低风险。** 唯一确定的风险项是**缺少代码签名**，而这是误报的主要来源。P7.0 的三方案中，"自替换"会额外引入自我覆盖行为，属于误报高危模式。

**处置建议**

1. 本结论作为 **P7.0 更新策略选型的输入**：在杀软误报维度上，自替换方案的初始风险高于引导器方案。
2. P7 必须做多引擎复检（不是单机杀软），并把结果写入发布报告。
3. 代码签名建议提前到 P7.0 一并评估——如果决定签名，自替换方案的可行性会明显上升。
4. 禁止在实现中引入任何"关闭自身校验""写入启动项""静默自我更新"等会显著抬高误报率的行为。
