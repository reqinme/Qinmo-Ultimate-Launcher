# 下载引擎设计规格（按域选型的第一个产物）

> **版本**：与方案 `v3.13` 对应 ｜ **状态**：设计已定，待 M1 实现 ｜ **落点**：方案 **§7.2**（差异表）+ M1 + M0 的 **S5**
>
> **带宽基线**：本规格全部判据基于**方案 §7.1 的实测数据表**（国际源 **0.22–0.28 MB/s**，网卡 681 Mbps，
> 瓶颈在跨境出口）。**§3 的"自适应爬坡"理由即来自此表**——固定并发在波动 27% 的链路上无意义。

> **来源（三份独立实现，交叉验证）**：
> - **LeviLauncher**（Go，GPL-3.0）`internal/downloader/downloader.go` 641 行 —— 状态机与竞态处理最完整
> - **NexBox**（Rust/AGPL-3.0 的 `nx-dl-engine`）—— 并发自适应与域名记忆最成熟
> - **Axolotl/Modrinth**（Rust，GPL-3.0）`util/download_manager.rs` —— 速度判定最细致
> - 参照：**HMCL**（Java）`FetchTask.java` —— 续传前置条件最严格
>
> 本文件是**设计规格**，不是方案修订。所有取值都注明来自哪一份实现、为什么这样取。

## 0. 一句话结论

**下载引擎采用"状态机 + 临时文件 + 校验后原子提交"的形态，并发用自适应爬坡而非固定值。**
三份实现里 **LeviLauncher 的竞态处理 + NexBox 的自适应 + Axolotl 的速度判定** 各取所长，
**并补上 NexBox 缺失、LeviLauncher 有而他们都写得不显眼的一环：`tmp → final` 的原子提交。**

## 0.5 ⚠️ v3.12 补正：**"哪个源快"和"瓶颈在哪"都不能假设**（用户反馈 + 源码核实）

### 0.5.1 PCL 为什么快——查到的实据

| 证据 | 位置 | 说明 |
|---|---|---|
| **并行分块** | `PCL-CE .../FileDownloader.cs` 的签名里 **`bool enableParallelChunks = true`** | **它的"快"主要来自单文件多段并行（HTTP Range 分块）**，不只是"多线程下多个文件" |
| 线程上限 | `PCL.Core/App/Config.cs:79` `[ConfigItem<int>("ToolDownloadThread", 63)]` | 默认 **63**；但这个数字在受限链路上**不是收益来源**（见 §3 的爬坡理由） |
| 超时 / 重试 | 同文件 `RequestTimeoutMilliseconds = 30_000`、`MaxDownloadRetries = 3` | 重试的语义是**换源**（见 PCL `FileDownloader.cs:56-70` 的"外层重试 × 内层遍历全部源"） |

**结论**：我们规格里已有的**自适应爬坡**是对的（对应"多线程"），但**缺了 PCL 真正的那一招：单文件多段并行下载**。
规格 §1 的 I1/I2（临时文件 + 原子提交）**天然兼容分块**——每段写进同一个 `.download` 的不同偏移，全部完成后再校验 + rename。**要把它补进 §3。**

### 0.5.2 ⚠️ 我之前实测里的一个混杂因素（重要）

**两次实测是分开做的**：**0.28 MB/s 是走 PAC 代理（`127.0.0.1:80`）测的；0.22 MB/s 是直连测的。**
**两条路径给出几乎同一个数（0.22 vs 0.28）——所以"这个上限到底属于代理还是链路"，目前没有定论。**
两个旁证：

1. **直连与走代理结果接近**——两个不同的路径给出同一个量级，**通常指向一个共同瓶颈**，
   但**"共同瓶颈具体是谁"必须由 S5 定位，不能在此下结论**；
2. **网卡是 681 Mbps**，而实测不到 3 Mbps——**差 200 倍**，需要解释才能接受。

**所以 S5 的第一件事不是"测并发"，是"先分清瓶颈在谁身上"。**

### 0.5.3 源优先级：**不能假设"官方比镜像快"**

用户反馈"**镜像源的下载速度可能比官方源更快**"——**这条与我归档项目的旧结论直接冲突**（第一轮实测"官方比 bmclapi 快约 8 倍"）。

**两个数据不能同时成立**，除非：**它们是在不同网络路径下测的**。而"哪条路径"恰恰是最容易变的东西。

**处置**：

| 旧写法 | 改为 |
|---|---|
| "官方优先、失败自动切镜像"（**预设了官方快**） | **先测后定**——每台机器首次使用时实测各源吞吐，**按实测结果排序**，并把结果缓存 |
| 方案 §7.1 的"镜像源=可用性刚需" | 保留（镜像的价值在"官方不通时仍能装完"），但**不再预设谁快** |

### 0.5.4 因此 S5 的测法要改（**必须先分清瓶颈**）

**原 S5 直接测"并发几档吞吐多少"——这样测不出"瓶颈在谁身上"。** 改为下面的矩阵：

| # | 测什么 | 想看什么 |
|---|---|---|
| **A** | **直连 vs 走 PAC 代理**，同一下载源 | **代理是不是瓶颈**（若两者几乎同速 → 代理无罪，是真带宽；若代理明显慢 → 换路径或不用代理） |
| **B** | **官方源 vs 镜像源**（各 3 次取中位） | **到底谁快**（不预设） |
| **C** | **单文件多段并行**：1 / 2 / 4 / 8 段，同一文件 | **分块是否有收益**（对应 PCL 的 `enableParallelChunks`） |
| **D** | **多文件并发**：4 / 16 / 63 个文件同时下 | 爬坡参数是否合理（**63 是我们的对照上限**，不是目标） |
| **E** | 校验开销（边下边校验 vs 下完再校验） | 是否值得流水线化 |

**通过标准相应改为**：**A/B 两项必须先出结论**（瓶颈归因 + 源排序），**C/D 才有意义**——
否则会得出"并发没用"或"官方源慢"这类**归因错误**的结论。

> **这条补正是有价值的**：它把 S5 从"测并发"改成"**先定位瓶颈，再谈优化**"。
> 我原来的测法会把"代理瓶颈"误判成"链路带宽不足"，从而错误地把预算和设计都建立在错的数字上。

| # | 不变量 | 依据 |
|---|---|---|
| **I1** | **未通过校验的字节，永远不以正式文件名存在于磁盘上** | LeviLauncher `:234` 用 `.download` 后缀；NexBox 用 `.fdownloading`（`downloader.rs:2099`） |
| **I2** | **提交（rename）与取消/暂停必须串行化**；重命名一旦成功，**先把任务从注册表摘掉，再发完成事件** | LeviLauncher `:472-484` 注释原文：*"Once the rename wins, detach the task before emitting completion so a late cancellation cannot contradict it."* |

| **I4** | **服务端忽略 Range（返回 200 而非 206）时，必须删掉临时文件重头下**，不许接着写 | LeviLauncher `:303-309`；HMCL `:441-451` 同结论 |
| **I5** | **续传前必须校验服务端是否真的支持**：`accept-ranges: bytes` + `Content-Encoding: identity` + `content-length` +（强 `ETag` **或** `Last-Modified`），任一缺失即放弃续传 | HMCL `FetchTask.java:145-169` |

## 2. 任务状态机

```
        ┌──────────┐
        │  Queued  │  排队（受并发闸门限制）
        └────┬─────┘
             ↓
        ┌──────────┐  pause   ┌─────────┐
        │Downloading│ ───────→ │ Paused  │
        └────┬─────┘ ←─────── └─────────┘
             │        resume
             ↓ 传输完成
        ┌──────────┐
        │Verifying │  ← 校验期间暂停：保留完整传输，恢复时重跑校验，
        └────┬─────┘     且不得发出越过 EOF 的 Range 请求
             ↓ 校验通过
        ┌──────────┐
        │ Committing│ ← 与 Pause/Cancel 互斥（见 I2）
        └────┬─────┘
             ↓ rename 成功
        ┌──────────┐
        │  Done    │
        └──────────┘

  任意状态 ──cancel──→ Cancelled（可选删临时文件）
  任意状态 ──失败──→ Failed（带错误分类）
```

**校验失败的重试策略**（LeviLauncher `:442-457`）：

```
MD5/哈希不匹配 → 删临时文件 → retry_count += 1
  retry_count < 3 → 等 1 秒 → 重新传输（发 "MD5 mismatch (attempt N/3), retrying..."）
  retry_count = 3 → 发 ERR_<TYPE>_MISMATCH，任务失败
```

**校验期间暂停的行为**（LeviLauncher `:424-426` 注释，**这条很容易漏**）：

> *"A pause during verification retains the complete transfer. Resuming runs all integrity checks again
> without an invalid HTTP Range request beyond EOF."*

即：**校验阶段按暂停，不要回退成"重新下载"**；恢复时重跑校验即可。

## 3. 并发模型：**自适应爬坡**（取代固定并发）

**为什么不固定**：我们实测链路是 **0.22–0.28 MB/s（跨境受限）**，波动本身约 27%。
固定并发在"带宽充裕"假设下才有意义；在这种链路上，**并发过高反而更慢**。

**NexBox 的参数（`segment_coordinator.rs:456-535`）直接采用**：

| 参数 | 取值 | 说明 |
|---|---|---|
| 初始 worker 数 | `4` | `RAMP_INITIAL_WORKERS` |
| 评估间隔 | `2s` | `RAMP_TICK_SECS` |
| 改善因子 | `×1.25` | `RAMP_IMPROVE_FACTOR` |
| 劣化因子 | `×0.65` | `RAMP_COLLAPSE_FACTOR` |
| 收缩触发 | 连续 `2` 次劣化 | `RAMP_SHRINK_STRIKES` |
| 上限 | `64` 并发段 | `MAX_SEGMENTS` |
| 分段门槛 | ≥ `2 MB` 才分段；尾部 `64 KB` | `MIN_SPLIT_BYTES` / `TAIL_MIN_SPLIT_BYTES` |

**Axolotl 的速度判定（`util/download_manager.rs:6-8, 57-107`）用于"这个源该不该换"**：

| 参数 | 取值 |
|---|---|
| 初始速度地板 | `256 KB/s`（`INITIAL_SPEED_FLOOR`） |
| 采样间隔 | `100 ms`（`SAMPLE_INTERVAL_MS`） |
| 样本历史 | `30`（`SAMPLE_HISTORY`） |
| 判定 | 滑动窗口加权均值；**自适应地板 = 近 10 样本均值 × 85%，且只增不减** |

**"只增不减"是关键**：地板只会上调——**避免因为一次网络抖动就把某个源永久判定为慢**。

**NexBox 的另一招（`segment_coordinator.rs:92-95, 262, 328, 396`）**：
**域名连接上限记忆 24 小时**（`CONN_CAP_TTL = 24h`，key `domain_conn_caps`，格式版本 `v3`）。
→ 探到某站只支持 N 连接就记住，**不反复试探**。对频繁访问的 `libraries.minecraft.net` / `resources.download.minecraft.net` 尤其有用。

## 5. 多源策略：**镜像 = URL 前缀改写表**（改掉我们原来的"多源列表 + 测速"）

**HMCL 的做法（`HMCLDownloadProvider.java:62-116, 124-149`）**：

```
MirrorRule = { 源前缀 → 目标前缀 }
```

规则表覆盖：BMCLAPI、Forge/NeoForge/Fabric maven、**Modrinth 与 CurseForge 的 API 与 CDN**。

**为什么比"多源列表"好**：
1. **一条规则服务所有 URL**，不需要为每个下载项维护多份源地址；
2. **天然覆盖内容平台 CDN**（整合包/mod 下载也走同一套）；
3. 新增镜像 = 加一条规则，不改代码。

**配合 Axolotl 的速度判定决定"当前用哪条规则"**，而不是二选一的硬开关。

> **⚠️ v3.12 补正（见 §0.5.3）**：本节原写法隐含"官方源更快、镜像只是备用"。
> **用户反馈与归档项目结论冲突** → 已改为 **先测后定**：
> **每台机器首次使用时实测各源吞吐，按实测排序并缓存结果**；镜像的价值同时在于"官方不通时仍能装完"。
> **不许在代码里写死优先级。**

**HMCL 还有一个省网络的设计**（`FetchTask.java:355-357`）：
读镜像返回的 **`x-bmclapi-hash`** 头，若为合法 SHA-1 就**用于缓存命中判断**（省一次网络往返），
**但最终仍以官方元数据的哈希为准做完整性校验**。
→ 与我们既有纪律"哈希基准只取官方元数据"**不冲突**：镜像的哈希只用于"跳过下载"，不用于"判定正确"。
**这条要写进实现注释，否则后人会误用。**

### 5.1 单文件多段并行（v3.12 新增，**PCL 真正的那一招**）

**PCL 的下载快，主因不是"下多个文件"，而是"**一个文件切成多段同时下**"**
（`FileDownloader.cs` 签名的 `bool enableParallelChunks = true`）。

**我们怎么加**（与 I1/I2/I8 完全兼容）：

```
一个文件 → 切成 N 段 → 每段带 Range 写进同一个 .download 的不同偏移
        → 每段独立续传、独立重试
        → 全部完成 → 整体校验（哈希）→ 原子 rename
```

| 项 | 取值 / 规则 |
|---|---|
| 段数来源 | **自适应爬坡的输出**（§3）——段数即 worker 数，不额外设一套 |
| 分段门槛 | **≥ 2 MB 才分段**（NexBox `MIN_SPLIT_BYTES`）；尾部 `< 64 KB` 不单独成段（`TAIL_MIN_SPLIT_BYTES`） |
| 上限 | **64 段**（NexBox `MAX_SEGMENTS`） |
| **不支持 Range 时** | **自动退化为单段顺序下载**（I4：返回 200 而非 206 即视为不支持） |
| 断点续传 | **每段各自记已下偏移**，持久化到进度状态（每 3 秒批量落盘，NexBox `DB_SAVE_INTERVAL_SECS`） |
| 进度口径 | 见 **I7**：`file_bytes`（各段偏移之和）与 `session_bytes` 分开 |

**⚠️ 一条纪律**：**分段下载必须与"两个字节口径"（I7）配套实现**——
多段并行下"已下多少"不再是一个顺序累加值，**如果口径不清，进度条会跳变或倒退**。

## 7. Rust 侧的落地形状（**按 Axolotl 的分层**）

```
crates/
  qul-download/            ← 独立 crate（NexBox 的做法：引擎与主工程依赖隔离）
    src/
      task.rs              任务状态机（§2）
      scheduler.rs         自适应爬坡 + 域名连接上限记忆（§3）
      transport.rs         HTTP：Range/If-Range、200-vs-206 处理（I4/I5）
      verify.rs            校验 trait（I3）
      commit.rs            原子提交 + 与取消的串行化（I1/I2）
      source.rs            镜像前缀改写表 + 速度判定（§5）
      events.rs            trait EventSink（NexBox events.rs:36-42）
      progress.rs          两个字节口径（I7）
```

**三条继承自参照实现的纪律**：

1. **`EventSink` 是 trait，且契约写明"同步 fire-and-forget，实现不得阻塞或长持锁"**
   （NexBox `events.rs:36-38`）→ **本 crate 不依赖 Tauri，可单测**。
2. **本 crate 重导出自己的 HTTP client 类型**，宿主不得混用其它版本的 client
   （NexBox `nx-dl-engine/src/lib.rs:24-26`，因主工程与引擎 reqwest 版本不同而必须这么做）。
3. **`fraction: Option<f64>`，`None` 表示"总量未知"**（Axolotl `event/mod.rs:190` 约定 `None` 为完成；
   我们改成 `None = 未知总量`，**因为"未知总量"在我们场景里更常见**——镜像不返回 `Content-Length` 时）。

## 8. 验收要点（**都能写成测试**）

| # | 验收项 | 怎么测 |
|---|---|---|
| 1 | **I1**：校验失败时磁盘上不存在正式文件名 | 注入"校验必失败"的 mock，断言最终只留下 `.download`（或已被删除） |
| 2 | **I2**：提交瞬间取消，事件不矛盾 | 在 rename 前后各注入一次 cancel，断言**不出现"已完成"与"已取消"同时到达** |
| 3 | **I4**：服务端忽略 Range | mock 服务器对带 Range 的请求返回 200 + 全量体，断言最终文件哈希正确（**不是拼接损坏**） |
| 4 | **I5**：续传前置条件缺失即放弃 | mock 去掉 `ETag`/`Last-Modified`，断言走"重头下"而非续传 |
| 5 | **校验期间暂停** | 校验中取消再恢复，断言**不发出越过 EOF 的 Range**、数据完整 |
| 6 | **自适应爬坡** | 模拟带宽曲线（先升后降），断言 worker 数按 §3 规则变化，且不震荡 |
| 7 | **域名连接上限记忆** | 同一域名连续两次任务，断言第二次不再试探超过上次记录的上限；24h 后失效 |
| 8 | **I6**：事件频率 | 跑 60 秒全速下载，统计事件数，断言 ≤ 5 次/秒 |
| 9 | **失败聚合** | 三个源全失败，断言 UI 能拿到三条失败原因而非只有最后一条 |
| 10 | **预分配** | Windows 下断言下载中的文件是**非稀疏**（实际占盘 = 预分配长度） |

## 9. 与既有方案的差异（**十一项，已回填进方案 §7.2**）

| # | 方案原写法 | 本规格改为 | 理由 |
|---|---|---|---|
| 1 | "并发下载，默认并发数待定" | **自适应爬坡，初值 4、上限 64、2s 一评** | 实测链路波动 27%，固定值无意义（NexBox 实证） |
| 2 | "多源 + 测速探针 + 优先级" | **镜像 = URL 前缀改写表 + 速度判定** | HMCL 实证：规则表更易维护且覆盖内容平台 CDN |
| 3 | "≥256 KB 探针测速" | 保留（Axolotl 的地板同为 256 KB），但**判定改用"近 10 样本均值 × 85%、只增不减"** | 固定窗口在波动链路上抖 |
| 4 | 未提 | **域名连接上限记忆 24h** | NexBox 实证，避免反复试探 |
| 5 | 未提 | **临时文件 + 校验后原子提交 + 提交与取消串行化** | LeviLauncher 实证（我们的原子写条款缺细节） |
| 6 | 未提 | **续传前置条件严格校验（I5）** | HMCL 实证 |
| 7 | 未提 | **敌意服务器宽容超时（60s）** | NexBox 实证 |
| 8 | 未提 | **两个字节口径分开（I7）** | LeviLauncher 的易错点，我们预先规避 |
| 9 | 未提 | **进度双层节流**（引擎 200ms + 宿主 200ms，对齐"≤10 次/s"） | NexBox `:814` + `download_accelerator.rs:709/734` |
| 10 | 未提 | **单文件多段并行下载**（段数复用爬坡输出；≥2 MB 才分段；上限 64；不支持 Range 时退化为单段） | **PCL `enableParallelChunks`**——它快的真正原因 |
| 11 | "官方优先、失败自动切镜像"（**隐含官方更快**） | **源优先级先测后定**：首次使用实测各源吞吐、按实测排序并缓存；**代码里不许写死优先级** | 用户反馈与归档项目旧结论冲突 → 只可能处在不同网络路径；见 §0.5.3 |

> **本表已回填进方案 `[DOWNLOAD]`（§7.2）的"十一项差异表"**——两处项数一致。
