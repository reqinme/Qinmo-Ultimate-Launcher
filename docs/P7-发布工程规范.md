## 2. 分发形态

### 2.1 单文件绿色版

发布产物：

```
QinmoUltimateLauncher.exe          307 KB    ← 唯一需要分发的文件
QinmoUltimateLauncher.pdb           86 KB    ← 调试符号，不随发布
QinmoUltimateLauncher.exe.config   174 B    ← 只是 supportedRuntime 声明，删掉也能跑
```

**没有任何第三方 DLL**，因为项目从 P0 起坚持零运行时依赖（HTTP 用 `HttpWebRequest`、
ZIP 用 `System.IO.Compression`、JSON 自写 DOM）。因此**不需要 Costura.Fody 或 ILMerge**。

已实测：把一个 exe 单独拷进空目录即可正常启动，并自动建出 `data/` 与 `game/`。
**首启不落地临时目录**——程序从不自解压。

### 2.2 便携与安装两态

不需要两个分发包，也不需要安装程序。**同一个 exe 按自己所在的位置决定数据落在哪**：

| 形态 | 放置位置 | 数据根 | 特点 |
|---|---|---|---|
| 便携 | 任意可写目录（U 盘、桌面、D 盘） | `<exe 同目录>/data` 与 `/game` | 拷走整个目录即迁移；卸载 = 删目录 |
| 安装 | 不可写目录（如 `Program Files`） | `<用户目录>\QinmoUltimateLauncher\data` | 多用户各自独立 |

判定是**运行时探测**，不是编译期开关。会话日志里记录 `placement=portable|userprofile`，便于排障。

**探测的必须是"便携数据根本身能不能建出来"，而不是"exe 目录可不可写"。**
两者不等价：exe 目录可写、但 `data` 这个名字已被一个文件占住时，
按 exe 目录判断会选便携模式，随后建目录失败——**程序照跑，却一个日志都不写**，
排障时人只会看到"哪都没有数据"。这一点已由回归测试锁死。

实测（用一个文件占住 `data` 这个名字）：

```
便携模式受阻 → 回退到 C:\Users\<用户>\QinmoUltimateLauncher\data\logs\session-*.log ✓
```

## 3. 更新机制

按 P7.0 选定的**自替换**实现。

### 3.1 命门已实证：运行中的 exe 可以给自己改名

整个方案成立与否，全押在一条 Windows 行为上：**运行中的可执行文件允许被改名**
（只是不允许覆盖或删除）。这是假设的话，选型就是空中楼阁。

实测方式：写一个最小控制台程序，让它在运行中执行与正式实现完全相同的两步文件操作。

```
self=...\qul-probe-run\probe.exe
step1 运行中自身改名: OK
step2 新文件就位: OK
复原: OK
退出码 = 0
```

**结论：方案成立，无需第二个进程。**

### 3.2 流程

```
1. 检查发布清单（新版本号、下载地址、SHA-256、最低兼容版本）
2. 用户点「立即更新并重启」——**更新永远由用户显式发起，不得静默自我替换**
3. 下载到 <数据根>/updates/pending.exe
4. 校验 SHA-256；不符即删除并报错，绝不进入第 5 步
5. 落盘 pending.json（阶段 = swapping）——**必须在替换之前写**，否则断电时无从判断
6. 两个 MoveFile：自身 → .old，pending.exe → 自身
7. 任一步失败：进程仍活着，**当场把 .old 改回原名**，报错退出，用户得到完好无损的旧版本
8. 成功：以新文件重启
```

### 3.3 回退

不依赖新版本自报成功（它可能根本没机会报），而是看**标记还在不在**：

```
替换成功后写 pending.json
新版本启动成功 → 删除它
下次任何版本启动时若发现它仍在且阶段为 swapping
    ⇒ 上次替换之后从未成功启动过
    ⇒ 用 .old 换回原路径，坏掉的那份挪到 .exe.failed（不删，便于排查）
    ⇒ 提示用户「上次更新未能启动，已回退到旧版本」
```

**核心语义由用例钉死**：`ShouldRollback` 只在"有标记 且 阶段为 swapping 且 备份名非空"时为真。
标记读不出来、格式坏掉、备份名为空，一律当作"没有待处理更新"——**绝不能因为一个坏标记让人开不了程序**。

### 3.4 启动时的状态机

**不能简单地"看到 swapping 就回滚"**——替换刚完成时，新版本的第一次启动本来就会看到 swapping，
那是正常状态而不是失败。靠"运行的版本是不是目标版本"把这两种情况分开：

| 磁盘上的标记 | 运行的版本 | 判定 | 含义 |
|---|---|---|---|
| 无 | — | `None` | 没有待处理更新 |
| `swapping` | **等于**目标版本 | `Adopt` | 我们正是刚被换上来的那一个 → 改标为 `applied`，等健康确认 |
| `swapping` | **不等于**目标版本 | `Discard` | 替换根本没发生，旧版本完好，标记是残留 |
| `applied` | 任意 | **`Rollback`** | 上次启动打过待确认标记却从未确认健康 ⇒ 上次启动中途死了 |

健康确认在应用真正起来之后做（删除标记）。**只有走到那一步才算这次更新活下来了。**

### 3.5 回退真机演练记录

不是逻辑推演，是在真实可执行文件上跑出来的：

```
演练布置
  app.exe      269312 B   坏掉的新版本（启动过一次，从未确认健康）
  app.exe.old  269313 B   旧版本（同一 exe 加一字节，便于用大小区分）
  pending.json            stage = applied
  game/saves/test.dat     用户数据哨兵

运行 app.exe preflight 1.7.10 之后
  app.exe              269313 B  ✅ 已换回旧版本
  app.exe.failed       269312 B  ✅ 坏的那个挪到一边（不删，便于排查）
  pending.json         已清除    ✅
  game/saves/test.dat  内容未变  ✅ 用户数据无损

会话日志
  previous update never confirmed health; rolling back to 0.1.0
  rolled back; the previous version will run on the next start
```

### 3.6 用户数据无损

靠**路径白名单**保证，不靠自觉：

- 更新只操作两个位置：主程序自身与 `<数据根>/updates/`
- 备份路径由 `ResolveBackupPath` 解析，**任何目录成分都会被剥掉**，只保留文件名。
  标记文件是可以被手工改的，不能让里面的 `..\..\game\saves\level.dat` 把文件操作引到存档上去。
- `data/`、`game/` 中的任何文件都不在更新路径上

## 4. 偏差归因

| 指标 | 预算 | 实测 | 归因 |
|---|---|---|---|
| 主程序体积 | 1–3 MB（上限 5 MB） | **307 KB** | 优于预算一个数量级；归因于零第三方依赖 + 自写 JSON |
| 冷启动到可交互 | ≤800 ms | **330–449 ms** | 达标 |
| 首启/二次差异 | ≤200 ms | **124 ms** | 达标 |
| 空闲内存 | 宽松上限 80 MB | **约 37.5 MB**（工作集） | ✅ 先前的"架构问题"归因已被推翻并修复，见 `性能实测记录.md` |

### 内存超标的归因结论

对照实验（详见 `性能实测记录.md`）：

- **空的 net48 WPF 窗口**（只有一句 `TextBlock`，同样 1120×820、同样清单、同样 Release）＝ **137.7 MB**
- 我们的启动器 ＝ 153.6 MB，即**界面自身只占 15.9 MB**
- 关掉启动刷新（不读 917 条清单、不探测 19 个 `java.exe`）后 ＝ 153.9 MB，**与完整启动一致**

也就是说：**超出的部分几乎全部来自"WPF + net48"这个技术栈的固有装载成本，而不是我们的实现。**

这是**规划阶段技术选型与内存预算没有对齐**：
规划同时固定了 "C# + WPF + net48" 与 "空闲内存 ≤80 MB"，而前者单独一项就超过后者。

**处置计划**：建议把该指标改写为相对形式——**"≤ 空窗口基线 + 60 MB"**。
这样它衡量的是我们的实现，而不是运行时的固有成本，将来换运行时时也不会失效。
`P0–P6` 阶段未为压低体积或启动时间牺牲分层与可测试性，符合预算纪律。

## 7. 完整周期演练（本地 HTTP，端到端）

不是桩，是真的起了一个本地 HTTP 服务，让旧版本从零下载新版本并替换自己。

```
准备
  publish-v1  → app.exe       版本 0.1.0.0
  publish-v2  → serve/new.exe 版本 0.2.0.0，sha256 写入清单
  本地 HTTP 服务（TcpListener 手写最小 HTTP 响应，不需要管理员权限）

第 1 步：旧版本执行 update --manifest … --apply
  当前版本 0.1.0.0
  发现新版本 0.2.0（0.3 MB）
  已下载并校验通过：…\data\updates\pending.exe
  替换完成，重启后生效。
  → app.exe 哈希 = 新版本 ✅   app.exe.old 哈希 = 旧版本 ✅
  → **标记留存，阶段 swapping** ✅（旧进程无权替新版本确认健康）

第 2 步：新版本第一次启动
  → 日志：adopted pending update 0.2.0; awaiting health confirmation ✅
  → 仍是新版本、未被回滚 ✅   确认后标记清除 ✅
```

### 演练中抓出的三个真实缺陷

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `update` 没注册进命令行动词表 | 启动器把它当界面参数，**弹了窗口在那里等** | 补进 `IsCliVerb` |
| 2 | 执行替换的**旧进程**在退出时把更新"确认健康"了 | 新版本一次都没跑过就被认定可用，**试运行形同虚设** | 只有"我们就是被换上来的那个版本"时才允许确认 |
| 3 | 版本比较用字符串相等 | 程序集是四段 `0.2.0.0`、清单写三段 `0.2.0`，判为不同 → 新版本启动时走 Discard | 改用版本语义比较 |

**第 3 个最危险**：它会让标记被清掉，于是**真正坏掉的更新再也不会被回滚**——
表面上一切正常，安全网却被悄悄拆掉了。三个缺陷各自都有回归用例。

## 8. 摘要不符的端到端演练

"先校验、再动任何东西"这条纪律不能只写在文档里。让本地服务按发布清单下载，
但清单里的 sha256 与文件实际内容**故意不符**：

```
当前版本 0.1.0.0
发现新版本 0.2.0（0.3 MB）
✘ 失败：QUL-DL-0002 文件损坏，正在重新下载。
   下载的文件校验未通过，已丢弃

主程序未被改动      = True
app.exe.old 未生成  = True
pending.json 未生成 = True
.part 残留          = 0
```

程序在**校验通过之前一步都不往前走**：不写标记、不备份、不替换、不留残渣。

### 与镜像安全声明的关系

"用镜像不降低完整性保证"这句话同样不能只是说法。
让镜像故意返回被篡改的字节、而官方源返回正确内容，然后观察引擎：

```
DownloadReport.IsComplete = true        （坏源被换掉了，整次下载仍然成功）
落盘内容 == 官方内容                     （篡改字节从未被写入磁盘）
Attempts = 2                            （第一次落在坏源上，第二次换源成功）
```

**镜像可以撒谎，但摘要来自官方元数据。撒谎只会让它的字节被丢弃并触发换源。**
这个用例是那句话的直接验证——反过来说，如果引擎信任了源声明的任何东西，它就会拿到篡改内容。
