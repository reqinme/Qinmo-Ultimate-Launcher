# ADR-0013 · 读、写、恢复三者必须共享同一把锁

- **状态**：已采纳
- **日期**：2026-10-01
- **来源**：M1 · 并发写安全（方案出口条件「**并发写同一实例不出错**」）
- **证据**：`crates/qul-infra/tests/concurrent_write.rs`（6 项）· `crates/qul-infra/src/fsx.rs`（13 项）

## 1. 背景

方案 M1 要求 **原子写 + 文件锁 + 单实例主进程**，出口条件是 **"并发写同一实例不出错"**。

实现顺序是：原子写（写临时文件 → 落盘 → 两步重命名替换）→ 加文件锁 → 加单实例守卫。
**这个顺序本身没有问题；问题在于"什么时候该持锁"没有想清楚。**

## 2. 决策

> **同一份文件的读、写、恢复（崩溃后修复）必须共享同一把锁。**
> 三者中任何两者不互斥，都会产出**只有并发时才出现**的故障。

具体落点（`crates/qul-infra/src/fsx.rs`）：

| 入口 | 加锁 | 说明 |
|---|---|---|
| `write_atomic` | 自己加 | 从"清 `.tmp`"到"删 `.bak`"整段串行 |
| `read_optional` / `read_recovering` | 自己加 | **恢复 + 读取在同一锁内** |
| `recover` | 自己加 | 给外部调用者 |
| `recover_locked` | **不加**（要求已持锁） | 给锁内的调用者；**锁内调 `recover` 会自死锁** |

## 3. 理由：三个**只有实测才会出现**的缺陷

这三个缺陷**单线程一万次都不会出现**。它们都是 `tests/concurrent_write.rs` 抓出来的。

### 3.1 两个写入者抢同一个 `.bak` → `NotFound`

第一版 `write_atomic` 不加锁，只用两步重命名：

```text
线程 A: rename(target -> .bak)   成功（target 没了）
线程 B: rename(target -> .bak)   失败：Os { code: 2, NotFound }
```

**根因不只是"报错"**：`.bak` 是**固定名**，而"检查 target 是否存在"与"rename 它"之间
**没有任何东西保证状态不变**——这是典型的 **TOCTOU**。

### 3.2 读者的"恢复"删掉了写入者正在用的 `.tmp`

加了写锁之后仍红。原因：`read_recovering` 调的 `recover()` **自己不加锁**，且会清理 `.tmp`：

```text
写入者: 创建 .tmp ────────────────────────► rename(.tmp -> target)
读者:            recover() 把 .tmp 删了 ☠
```

于是写入者的 rename 报 `NotFound`。

**关键认识**：**"恢复"和"写入"是同一份状态的两种操作，必须互斥。**
把 `.tmp` 当成"垃圾"随手清掉，是把它当成了别人的东西——
**而它此刻可能正是某人正在写的文件。**

### 3.3 读者在两步重命名之间看到"文件不存在"

修完 3.2 之后还红：`read_recovering` 在 recover 之后**释放锁再读**，
于是读者可能落进那个极短窗口（target 已挪走、新的还没就位）。

**这个失败比"读到半截"更隐蔽**：

| 失败形态 | 表现 | 用户看到 |
|---|---|---|
| 读到半截 | 解析器能报出来 | "配置损坏"（有提示） |
| **读到"不存在"** | **被上层当成首次运行** | **"我的设置被重置了"（无提示）** |

所以 `read_optional` 这个入口是**必须的**：它把"不存在"当成一种**正常状态**
（首次运行就是这样），而不是错误。

## 4. 两个必须分开的入口：`read_optional` 与 `read_recovering`

"文件不存在"有两种真实语义，**不能用同一个返回值表达**：

| 语义 | 该用哪个 | 为什么 |
|---|---|---|
| 配置文件不存在 = 首次运行（**正常**） | `read_optional` → `Ok(None)` | 报成错误会让上层走进错误处理，而正确路径是"用默认值" |
| 已下载的文件不存在 = **故障** | `read_recovering` → `Err` | 报成"正常"会让上层以为"还没下过"，于是**静默重下**而不是报错 |

## 5. 代价（如实记）

| 代价 | 缓解 |
|---|---|
| 每个被写的文件旁边多一个 0 字节 `.lock` | **有意保留**：用"文件存在与否"当锁哨兵，崩溃后会留下**永远拿不到的锁**；而操作系统文件锁**进程一死就自动释放**，所以文件留着无害 |
| 读取也变成串行的 | 我们的读都是短操作（毫秒级），而**并发读同一份正在被替换的文件本来就没有正确答案** |
| 两步重命名有一个极短窗口 | **每次都是整文件替换**，所以恢复后的内容要么完整旧版、要么完整新版，**永远不会是半截** |

## 6. 影响

- **M2（下载引擎）**：每个下载目标的落盘都必须走 `write_atomic`，
  **不许自己 `File::create` 写**——否则"校验和不通过"会变成一个**间歇性**故障。
- **M3（启动链路）**：`launcher_profiles.json` 这类**游戏自己也在写**的文件，
  我们的锁**管不到游戏进程**。M3 必须用"读-改-写 + 校验"而不是假设独占。
- **M1 出口条件**："并发写同一实例不出错"已有**可复现的实测**（见 §3 的测试文件）。

## 7. 一条更一般的教训

> **"清理垃圾"必须先确认那不是别人正在用的东西。**

三个缺陷里有两个（3.2、3.3）都源于同一个想法：
**"这些中间文件是垃圾，看到就清掉"**。
而中间文件之所以叫"中间"，是因为**某个操作正在进行**——
**一个不持锁的清理者，等于一个随时会踩进别人操作中间的执行者。**

这与本项目此前学到的两条是同一类错误的三个面孔：

| 场景 | 同一个错误的形态 |
|---|---|
| 检查与使用之间状态可变（本 ADR 3.1） | TOCTOU |
| 清理者踩进操作中间（本 ADR 3.2） | 把"中间态"当成"垃圾" |
| 检测与匹配用了同一套思路（licence 探测器） | 用被测对象本身当判据 |
