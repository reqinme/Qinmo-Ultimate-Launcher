# 灵动岛的队列接线：**边界在哪，以及为什么不能一刀切进去**

> **这份文件是一次"停下来想清楚"的产物**，而它不是计划，是**发现**。
> 它记的是：我第一次试图把进度接到前端时，**撞到了一面墙**，而墙的位置
> 说明了一件关于分层的事。

---

## 1. 我撞到了什么

第一版的 `install` 命令长这样：

```rust
#[tauri::command]
async fn install(version_id: String, instance_root: String, on_event: Channel<IslandState>, ...) {
    let result = tauri::async_runtime::spawn_blocking(move || {
        qul_infra::install::probe_installability(&vid, &root, &cancel)   // ← 这个函数不存在
    })...
}
```

**`probe_installability` 不存在。** 而真实的签名是：

```rust
pub fn install(
    d: &Descriptor,        // ← 版本详情
    env: &Env,             // ← 平台
    version_id: &str,
    instance_root: &Path,
    cfg: &InstallConfig,
    transport: &dyn Transport,   // ← 网络怎么走
    cancel: &CancelToken,
    sink: &dyn StageSink,
) -> Result<InstallOutcome, InstallError>
```

**关键在于前两个与第六个参数**：`Descriptor`、`Env`、`Transport`。

- `Descriptor` 要**先解析版本详情** —— 而"从哪拿详情、缓存在哪、没有时要不要联网"
  是一个**决策**（`install_cmd.rs` 里那段"先本机缓存，再联网"就是这个决策）。
- `Transport` 要**调用方选** —— 而"用 WinHTTP 还是 `NoNetwork`"是**策略**。

**两条都是编排，不是翻译。** 而我把它们放进了命令层。

---

## 2. 墙的位置说明的事：`qul-app` 是空的

方案 §3.5 的三层是：

```
qul-core     纯规则，零 IO
qul-infra    IO（下载 / 解压 / 进程 / fsx）
qul-app      编排  ← **它现在是空壳**（128 行，另一个是测试）
qul-cli      CLI 外壳
src-tauri    Tauri 命令层（**薄壳**）
```

**而 `qul-app` 空着，正是这次撞墙的原因。**

现在那份编排**住在 `qul-cli/src/install_cmd.rs` 里**：

| 那里的编排 | 它是什么 |
|---|---|
| "先本机缓存，再联网取详情" | **策略** |
| "选哪个 transport" | **策略** |
| "把 `StageSink` 的消息打成中文进度" | **表现**（而它其实该在前端） |
| "决定要不要装资产" | **策略** |

**这些都不是 CLI 特有的。** 而 Tauri 命令层需要的是**同一份**编排。

### ⚠️ 所以正确的做法不是"在命令层里再写一遍"

一个"把 `install_cmd.rs` 的逻辑复制进 `main.rs`"的做法会立刻产生：

- **两份"先缓存再联网"的策略** —— 而它们会漂移
- 两份进度文案 —— 而它们会不一致
- 两次"要不要装资产"的判断 —— 而它们会不同

**而那正是 `qul-app` 该避免的事。**

## 3. 所以这件事的正确形状是三层，而中间那层现在还不存在

```text
① qul-app        一个 install(version_id, root, cfg, transport, cancel, sink) 的编排函数
                 —— 它内含"先缓存再联网"与"选 transport"两条策略
        ↓
② src-tauri      一个 ChannelSink：把 StageSink 的消息翻译成 IslandState，
                 经 Channel<IslandState> 推给前端（**纯翻译，零策略**）
        ↓
③ web/src        把收到的 IslandState 推进内核算好的队列语义（前端的那一半）
```

**而 ① 是这一件事的前提** —— 没有它，② 只能自己编策略。

---

## 4. 而这一轮**学到的那一件事**：`Channel` 而不是全局事件

Tauri 2 有两条推消息的路，而它们的区别**正好撞上 §7.1 的硬规则**：

| | 全局事件（`app.emit`） | **`Channel<TSend>`** |
|---|---|---|
| 作用域 | **所有窗口** | **这一次调用的这一个前端** |
| 多个安装同时跑 | 事件**混在一起** | 各自一条流 |
| 谁收得到 | 任何人 | 只有传了这个 channel 的那个调用 |

§7.1 的硬规则是「**任意时刻只有一个岛、一个主状态**」。

**而"两个安装的进度混在一条全局事件流里"会让那条规则在消息层就被破坏** ——
内核那 22 条测试管的是队列，而它们**管不到消息层**。

所以：**用 `Channel<IslandState>`**。它的签名（Tauri 2.12.1 实测）：

```rust
pub struct Channel<TSend = InvokeResponseBody> { … }
impl<TSend> Channel<TSend> {
    pub fn send(&self, data: TSend) -> crate::Result<()>
    pub fn new<F: Fn(InvokeResponseBody) -> crate::Result<()> + Send + Sync + 'static>(…)
}
```

而 `IslandState` **已经**派生了 `Serialize`（`crates/qul-core/src/island.rs`），
所以它可以直接作为 `TSend` —— **不需要在命令层另编一份状态枚举**。

> 而"另编一份"正是要避免的：那会让内核那 22 条抢占与队列测试
> 与界面之间出现**第二个真相来源**。

---

## 5. 而这一步**不需要新决定**，只需要把 `qul-app` 填上

它**不引任何新依赖**（编排层只用 `qul-core` + `qul-infra`），
而它顺带解决一件已被记录在案的事：

> `SESSION.md` 里写着：**"M2 有一个已记录的架构缺口：`qul-app` 是空壳，
> CLI 直接调 `qul-infra`。"**

也就是说：**这一步不是"为了 Tauri 才做的"，它本来就是欠着的。**

---

## 6. 所以下一轮的顺序是

| # | 做什么 | 为什么是它 |
|---|---|---|
| **1** | 把 `install_cmd.rs` 里的编排**搬进 `qul-app`** | 它本来就是欠着的（M2 缺口），而命令层需要它 |
| **2** | `qul-cli` 改成调 `qul-app` | 证明①是**同一份**编排（否则搬了个寂寞） |
| **3** | 在 `src-tauri` 写 `ChannelSink` + `install` 命令 | 纯翻译，零策略 |
| **4** | 前端：`Channel` 的 `onmessage` → 灵动岛队列 | ③的另一半 |

**而第 1 步有一条现成的验收**：搬完之后 `cargo test --workspace` 应当**仍然全绿**
（那条路径已被 `launch_chain` 与 `install` 的测试覆盖过），
而 `install_cmd.rs` 应当**变薄到只剩参数解析与打印**。
