# 规划与实际对照

> 这份文档存在的理由：路线图（v1.2）里写了四个"核心抽象"的名字，
> 而实现里有的改了名、有的换了形态、有的根本没建。
>
> **文档提到一个不存在的类型，比文档没写更糟**——读者会去找它，
> 找不到时无法判断是"我理解错了"还是"它没做"。
> 本项目对偏差的处置一贯是**记录而不是抹掉**，这里同样。

对照基准：`Minecraft启动器-架构规划与路线图-v1.2.md` 第 4.2 节与第 6 节。
核对方式：从文档里机械抽取反引号中的标识符，逐个到 `src/` 里查找。

---

## 1. `IRuntimeProvider` → 实际为 `IJavaRuntimeProvider`

| | |
|---|---|
| 规划 | `IRuntimeProvider`（运行时提供方）：探测、选择、能力声明（未来含获取） |
| 实际 | `Application/Ports/IJavaRuntimeProvider.cs` |
| 性质 | **改名并收窄** |

路线图把"运行时"当作一个可扩展到其他语言的抽象（为将来接其他游戏留口）。
实现时它只服务 Java，且**没有第二个实现者**——把名字写成 `IJavaRuntimeProvider`
比留一个泛化的 `IRuntimeProvider` 更诚实：它现在不打算支持别的运行时。

**如果将来真要接第二个运行时**，正确的做法是那时再引入泛化层，
而不是现在留一个只有单一实现的"通用"接口——那种接口的形状必然是猜的。

---

## 2. `IContentSource` → 实际为 `DownloadSourcePolicy` + 内置的多源回退

| | |
|---|---|
| 规划 | `IContentSource` 多实现：版本清单、库、资源、附加内容的统一获取；MVP 仅注册官方源，P10 加镜像实现 |
| 实际 | `Domain/Downloads/DownloadSourcePolicy.cs`（策略）+ `DownloadEngine` 内的多源回退与 `SourceHealth` |
| 性质 | **形态变了：从"多实现接口"变成"策略 + 数据驱动"** |

**这是四处偏差里唯一真正结构性的一个**，值得说清楚为什么。

规划设想的是"一个源 = 一个接口实现"，由容器注入。实际做下来发现：

- 源的差异**几乎全部是"换个 base url"**，而不是"换一套行为"。
  官方源与镜像源在同一套解析、校验、续传逻辑上跑，差的是地址与健康度。
- 真正需要按源区分的是**健康度统计要按 (主机, 类型) 分开记账**
  （镜像可能只有库文件缺失，资源对象其实是好的），这是**数据**，不是虚方法。
- 接口会在需要按源注入不同实现时才有价值，而这里是**同一个引擎在多个地址间回退**。

所以最终形态是：`DownloadSourcePolicy` 决定"这个条目该按什么顺序试哪些地址"，
`DownloadEngine` 负责执行与记账，`SourceHealth` 负责按 (主机, 类型) 累积失败。

**代价要说清楚**：如果将来要接一个**行为确实不同**的源
（例如需要私有认证、返回不同结构的清单），这个形态需要真的引入接口才能容纳。
届时是一次真实的重构，而不是加一个实现类。**这一点我选择现在写下来，而不是等它发生。**

## 3. `IGameBackend` —— 未实现（规划中即属 P11）

| | |
|---|---|
| 规划 | "启动一个游戏"的统一契约：预检、安装/准备、启动计划、进程监控；Java 版、基岩版各实现一个 |
| 实际 | 无 |
| 性质 | **属于未开工的阶段，不是偏差** |

路线图自己写明它服务于"基岩版（若 P11 结论为接）"。P11 尚未开始，因此不存在。

**但要说清一个事实**：P4 做出来的 `LaunchPipeline` + `LaunchPlanBuilder`
就是 Java 版这一份契约的事实上的实现，只是**没有抽成一个接口**。
抽它的唯一理由是"要有第二个实现"——在没有第二个实现之前抽出来的接口，
形状必然是照着第一个实现画的，那不是抽象，是同义反复。

## 4. `IInstallation` —— 未实现（规划中即属后续阶段）

| | |
|---|---|
| 规划 | 一次"可启动的配置"：版本 + 加载器 + Java + 内存 + 目录；用于多实例、整合包、多后端并存 |
| 实际 | 无独立类型；配置分散在 `LauncherConfig` 与各次启动时的参数里 |
| 性质 | **属于未开工的阶段，不是偏差** |

**这是四处里唯一一处"将来可能真的会疼"的地方。** 现在只能有一个"当前实例"：
版本、身份、内存、目录都是全局单份配置。
真要做多实例时，需要把这一组东西收成一个可命名的实体，
而那时的改动会**触及界面、配置存储与启动链路三处**，不是加一个类就完事。

P4 的范围内不需要它，所以现在不做是对的；**但它不是"零成本可后补"的**，
将来排期时请按一次真实重构估工，而不是按一个新增功能估工。

## 5. 机械核对没能覆盖的部分

这次核对靠的是"文档反引号里的标识符 → 源码查找"。
它抓不到两类问题，**而这两类比上面四条更容易出错**：

1. **行为描述与实现不符**。例如文档写"只在 X 时返回真"而代码在 X、Y 时都返回真。
   标识符都存在，但断言是错的。这一轮里实际抓到过一次
   （`P7-发布工程规范.md` §3.3 描述的 `ShouldRollback` 语义与代码相反），
   **那次是偶然撞见的，不是这个机械检查抓到的。**
2. **数值与实测不符**。体积、耗时、内存这类数字会随实现变化而失效。

所以这份对照文档**不能替代人工复核**，它只是把"名字找不到了"这一类问题变成机械可查。
---

## 6. 这个检查的噪声率（重要）

机械核对的结果是 **453 个被引用的标识符里，240 个在源码里找不到**——

而**真正有问题的只有 2 个**。其余 238 个是：

| 类别 | 例子 |
|---|---|
| JSON 字段名 | `assets_index_name`、`launcher_name`、`user_type` |
| .NET / WPF 类型与成员 | `HttpWebRequest`、`VirtualizingStackPanel`、`RequerySuggested` |
| 我们自己定义的样式与画笔名 | `Qul.Brush.Danger` 的 `Danger`、`Pill`、`RaisedHover` |
| 枚举成员（抽取时没覆盖） | `DlFailed`、`NetResourceMissing`、`IoPathEscapesRoot` |
| 属性名（抽取时只覆盖了字段与带参方法） | `StartupNotice`、`IsComplete` |
| 外部项目与协议术语 | `AdoptOpenJDK`、`Zulu`、`AADSTS70002`、`invalid_client` |
| 测试方法名 | `Redactor_MasksUuidAndIp` |

**结论：这个检查不能当门禁用。** 240 个命中要人工看，而其中 99% 是噪声——
一个需要人工过滤 240 条的检查，第二天就会被所有人忽略。

它的正确用法是**一次性审计**：跑一遍、把结果过一遍人眼，
把真正的偏差记下来（就是本文前四节），然后**不要把它接进 CI**。

真要接进 CI，得先把抽取规则做准（解析 C# 而不是正则、识别 JSON 键、
识别 XAML 资源名……），那件事的成本远大于它防住的问题。
