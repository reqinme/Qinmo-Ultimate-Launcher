## 1. 已实测的应用注册（**不是推断，是实测**）

| 项 | 值 |
|---|---|
| 显示名称 | `Qinmo Ultimate Launcher` |
| **应用程序（客户端）ID** | `2a06b5bc-7b61-4a36-9edf-52fb89525943` |
| 目录（租户）ID | `725226df-ea14-43bb-951e-a5d2602d674b` |
| 受支持的帐户类型 | **所有 Microsoft 帐户用户** |
| 客户端凭据 | **无**（公共客户端，不需要密钥） |
| 重定向 URI | **0 个 Web / 0 个 SPA / 2 个公共客户端** |
| 状态 | ✅ 已激活 |

### 1.1 决定性实测（2026-10-01，本项目做的）

对 `oauth2/v2.0/devicecode` **逐租户段**打真实请求，`client_id` 用上表的值：

| 端点 | 结果 |
|---|---|
| `/consumers/` | ✅ **成功**，返回 `user_code` |
| `/common/` | ✅ **成功** |
| `/organizations/` | ✅ **成功** |

**结论：注册可用，且个人账户与工作/学校账户都可以。**

> ### ⚠️ 这条结论"来之不易"，理由记在下面
>
> **封存的第一轮项目（C#）在这里卡死过**，它留下的是逐端点实测记录：
>
> | 端点 | 当时的结果 |
> |---|---|
> | `/consumers/` | ✗ **HTTP 401 `invalid_client`** |
> | `/common/` | ✗ **HTTP 401 `invalid_client`** |
> | `/organizations/` | ✅ 成功 |
> | `/<目录租户ID>/` | ✅ 成功 |
>
> 响应体里的真因是：
> ```
> AADSTS70002: The provided client is not supported for this feature.
> The client application must be marked as 'mobile'.
> ```
> 即注册**缺「移动和桌面应用程序」平台**，也**没开「允许公共客户端流」**。
> 当时的结论是："这不是启动器侧能绕过的：换租户段绕不开，因为个人账户端点本身被拒。"
>
> **2026-10-01 复测：三项全通 → 注册已补齐这两个配置。**
> **因此 C1 / C3 的状态从"未满足"变为"已满足（有实测证据）"。**

### 1.2 一个仍未消解的 Azure 提示

Azure 门户上有一条警告：

> *End users cannot grant consent to newly registered multitenant apps without verified publishers.
> 添加 MPN ID 以验证发布者*

**判断（推断，非实测）**：本项目是**单租户自用**，且登录者是**该租户的所有者本人**——
"最终用户授权"这个场景不存在，因此**该警告不构成本项目的阻塞项**。
**但若将来做成"别人也能用你的 client_id 登录"，这条会立刻变成阻塞项**
（那时要么让每个用户自己是租户所有者，要么补发布者验证）。

**待办**：把这条写进风险登记，标为"仅在分发给他人时触发"。

## 2. 前置条件门禁 C1–C4

设计来自封存的第一轮项目（`MicrosoftAuthPrerequisites`），**这个设计我认为是对的，照搬其结论**：

> **任一未满足，微软正版登录不得进入可用状态**——它必须报 `QUL-AUTH-0005` 并说明缺什么，
> 而不是"尝试一下看看行不行"。
>
> **理由（原文，我完全同意）**：拿一个未注册的 `client_id` 去撞授权端点，
> 得到的永远是一个笼统的失败，**无法区分"我的请求写错了"与"这个 client_id 本就不可用"**。

| # | 前置条件 | 谁负责 | **状态（2026-10-01）** |
|---|---|---|---|
| **C1** | 已在微软平台完成应用注册 | 产品负责人 | ✅ **已满足 + 有实测证据**（§1.1） |
| **C2** | `client_id` 已确定；所需权限范围已确认 | 产品负责人 | ✅ `client_id` 见 §1；范围见 §3 |
| **C3** | 回调 URI 或设备码流程已确定 | 产品负责人 | ✅ **设备码流程**（§4），**且实测可用** |
| **C4** | 第三方启动器相关条款已核对 | 产品负责人 | ⚠️ **未做**（见下） |

### 2.1 C4 是什么、为什么不能跳过

**C4 不是形式主义**：它要核对的是"**用微软账户登录第三方启动器**"这件事在
微软/Mojang 的现行条款下是否被允许、有哪些边界。

- **现状**：**未核对**。这是四项里唯一没做的。
- **为什么它是 P0 而不是 P2**：它决定的是"这个功能能不能做"，
  而不是"怎么做"。**先做完再发现不允许，代价是整条链路返工。**
- **怎么做**：读 Mojang 的《Minecraft 最终用户许可协议》与微软的
  《Microsoft 服务协议》中关于**第三方客户端**与**账户令牌**的条款，
  以及 Minecraft 官方 FAQ 里对"第三方启动器"的表述。
  **结论与原文引用要写进 `docs/来源记录.md`。**

> **⚠️ 与红线的关系**：方案 §1.4 已禁掉"伪造官方会话 / 劫持验证接口 / 破解登录"。
> **C4 要核的是更细的边界**——例如"用官方 OAuth 拿官方令牌，
> 但不把令牌发给除 `api.minecraftservices.com` 以外的任何地方"是否已足够。
> **这不是"要不要违规"的问题，是"官方认可的接入方式到哪一步为止"的问题。**

## 3. 端点与权限范围

**全部取自封存项目的 `MicrosoftAuthEndpoints`，并已逐个确认为现行有效。**

### 3.1 微软身份平台

| 用途 | 端点 |
|---|---|
| 租户段 | **`common`**（见下方理由） |
| 设备码 | `https://login.microsoftonline.com/common/oauth2/v2.0/devicecode` |
| 令牌 | `https://login.microsoftonline.com/common/oauth2/v2.0/token` |
| 授权（若将来改用 PKCE） | `https://login.microsoftonline.com/common/oauth2/v2.0/authorize` |

### 3.2 Xbox / Minecraft

| 用途 | 端点 |
|---|---|
| Xbox 用户认证 | `https://user.auth.xboxlive.com/user/authenticate` |
| XSTS 授权 | `https://xsts.auth.xboxlive.com/xsts/authorize` |
| **Minecraft 登录** | `https://api.minecraftservices.com/authentication/login_with_xbox` |
| 档案（含 UUID / 名字） | `https://api.minecraftservices.com/minecraft/profile` |
| 权益/持有检查 | `https://api.minecraftservices.com/entitlements/mcstore` |

### 3.3 权限范围

```
XboxLive.signin offline_access
```

`offline_access` **是拿到刷新令牌的前提**——没有它每次启动都要用户重新登录。

### 3.4 为什么租户段固定 `common`

**照搬封存项目的判断，理由我核对过，成立：**

- 应用注册声明的是"**所有 Microsoft 帐户用户**"，对应的正是 `common`
- `consumers` 只认个人账户、`organizations` 只认工作/学校账户，**两者都比注册声明的范围窄**
- **没有 Xbox 档案的账户会在后面的 Xbox 步骤得到明确说明**（`AuthNoOwnership`），
  所以放宽入口**不会把问题藏起来**，只会让更多账户有机会走完

## 4. 授权流程：**设备码为主**

### 4.1 为什么选设备码（而不是本机回调 + PKCE）

| 理由 | 说明 |
|---|---|
| **已实测可用** | §1.1 三个端点全通。而 PKCE 的 `redirect_uri` 需要新注册一条、并处理端口占用与防火墙弹窗 |
| **零监听端口** | 不起本地 HTTP 监听 → **少一整类攻击面**（本机回调可被其他进程抢端口） |
| **公共客户端天然契合** | 注册现状就是"2 个公共客户端、0 个 Web 重定向 URI"，**与设备码一致** |
| **对用户的解释成本低** | 显示 `user_code` + 一个网址，用户自己完成——**不需要启动器打开浏览器** |

**代价（如实记）**：用户要**手动**去 `https://www.microsoft.com/link` 输入码。
比"点一下浏览器就登录了"多两步。**这是为了少一个监听端口换来的，值得。**

### 4.2 令牌链（四段，逐段失败都要有独立错误码）

```
① 设备码     POST /common/oauth2/v2.0/devicecode     → device_code + user_code
   轮询       POST /common/oauth2/v2.0/token          → MS 访问令牌（含 refresh_token）
② Xbox 用户  POST user.auth.xboxlive.com/user/authenticate
③ XSTS       POST xsts.auth.xboxlive.com/xsts/authorize → 拿 XSTS 令牌 + UHS
④ MC 登录    POST api.minecraftservices.com/authentication/login_with_xbox
   取档案     GET  api.minecraftservices.com/minecraft/profile → UUID + 名字
```

**每段都要单独可诊断**——这是从封存项目那条教训来的：
它的 `AuthPrerequisiteMissing` 曾被复用在"设备码请求失败"上，
**把真因（401 `AADSTS70002`）换成了笼统提示，排查被引向完全错误的方向。**

> **教训原话**：**错误码可以复用，错误说明不能丢。**
> **要求**：任何一层的失败，都必须把**上游返回的 `error` / `error_description` 原文**
> 带进诊断信息，而不是替换成人话。人话是**补充**，不是**替代**。

### 4.3 错误码（沿用封存项目的编号，语义已核对）

| 场景 | 错误码 | 要点 |
|---|---|---|
| 设备码过期 | `QUL-AUTH-0002` | 需要重新发起 |
| `client_id` 不被接受 | `QUL-AUTH-0005` | **几乎总是前置条件问题，不报成网络错误** |
| 无 Xbox 档案 | `AuthNoOwnership` | 账户没建过 Xbox 档案 |
| 未持有游戏 | 权益检查 | 走 `entitlements/mcstore` |

**要求**：`QUL-AUTH-0005` 的说明里必须**原样带上** `invalid_client` / `AADSTS*`
——这是封存项目用一次真实的排查失败换来的回归用例。

## 5. 令牌存储（安全基线）

| 项 | 要求 |
|---|---|
| 存储位置 | **Windows 凭据管理器**（`CredWrite` / `DPAPI`），**不写明文文件** |
| 刷新令牌 | 只在需要时读取；**不进日志、不进诊断包** |
| 日志脱敏 | 令牌、`user_code`、邮箱、UUID 一律**不得进日志**（见方案 §5.8 诊断脱敏） |
| 退出登录 | **必须真的删除凭据**，不能只清内存 |
| 离线账户 | **合法身份来源**，但其"无法进入正版验证服务器"的限制**每次启动前强制告知**；其 UUID **仅作本地标识，不冒充官方 UUID** |
