# P7.0 · 更新策略选型

> 依据：《Minecraft 启动器 · 架构规划与路线图（v1.2 正式版）》P7.0（P7 前置决策点）与决策 10。
> **本文件是决策记录。** 结论一旦固化，P7 主体按它实现；若要改选，需先改本文件。

---

## 1. 结论

**选定：自替换（rename + move，双阶段提交，进程内可回滚）。**

**仅在更新发生的那一刻**替换自身可执行文件；常态启动不引入任何额外进程、不读任何额外文件。

另两个方案落选的理由一句话概括：

| 方案 | 落选理由 |
|---|---|
| 引导器 | **破坏单文件承诺**，且**每次冷启动都要多一跳**——用常态成本换一次性收益 |
| 外部更新器 | 多一个分发物；其收益（回退）自替换用 `.old` + 待确认标记同样能拿到 |

---

## 2. 四维对比

| 维度 | 自替换 | 引导器 | 外部更新器 |
|---|---|---|---|
| **杀软误报** | 中 | 低 | 中 |
| **回退能力** | 强（设计后） | 天然 | 强（取决于工具） |
| **单文件形态** | **保持** | **破坏**（主程序 + 引导器） | 保持（更新器只在更新时需要） |
| **冷启动影响** | **无** | **每次 +1 跳** | 无 |

### 2.1 杀软误报：为什么"中"是可接受的

先纠正路线图初版假设里的一个偏差。初版把自替换标为"风险较高"，理由是"自我覆盖行为易被关注"。但**真正触发启发式的不是"谁来改这个文件"，而是"做了哪几类动作"**：

| 动作模式 | 信号强度 | 谁在做 |
|---|---|---|
| 把可执行文件写到临时目录并执行 | **高**（典型 dropper） | 内嵌助手型、自解压型 |
| 修改/删除正在运行的自身映像 | 中 | 自替换、外部更新器 |
| 用另一个进程替换主程序并重启 | 中 | 引导器、外部更新器 |
| 下载一个 exe 放到它该在的位置 | 中 | 三者都有 |

也就是说：**引导器与外部更新器同样会执行"替换主程序"这个动作**，只是换了个进程去做。而它们额外引入了"多一个可执行文件"或"从资源里写出一个 exe"——后者恰恰是上述风险最高的 dropper 模式。

自替换在本方案里的**具体动作只有两个**：

```
MoveFile(自身.exe        →  自身.exe.old)     // 运行中的 exe 允许被改名
MoveFile(updates/新.exe  →  自身.exe)         // 旧路径此时已空出
```

**没有写临时目录、没有从资源释放可执行文件、没有注入、没有常驻进程。**

仍然把它记为"中"而不是"低"，是因为我们**无法在本机验证**真实误报率——那需要正式签名的二进制与第三方多引擎检测。因此本维度附带两个强制缓解措施，并作为结论成立的前提：

1. **更新必须由用户显式发起**，不得静默自我替换。自主修改自身映像才是真正的大信号；用户点一下"立即更新并重启"把这件事变回普通操作。
2. **P7 必须完成代码签名评估与实施。** 未签名的自我替换风险显著高于已签名；若签名最终不可行，本结论作废，改选外部更新器（见 §6）。

### 2.2 回退能力：自替换需要设计，但可以做到强

路线图写得对："需自建回退机制"。本方案用三件事把它做实，见 §3.3。

### 2.3 单文件形态：这是决定性的一维

"单文件绿色版"写在本项目的目标里，也是它与 Electron / JRE 系启动器的核心区别（319488 B / 约 312 KB vs 70 MB+）。
引导器把它变成"主程序 + 引导器"两件，这是**产品形态的降级**，不是实现细节。

### 2.4 冷启动影响：引导器要付常态成本

实测冷启动到可交互 **330–449 ms**（预算 800 ms，宽松 1.5 s），余量约 350–470 ms。

一个 net48 写的最小引导器，仅 CLR 初始化就要 80–150 ms，加上进程跳转约 30 ms —— **大约吃掉余量的三分之一**，而且**每一次启动都要付**，只为了几个月一次的更新。

自替换的常态成本是 **0**：不更新时，程序里连一条相关代码路径都不会走到。

## 3. 选定方案的设计

### 3.1 常态

用户只运行一个 `QinmoUltimateLauncher.exe`。
不更新时，更新模块只做一件事：启动后异步检查一次发布清单（可关闭）。**不产生额外进程，不影响冷启动。**

### 3.2 更新流程

```
1. 检查发布清单（含新版本号、下载地址、SHA-256）
2. 用户点「立即更新并重启」
3. 下载新主程序到 <数据根>/updates/pending.exe
4. 校验 SHA-256 —— 不符即删除并报错，绝不进入第 5 步
5. 写 <数据根>/updates/pending.json：
      { 目标版本, 新文件哈希, 旧文件备份名 ".old", 阶段: "swapping" }
6. 执行两处 MoveFile（见 §2.1）
7. 若第 6 步任一步失败：**当场用 .old 改回原名**（进程仍活着，能自己收拾），
   报错退出，用户得到的是完好无损的旧版本
8. 成功：以新文件重启
```

### 3.3 回退（硬要求）

回退靠**"上次更新有没有活下来"**来判断，而不是靠新版本自报成功：

```
新版启动成功 → 删除 pending.json（并删除 .old，保留最近一代即可）
新版启动失败 → pending.json 仍在磁盘上
下次任何版本启动时，发现"有 pending.json 但阶段仍是 swapping"，
即判定上次替换后从未成功启动过：
    → 把 .old 改回原名
    → 删除 pending.json
    → 提示"上次更新未能启动，已回退到 <旧版本>"
```

**回退全程不触碰 `data/` 与 `game/`**：更新只操作可执行文件与 `updates/` 目录，用户配置、存档、缓存一律不动。这一点由路径白名单保证，而不是靠"注意别写错"。

### 3.4 三种失败各自的归宿

| 失败点 | 用户看到什么 | 系统处于什么状态 |
|---|---|---|
| 下载中断 | "下载失败，可重试" | 旧版本完好 |
| 哈希不符 | "文件校验未通过，已丢弃" | 旧版本完好 |
| 替换中途失败 | "更新未完成，已恢复原版本" | 旧版本完好（进程内已改回） |
| 替换成功但新版启动即崩 | "上次更新未能启动，已回退" | 下次启动自动回到旧版本 |
| 断电（窗口极窄） | 快捷方式打不开 | `.old` 仍在，可手动改名恢复；见 §5 已知残余风险 |

## 4. 与既有约束的一致性核对

| 约束 | 是否满足 | 说明 |
|---|---|---|
| 单文件绿色版 | ✅ | 更新路径不引入第二个分发物 |
| 不落地临时目录 | ✅ | 更新物落在 `<数据根>/updates/`，非系统临时目录；且**首启不涉及更新** |
| 冷启动 ≤800 ms | ✅ | 常态零影响 |
| 主程序 ≤5 MB | ✅ | 更新模块是几百行代码，量级可忽略 |
| 合规红线 | ✅ | 只从本项目的发布源取更新；不接触任何官方端点、不伪造签名 |
| 用户数据无损 | ✅ | 路径白名单，只动 exe 与 `updates/` |
| 零第三方依赖 | ✅ | 只用到 `System.IO` 与 `HttpWebRequest` |

## 5. 已知残余风险

1. **断电窗口。** 第 6 步的两个 `MoveFile` 之间断电，会留下"没有 `app.exe`、但有 `app.exe.old`"的状态。窗口是两个元数据操作之间的微秒级，但确实存在。
   缓解：`pending.json` 里记着旧文件名；用户重新运行 `.old` 即可自愈。
   **不为此引入常驻守护进程**——那会破坏单文件与冷启动两条约束。

2. **杀软误报无法在本机证伪。** 见 §2.1；结论以"完成代码签名 + 更新仅由用户显式发起"为前提。

3. **`.old` 会短暂占用一份磁盘副本**（约 312 KB）。可忽略。

---

## 6. 若要改选，选什么

如果 P7 阶段发现下述任一情况，**改选外部更新器**，本文件同步修订：

- 代码签名最终不可行；
- 真实分发后出现可复现的杀软误报，且经签名仍无法消除。

改选后的形态：主程序保持单文件，另发布一个独立的小更新器；
更新器等待主进程退出 → 校验哈希 → 原子替换 → 启动新版 → 失败则用 `.old` 恢复。
代价是多一个分发物（**但不影响常态冷启动，也不破坏"用户日常只需要一个 exe"**）。

**不会改选引导器。** 它要求用户接受"每次启动都多一跳"与"两件套"，而这两项恰好是本项目相对同类启动器的主要优势。
