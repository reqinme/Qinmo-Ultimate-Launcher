| **v2.2** | **按 S2 实测修正"零 CSS 模糊"的理由，并给模糊立可用边界**（U2 尖刺结论）——**① 事实更正**：约束 1 原文说"Windows 上 WebView2 的窗口级透明会**破坏** CSS `backdrop-filter`（平台缺陷）"，**S2 实测推翻**：透明与不透明下卡片区像素**逐字节相同（平均差 0.00 / 最大差 0，各 28500 采样点）**，模糊比值都是 **0.379**。**② 结论不变、性质变了**："零 CSS 模糊"从**"平台做不到"**变成**"我们主动不这么做"**——前者是妥协，后者是设计判断，**后者稳固得多**。**③ 新增约束 1a「模糊是可选的门，不是随便用的工具」**：技术上既然可用，就必须防它变成"到处毛玻璃"——**模糊只允许出现在浮层/抽屉/岛展开态这类"临时盖在内容之上"的位置，每处都要过评审；内容区卡片不得用模糊**（否则约束 2"纯色兜底也必须好看"失效）。**④ §9 那处"因为限制被迫放弃模糊…限制与品味刚好同向"改为**：**不是限制逼我们这么做，是我们自己选了它，而它恰好也对品味有利**——原文把功劳记给了平台限制，**于是项目白丢了一次"主动把品味当理由"的机会**（"我们不用玻璃拟态"该是因为它俗，不是因为我们做不到）。<br>**证据**：`docs/M0-尖刺报告.md` 附录 S2（6 格矩阵 + 判据先于数据确定 + 两条方法学教训）；截图 `spikes/s1-material/out/shot-{opaque,trans}-{blur,noblur}.png`。**⚠️ 同轮发现一处文档自相矛盾**（任务书说"窗口不透明 + 材质走 DWM" vs S1 结论"材质需要 `transparent(true)`"），**只记录未修改**，等裁决。 |
| **v2.1** | **主页插件网格**（用户定稿）——**① 新增 §4.6.8**：主页 = **大横幅（固定）+ 插件磁贴网格（自己滚）**；**插件头部（＋添加 / ⚙设置）固定在滚动区之外**（否则插件一多，这两个按钮就被滚走）；**12 列网格，插件可占 1/4 / 1/3 / 1/2 / 整行四档**，**拖动时按落点决定变哪一档**（拖拽同时完成"改顺序"与"改占宽"）。**② 每个插件三个操作缺一不可**：**⠿ 拖拽**（顺序与占宽，**不要在设置页里排**——那里看不到实时效果）、**⋮ 菜单**（隐藏 / 切形态 / 移到最前）、**⚙ 插件设置**（能看到全部可用插件，含当前未显示的）。**③ 三条硬规则**：**开关关掉＝主页不显示但设置里仍列着**（否则关掉就再也找不回来，这是"可配置界面"最容易犯的错）；**插件不是导航层级**（不参与一/二/三级，关掉不影响任何导航）；**同一件事不许两个入口**（与 §4.6.7 同源，故"最近运行"与"快速启动"的重叠需合并或降级）。**④ 形态两档**（丰富 / 极简）+ 一键预设（丰富 / 精简 / 极简）。**⑤ 插件清单七项**：最近运行 · 快速启动 · 下载队列 · 游玩统计 · **实例体检** · 我的分组 · 产品状态；其中**"实例体检"是本项目架构独占**——有能力描述符 + `reason`，"为什么这个实例不能用"是**可以算出来的**，不必等启动失败。**⑥ 空态不占半屏**：无数据时折叠为一行提示（空态是发现功能的入口，但不必用整块空间来喊）。<br>**同期**：身份规格 v1.1 补「四种身份来源 + 账户层/授权层拆分」；配置规格 v1.1 补「产品级作用域」。 |
| **v2.0** | **界面稿的文案纪律：禁止编造氛围文案**（用户抓错）——**① 起因**：用户问"**营火已经点好了是什么意思？我好像没有说要加这个**"。这句**是参考图里那个启动器的随机提示语**（Minecraft 的"启动器格言"传统），我把它当成"语气示范"，**照着调性另编了一句**塞进效果图。**② 危害**：**编出来的文案出现在给用户过目的界面里，会被当成设计的一部分**——这比写错颜色严重，因为**颜色错了看得见，编的文案会被当成约定**。**③ 根因与 §4.6.1.1 同一个：把"参考里恰好写着的东西"当成了"需求"**——那次抄的是别人的**功能**，这次抄的是别人的**语气**。**④ 新增 §4.6.1.3 四条纪律**：只能放"**事实性占位**"（真实字段：版本号/模组数/时间/磁盘占用/账户名/日期）；**禁止编造氛围文案**（问候语/格言/口号/俏皮话）；必须编的地方**显式标 `〈待定文案〉`**；**不得把参考项目的文案搬进我们的稿子**。**⑤ 具体结论：主页不放问候语**——理由是产品性的：主页纵向空间宝贵、同一句话看三遍就是噪音、**更糟的是它会藏住状态**（最显眼的位置放闲话，而"基岩版未授权"缩在小部件里）；**要留就留带信息的**（`1.20.1 · Fabric 已就绪 · 38 个模组`）。<br>**同轮定稿**：主页问候语**删掉**（只留日期）；**「实例体检」小部件保留**（用户确认——它是我们架构独占的：有能力描述符 + reason，"为什么这个实例不能用"是**可以算出来的**，不必等启动失败）；主页右侧小部件改为**我们自己的内容**（游玩统计 / 我的分组 / 下载队列 / 实例体检），**不抄参考图的功能**。 |
| **v1.9** | **二级栏跟着一级走（硬规则）+ 产品全局状态**（用户看图时抓错）——**① 新增 §4.6.1.1**：用户原话"上一级点击的是主页，然而下面却显示的是实例的分类，这对吗？"——**我错在一级选中「主页」却把「分组」放进二级栏，而分组是"实例"的分类**；**犯错的动机很自然：侧边栏中间有块空白，想填上**，所以这条**不能靠自觉，写成硬规则**：「**二级栏内容由当前一级决定；一级没有下级时二级栏就是空的；不许把别处的下级拿来填**」，并给出**四页对应表**（主页＝空 / 实例＝产品+分组 / 下载＝可下载类型+装到哪个实例 / 设置＝设置类别+按产品）。**② 形式纪律**：二级栏**用竖排列表（与一级同类）**，**不用横排分段控件、不用横排胶囊**——理由：形式不同会被读成"另一类东西"，那就不构成"下级"（我一度在两处用了第三种形式，已改回）；并记明**横排分段控件只用于"筛选/排序"这类页内控件，不用于表达层级**。**③ 新增 §4.6.1.2**：「当前产品」是**全局状态**，主页横幅 / 实例页二级栏 / 下载页「装到」**三处都能切、三处联动**，**必须是同一个状态源**（不许各存各的）。<br>**四页对照图**：`docs/_artifacts/_archive/v07-0-rule.png`（规则表）、`v07-1-home.png`、`v07-2-instances.png`、`v07-3-download.png`、`v07-4-settings.png`。 |
| **v1.8** | **主界面改版：参照官方启动器的结构**（用户决定换布局）——**① §4.6.1 改为「账户 + 产品 + 导航」四段式**：账户卡 / **产品段（唯一允许增长的一段）** / 固定七项导航 / 下段工具，并新增**留白纪律**（用户明确选择"就让它空"——那段空间是**预留给产品列表增长的**，填了将来加产品就得挪走；同时**否决**了"把实例列表搬进左栏"因为它与导航争夺同一件事）；**② §4.6.5 补「主界面改版」小节**：写明**借结构、不借表达**的界线（布局不受版权保护；文字全部自写、图形全部自绘、配色用我们的令牌、**不用官方任何素材**），并给出主界面五区的职责；**③ 新增「封面图的纪律」（红线级）**——封面图**一律自绘或用户自有**，**禁止使用 Mojang / Microsoft 的官方素材、素材包、商店截图**；自绘方案要求**"按实例 id 稳定生成配色"**（同一实例每次颜色必须一样，否则用户无法靠颜色认实例，且不可测试）；**④ 各层随产品变不变**改为覆盖新版五区（产品差异只出现在**产品段选择 / 二级左栏 / 推荐位 / 横幅字段**四处）。<br>**素材说明**：本版效果图的横幅与缩略图是**中性渐变占位并显式标注**——真实产品此处需要自绘或用户自有的封面图，**这是一个尚未解决、且不该由我替你决定的问题**。 |
| **v1.7** | **把"产品维度"重构成两层结构**（查同类实现后修正）——**① §4.6.4 重写为「两层结构：通用能力 与 产品详情」**：起因是补基岩能力时**连着别扭两次**（架构测试的禁用词表把"产品名"与"内容类型"混在一起），查 `repos/Portal`（同时支持两种形态，UI 层 **79 处 / 19 个文件**、Core 层 **55 处**产品分叉，且**没有任何能力矩阵**）后看清根因——**我把"详情层"的东西放进了"实例层"的枚举**。**采纳它的分层、不采纳它的写法**（那是方案 §3.3 明确要消灭的 `if (product == ...)`）。**② 代码侧拆分**：`CapabilityKey` 只留**通用**能力（14 项，含 `DetectInstalled`）；新增 `DetailKey`（`Shaders` / `BehaviorPacks` / `SkinPacks` / `Loaders` / `ProductDependencies`）与 `InstanceDetail`（`FileSystem` / `StoreSandbox` / `Universal`）；`Capabilities` **两张表分开存**，让"通用项 vs 产品专属项"由**类型**区分。**③ 一条命名纪律**：**产品名不是决定能力的那个轴**——`BedrockPackaging::Gdk/Uwp` 被架构测试拦下，改为 `Packaging::FileSystem/Sandbox`。**理由有证据**：同一个 `StoreSandbox` 详情，给沙箱形态后连内容包也不能管了——**"同一产品内形态不同"与"产品不同"由同一个机制表达，不需要为形态另开一个"产品"**。品牌名只该出现在 **Provider 适配代码**与**面向用户的 `reason` 文案**里（参照：它 134 处 vs 我们目标 1 处）。**④ 新增 §4.6.5「界面各层怎么随产品变」**：明确**一级页面完全不随产品变**（含侧边栏七项）、**主页只换文案细节**、**只有二级左栏与下载类型真正换**——**这是两层结构换来的东西：产品差异不会把界面复制成两份**。 |

## 1. 设计意图（一句话）

**靠系统材质建立纵深，靠不透明度阶梯与描边建立层次，靠灵动岛承担"此刻发生什么"，靠能力描述符让界面不认识具体游戏。**

**这一层的差异化定位**（方案 §1.2 的第一条）：界面质感是**唯一"看一眼就知道不同"的维度**。
**因此它值得多花时间**——而下载进度条的动画之类，追平即可。

## 2. 硬约束（**不可协商，其余设计都是它的推论**）

| # | 约束 | 来源 / 理由 |
|---|---|---|
| **0** | **窗口必须启用 `transparent(true)`** | 🔴 **材质能不能存在的前提**。实测：不加它时 `apply_mica` / `apply_acrylic` / `apply_tabbed` **全部返回 `Ok` 但毫无可见效果**——因为 WebView2 默认以不透明背景填满窗口，把 DWM 材质整个盖住。像素分析证据见 `docs/M0-尖刺报告.md` §2。**这条不是实现细节，是前提** |
| **1** | **窗口取 DWM 系统材质；界面层零 CSS 模糊** | 🔵 **v2.2 修正：这条的理由变了**。原写法是"Windows 上 WebView2 的窗口级透明会**破坏** CSS `backdrop-filter`（平台缺陷）"——**S2 实测推翻了这个预判**：透明与不透明下，卡片区像素**逐字节相同（平均差 0.00 / 最大差 0）**，模糊比值都是 0.379。所以**"零 CSS 模糊"从"平台做不到"变成"我们主动不这么做"**——**结论不变，但它是设计判断，不是能力妥协**。详见 `docs/M0-尖刺报告.md` 附录 S2 |
| **2** | **纯色兜底也必须好看** | 若设计靠模糊支撑，则 Win10 / 关闭透明效果的机器上界面即废。**层次必须靠排版、描边、留白成立** |
| **3** | **层次只用三样东西表达**：不透明度阶梯、描边、留白 | 这是约束 1 的补偿方案，也是设计语言的收敛结果。**v2.2 补充**：本条**不因 S2 通过而放宽**——模糊**可用但不作主力**（见约束 1a） |
| **1a** | **模糊是"可选的门"，不是"随便用的工具"** | **v2.2 新增（S2 结论的落地）**。既然技术上可用，就必须防止它变成"到处毛玻璃"：**模糊只允许出现在浮层/抽屉/岛展开态这类"临时盖在内容之上"的位置**，**每个位置都要过评审**；**内容区卡片不得用模糊**（那会让"纯色兜底也必须好看"这条失效）。**理由**：能用的东西会被滥用，而**约束 2 要求的恰恰是"不靠模糊也成立"** |
| **4** | **界面代码永不写十六进制色值** | 只能引用语义令牌（由 lint 强制） |
| **5** | **动效只用 `transform` 与 `opacity`** | 不触发布局、不掉帧 |
| **6** | **禁止**：多层阴影叠加、发光扩散、渐变叠模糊 | 阴影**只有 4 档**（`elev.0`–`elev.3`），不许即兴加 |
| **7** | **禁止**：布局动画、>300ms 的等待动画、并行 >2 组动画 | 除了转鼓（且需在"减少动态效果"下静止） |

## 3. 三层材质

```
┌─ 第一层 · 窗口背景 ────────── DWM 材质（Mica → Acrylic → 纯色 三级降级）
│  ┌─ 第二层 · 容器面板 ──────── 半透明填充 8–12% + 1px 语义描边 + 圆角 12–16px
│  │  ┌─ 第三层 · 内容卡片 ────── 不透明或高不透明度填充 + 圆角 8–12px + 更弱描边
│  │  └──────────────────────────
│  └────────────────────────────
│        ╭──── 浮层：灵动岛 / 弹窗 / 菜单 ────╮   最高对比 + 内描边 + 单层投影
└────────┴────────────────────────────────────┴──
```

### 3.1 三层的具体参数

| 层 | 填充 | 描边 | 圆角 | 投影 |
|---|---|---|---|---|
| **窗口背景** | DWM 材质（不自己画） | 系统默认值 | 系统默认值 | 系统默认值 |
| **容器面板** | `surface.panel`，**不透明度 8–12%** | `stroke.subtle`，1 px | `radius.lg`（12–16 px） | 无 |
| **内容卡片** | `surface.card`，不透明或高不透明度 | `stroke.subtle`（更弱） | `radius.md`（8–12 px） | 无 |
| **浮层**（岛/弹窗/菜单） | `surface.raised`，最高对比 | `stroke.strong`（内描边） | `radius.xl` | **单层** `elev.2` |

**纪律**：
- **不透明度阶梯是固定的档位，不是随手调的数值**。需要"比 panel 亮一点、比 hover 暗一点"时，**从成阶调色板里取**（见 §5）。
- **描边是 1 px，不是"差不多 1px"**——它承担了本该由模糊承担的"分层"职责。
- **卡片本身不带投影**；投影只用于**浮层**。这是"层次靠描边，不靠阴影"的具体体现。

### 3.2 字体与排版（**v1.2 补：此前整份规格缺字体规格**）

> **前提**：这是**中文界面**，且**运行在 Windows 上**。
> 字体选型的第一原则是：**用系统自带的，不打包字体**——打包 CJK 字体一个就 10–20 MB，直接吃掉 25 MB 体积预算的一半。

#### 字体族与回退链（**已在本机实测**）

```
界面（UI）
  "Microsoft YaHei UI"   ← Windows 自带，UI 专用变体（比 "Microsoft YaHei" 更适合界面）
  "Noto Sans SC"          ← 已确认本机存在（实测）
  system-ui
  sans-serif

等宽（日志 / Console / 代码）
  "Cascadia Mono"        ← Win11 自带
  "Consolas"
  ui-monospace, monospace

拉丁文/数字（**可选增强，默认不启用**）
  "Inter" → system-ui    ← 见下方"关于 Inter"的结论
```

#### 关于 Inter：**默认不打包**（v1.3 消解一处矛盾）

> **⚠️ 此前本节自相矛盾**：先说"**不打包字体**"，又在字体栈里写"若决定内置 Inter（约 300 KB）"。

**结论**：

| 项 | 决定 |
|---|---|
| **默认** | **只用系统字体**（`Microsoft YaHei UI` / `Noto Sans SC`）——**不打包任何字体** |
| Inter 的定位 | **可选增强，不进一期**。若 M4 阶段实测发现"雅黑的拉丁字形在数字/英文上不够好"，**那时再单独决策** |
| 若将来引入 Inter | ① 许可为 **SIL OFL 1.1**（可自由分发，需保留许可文件）；② 仅子集化拉丁字符（**约 100–150 KB，不是 300 KB**）；③ **必须记入 `docs/来源记录.md`** |
| **理由** | 0 体积成本优先；**Inter 解决的是"好看一点"，不是"缺了不行"**——而 25 MB 体积预算要留给真正的功能 |

**顺带修正一个数字**：外部建议里的"约 300 KB"偏大——Inter 完整字重族确实有几百 KB，
但**只取 Regular/Medium 两个字重的拉丁子集约 100–150 KB**。这类数字**必须按实际子集核算，不能照抄**。

> **⚠️ 修正一处外部建议**：有人建议"优先 WQY（文泉驿）、回退 Noto Sans CJK SC"——**两者都不适合本项目**：
> | 建议 | 为什么不采纳 |
> |---|---|
> | **WQY 优先** | WQY 是**Linux 发行版**为补 CJK 覆盖而带的字体，**Windows 上默认不存在**。写它会静默回退，等于没写 |
> | **"Noto Sans CJK SC"** | 这是**Google 上游的族名**；Windows 上的实际族名是 **`Noto Sans SC`**（本机实测确认）。**名字写错 = 回退失效** |
>
> **纪律**：**字体族名必须用本机实测确认过的名字**，不能照抄其它平台的写法。这条与"许可证要用源码核实"是同一类纪律。

#### 字号阶梯（4 的倍数，与 `space` 阶梯同源）

| 语义 | 字号 | 行高 | 用途 |
|---|---|---|---|
| `font.caption` | 11 px | 16 px | 状态条、辅助说明 |
| `font.body-sm` | 12 px | 18 px | 次要信息、表格 |
| **`font.body`** | **13 px** | **20 px** | **正文默认**（Windows 桌面软件的舒适区） |
| `font.body-lg` | 14 px | 22 px | 强调正文、列表项 |
| `font.title-sm` | 16 px | 24 px | 卡片标题 |
| `font.title` | 20 px | 28 px | 页面标题 |
| `font.display` | 28 px | 36 px | 首页主标题 |

**字重只用三档**：`400` / `500`（强调）/ `600`（标题）。**不用 700+**——CJK 粗体在小字号下发糊。

#### 行高与中英混排

| 项 | 规则 |
|---|---|
| **行高** | 中文正文 **1.5–1.6**（比拉丁文的 1.4 略宽）；紧凑列表可用 1.4 |
| **中英混排间距** | **不手动加空格**——现代字体（雅黑/Noto）已含侧边距。**手动加空格会在缩放和不同字体下变成新的不齐** |
| **数字** | 表格与统计数字用 `font-variant-numeric: tabular-nums`（**等宽数字**，避免跳动） |
| **标点** | 中文标点用全角，但**括号内是纯英文/数字时用半角** |
| **截断** | 单行 `text-overflow: ellipsis`；多行最多 2 行（列表项）或 3 行（描述） |

#### 字体加载

**不打包、不远程加载**（与 §2 约束"不加载远端脚本"同源）。
字体栈**写在令牌文件里**，组件只引用 `font.family.ui` 之类的语义名——**与颜色令牌同一套纪律**。

### 3.3 DPI 缩放与响应式（**v1.2 补**）
> **方案 §7 的性能预算表里有"材质降级"一行**（高对比度 / 省电 / 远程桌面 / Win10 四场景 100% 正确降级）——
> **而"150% / 200% 下不模糊、不裁切"这条验收在现行方案里不存在**，它来自**已封存的第一轮项目**
> （`_archive/docs/` 内的 C#/WPF 方案，章节号 `§6.5`）。
>
> **本条据此确立**：**高分屏正确性应作为我们自己的验收项**（而不是"继承来的"）——这正是本节存在的理由。

#### 缩放策略

| 项 | 规则 |
|---|---|
| 基准 | **以 100% 为基准设计**，其余比例靠**相对单位**自动跟随 |
| **描边** | ⚠️ **物理像素线不能等比缩放**。见下方"描边的具体 CSS 策略" |
| **禁止** | **禁止用全局 `transform: scale()` 缩放 UI**（会让文字与描边一起发虚） |
| **圆角** | **等比缩放**（用 `rem` / `em`），因为圆角是"形状"不是"像素线" |
| **间距** | 等比缩放（`space` 令牌基于 `rem`） |
| **字号** | 等比缩放，但**最小值钳制在 11 px**（缩放后不得更小） |
| **图标** | 等比缩放；**线性图标必须用 SVG**（位图在任何非整数缩放下都糊） |
| **WebView2** | 需确认 WebView2 的 DPI 感知与 Tauri 窗口一致（**列入 M4 门禁的验证项**） |

**纪律**：**"像素线"（描边）与"形状"（圆角、间距、字号）用两套单位**——
混用是高分屏界面发虚的头号原因。

#### 描边的具体 CSS 策略（**v1.3 补：此前只说"用某写法"，不可执行**）

> **此前的问题**：原文写"用 `1px` 配合 `transform: scale()` 的替代写法，**或**改用 `0.5px` + `devicePixelRatio` 判定"——
> **既没给写法，又给了两个互斥的方向，还顺手建议了一个被本规格禁止的做法（全局 scale）**。现在定死：

```css
/* 令牌层：定义"发丝线"的厚度 */
:root {
  --hairline: 1px;
}

/* 高分屏：>=2 设备像素比时用半分线，让它在物理像素上仍占 1 px */
@media (min-resolution: 2dppx) {
  :root { --hairline: 0.5px; }
}

/* 组件层：只用令牌，不写字面值 */
.panel { border: var(--hairline) solid var(--stroke-subtle); }
```

| 规则 | 内容 |
|---|---|
| **默认** | `--hairline: 1px` |
| **`@media (min-resolution: 2dppx)`** | `--hairline: 0.5px`（在 200% 缩放下，0.5 CSS px = 1 物理 px） |
| **禁止** | ❌ **禁止全局 `transform: scale()` 缩放 UI**（文字与描边一起糊）<br>❌ **禁止把描边写成 `0.5rem` / `2px`**（那会随字号或比例变成粗边）<br>❌ **禁止在组件里写字面厚度**，只能引用 `--hairline` |
| **Tauri 侧** | 需确认 **WebView2 的 DPI 感知与 Tauri 窗口一致**，否则 CSS 的 `dppx` 与真实缩放会对不上 → **列入 M4 门禁验证项** |

#### 响应式断点（3 档，**v1.3 修正：删掉不可达的 compact**）

> **⚠️ 此前这里有个自相矛盾**：写着 `compact < 1140px`，而**最小窗口就是 1140 px** → **该断点永远不可达**。
> **处置：删掉 `compact`**（不做"缩到 1140 以下"的窄布局——桌面启动器没有这个场景）。

| 断点 | 宽度 | 布局 |
|---|---|---|
| **`default`** | **1140–1440 px** | **标准布局**（**最小窗口宽就是 1140 px**，故这是最窄的情况） |
| `wide` | 1440–1920 px | 主页卡片从 3 列变 4 列；内容区留白加大 |
| `ultrawide` | > 1920 px | 内容区**居中限宽**（最大 1600 px），不做无限拉伸 |

> 最小窗口尺寸 **1140 × 715**（与 NexBox 的实测值一致——那个尺寸能容纳左导航 + 三列卡片）。
> **窄屏适配不在本项目的范围内**——它是 Windows 桌面应用，不是响应式网站。

#### 触控与点击目标

| 项 | 最小尺寸 |
|---|---|
| 主要按钮高度 | **32 px** |
| 图标按钮点击区 | **32 × 32 px**（图标本身可 16–20 px，但**点击区不得小于 32**） |
| 列表项高度 | 28 px（紧凑）/ 36 px（默认） |
| 输入框高度 | 32 px |

**理由**：即使不做触屏，**32 px 也是"鼠标不容易点错"的下限**；小于此值的图标按钮在误点率上会明显上升。

#### 4.1.1 状态条的两张表（**v2.4 新增：机器可核对**）

| `source` | 源 | yes |
| `speed` | 网速 | yes |
| `runtime` | 运行时 | no |
| `memory` | 内存占用 | no |

（**常驻**那一列用 `yes` / `no` 而不是"是/否"：**机器要读它**，

**尺寸与真实的变量**：

| 变量 | 作用域 | 值 |
|---|---|---|

> `"version"` **逐字相同**（同一个脚本钉着这三处）。上面 ASCII 里的
> `v0.1.0` 只是草图 —— 三处一致比"草图里写的是什么"重要。

### 4.2 导航是**两段式**（本层最重要的结构决定）

| 区域 | 生成方式 | 为什么 |
|---|---|---|
| **产品相关区**（内容 / 存档 / 下载类型） | **能力描述符自动生成** | Java 版有"光影"、基岩版有"行为包"，差异必须自动消化 → **消灭 `if (product == "java")` / `if (buildType == UWP)`** |
| **工具区（百宝箱）** | **入口固定、工具全部可见** | 百宝箱的意义就是"我想找个工具，能看见它"；藏进二级或按能力过滤掉就失去了作用 |

**不适用的项 = 禁用态 + 一句原因，永不隐藏。**
例：基岩版实例上"光影管理"显示不可用，并注明"基岩版不支持光影"。
**理由**：找不到东西的挫败感，比看到一个带解释的禁用按钮更糟。

#### 4.5.1 事件契约表（元素 × 事件族）

> **为什么需要这张表**：标题栏的**根部**处理三个事件族 —— `pointerdown` = 拖窗口 · `dblclick` = 最大化/还原 · `contextmenu` = 系统窗口菜单（见 §4.5.3）。每个交互元素都必须对**每一个**事件族明确表态。
>
> 🔴 **而"漏一格"是有前例的**：`faa7fa1` 那个真 bug 就是这张表缺一格的后果 —— 三个窗口控制排除了 `pointerdown`、**漏了 `dblclick`** ⇒ 双击「关闭」**先最大化再关闭**。同一种形状还有一次：`disabled` 的搜索框**仍然会收到 `pointerdown`**（`disabled` 拦的是 click 与 focus），所以那一格也不能省。
>
> **符号**：`吞` = 事件在**标题栏根部**被那道闸拦下（`TitleBar.tsx` 的 `swallowed()`，判据来自 `contract.ts` 的 `swallows()`）· `冒` = 交给根部（那正是"空白处"的定义）· `不做` = 明确决定不处理（理由见下方三个决定）· `不适用` = 不在标题栏的 DOM 子树里，靠结构成立。
>
> ⚠️ **v2.2 的一处修正**：`吞` 早先写的是"子元素自己 `stopPropagation`"，而实现时**实测**发现 `disabled` 的搜索框**收不到 React 的合成 `onDoubleClick`**（React 对"实际禁用"的表单元素不派发鼠标类合成事件）⇒ 把排除挂在元素上会**静默漏掉一格**（双击搜索框冒到根部、窗口被最大化）。所以那道闸搬到了**根部**，用 `data-titlebar-item` 反查事件落在哪个元素上。抓到这件事的就是本表的第一个产物（`contract.test.tsx` 的逐格遍历），它**第一次跑就红了**。
>
> **状态**：`已实现` · `结构性`（靠 DOM 结构，不靠事件处理）· `未实现`。

**三个决定**（v2.2 定稿）：

1. **`contextmenu` 一律「不做」**。§4.5.3 的原文要求"空白处右键 → **系统窗口菜单**（含移动/大小/最小化/关闭）"，而：① 同一集合系统已经由 `Alt+Space` 提供；② 代价落在 `SetWindowSubclass` + `WM_NCRBUTTONUP` / `TrackPopupMenu`，而那是**一处能弄坏输入**的改动，而输入层刚吃过一次"漏排除一个事件族"的亏；③ **"不做"也必须写进表里** —— 本节自己就是"留空 ⇒ 静默缺陷"的活例子。**留待 M4.5 之后再评估。**
2. **`Win + ←/→/↑` 是平台事实，不是我们的按键功能**：它由 `decorations: false` + `resizable: true` 交给系统执行，我们**没为它写一行代码**。而 §4.5.4 的降级线正压在这条事实上 ⇒ 它只能**在真窗口里人验**（jsdom 没有窗口管理器）。
3. **高 DPI 的命中区按物理像素核对**（§4.5.5）：窗口矩形、拖动区、按钮命中区一律以物理像素为准；逻辑像素只是布局单位。本机实测：150% 缩放 ⇒ 逻辑 1280×800 = 物理 1942×1213。

**留白纪律（v1.8 新增，用户明确选择）**：

> **产品段与下段之间的空白是有意留的，不填。**

> **理由**：那段空间是**预留给产品列表增长的**。官方启动器在这里堆了 7 个产品，
> 我们只有 2 个——**一旦把别的东西填进去，将来加产品时就得把它挪走**。
>
> **对照**：我们考虑过"把实例列表搬进左栏填满"，**已否决**——实例列表属于「实例」页，
> 搬进左栏会**与导航争夺同一件事**（同 §4.6.6 的判据："同一件事不许两个入口"）。

**为什么下段的顺序好**（值得记，因为**它比同类产品自洽**）：
下段从**操作**渐进到**静态**——账号管理/百宝箱是「要干活的」，设置/关于是「配置与信息」。

#### 4.6.1.1 🔴 二级栏跟着一级走（**v1.9 新增，硬规则**）

> **这条是用户在看图时抓出的错误**，值得记下经过，因为**这个错误非常容易再犯**。

**用户的原话**：

> **"上一级点击的是主页，然而下面却显示的是实例的分类，这对吗？不应该是我上一级点击的是实例吗"**

**我当时错在哪**：一级选中的是「主页」，二级栏却显示了**「分组」**——
而**分组是"实例"的分类**。我之所以这么放，动机很自然：**侧边栏中间有一块空白，想把它填上。**

> ⚠️ **正是这个"想填空白"的动机导致了错误。** 所以这条不能靠自觉，必须写成硬规则。

##### 规则

> **二级栏的内容由当前一级决定。一级没有下级分类时，二级栏就是空的。**

> （与 §4.1.1 的 `yes`/`no` 同一个约定）。

> **每个 `static` 二级项的路径都必须有一条同路径的路由，除非它就是一级页** ——

> **不用于表达层级。**

#### 4.6.1.2 「产品」是全局状态（**v1.9 新增，用户定稿：方案 A**）

**问题**：`实例` 与 `下载` 两页也按产品分。若产品只能在主页选，用户切到实例页时**界面不知道该显示哪个产品**。

**定稿**：

> **「当前产品」是一个全局状态**，主页、实例页、下载页**三处都能切换**，**三处联动**。

| 在哪切 | 形态 |
|---|---|
| **主页** | 大横幅顶端的胶囊（"Java 版 / 基岩版"） |
| **实例页** | **二级栏顶部的产品列表**（Java 版 / 基岩版，各带实例数） |
| **下载页** | 二级栏的**「装到」**区（选目标实例，产品随之确定） |

**为什么不是"只在主页选"**：**"我在看哪个产品的实例"是实例页的必要前提。**
若产品选择器不在这页，用户切产品要**先回主页**，多一次跳转。

**实现约束**：**三处必须是同一个状态源**，不许各存各的（否则会出现"主页显示 Java、实例页显示基岩"这类不一致）。

#### 4.6.1.3 🔴 界面稿里的文案纪律（**v2.0 新增**）

> **这条防的是"我编的文案被当成需求"。** 起因见下。

**用户的原话**：

> **"营火已经点好了是什么意思？我好像没有说要加这个"**

**我错在哪**：用户给的一张参考图里有一行**"营火已经点好了。"**——
那是**那个启动器里的随机提示语（Minecraft 的"启动器格言"传统）**。
我把它当成了"问候语的语气范围"，**照着调性又编了一句**塞进效果图。

**危害**：**它出现在给用户过目的界面里，用户会以为那是设计的一部分。**
这比写错一个颜色严重——**颜色错了看得见，编出来的文案会被当成约定。**

> ⚠️ **根因与 §4.6.1.1 是同一个：把"参考里恰好写着的东西"当成了"需求"。**
> 那次抄的是别人的**功能**（固定的世界 / 固定的服务器），这次抄的是别人的**语气**。

##### 规则

| # | 规则 |
|---|---|
| 1 | **效果图与规格里的文字，只能是"事实性占位"**——真实存在的字段（版本号、模组数、时间、磁盘占用、账户名、日期） |
| 2 | **禁止编造"氛围文案"**：问候语、格言、口号、俏皮话 |
| 3 | **必须编的地方，显式标成 `〈待定文案〉`**，让用户一眼看出这是占位而不是设计 |
| 4 | **不得把参考项目里的文案搬进我们的稿子**（哪怕只是"语气示范"） |

##### 一个具体结论：主页不放"问候语"

> **主页那块位置不放氛围文案。** 日期（事实）可以留，**问候语删掉**。

**理由恰好是产品性的**：
- 主页纵向空间宝贵（右侧还有一列部件），**一句不带信息的问候占一行**
- **用户每次打开都看到同一句话，三遍以后就是噪音**
- 更糟的是**它会藏住状态**：把最显眼的位置用来放闲话，而"**基岩版未授权**"却缩在小部件里

**要留一句话，就留带信息的**：`1.20.1 · Fabric 已就绪 · 38 个模组 · 依赖已校验`。
**那是状态，不是问候。**

#### 4.6.4 ⭐ 两层结构：**通用能力**与**产品详情**

> **这一节是修正后重写的。** 起因：给基岩版补能力时**连着别扭两次**——
> 架构测试的禁用词表把"产品名"与"内容类型"混在一起、通用项与产品专属项挤在同一张表。
> 查了同类实现后看清根因：**我把"详情层"的东西放进了"实例层"的枚举。**

##### 参照：一个同时支持两种产品的实现怎么分层

`repos/Portal`（Avalonia，同时支持两种 Minecraft 形态）的 `MinecraftInstance`：

| 层 | 它放什么 | 是否按产品分叉 |
|---|---|---|
| **实例层** | 目录、名称、图标、备注、收藏、游玩时长、磁盘占用 | **完全通用** |
| **详情层** | 一种形态：JVM 参数 / 内存 / 独立实例；另一种：自己的 `Config` | **各自一套** |

**但它用 `if (Type == X)` 贯穿全局**：UI 层 **79 处 / 19 个文件**，Core 层 **55 处**，
**合计 134 处**，且**没有任何"能力矩阵"**。

**那是方案 §3.3 明确要消灭的写法**（"界面里到处是 `if (product == "java")`"）。
**所以我们不照抄它的写法，只采纳它的分层。**

##### 我们的两层

```
通用能力（crates/qul-core/src/caps.rs → CapabilityKey）
  CreateInstance · Launch · Preflight · DetectInstalled
  Mods · ResourcePacks · Worlds · Configs · Screenshots
  CrashAnalysis · LogFiltering · Snapshots · Isolation · OfflinePlay
  ↑ 任何产品都成立。这一层里**不许出现产品专属概念**（由架构测试强制）。

产品详情（→ InstanceDetail + DetailKey）
  实例**恰好持有一种**详情，由**类型**保证"不可能两者都是、也不可能都不是"
  FileSystem    （实例数据是普通文件）→ 光影 · 加载器
  StoreSandbox  （数据在 MSIX 沙箱里）→ 行为包 · 皮肤包 · 依赖组件
  各详情还必须**如实声明自己不支持的那些**（带原因），而不是省略
```

##### 🔴 一条我认为重要的命名纪律：**产品名不是那个轴**

`DetailKey` 的成员是**按能力**命名的（中性的 `BehaviorPacks`，**不带产品名**）。
同理 `InstanceDetail` 的变体也**按"数据在哪"命名**，而不是按品牌：

| 曾经的（被架构测试拦下） | 现在的 |
|---|---|
| `InstanceDetail::Bedrock(BedrockPackaging)` | `InstanceDetail::StoreSandbox` |
| `BedrockPackaging::Gdk / Uwp` | `Packaging::FileSystem / Sandbox` |

**为什么这个改名不只是"换个词"**：

> **决定"能不能管内容包"的不是"这是哪个产品"，而是"数据在普通文件里还是在沙箱里"。**

**证据**：同一个 `StoreSandbox` 详情，给沙箱形态之后**连内容包也不能管了**——
**"同一产品内形态不同"与"产品不同"造成的差异，由同一个机制表达**，
**不需要为形态另开一个"产品"。**

**品牌名只该出现在两个地方**：**Provider 的适配代码**（那本来就是产品专属的）
与**面向用户的 `reason` 文案**。

##### 界面怎么用它（**界面逻辑只有两行**）

```
第一段（通用）：遍历 CapabilityKey::ALL，取 enabled 的项
第二段（详情）：遍历 DetailKey 的并集，取 enabled 的项
两者拼起来 = 该实例的第二级左栏
```

##### 纪律（四条）

| # | 规则 |
|---|---|
| **1** | **界面不许出现任何产品名**。由 `crates/qul-core/tests/architecture.rs` 的架构测试强制：**生产代码的代码与字符串**里出现产品名即失败（注释与测试除外） |
| **2** | **`reason` 必须是人话且面向用户**——它是**产品信息**，不是错误提示 |
| **3** | **新增能力时必须显式决定它属于哪一层**：通用（`CapabilityKey`）还是详情（`DetailKey`）。**放错层会被测试拦住** |
| **4** | **详情枚举与产品枚举都不许用品牌命名**。按"数据在哪 / 有什么能力"命名 |

##### ⚠️ 诚实记下这条边界

**"界面完全不提到产品"做不到 100% 干净。**
因为"哪个详情会出现哪些条目"这份数据**必然要提到产品**——
**我们能做的是把它压缩到 Provider 侧一处，而不是消灭它。**

**对照**：参照实现是 **134 处**；**我们的目标是 1 处**（Provider 的能力表）。
**这个数字本身就是这条设计值不值得的判据。**

| **用户自有** | 玩家自己的游戏截图 |
| **中性占位** | 没有图时用中性渐变 + 明确标注"占位" |

**"按实例 id 稳定生成配色"很要紧**：**同一个实例每次看到的颜色必须一样**——
随机配色会让用户无法通过颜色认实例。这也让它**可测试**（同输入同输出）。

##### 各层随产品变不变

| 层 | 随产品变吗 | 说明 |
|---|---|---|
| **标题栏** | ❌ 不变 | 品牌与窗口控制都一样 |
| **左栏 · 账户卡 / 导航段 / 下段** | ❌ **完全不变** | 与产品无关 |
| **左栏 · 产品段** | ✅ 选择变 | 选中的产品决定「实例」页看谁 |
| **大横幅** | ⚠️ **内容变、结构不变** | 仍是"当前实例的画面 + 状态 + 主操作"，只是具体字段随产品 |
| **搜索行** | ❌ 不变 | |
| **内容区** | ⚠️ **卡片内容变** | 仍是横排卡片 |
| **右栏** | ⚠️ **推荐内容变** | 推荐位随产品（Java 推模组/整合包；基岩推行为包/皮肤包） |
| **二级左栏** | ✅ **换一整套** | 见 §4.6.4 |

**一句话**：**产品差异只在"产品段选择、二级左栏、推荐位、横幅字段"四处出现；
其余页面完全共用。** 这就是两层结构换来的东西。

#### 4.6.6 一级页面也要能分辨产品

> **此前的漏洞**：四张效果图**只有一种产品的实例**，而**实例列表连"产品"列都没有**——
> 用户看不出哪个实例属于哪个产品。**这是"产品维度在界面上不可见"的缺陷。**

| 位置 | 怎么显示产品 |
|---|---|
| **实例列表** | **新增「产品」列**——与「加载器」列**分开**。因为一种产品的实例没有加载器，混在一列会让两种语义打架 |
| **主页的当前实例卡** | **产品徽标**（小色块 + 短文字），放在实例名旁 |
| **主页的「最近运行」卡** | **产品徽标**（小尺寸） |
| **标题栏** | **不做产品切换器**——切换产品 = 选择实例，那是「实例」页的事。**标题栏多一个切换器会与实例列表争夺同一件事** |
| **状态条** | 已有产品药丸 → **改为动态**：显示当前实例的产品 |

**产品徽标的规格**：每个产品一个**固定色 + 短文字**，**不用图标**
（图标在不同产品间难辨识，而文字一眼可读）。颜色取自语义令牌，**不许硬编码**。
#### 4.6.7 🔴 内容功能的边界（**用户定稿，防双入口**）

> **一句话**：**下载页负责「装进来」，实例内部负责「管起来」。**

| 位置 | 定位 | 做什么 | **不做什么** |
|---|---|---|---|
| **下载页** | **获取** | 搜索 / 浏览 / **安装到某个实例**；游戏版本、加载器、模组、资源包、整合包、光影 | ❌ **不管理已装内容**（不启用/禁用、不排序、不改配置） |
| **实例内部 → 模组等** | **管理** | **已装的**：启用/禁用 · 排序 · 查依赖冲突 · 更新 · 删除 · 查看文件 | ❌ **不搜索、不发现新内容**（要装新的请去下载页） |

**推论（必须实现，否则边界会渗漏）**：

| # | 推论 |
|---|---|
| 1 | 在**下载页**搜到一个**已安装**的模组时，**不能就地给出"启用/禁用"**——要显示「已安装」并给**跳转到该实例**的入口。**否则管理动作就从实例里漏到了下载页** |
| 2 | **实例内部的模组页不给"搜索并安装"**——最多给一句「要装新的？去下载页」的入口 |
| 3 | **同一件事不能有两个入口**。评审时若发现某功能两处都能做，**必须有一处降级为"跳转到另一处"** |

#### 4.6.8 主页插件网格（**v2.1 新增：用户定稿**）

> **这是我们自己的机制，不是"照参考图抄的一个首页"。** 参考图只提供了**形式**（卡片式、可开关），
> **内容与规则全部是我们自己的**——参见 §4.6.1.3 的"形式类似 ≠ 一模一样"。

##### 为什么主页要有插件

**主页不该是一张固定布局**：有人只要"点一下就进游戏"，有人要看下载进度、要看哪个实例坏了。
**用可开关的插件解决，而不是做一个"谁都够用"的折中布局**（那种布局对所有人都不够用）。

##### 结构：**横幅固定，插件区自己滚**

```
主内容区
┌── 大横幅（固定）──────────────────────────────────┐
│ [Java 版|基岩版]   产品切换                        │  ← §4.6.1.2 要求主页可选产品
│ 1.20.1 · Fabric 已就绪 · 38 个模组                 │
│ [▶ 启动] [管理实例] [打开目录]                      │
└───────────────────────────────────────────────────┘
  插件  拖拽调位置与占宽        [＋添加插件] [⚙插件设置]    ← 头部固定
┌── 插件区（**这块滚**）──────────────────────────────┐
│ ┌─ 最近运行 (1/2) ────┬─ 快速启动 (1/4) ─┐          │
│ ├─ 下载队列 (1/4) ─┬─ 游玩统计 (1/4) ─┬─ 实例体检 ─┤ │
│ └─────────────────┴───────────────┴──────────┘     │
└───────────────────────────────────────────────────┘
```

| 决定 | 内容 |
|---|---|
| **横幅** | **固定在顶部，随内容滚会失去"它是主角"的意思** |
| **插件区** | **自己滚**（`overflow-y: auto`），**横幅不动** |
| **插件头部**（＋添加 / ⚙设置） | **固定在滚动区之外** —— 否则插件一多，这两个按钮就被滚走了 |

##### 插件占宽（4 档）

| 档 | 栅格 | 用途 |
|---|---|---|
| **1/4 宽** | `span 3` | 小件：快速启动、游玩统计、产品状态 |
| **1/3 宽** | `span 4` | 默认档 |
| **1/2 宽** | `span 6` | 宽件：最近运行（横排四张小卡） |
| **整行** | `span 12` | 少数需要全宽的 |

**底层是 12 列网格**；**拖动插件到别的位置时，按落点决定它变成哪一档**（拖拽同时完成"改顺序"与"改占宽"）。

##### 每个插件的三个操作（**缺一不可**）

| 控件 | 作用 | 为什么不能省 |
|---|---|---|
| **⠿ 拖拽手柄** | 改**顺序**与**占宽** | 顺序只能拖，**不要在设置页里排**（设置页看不到实时效果） |
| **⋮ 菜单** | 隐藏这张 / 切「丰富·极简」/ 移到最前 | 就地操作，不用跳去设置页 |
| **⚙ 插件设置** | 一次看到**全部可用**插件（含当前未显示的） | 否则隐藏了就再也找不回来 |

##### 🔴 三条硬规则

| # | 规则 | 理由 |
|---|---|---|
| **1** | **开关关掉 = 主页不显示，但设置里仍然列着** | **否则关掉就再也找不回来了**——这是"可配置界面"最容易犯的错 |
| **2** | **插件不是导航层级**（与 §4.6.1.1 的层级无关） | 插件是**主页内部的磁贴**，不参与"一级 / 二级 / 三级"；关掉插件不影响任何导航 |
| **3** | **同一件事不许两个入口**（与 §4.6.7 同源） | 若两个插件做同一件事（例如"最近运行"与"快速启动"都能启动），**必须合并或让其中一个降级为跳转** |

##### 形态：丰富 / 极简

| 形态 | 含义 |
|---|---|
| **丰富** | 显示该插件的完整信息 |
| **极简** | **只留最关键的一行/一个按钮**（例如"快速启动"极简后只剩一个启动键） |

**顶部另有一键预设** `丰富 / 精简 / 极简`：**切一次，各插件的开关与形态一起变**，省得逐项调。

##### 当前插件清单（**会增删，增删须过评审**）

| 插件 | 来源 | 备注 |
|---|---|---|
| **最近运行** | 已有数据（游玩时长、最近运行） | 可占 1/2，横排四张实例小卡 |
| **快速启动** | 当前实例 | **极简档的典型**；与"最近运行"存在重叠，见规则 3 |
| **下载队列** | 下载引擎 | 主页必须能看到进行中的下载 |
| **游玩统计** | 已有数据 | 近 7 天柱状 + 今天/本周合计 |
| **实例体检** | **能力描述符 + `reason`** | **本项目的架构独占**：因为有能力描述符，"为什么这个实例现在不能用"是**可以算出来的**，不必等启动失败 |
| **我的分组** | 实例分组（用户定稿） | 点一下直接筛实例 |
| **产品状态** | 账户层 / 授权层拆分（身份规格 §1.3.3） | 两个产品的授权与磁盘占用 |

> **"实例体检"值得单独说**：它是**别的启动器抄不走的一张卡**——
> 用 `if (product == "java")` 那种写法给不出统一答案，而我们的能力描述符可以。

##### 空态

**空态不占半屏。** 插件内无数据时**折叠为一行提示**（例如"还没有固定的服务器 → 去固定一个"），
**而不是留一块空白卡片** —— 空态是"发现功能"的入口，**但不必用整块空间来喊**。



> ⚠️ **本节原有的四小节（窗口控制按钮 / 拖动与命中区 / Snap Layouts / 高 DPI 与多显示器）已在 v2.2 上移到 §4.5** —— 它们本来挂在这里（四个没有编号的 `####`），而 §4.5 的正文是空的；后果是**任何按节号的引用都指不到它们**。**这里不再保留副本**：同一个规格有两处，一处改了、一处没改，就会漂移。

## 5. 设计令牌（两层结构）

### 5.1 结构（**v1.3 重写：此前令牌不全，M4 的 20 个组件写不出来**）

> **⚠️ 此前的问题**：只定义了 `surface.panel/card/raised` + `stroke` + `text` + `accent`，
> 而 §6.3 的门禁却要求"**每个组件含 6 种状态**"——**没有 hover/active/selected/disabled 这些令牌，那 20 个组件根本无法落地**。
> 实测缺口：`surface.hover` / `surface.active` / `surface.selected` / `surface.disabled` / `text.on-accent` /
> `focus.ring` / `overlay.scrim` / `easing` / `cubic-bezier` —— **全是 0 处**。本节补齐。

#### 第一层 · 调色板（成阶）

> **v1.3 修正命名**：原来叫 `gray.100 … gray.900`，但**同一个 `gray.100` 在深色主题下是最亮的 `#F5F5F7`、在浅色主题下是最暗的 `#1A1A1C`**——
> **"成阶"的直觉因此丧失**（数字大反而亮/暗不定）。
> **改为 `gray.0 … gray.9`，语义固定为"离背景越远、数字越大"**（即 0=最贴近背景，9=对比最强）。
> 实现时深浅主题各自映射到不同的具体明度，**但令牌名不再暗示"亮或暗"**。

```
primary.0 … primary.9          # 强调色阶（可随实例替换整条）
secondary.0 … secondary.9      # 次级色阶
gray.0 … gray.9                # 中性阶（0=最近背景，9=对比最强）
red / yellow / green / blue    # 语义基色（各配 0–9 阶按需）
black / white / transparent
```

#### 第二层 · 语义令牌（**组件只准用这一层**）

```
【材质与表面】

【描边与分隔】

【文本】
```

**来源**：ATLauncher `themes/ATLauncherLaf.properties:26-91`（已对着源码核实）——
它的两层结构与 17 套主题复用同一套语义令牌，是我们直接采纳的形态。
**⭐ 标记的 12 项是本轮补的**，此前缺失。

**为什么必须有成阶层**：语义令牌解决"改一处全站生效"，但**解决不了"我需要一个比 panel 亮一点、又比 hover 暗一点的色"**。
没有成阶层时，这种需求会退化成"随手调一个透明度"——**而那正是 §2 约束 4 要禁止的写法**。

### 5.2 主题（四态）

**深色（默认）/ 浅色 / 跟随系统 / 跟随实例**（每个实例可指定强调色）。

**纪律**：**主题只提供调色板，语义层不动。** 17 套主题靠这一条复用整套组件。

### 5.3 明暗两套参考色值（**v1.2 补：此前只有结构、没有值**）

> **⚠️ 位置纪律**：按 §5.1 的两层结构，**色值属于"调色板层"，语义层只做引用**。
> 下表给出**可直接开工的起步值**——它让 M4 门禁不因"等配色"而卡住；**不是最终定稿**，允许在 M4 阶段微调。
>
> **关键约束**：所有色值**必须满足对比度**（正文 ≥ 4.5:1，大字号 ≥ 3:1）——
> **这是硬线，不能靠"看起来还行"**。选值时可先用工具核算，M4 的质感验收会用 impeccable 的对比度规则复核。

#### 调色板（成阶，**v1.3 改用 `gray.0–9` 命名**）

> **命名规则**：`N` 越大 = **离背景越远 / 对比越强**。**不再用"亮或暗"暗示**——那正是原 `gray.100` 在深浅主题下各指一端的混乱来源。

| 令牌 | 深色（明度） | 浅色（明度） | 用途 |
|---|---|---|---|
| `gray.9` | `#F5F5F7`（最亮） | `#1A1A1C`（最暗） | **对比最强**：主文本、强描边 |
| `gray.7` | `#A1A1A6` | `#4A4A4F` | 次文本基准 |
| `gray.5` | `#6E6E73` | `#8E8E93` | 禁用文本 |
| `gray.3` | `#2C2C2E` | `#D1D1D6` | 分隔线基准 |
| `gray.0` | `#1A1A1C`（最暗） | `#F5F5F7`（最亮） | **最接近背景**：兜底底色 |
| `accent.5` | `#4C9AFF` | `#0A66C2` | 强调色基准（**可随实例覆盖，但有约束，见下**） |
| `success.5` / `warning.5` / `danger.5` | `#3FB950` / `#D29922` / `#F85149` | `#1A7F37` / `#9A6700` / `#CF222E` | |

#### ⭐ 对比度约束与 `text.on-accent`（**v1.3 补：此前只给色值，没给"配什么文字"**）

> **此前的问题**：深色 `accent.5 = #4C9AFF`，**若当按钮背景配白字，对比度不足**。
> 这不是"选色不佳"，是**规格里缺了"强调色之上用什么文字"这个令牌**，实现者只能各猜各的。

| 规则 | 内容 |
|---|---|
| **`text.on-accent` 必须定义** | 默认：`accent.5` 的**相对亮度 > 0.45 → 用深色文字**；否则用浅色文字。**实现时按公式算，不写死** |
| **实例自定义强调色的约束** | **不允许任意取色**。给出**可选色板（8–12 个预设）**，每个预设**已核算过** `text.on-accent` 与对比度；用户从预设里选，不做自由取色 |
| **理由** | 自由取色必然产生对比度不合格的组合，**而对比度是可访问性的硬线**（正文 ≥ 4.5:1，大字号 ≥ 3:1） |
| 若将来要开放自由取色 | 必须**自动计算前景色**并**在对比度不足时拒绝或自动校正**——不能只提示 |

**其余状态色同理**：`state.*.bg`（提示条背景）**必须各自标注配套文字色**，不能"背景用了就用默认文字"。

#### 语义令牌（引用调色板，**组件只准用这一层**）

| 语义令牌 | 深色取值来源 | 浅色取值来源 | 说明 |
|---|---|---|---|
| `Material.Backdrop` | `#202020` | `#F3F3F3` | **材质不可用时的兜底色**（有材质时被 DWM 覆盖） |

| `surface.card` | `rgba(255,255,255,0.12)` | `rgba(255,255,255,0.72)` | 内容卡片 |
| `surface.raised` | `#2C2C2E` | `#FFFFFF` | 浮层（岛/弹窗/菜单） |
| `stroke.subtle` | `rgba(255,255,255,0.10)` | `rgba(0,0,0,0.10)` | 1 px 弱描边 |
| `stroke.strong` | `rgba(255,255,255,0.22)` | `rgba(0,0,0,0.22)` | 浮层内描边 |
| `text.primary` | `#F5F5F7` | `#1A1A1C` | 正文 |
| `text.secondary` | `#A1A1A6` | `#4A4A4F` | 次要信息 |
| `text.disabled` | `#6E6E73` | `#8E8E93` | 禁用态 |

> **两条使用纪律**：
> 1. **面板与卡片用"白色/黑色 + 低透明度"而不是固定灰色**——这样在 DWM 材质之上能自然透出材质，**换成纯色兜底时也不会脏**。
> 2. **浮层用不透明色**（`surface.raised`）——它是"浮在最高层"的，必须与背景明确分离；靠描边 + 单层投影实现，**不靠透出材质**。

### 5.4 视觉强度阶梯与"表现层令牌"（**v1.4 新增**）

> **编号修正（补 SESSION.md 那一轮顺手做的）**：本节的五个子节此前被编成 `5.5.1`–`5.5.5`，
> 而紧接着的 L1063 就是**真正的 `### 5.5 日志分级色（令牌化）`** —— 父节是 5.4、子节却叫 5.5.x，
> 于是「按节号引用」这件事**从写下的那一刻就指不到东西**（`tools/audit-milestone.ps1` 把它记为
> dangling P1：`section 5.4.1 / 5.4.3 has no matching heading`）。现改为 `5.4.1`–`5.4.5`，
> **标题文字一字未动**，全仓库除这五行之外没有任何地方引用过 `5.5.x`（已 grep 核实）。

> **为什么要有这一节**：本项目已经存在**四个各自独立的视觉偏好**——
> 主题四态（§5.2）、材质档位（§3.4）、`prefers-reduced-motion`（§8.3）、`prefers-contrast`（§7.5）。
> **它们平行存在、没有优先级**，于是每新增一种视觉表现（渐变、动效、光晕……）
> 都要重新回答"这几层怎么叠加"。**再加一个"增强视觉开关"只会让这个问题更糟。**
>
> **本节的解法不是加一个开关，而是给已有的这些偏好定出优先级。**

#### 5.4.1 阶梯（**四条，自上而下**）

| 层 | 来源 | 可调范围 | 谁能改 |
|---|---|---|---|
| **1. 系统能力** | 高对比度 / 省电 / 远程桌面 / `prefers-reduced-motion` / `prefers-contrast` | **只能收紧，不能放开** | 操作系统，**不可协商、不可被界面覆盖** |
| **2. 材质档位** | `Material.Full` / `Reduced` / `None`（§3.4） | **自动、只降不升** | 系统触发自动降级；用户可**手动降低**（设置里的材质档位） |
| **3. 视觉强度** | `Visual.Standard`（默认）/ `Visual.Enhanced` | **用户可调** | 用户（设置里） |
| **4. 实例强调色** | 每个实例可指定强调色（§5.2） | **最窄的作用域** | 用户（按实例） |

#### 5.4.2 三条纪律（**这是本节的实质**）

| # | 纪律 | 含义 |
|---|---|---|
| **①** | **向下只累加收紧，不叠加放开** | 第 1 层说不行，第 2/3/4 层**都不得放开**。高对比度模式下，`Visual.Enhanced` **不生效**，且**不报错**——它只是被上层收紧了 |
| **②** | **绝不新增一个与这四层平行的视觉开关** | 新的视觉表现若要可配置，**必须落到这四层中的某一层**，不许自己开一层。**这条是为了防复杂度增长，不是为了限制功能** |
| **③** | **`Visual.Enhanced` 不是"更炫"的同义词，是"允许动用装饰性表现"** | 它**不放开** §2 的约束 6（禁发光扩散）与约束 7（禁无限循环动画）。**增强 ≠ 豁免** |

#### 5.4.3 装饰性与信息性（**决定一个效果能不能被开关关掉**）

| 判据 | 类别 | 归属 |
|---|---|---|
| **去掉它，用户就丢失或无法判断信息** | **信息性** | **永远存在**，不随视觉强度改变。例：进度、状态点、错误色、`focus.ring`、禁用态与原因的可见性 |
| **去掉它，只是变朴素，信息不受影响** | **装饰性** | 可随 `Visual.Standard / Enhanced` 增减。例：卡片边缘光的渐变流动、数字滚动计数、进度条缓动补充 |

**这条判据是本节唯一需要**判断**的东西**——它不靠"感觉哪个更炫"，靠**"删掉它会不会丢信息"**。

#### 5.4.4 表现层令牌（第三层令牌）

**结构**：`调色板层` → `语义层` → **`表现层`**（新增）。

```
表现层令牌（只放不违反 §2 约束 6/7 的东西）
  edge.gradient         卡片边缘光的渐变（替代单色描边）
  edge.gradient.hover   悬停时的渐变（可含强调色）
  motion.countUp        数字滚动计数（一次性，默认 800ms）
  motion.progressEase   进度条缓动补充（一次性）
  intensity.standard / intensity.enhanced   两档的表现层取值集
```

**纪律**：

| # | 规则 |
|---|---|
| 1 | **组件只准用表现层令牌，不许内联写渐变与动效参数**（与"颜色只准用语义令牌"同源） |
| 2 | **表现层令牌的取值必须整档切换**（`intensity.standard` / `intensity.enhanced`），**不许组件各取一半** |
| 3 | **`Visual.Enhanced` 默认关闭**——理由：**默认值是给所有人用的**，而"更丰富"是少数人在少数时候想要的 |
| 4 | **新增装饰性效果 = 改本文件 + 加一条令牌**，不许在组件里直接写 |

#### 5.4.5 与 M4 的关系（**为什么现在就要定，而不是等材质出来**）

**必须在 M4 骨架开工前定死**，否则"开关影响哪些组件、哪些永远不受影响"
会在实现中被**逐个临时决定**，而**临时决定的集合是不可收拢的**。

**因此 M4 门禁新增一项**：**表现层令牌文件存在，且 `intensity.standard` 与
`intensity.enhanced` 两档的取值集都已定义**——**即使 `enhanced` 这一档暂时为空**
（空集也是明确的答案："暂时没有增强项"，而不是"还没想"）。

## 6. 前端栈与 M4 前置门禁

### 6.1 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 / 构建 | **TypeScript 严格模式 + Vite** | Vite 是 Tauri 官方模板默认 |
| UI 框架 | **React 19** | Framer Motion 的弹簧动画是灵动岛的关键依赖 |
| **状态管理** | **Zustand** | 无 Provider 地狱、无样板；与"数据单向从 Rust 流入"契合 |
| **路由** | **TanStack Router** | 类型安全 → **编译期挡住"跳转到未注册的能力页"** |
| **CSS** | **纯 CSS Modules + CSS 变量令牌** | 见下 |
| 无头组件 | **Radix Primitives** | 只取行为与 a11y，**样式全部自己写** |
| 数据层 | **TanStack Query** | 缓存 key = 实例 id / 版本 id |

| 图标 | 自绘 SVG（lucide 风格线稿） | 素材自制、来源可追溯 |

### 6.2 为什么不选 Tailwind（**值得单独记**）

我们的设计语言是**语义化的层次**（`surface.panel` / `stroke.subtle`）。
Tailwind 写成 `bg-white/10 border border-white/15` 时，**"这是第几层"就查不出来了**，
且从类名无法回答"这个组件用了哪一档 elevation"。

**它不是不能用，而是会主动对抗 §2 的约束 3。**
同理不选 CSS-in-JS：运行时开销与冷启动预算冲突，而 CSS 变量已经解决了动态主题。

## 7. 灵动岛

### 7.1 定位

**它不是装饰，是"把此刻唯一值得看的事提到顶层"。**
**硬规则：任意时刻只有一个岛、一个主状态。** 多个通知**排队**，不并排。

### 7.2 状态表

| 状态 | 触发 | 岛内内容 | 点击行为 |
|---|---|---|---|
| `Idle` | 无事发生 | 极小胶囊：源 + 账户（≤120 px） | 展开账户/源快速面板 |
| `Probe` | 启动前预检 | 转鼓 + "预检中 · 3 项" | 预检详情 |
| `Download` | 下载中 | 环形进度 + "62% · 1.2 GB/1.9 GB · ↓12.4 MB/s · 剩余 2 分" | 完整任务列表 |
| `Install` | 安装加载器/整合包 | 阶段步进 + 当前文件 | 安装日志 |
| `Launch` | 组装与拉起 | 五阶段步进（解析/下载/校验/解压/启动） | 日志抽屉 |
| `Running` | 游戏运行中 | 计时 + 内存占用（+ 局域网状态） | 打开日志 / 结束进程 / 复制诊断 |
| `Error` | 任何失败 | 错误码 + 一句人话 | 展开诊断与"复制诊断信息" |
| `Update` | 发现新版本 | 版本号 + "重启更新" | 触发更新流程 |

**产品无关性**：以上 8 态**全部与产品无关**——"下载中/运行中"对任何游戏都成立。
产品差异**只在展开面板的字段清单**里（由 `Provider.ui_hints(instance)` 驱动，**不写分支**）：

- Java 版 `Running` → JVM 内存、局域网状态
- 基岩版 `Running` → 进程存活探测、依赖组件状态（无 JVM 概念）

### 7.3 交互与实现约束

| # | 约束 |
|---|---|
| 1 | **单实例 + 队列**；`Error` 优先级最高可抢占，其余按到达顺序 |
| 2 | **两态**：`Compact`（高 32 px）/ `Expanded`（高 ≤220 px）。切换**只用 `transform` + `opacity`** |
| 3 | **可拖拽 + 位置记忆**；默认贴顶居中 |
| 4 | **可关闭**：拖出边界或点 ✕ 收起为状态条一行，**任务不丢失** |
| 5 | **进度节流**：≥100 ms 或变化 ≥1% 才刷新（引擎侧 200 ms + 宿主侧 200 ms 双层，对齐"≤10 次/s"） |
| 6 | **不做**：多任务并排、随动波形、无限循环动画（转鼓除外且需可静止） |

### 7.4 事件源（**v3.9 按 PCL 源码修正过**）

> ⚠️ 我原来写"进程探测 / 窗口探测 / 日志观测**三法比选**"**是错的**——**它们不是竞品，是分工**。

| 机制 | 负责 | PCL 依据 |
|---|---|---|
| **日志子串匹配** | **五步启动进度**（已出现日志输出 / 游戏用户已设置 / LWJGL 版本确认 / OpenAL 已加载 / 材质已加载） | `ModWatcher.cs:476-500` |
| **窗口探测（拿 HWND）** | **窗口就绪**（`WindowLoaded` / `FmlWindowLoaded` / `LoadComplete`） | `ModWatcher.cs:548, 593, 616` |
| **独立一档** | `SecurityBlocked`（安全拦截） | `ModWatcher.cs:578` |

**崩溃识别分三档语气**（不是"崩了/没崩"二元）：

| 事件 | 含义 |
|---|---|
| `Crash.Detected` | 已崩溃（2 秒后才分析） |
| `Crash.Suspected` | 尚未加载完成，**可能**已崩溃 |
| `Crash.AbnormalExit` | 返回值异常 |

且**日志先被分类为"崩溃的"或"关闭的"**（`Log.CrashDetected` / `Log.CloseDetected`）
——**避免把用户正常退出报成崩溃**。

**强杀两级**：`TerminateProcess` → 超时后 `taskkill.exe`。

**基岩版的信号源**由 M0 的 **S8.2** 实测决定（进程/窗口/日志三法比选）。

### 7.5 可访问性（**v1.3 重写：此前只覆盖灵动岛，全局缺失**）

#### 全局要求（适用于所有页面与组件）

| # | 要求 | 具体做法 |
|---|---|---|
| **G1** | **焦点必须可见** | 用 `focus.ring` 令牌（**不是浏览器默认 outline，也不是去掉 outline**）。**只在键盘导航时显示**（`:focus-visible`），鼠标点击不显示 |
| **G2** | **Tab 顺序符合视觉顺序** | 左导航 → 主内容 → 状态条。**不用 `tabindex` 正数**打乱顺序（正数 `tabindex` 是反模式） |
| **G3** | **键盘可完成全部操作** | 每个可点元素都能 Tab 到并回车/空格触发；浮层打开后**焦点被困在浮层内**，`Esc` 关闭并把焦点还给触发元素 |
| **G4** | **颜色不单独承载信息** | 状态不能只靠颜色区分（如"成功"必须有图标或文字）。**色盲用户占男性约 8%** |
| **G5** | **对比度硬线** | 正文 ≥ **4.5:1**；大字号（≥18 px 或 14 px 粗体）≥ **3:1**。见 §5.3 的 `text.on-accent` 约束 |
| **G6** | **`prefers-reduced-motion` 全局生效** | **不是只对灵动岛**。全局降级为直接切换（`duration: 0`），**转鼓静止** |
| **G7** | **高对比度模式** | 系统开高对比度 → **强制纯色材质**（§3.4）+ 描边加强 + **禁用所有透明度叠加** |
| **G8** | **图标按钮必须有可访问名** | `aria-label`（视觉是图标，语义要有文字）；**纯装饰图标 `aria-hidden="true"`** |
| **G9** | **动态区域用 `aria-live`** | 只用于**结果类**变化（下载完成、错误出现）。**进度条不要用 `aria-live`**（会刷屏），用 `role="progressbar"` + `aria-valuenow` |
| **G10** | **表单错误可被识别** | `aria-invalid` + `aria-describedby` 指向错误文案，**不能只靠红框** |

#### 灵动岛专属（保留）

| 项 | 要求 |
|---|---|
| 状态播报 | `aria-live="polite"`（**错误用 `assertive`**） |
| 进度 | `role="progressbar"` + `aria-valuenow/min/max` |
| 减少动态效果 | 岛的形变退化为直接切换 |
| 键盘 | 岛可 Tab 到达；`Expanded` 态内可键盘操作全部动作 |

### 7.6 页面级三态规范（**v1.3 补：此前只有百宝箱的空状态**）

> **此前的问题**：百宝箱空状态写得很细，但**主页 / 实例 / 下载 / 存档 / 账户 / 设置都没有三态规范** →
> 每个页面会各写各的，最终风格不统一。

**每个数据页面必须实现三态，且共用同一套容器**（与 §5.7 错误级别表的分级原则一致：**同级别共享同一视觉容器**）：

| 态 | 触发 | 视觉 | 必须给的三样 |
|---|---|---|---|
| **Loading** | 首次加载 / 数据未到 | **骨架屏**（不用转圈）——骨架形状必须**贴近真实内容的布局** | ① 进度感 ② 不遮挡已有的可操作区 |
| **Empty** | 加载完成但无数据 | 图标（48 px 线性 SVG）+ 主文案 + 说明 + **主行动按钮** | ① 这是干什么的 ② 推荐从哪开始 ③ 怎么看到全部 |
| **Error** | 加载失败 | 图标（`danger`）+ 错误码 + 人话原因 + **建议 + 可点击操作** | ① 为什么失败 ② 怎么办 ③ 重试 / 导出诊断 |

**规则**：

| # | 规则 |
|---|---|
| 1 | **三态共用同一个容器组件**（`PageState`），页面只传参数——**不许各页面自己搭** |
| 2 | **Loading 用骨架屏而非转圈**——骨架能提前暗示布局，转圈只表示"在忙" |
| 3 | **Empty 不得出现"暂无数据"**（同 §4.3.1 的措辞纪律） |
| 4 | **Error 必须是"错误码 + 原因 + 建议 + 操作"四件套**（与 §5.7 的"阻断级"一致） |
| 5 | **局部失败不整页报错**：只有该区块失败时，**只让该区块进 Error 态**，页面其余部分照常可用 |
| 6 | **骨架屏不得闪烁**：最短显示 300 ms（避免"闪一下就没"） |

## 8. 动效

### 8.1 具体曲线与弹簧参数（**v1.3 补：此前只有"Ease-Out / 弹簧"这种描述，Framer Motion 无法照此实现**）

| 场景 | 时长 | 曲线 / 弹簧 | 属性 |
|---|---|---|---|
| 岛 状态切换 | 180–240 ms | `easing.standard` = `cubic-bezier(0.2, 0, 0, 1)` | `opacity` + `transform` |
| **岛 Compact↔Expanded** | — | **`spring.island = { stiffness: 420, damping: 34, mass: 0.9 }`** | `scaleY` + `opacity` |
| 卡片悬停 | 120 ms | 线性 | `opacity` + `translateY(1px)` |
| 浮层进场 | 180 ms | `easing.enter` = `cubic-bezier(0, 0, 0.2, 1)` | `opacity` + `scale(0.98→1)` |
| 浮层出场 | 140 ms | `easing.exit` = `cubic-bezier(0.4, 0, 1, 1)` | `opacity` + `scale(1→0.98)` |
| 页面切换 | 180 ms | `easing.standard` | `opacity` + `translateX(8px)` |

**弹簧参数怎么定的**：`stiffness 420 / damping 34` 接近临界阻尼（**几乎不过冲**）——
灵动岛是"状态指示器"不是"玩具"，**回弹过冲会显得廉价**。若实测手感偏"硬"，优先**降 stiffness** 而不是加 damping。

**令牌位置**：以上曲线与弹簧参数**都在令牌文件里**（§5.1 的 `easing.*` / `spring.island`），组件只引用不写字面值。

### 8.2 禁止项

**禁止**：Layout 动画、驱动 `Width/Height` 的动画、无限循环动画（转鼓除外）、>300 ms 的等待动画、并行 >2 组。

### 8.3 `prefers-reduced-motion`（**全局，不只是灵动岛**）

```css
@media (prefers-reduced-motion: reduce) {
  :root { --duration-fast: 0ms; --duration-base: 0ms; --duration-slow: 0ms; }
}
```

| 项 | 降级后 |
|---|---|
| 全部过渡与动画 | **直接切换**（时长归零） |
| 灵动岛形变 | 直接切换 |
| 转鼓 | **静止**（不转） |
| 骨架屏 | 保留（它不是"动效"，是"加载指示"） |
| **不得** | 不得因为"没有动画"就**去掉状态变化的视觉反馈**——降级的是动效，不是反馈 |

>
> ⚠️ **v2.2 更正（S2 之后）**：原文说"**因为 WebView2 的限制被迫**放弃 CSS 模糊……限制与品味在这里刚好同向"。

> 所以这句话要改成：**不是限制逼我们这么做，是我们自己选了这个方向，而它恰好也对品味有利。**
>
> **这个更正本身值得记**——原来的说法把功劳记给了"平台限制"，
> 于是项目失去了一次**主动把品味当理由**的机会：
> **"我们不用玻璃拟态"应该是因为它俗，而不是因为我们做不到。**
> （同理的还有约束 2：**"纯色兜底也必须好看"是设计追求，不是能力妥协**。）

### 11.1 ⚠️ S1 与 M4 的先后顺序

> **背景**：§11 的"纪律"（未验证项 #1 没结论前不写 §4 布局代码）与 §6.3 的 M4 门禁（含"路由骨架"）**曾互相打架**——

| 段 | 时机 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| **① S1 结论之前** | U0–U5 | **令牌文件**（§5）· **基础组件**（§6.4，只做样式与状态）· **全局 a11y**（§7.5）· **数据层贯通示例** · **页面三态容器**（§7.6）· 三条 lint 规则 | ❌ 不写 §4 的**具体布局**（标题栏方案、岛的位置）<br>❌ 不定"岛贴顶居中"这类依赖 A 计划的参数 |

#### 六项降级样式参数（B2 用；A 计划下也用于"用户手动关闭材质"时）

> **v1.3 修正**：此前只给了深色一列——**浅色主题的兜底参数完全不同**（深色靠"提亮叠加"，浅色靠"压暗叠加"），必须分列。

| # | 项 | 有材质（深/浅同） | **纯色兜底 · 深色** | **纯色兜底 · 浅色** |
|---|---|---|---|---|
| 1 | 窗口背景 | DWM 材质 | `Material.Backdrop` = `#202020` | `Material.Backdrop` = `#F3F3F3` |
| 2 | 容器面板 | `rgba(255,255,255,0.08)` / `rgba(0,0,0,0.04)` | **提到 `rgba(255,255,255,0.10)`** | **提到 `rgba(0,0,0,0.06)`** |
| 3 | 内容卡片 | `rgba(255,255,255,0.12)` / `rgba(255,255,255,0.72)` | **提到 `rgba(255,255,255,0.14)`** | **提到 `rgba(0,0,0,0.09)`** 或改用实色 |
| 4 | 描边 | `stroke.subtle`（深 10% 白 / 浅 10% 黑） | **加强到 14% 白** | **加强到 14% 黑** |
| 5 | 浮层投影 | `elev.2` 单层 | **保持**（浮层本来就不依赖材质） | **保持** |
| 6 | 灵动岛对比 | 靠材质透出区分 | **改 `surface.raised` 不透明 + `stroke.strong` 内描边** | **同左**（浅色下更需描边，因为浅底色与白浮层差异小） |

**规律**：**深色靠"提亮"拉开层次，浅色靠"压暗"拉开层次**——同一套不透明度数值在两套主题下效果相反，
**所以兜底参数必须分列，不能共用一列**。

**触发方式**：自动（§3.4 的降级规则）+ **用户手动开关**（设置页的材质档位 `Full / Reduced / None`）。

> **这一节的意义**：**它把"最坏情况"从"到时候再想"变成"现在就有参数"**。
> S1 的结论无论如何，§4 的布局都有对应方案——**这才是"未验证项"该有的处理方式。**
