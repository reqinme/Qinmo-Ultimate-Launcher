# 配置与设置规格

> **版本**：与方案 `v3.13` 对应 ｜ **锚点**：`[CONFIG]` ｜ **落点**：M4 的「设置」页、`qul-infra`
>
> **为什么这份规格必须现在写**：M4 一动工就要读写设置。
> **现在定成本最低；等界面铺开再改，要动的是前后端两侧。**
>
> **单一真源**：本文件是**配置层**的唯一真源。方案保留决策，**具体形态以本文件为准。**

---

## 1. 一句话

> **配置用「全量快照 + 原子 patch」读写，而不是「一堆 getter/setter」。**

```
get_config()          →  返回一份完整快照
apply_config(patch)   →  提交一处改动（可一次改多项）
```

**不用**：`set_memory(x)` / `get_memory()` / `set_theme(y)` / `get_theme()`……

**理由（三条，按重要性）**：

| # | 理由 | 大白话 |
|---|---|---|
| **1** | **不存在字段级一致性** | 一次读到的永远是**一份一致的快照**，不会"前半新后半旧" |
| **2** | **patch 可以校验** | 内存填 `-1` → **写入前就被拒**，而不是写进去之后启动时才发现 |
| **3** | **新增配置项不必新增命令** | 加一个"侧边栏宽度" → **只改数据结构**，前后端接口不动 |

**第 3 条与方案 §3.3「加能力不必改主程序」是同一种思路**——**这次是配置维度上的同一件事**。

## 2. 磁盘格式与位置

| 项 | 决定 | 理由 |
|---|---|---|
| **格式** | **JSON** | ① **与实例数据一致**（§5.5 的 `profile.json`），**不新引第二种格式**；② 人能直接看懂，便于排障；③ `serde_json` 零额外依赖，不增二进制体积 |
| **位置** | `%APPDATA%\Qinmo\config.json`（单文件） | 与实例数据分开：**配置是启动器级的，实例数据是实例级的**（§4.6.3 的两级架构） |
| **编码** | UTF-8 **无 BOM** | 与仓库内所有文本一致。**带 BOM 会被 serde 拒**（这是一个真实的踩坑点） |
| **写入** | **临时文件 + 校验 + 原子改名** | 与下载引擎同一条纪律（§7.2）：**杜绝"写到一半断电 → 配置损坏"** |

### 2.1 关于 JSON 没有注释（**写下来，免得以后有人重问**）

JSON **不支持注释**，TOML 支持。**对"用户会手改"的配置文件，注释是有价值的。**

**但我们仍然选 JSON**，因为：**配置只由设置界面写**，手改是例外情形而非主要用法。
**如果将来真的允许手改配置**，那时再评估是否换 TOML——**但那会是一次真正的迁移，现在不为它预留复杂度**。

## 3. 快照与回退（**用户不需要做决定**）

**纪律：快照是自动的，不给用户"要不要快照"的选项。**

> 把"要不要快照"抛给用户是**认知负担**，而且**用户在改之前根本不知道这次改动值不值得快照**。

| 项 | 决定 |
|---|---|
| **何时产生** | **每次 `apply_config` 成功后，自动生成一个快照** |
| **保留数量** | **最近 10 个**，满了删最老的（**环形**） |
| **存哪** | `%APPDATA%\Qinmo\config.history\` 下带时间戳的文件 |
| **界面在哪** | 设置 →「高级」→「配置历史」；**默认不显眼，但必须可达** |
| **回退动作** | 选中某个快照 → 「恢复」→ **先校验 + 先备份当前配置**，再覆盖 |
| **失败不阻断** | **快照写失败不得导致 `apply_config` 失败**（快照是保障，不是主流程） |

**"快照写失败不阻断"这条很重要**：如果因为磁盘满导致保存不了快照，**用户改设置这件事仍应成功**——
否则一个辅助功能会把主功能拖死。

## 4. 校验（**在写入前，不在写入后**）

`validate.rs` 的职责：**任何 patch 在落地之前必须过关**。

| 类 | 例 | 失败时 |
|---|---|---|
| **范围** | 内存 `256..=32768`（MB） | 拒，并说明合法范围 |
| **枚举** | 主题 ∈ {跟随系统, 深色, 浅色} | 拒 |
| **路径** | Java 路径必须存在且可执行 | 拒，并指出哪个路径 |
| **互斥** | 代理"手动"模式下必须给地址 | 拒 |
| **越界保护** | 数值不得溢出；字符串长度上限 | 拒 |

**纪律**：

| # | 规则 |
|---|---|
| 1 | **校验在写入前**。绝不允许"先写进去、启动时再报错" |
| 2 | **错误必须说明"哪一项、为什么、合法范围是什么"**——不许只说"参数无效" |
| 3 | **校验规则与类型定义放在一起**（`validate.rs`），不许散进各个调用点 |

## 5. ⭐ 版本化与迁移（**这一节是外部建议漏掉的**）

**问题**：将来把一个设置**改名**或**删掉**，用户已有的 `config.json` 怎么办？

- 不管 → 旧字段永远留着，**越积越乱**
- 直接删 → **用户的设置会静默丢失**

**处置：复用方案 §4.7 的机制，不另发明一套。**

| 项 | 决定 |
|---|---|
| **版本字段** | `config.json` 里写 `"__version": <整数>`，**每次破坏性改动 +1** |
| **迁移时机** | **读取时**：发现版本低于当前 → **先迁移、再使用** |
| **迁移前** | **必须先备份**（复用 §3 的快照机制） |
| **失败不阻断** | **迁移失败 → 用默认值启动，并把旧文件重命名为 `config.json.failed`**，**不删**。**绝不因配置问题让启动器起不来** |
| **未知字段** | 读取时**保留但不使用**（`serde` 默认忽略）；写回时**是否丢弃**要显式决定——**默认丢弃**，避免垃圾字段永久累积 |
| **迁移函数** | 每步一个纯函数 `v1_to_v2(old) -> new`，**可单独测试**（与实例数据迁移同构） |

**为什么"失败不阻断"要写得这么硬**：配置是**启动器能不能起来**的前置。
**一个坏掉的配置文件让用户再也打不开启动器，是最糟糕的失败模式。**

## 6. 前端中间层（`utils/api`）的边界

**纪律**（源自对同类实现的观察，见 `docs/MoLaunch-源码调研.md` §4.2）：

> **前端的业务组件不许直接调 IPC**；所有调用经统一中间层，并受类型约束。

**但中间层自己也不许长成逻辑层**。所以加一条**反向约束**：

| 中间层**只做**三件事 | 中间层**不做** |
|---|---|
| ① 请求转发 | ❌ 数据转换（改字段名、拼数据） |
| ② 错误统一包装 | ❌ 排序 |
| ③ 凭据注入 | ❌ 去重 |
| | ❌ 任何"业务判断" |

**为什么要有这条反向约束**：`api.获取模组列表()` 里若写了"去重 + 按名排序"，
它就**从传输层变成了逻辑层**——**两个月后没人敢改它**。

**判据**：**如果一个函数的实现需要知道"模组是什么"，它就不属于中间层。**

## 7. CSP 白名单（**编译期常量，不是配置项**）

> ### ⚠️ 这里刻意**不采纳**一条外部建议
>
> 外部建议："白名单别硬编码，留一个配置文件项，这样加镜像、加代理都不用改代码。"
>
> **不采纳，因为那会把安全边界变成运行时数据。**
>
> **CSP 是闸门**；**如果闸门能被配置改，那么"能改配置的东西"就能扩权**——
> 一个被投毒的依赖只要往配置里写一行 `evil.com`，这道闸门就失效了。
>
> **它举的两个例子（加镜像、加代理）恰恰是最不该走配置的**：
> 我们有 PAC 代理，**若代理地址来自配置，改一个字段就能把全部流量导向攻击者的服务器**。

**做法**：**白名单是编译期常量**，集中定义在**一处**，改它必须改代码、过一次提交。
**"要改代码"不是缺点,是这道闸门的意义。**

| 项 | 规则 |
|---|---|
| 定义位置 | **一处**（Rust 侧常量），不许散落 |
| 内容 | 只列**必需**的域：微软登录 / Mojang / Xbox / 镜像 / 本地 IPC |
| `object-src` | `'none'` |
| `frame-ancestors` | `'none'` |
| `base-uri` | `'self'` |
| **加域名的条件** | 必须是**产品功能需要**；**不许因为"某个依赖要连它"** |
| 加域名的动作 | **改那一处常量 + 在提交信息里写明"为什么需要这个域"** |

## 8. 开屏窗口的边界（**防止它长胖**）

**方案**：主窗口 `visible: false` 先藏着；一个**小、透明、置顶、不占任务栏**的开屏窗口先出现；
主窗口就绪后切换。**（S1 已验证所需的 `decorations: false` + `transparent: true` 可用。）**

> ### ⚠️ 显式规定它能放什么，因为它极容易长胖
>
> 滑坡是这么发生的：**"反正窗口已经有了，顺手加个 X 吧"** → 开屏越画越慢 →
> **而"先出小窗"的全部价值就在于它出得快**。变胖之后，冷启动优势被吃掉，**而没人会记得是因为什么**。

| ✅ 能放 | ❌ 不能放 |
|---|---|
| Logo / 品牌标 | 设置面板 |
| 进度条或加载文字 | 模组列表、实例列表 |
| 版本号 | **任何可交互内容**（按钮、输入框、菜单） |
| **一小段状态文字**（"检查更新中…"） | 任何**需要网络返回**才能显示的内容 |

**硬性判据**：**开屏窗口的内容必须是"不需要等待任何 IO 就能画出来"的。**
凡是需要 IO 的，都属于主窗口。

**计时目标**：开屏窗口**首帧 ≤150ms**（冷启动总预算 ≤700ms 的一部分）。

## 9. ⭐ 状态锁工具（**现在就写最小版，不要等**）

**原计划**："写 `qul-infra` 时自然会写。"

**改为：现在就写一个最小版。** 理由：

> 如果 M4 开始有人手写 `lock()` → 复制 → `drop()`，
> **写到第三个地方之后，第四个就会照抄第三个的写法**（可能带着 bug），
> **然后 bug 就扩散了。在第一次手写出现之前拦住，比事后重构便宜得多。**

**最小版（约 50 行，够用就行）**：

```rust
// qul-infra/src/state.rs
/// 借一份不可变快照，**锁在函数返回前就释放**。
///
/// 这是唯一被允许的读取姿势：调用方拿到的是 clone，不是锁。
pub async fn snapshot<T, R>(cell: &RwLock<T>, f: impl FnOnce(&T) -> R) -> R
where T: Clone;

/// 借锁做一次修改，**锁的作用域由本函数界定**。
///
/// 调用方**无法**把锁带出去——这正是它存在的意义。
pub async fn mutate<T, R>(cell: &RwLock<T>, f: impl FnOnce(&mut T) -> R) -> R;
```

**纪律**：

| # | 规则 |
|---|---|
| 1 | **业务代码不许直接 `lock()` / `read()` / `write()`**——只能经这两个函数 |
| 2 | 返回的是 **clone 或纯值**，**不许返回 guard** |
| 3 | **由架构测试强制**（扫源码里是否出现裸 `.lock()` / `.write().await`） |

**第 3 条是关键**：**只为"别忘了解锁"写文档是不够的——那正是会失败的机制。写成测试才成立。**

（这条与已有的 6 条架构约束同源：`crates/qul-core/tests/architecture.rs`。）

## 10. "先找再写"的**配套动作**

**纪律**："写新代码之前先搜有没有现成的。"

**但光有纪律没用**——拿到这条纪律的人会问"怎么搜？"

**配套动作**（本项目无人审查，所以是自问）：

> **每完成一个功能，在提交前问一次：**
> **"这个功能里，有没有哪一块是已有代码已经做过的？"**
>
> 若有 → **要么改成复用，要么在提交信息里写明"为什么不用已有的那个"。**

**与本项目已有纪律的关系**：这条是 §4.6.1「不新增平行的顶级入口」在**代码维度**的对应物。
**界面侧不许两个入口，代码侧不许两份实现。**
